## 1. Contexto & Escopo

### 1.1 Problema

Quando uma LLM futura (ou um novo desenvolvedor) entra no projeto e precisa entender **por que** uma decisão foi tomada — escolha de Hibernate vs JPA Criteria, refatoração que mudou status machine, supersedência de um épico — a informação está espalhada:

- **ADRs** (`docs/adr/`) — decisões formais individuais, sem contexto de "épico que deu origem".
- **Stories e épicos** (`ai/epics/**/`) — narrativa, mas extensa: 150-450 linhas cada; recuperar "decisões + alternativas + consequências" exige leitura linear.
- **PRs e commit history** — ruído alto; mensagens de commit raramente capturam o "porquê estratégico".
- **Slack/conversas** — efêmero; perdido em 60 dias.
- **`x-internal-story-report`** — gera `story-completion-report-XXXX-YYYY.md`, mas é **relatório estático** (status, coverage, PR number); não é "memória inteligente para LLM futura".

A consequência operacional aparece em três cenários:

**Cenário A — Pergunta recorrente.** "Por que decidimos manter Spring 3.x e não migrar para 4?" Cada vez que aparece, alguém escava ADR + commits + Slack pra reconstruir. Custo: ~15-30min por reconstrução, somando dezenas de horas por trimestre.

**Cenário B — LLM futura ingenua.** Uma sessão Claude futura, sem contexto histórico, sugere "vamos usar Pact full mode" — sem saber que esse caminho foi avaliado, rejeitado em alternativa-descartada do EPIC-0072, e por que. Re-litigar o já decidido.

**Cenário C — Onboarding de novo dev.** Pessoa lê código + rules + system.md, entende **o quê**, mas não o **porquê** das escolhas que vê. Reconstrói por leitura cruzada caótica. Tempo de produtividade alto.

A solução **não é mais documentação** — é **camada de memória estruturada e indexável**, otimizada para retrieval (humano ou LLM via RAG-like). Por epic concluído, gerar **summary inteligente** com:
- contexto compacto (problema + hipótese);
- decisões com why (extraídas das seções "Decisões Arquiteturais" do épico);
- trade-offs explícitos (alternativas descartadas);
- padrões reutilizáveis (extraídos do épico — ex.: "stack-aware via capability families");
- anti-padrões observados (extraídos do épico — ex.: "skill única com switch gigante = rejeitado");
- links semânticos para reports/PRs/ADRs/stories;
- frontmatter para indexação (tags, capabilities, rules afetadas, dependências entre épicos).

E uma skill `/x-memory-search` que faz retrieval seletivo por tag/capability/keyword sem carregar tudo no contexto.

### 1.2 Hipótese

> Se cada épico concluído gerar obrigatoriamente `ai/memory/epic-XXXX-summary.md` (template inteligente, frontmatter indexável, ≤ 200 linhas), e se introduzirmos `/x-memory-search` que faz retrieval seletivo via grep + frontmatter index (sem RAG vetorial — local, gratuito, suficiente para o volume), então:
> - LLMs futuras (e novos devs) recuperam decisões+contexto em segundos, não em escavações;
> - re-litígio de decisões já tomadas cai drasticamente;
> - memória cresce de forma podável (entries antigas podem ser arquivadas; índice continua funcional);
> - o sistema fica auto-documentado em camada estratégica, complementar a `system.md` (estado atual) e ADRs (decisões individuais).

### 1.3 Escopo

Este épico entrega:

1. **`ai/memory/`** estrutura:
   ```
   ai/memory/
   ├── _index.yaml              # frontmatter agregado (tags, capabilities, ordering)
   ├── epic-0069-summary.md     # 1 por épico
   ├── epic-0070-summary.md
   ├── ...
   └── README.md                # como ler / como buscar
   ```
2. **`_TEMPLATE-EPIC-MEMORY-SUMMARY.md`** — template do summary inteligente:
   ```yaml
   ---
   epic-id: EPIC-XXXX
   slug: epic-slug
   summary-version: 1.0
   tags: [refinement, dor-gate, governance]
   capabilities-affected: [governance.refinement-gate]

     - automated-refinement-without-operator
     - inline-validation-instead-of-hook
   superseded-by: null
   indexable: true
   ---

   # Memory: EPIC-0069 — Story Refinement & DoR Gate

   ## Why this epic existed
   <Compacto: problema em 1-2 parágrafos.>

   ## Hypothesis tested
   <Hipótese declarada e resultado real.>

   ## Decisions taken (with why)
   <Lista enxuta: decisão → motivo → consequência. Extraída da seção 6 do épico.>

   ## Reusable patterns produced

   <O que se observou como ruim e a equipe decidiu evitar.>

   ## Links
   - Epic: `ai/epics/epic-XXXX-slug/epic-XXXX.md`
   - ADRs: ADR-NNNN, ADR-NNNN
   - PRs: #NNN, #NNN, #NNN
   - Reports: `plans/epic-XXXX/reports/...`
   - Stories: link para cada story do épico
   ```
3. **Skill interna `/x-internal-epic-summary`** (model: `haiku`, determinística):
   - Lê `epic-XXXX.md` v2 (EPIC-0070 friendly), todas as `story-XXXX-*.md`, ADRs referenciados, story-completion-reports.
   - Extrai: problema, hipótese, decisões (seção 6), alternativas (seção 6), padrões/anti-padrões (heurística por palavras-chave + Decision Rationale).
   - Compõe `ai/memory/epic-XXXX-summary.md` via template + atualiza `ai/memory/_index.yaml`.
   - Invocada **automaticamente** ao fim de Phase 5 de `x-epic-implement` (último passo, MANDATORY).
4. **Skill `/x-memory-search`** (user-invocable):
   - Modos: `--by-tag <tag>`, `--by-capability <id>`, `--by-rule <NN>`, `--by-pattern <keyword>`, `--by-epic <ID>`.
   - Implementação: grep + parse de frontmatter + ranking simples (boost para matches em tags > content). Sem RAG vetorial — desnecessário para o volume.
   - Saída: lista de epic-summaries relevantes + 1-3 frases de "why" por entry.
5. **Capability `governance.ai-memory`** (universal).
6. **Rule 33 — AI Memory Production** + **ADR-0024**.
7. **CI script `audit-memory-coverage.sh`** (Camada 2) — varre épicos `Concluída` e falha se algum não tem `ai/memory/epic-XXXX-summary.md` correspondente.
8. **Rule 27 (Zero-Bypass) atualizada** — surface 14 nova: `ai/memory/epic-XXXX-summary.md` como artefato evidência mandatório de epic.
9. **Smoke test E2E** (`Epic0075MemoryLayerSmokeIT`) cobrindo: summary gerado pós-Phase 5; busca por tag retorna entries esperados; busca por capability funciona; índice atualizado consistentemente; arquivamento manual respeitado (sem reconstruir summaries deletados intencionalmente).
10. **Memória "seed" inicial**: gerar retroativamente `epic-summary.md` para epics 0040–0068 (já concluídos) — 1 epic dogfood + 28 retro-summaries em batch (story-0075-0006).

### 1.4 Fora do escopo

- **RAG vetorial** (embeddings, FAISS, Pinecone): desnecessário para o volume. Se passar de 200 entries, reavaliar.
- **Memória integrada com Claude Code harness memory** (`~/.claude/projects/.../memory/`): essa é session-scoped e do harness; nossa memória é repo-scoped e versionada.
- **Resumo automático de stories individuais**: granularidade de épico é suficiente.
- **Linkagem semântica entre summaries** (knowledge graph): poderia ser épico futuro.
- **Publicação externa** (web, gitbook): summaries ficam internos ao repo.
- **Auto-arquivamento de summaries antigas**: manual via `_index.yaml` flag `indexable: false`.

### 1.5 Entrega de Valor

- **Valor primário:** decisões+alternativas+padrões ficam recuperáveis em segundos via `/x-memory-search`. Re-litígio cai.
- **Valor secundário:** onboarding ganha recurso novo (lê `ai/memory/_index.yaml` + summaries dos últimos 5 épicos = panorama estratégico em 1h).
- **Valor terciário:** LLMs futuras (sessões Claude novas) ganham contexto histórico sem precisar reler todos os épicos.
- **Métrica de sucesso primária:** ≥ 1 retrieval por semana via `/x-memory-search` registrado em telemetria, em 1 mês pós-rollout.
- **Métrica de sucesso secundária:** redução qualitativa de perguntas "por que escolhemos X em vez de Y?" no Slack.
- **Sinal qualitativo:** novo dev consegue explicar 3 decisões estratégicas após 1h lendo `ai/memory/`.

## 6. Decisões Arquiteturais

### 6.1 Por que skill determinística (haiku) e não interativa (sonnet)

Summary é template-driven: extrai decisões da seção 6 do épico, lista alternativas, links. Não há criatividade necessária — apenas síntese estruturada. Haiku é suficiente, mais barato, mais rápido, mais determinístico (resultados estáveis entre execuções).

**Decisão:** `x-internal-epic-summary` em haiku.

**Alternativa descartada:** sonnet com criatividade narrativa. Rejeitado: instabilidade entre runs; custo desnecessário.

### 6.2 Por que retrieval por grep+frontmatter e não RAG vetorial

Volume atual ~30 epics; em 2 anos talvez 200. Grep + frontmatter index responde em < 100ms para esse volume. RAG vetorial exige infra (embeddings, vector DB), latência de chamada, custo. Custo > benefício para esse volume.

**Decisão:** grep + frontmatter index. Reavaliar quando passar 200 entries.

**Alternativa descartada:** RAG vetorial desde o início. Rejeitado: over-engineering.

**Consequência:** `_index.yaml` precisa estar consistente; skill `x-internal-epic-summary` mantém sincronização.

### 6.3 Por que memória versionada no repo e não harness memory (`~/.claude/...`)

Harness memory é session/projeto-scoped e do operador individual. Nossa memória é coletiva, versionada, parte do projeto. Pessoa nova clona o repo e tem acesso completo.

**Decisão:** `ai/memory/` no repo, versionada via git.

**Alternativa descartada:** depender só do harness memory. Rejeitado: invisível para outros membros.

### 6.4 Por que retro-seed em 1 batch e não incremental

Retro-seed é trabalho duplicado se feito incremental (uma sessão por epic). Batch único maximiza throughput, gera summaries de qualidade comparável, alimenta o sistema com volume útil desde release 1.

**Decisão:** batch único em story-0075-0006, com revisão humana de spot-check.

**Alternativa descartada:** incremental (1 epic por release). Rejeitado: muito lento.

**Consequência:** story-0075-0006 é grande (alta complexidade, mas pragmática).

### 6.5 Por que summary capped em 200 linhas

Summaries longos derrotam o propósito (custo de leitura alto). Cap force compactação.

**Decisão:** template enforce ≤ 200 linhas; skill aborta se ultrapassar.

**Alternativa descartada:** sem cap. Rejeitado: drift inevitável.

### 6.6 Por que Rule 33 e não fundir com Rule 24

Rule 24 (Execution Integrity) cobre evidência de **execução** (artefatos pós-implementação). Rule 33 cobre evidência de **memória estratégica** (síntese para retrieval futuro). Conceitos distintos.

**Decisão:** Rule 33 separada.

**Alternativa descartada:** fundir. Rejeitado.
