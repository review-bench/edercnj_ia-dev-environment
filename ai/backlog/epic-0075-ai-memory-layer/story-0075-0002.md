## 1. Contexto & Escopo

Como **arquiteto**, quero publicar `_TEMPLATE-EPIC-MEMORY-SUMMARY.md` com frontmatter v3.0 (Rule 28) tipado e body capped em 200 linhas para que a skill `/x-internal-epic-summary` (story 0003), o retro-seed (story 0006) e a busca `/x-memory-search` (story 0004) operem sobre um schema estável.

O template é o **gargalo arquitetural do épico** (ver IMPLEMENTATION-MAP §7): se mal-modelado, quebra retrieval e força regeneração de todas as 28 entries do retro-seed. Esta story por isso bloqueia 3 outras (0003, 0004, 0006).

### 3.1 Frontmatter v3.0 — schema canônico (decidido)

```yaml

# Identidade

slug: epic-slug                     # required, kebab-case
summary-version: "1.0"              # required, semver
created: "YYYY-MM-DD"               # required
last-updated: "YYYY-MM-DD"          # required

# Indexação (controlado por _index.yaml — duplicado aqui para fonte única no arquivo)
indexable: true
archived: false
superseded-by: null                 # EPIC-YYYY ou null

# Taxonomia (alimenta /x-memory-search)
tags: []                            # required, array de strings, taxonomia canônica abaixo
capabilities-affected: []           # required, array de capability IDs (formato category.subcategory.atomic)
rules-affected: []                  # required, array no formato "Rule NN" ou "Rule NN (NEW)"
adrs-referenced: []                 # required, array no formato "ADR-NNNN"

# Padrões e antipadrões (indexáveis por busca textual + tags)
patterns-introduced:                # required, lista (pode ser vazia)
  - id: pattern-slug-kebab-case
    summary: "1-2 frases descrevendo o padrão"
antipatterns-rejected:              # required, lista (pode ser vazia)
  - id: antipattern-slug-kebab-case
    summary: "1-2 frases descrevendo o anti-padrão e o porquê da rejeição"

# Grafo de dependências entre épicos (alimenta busca --by-epic transitiva)
dependencies-of: []                 # array de EPIC-XXXX (épicos pré-requisito)
dependencies-for: []                # array de EPIC-XXXX (épicos que dependem deste)
---
```

## 8. Decision Rationale

**Decisão:** taxonomia de tags inicial fechada com 30 tags em `tags-catalog.yaml`, mas extensível.
**Motivo:** evita explosão semântica (mesma decisão indexada com 5 tags sinônimas) e preserva qualidade de busca.
**Alternativa descartada:** tags livres sem catálogo. Rejeitado: drift inevitável após 50+ entries.
**Consequência:** review humano para adicionar nova tag — overhead pequeno (KP playbook documenta processo).

**Decisão:** `patterns-introduced` e `antipatterns-rejected` como listas de objetos `{id, summary}`.
**Motivo:** linkagem entre summaries (busca por `id` exato em outro summary) + busca textual em `summary`.
**Alternativa descartada:** lista de strings (slugs). Rejeitado: perde a 1-2 frases que dão contexto sem abrir o summary inteiro.

**Decisão:** cap 200 linhas é hard error, não auto-truncate.
**Motivo:** auto-truncate degrada silenciosamente; hard error força revisão humana e mantém qualidade.
**Alternativa descartada:** auto-truncate com warning. Rejeitado: drift inevitável.

**Decisão:** seções fixas no body, ordem fixa.
**Motivo:** parsing determinístico downstream (story 0003 e 0004 dependem da estrutura).
**Alternativa descartada:** seções flexíveis. Rejeitado: complexidade desnecessária na skill de extração.
