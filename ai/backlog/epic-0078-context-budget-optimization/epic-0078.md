## 1. Contexto & Escopo

**Chave Jira:** TBD

Reduzir tokens always-loaded por turno do LLM de ~52k → ~22k (–58%) sem remover qualquer gate, fase, hook ou política. Estratégia única: separar **contrato normativo** (rules curtas, ≤80 linhas, sempre ativas) de **referência operacional** (Knowledge Packs lazy-loaded, lidos apenas pelas skills que precisam).

Drivers mensurados em `awesome-austin-c3703b`: CLAUDE.md raiz ~5.5k tokens, 25 rules ~43k tokens, SKILL.md `x-epic-implement` ~3.8k. Conteúdo de exemplo (262 linhas Java em Rule 12), matrizes de fallback (Rule 19), regex BNF (Rule 30/Rule 25), 12 superfícies (Rule 27), 7 dimensões (Rule 29) e decision-trees (Rule 26) carregam sempre — são consultados raramente.

A arquitetura final mantém todos os 4 layers de enforcement operacionais (Camadas 0-4), todos os 17 audit scripts, e todas as 14 hooks Bash. Apenas a localização do conteúdo de referência migra de `.claude/rules/` para `.claude/knowledge/{security,lifecycle,governance}/`.

### 1.1 Referências e Anexos

- [docs/specs/SPEC-context-budget-optimization-v1.md](../../docs/specs/SPEC-context-budget-optimization-v1.md)
- ADR-NNNN — "Rules são contratos curtos; KPs carregam exemplos" (a publicar em story-0078-0016)

### 1.4 Fora do escopo

Para preservar o foco e evitar escopo creep, este épico explicitamente NÃO inclui:

1. **Reescrita semântica de rules** — o conteúdo normativo (Invariants, Forbidden, Enforcement) é preservado byte-a-byte; apenas a localização migra.
2. **Remoção de qualquer audit script ou hook** — todos os 17 audit scripts e 14 hooks Bash permanecem operacionais.
3. **Reorganização de capabilities ou taxonomia de skills** — escopo do EPIC-0064 (já concluído) e fora deste épico.
4. **Mudanças no formato de telemetria** — `events.ndjson` mantém schema atual.
5. **Reescrita de orchestrators (`x-epic-implement`, `x-story-implement`, etc.)** — apenas adicionam `Read <KP-path>` quando consomem KPs slim (RULE-007).
6. **Migração de skills v1 para v2** — schema-aware behavior preservado; este épico é ortogonal a refactors de schema.

### 1.5 Hipótese de Valor

> Se **migrarmos referência operacional de rules always-loaded para KPs lazy-loaded e consolidarmos contratos de lifecycle (Rules 24/27/29/45 → Rule 19)**,
> então **tokens always-loaded por turno LLM cairão de ~52k para ≤22k (-58%)**
> porque **Knowledge Packs são carregados sob demanda apenas pelas skills que os referenciam, enquanto rules permanecem sempre ativas no system prompt**.

A hipótese é falsificável via `scripts/measure-context-budget.sh` (story-0078-0001) que produz um número objetivo em tokens; baseline é commitada em `governance/baselines/context-budget.json` antes de qualquer slim começar (DoR §5).

### 1.7 Alternativas Estratégicas Avaliadas

#### Alternativa A — Comprimir rules existentes (rejeitada)

**Descrição:** reescrever rules atuais em forma "abstract", removendo exemplos pedagógicos e matrizes detalhadas. Ex.: Rule 12 manteria apenas "não escreva SQL com concatenação. Ver CWE-89".

**Por que rejeitada:**
- Mantém carga always-loaded (apenas reduz, não migra para lazy).
- Perde contexto pedagógico — LLM precisa adivinhar exemplos quando audit dispara.
- Trade-off ruim: economia de ~30% em tokens vs. queda significativa de fidelidade arquitetural nas reviews.

#### Alternativa B — Manter 5 rules de lifecycle separadas com index unificado (rejeitada)

**Descrição:** preservar Rules 19/24/27/29/45 como arquivos separados, criando apenas um `00-lifecycle-index.md` que cross-linka.

**Por que rejeitada:**
- Não reduz tokens — index adicionaria ainda mais carga.
- Mantém superfície de manutenção fragmentada (5 arquivos com sobreposição).
- Auditors continuariam duplicando regex de detecção de bypass entre 5 fontes.

#### Alternativa C — Rules como contratos curtos + KPs lazy-loaded (ESCOLHIDA)

**Descrição:** rules permanecem sempre ativas mas em forma curta (≤80 linhas: Purpose + Invariants/Forbidden + Enforcement table + Reference link); referência operacional (matrizes, BNF, exemplos, decision-trees) migra para `.claude/knowledge/{security,lifecycle,governance}/` lazy-loaded.

**Por que escolhida:**
- Reduz tokens always-loaded em ~58% (medido).
- Preserva 100% do conteúdo normativo e pedagógico (apenas relocaliza).
- Mantém todos os 4 layers de enforcement (Camadas 0-4) operacionais.
- Padrão de `Read <kp-path>` já existe em skills desde EPIC-0007 — baixo risco de adoção.
- Permite pruning futuro por capability (RULE-005) sem refactor adicional.

### 6.1 Carregamento Obrigatório do KP de Segurança

A migração de Rule 12 (Security Anti-Patterns) para `knowledge/security/anti-patterns/` cria risco de skills de implementação gerarem código sem acesso ao catálogo CWE/J1-J8 quando a rule slim não basta. Para mitigar:

1. **RULE-012 (§4)** torna obrigatório que skills de implementação declarem `Read .claude/knowledge/security/anti-patterns/index.md` em sua phase de planejamento.
2. **`audit-kp-references.sh --security-strict`** (story-0078-0015) valida cobertura: exit `4 SECURITY_KP_MISSING` se qualquer skill de implementação omitir o `Read`.
3. **`SecurityAntiPatternKpCoverageIT`** (story-0078-0005) garante a cobertura no nível Java de testes integrados — falha CI quando skill nova é adicionada sem o `Read`.
4. **Mapping mantido em `governance/baselines/security-kp-coverage.json`** lista as skills que MUST referenciar o KP. Imutável após EPIC-0078 mergeado (RULE-006 EPIC-0058).

Esta tripla camada (RULE-012 + audit script + Java test) garante que a migração de Rule 12 para KP lazy-loaded não degrada a capacidade do LLM de gerar código seguro durante TDD cycles.

## 8. Decision Rationale

**Decisão:** Separar contratos normativos (rules) de referência operacional (KPs) ao invés de comprimir rules atuais.
**Motivo:** Comprimir rules manteria carga always-loaded; mover para KPs torna conteúdo lazy. Skills consumidoras já têm padrão de `Read <kp-path>` consolidado (knowledge-packs existem desde EPIC-0007).
**Alternativa descartada:** Reescrever rules em forma "abstract" (ex.: "Rule 12 says: don't write SQL with concatenation. See examples in CWE-89"). Rejeitado: perderia exemplos pedagógicos.
**Consequência:** Skills que dependem de exemplos precisam declarar `Read` explícito (RULE-007). Mais boilerplate por skill, mas contrato claro.

**Decisão:** Consolidar Rules 19/24/27/29/45 em "Lifecycle Integrity Contract" canônico (Rule 19) com 5 KPs filhos.
**Motivo:** As 5 rules sobrepõem-se em "bypass / evidência / camadas / exit codes" — sem fonte única, audits e leitores duplicam esforço. Consolidação reduz superfície de manutenção.
**Alternativa descartada:** Manter 5 rules separadas com index unificado. Rejeitado: não reduz tokens, só desloca.
**Consequência:** Rule 19 cresce ~20% em tamanho mas absorve ~700 linhas das outras 4. Net: economia significativa após release n+2.

**Decisão:** Pruning por capability é advisory por 1 release antes de hard-prune.
**Motivo:** Risco de poda silenciosa (Risco 5 do SPEC) — perfis novos podem não declarar capability esperada e perder rule.
**Alternativa descartada:** Hard-prune imediato. Rejeitado: viola RULE-006 (fail-open).
**Consequência:** Story-0078-0014 ganha 1 release de "warn-only" antes de virar bloqueante.
