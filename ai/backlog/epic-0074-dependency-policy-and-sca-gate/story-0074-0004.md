## 1. Visão

Como **CI guardian**, quero CI script `audit-dep-policy.sh` que:
1. Roda em PRs para `develop`/`epic/*` como Camada CI (Rule 26 §Taxonomy — `scripts/audit-*.sh`).
2. Lê o YAML do projeto do PR alvo, invoca `x-dep-policy-validate` em modo non-interactive.
3. Falha o build com `DEP_POLICY_VIOLATION` (exit 1) se qualquer `block-on: any-violation` é violado.
4. Implementa `--self-check` mandatório (Rule 26 §`--self-check` Flag) — verifica `jq` em PATH + `audits/dep-policy-baseline.txt` legível (se declarado).
5. Conhece baseline (`audits/dep-policy-baseline.txt`) para grandfather findings pré-rollout — formato `<dep-coordinate>::<finding-id>  # reason — YYYY-MM-DD`.

…para fornecer **defesa em profundidade** sobre o gate runtime de Phase 3 (story-0074-0005): se o hook local foi desativado (`CLAUDE_RECOVERY_MODE=1`) ou o operador pulou o orquestrador, o CI ainda pega.

## 2. Entrega de Valor

- **Valor primário:** Camada CI bloqueante sobre dependency policy — bypass local não compromete `develop`.
- **Valor secundário:** baseline grandfather permite adoção incremental — projeto não precisa "limpar tudo de uma vez" para ativar policy.
- **Valor terciário:** `--self-check` participa do pre-flight CI (Rule 26 §`--self-check`) — script estruturalmente quebrado aborta antes do main matrix.
- **Métrica primária:** zero PRs merged em `develop`/`epic/*` com `DEP_POLICY_VIOLATION` post-rollout (medido por audit log do CI).
- **Métrica secundária:** `--self-check` exit 0 em ambiente CI padrão (jq instalado por workflow); exit 2 quando jq ausente — testado em CI sem jq.

## 3. Acceptance Criteria (Gherkin — 4 categorias mandatórias)

```gherkin
Cenario: Happy — violação detectada em PR
  DADO PR para develop com pom.xml introduzindo dep com CVE-HIGH não-mitigada
  E setup-config.yaml com dependencies.policy.enabled=true + block-on default
  QUANDO audit-dep-policy.sh roda no CI
  ENTÃO exit 1 com DEP_POLICY_VIOLATION
  E stderr contém finding (dep + CVE + CVSS)
  E build é marcado failed com check name "audit-dep-policy"

Cenario: Degenerate — projeto sem policy ativa
  DADO setup-config.yaml com dependencies.policy.enabled=false (ou ausente)
  QUANDO audit-dep-policy.sh roda
  ENTÃO exit 0 (no-op)
  E stdout contém "policy disabled — gate skipped"
  E nenhum finding processado

Cenario: Error — --self-check em ambiente sem jq
  DADO CI runner sem jq instalado
  QUANDO audit-dep-policy.sh --self-check roda
  ENTÃO exit 2 com OPERATIONAL_ERROR
  E stderr contém "jq required"
  E pre-flight CI aborta antes do main matrix (Rule 26)

Cenario: Boundary — finding registrado em baseline é grandfathered
  DADO finding (dep + CVE) presente em audits/dep-policy-baseline.txt
  E PR não introduz NOVOS findings
  QUANDO audit-dep-policy.sh roda
  ENTÃO exit 0 (finding ignorado por estar em baseline)
  E stdout indica "1 grandfathered finding"
  E novo finding (não-baseline) ainda dispararia DEP_POLICY_VIOLATION
```

## 6. Decision Rationale

**Decisão:** Camada CI separada do Phase 3 invocation (Camada Hook implícita via `x-story-implement` orquestrador). **Motivo:** defesa em profundidade — se o operador roda fora do orquestrador (bypass) ou hook local está desativado (`CLAUDE_RECOVERY_MODE=1`), o CI ainda detecta. **Alternativa descartada:** confiar apenas no hook local. Rejeitada — bypass é opcional na conta do operador, mas merge para `develop` deve ter gate inegociável (princípio da defesa em profundidade — Rules 24/26/27). **Consequência:** redundância intencional (skill + CI rodam validação parecida); custo aceitável (poucos segundos de CI vs risco de merge inseguro).

## 7. Refinement Notes (consolidadas)

- **Performance (parsing big depTrees):** target ≤ 60s para projetos com ≤ 500 deps transitivas; parser deve usar lookup `Map<coord, finding>` (O(N)) em vez de busca aninhada (O(N²)).
- **Interação com `<!-- audit-exempt: <reason> -->`:** este marker é para audits de SKILL.md (Rule 22/24); aqui a equivalência é o `audits/dep-policy-baseline.txt` (entry com `# reason`). Documentar diferença no `--self-check` output e no script header.
- **Imutabilidade do baseline:** após o merge do EPIC-0074, baseline file é append-only (similar ao baseline de Rule 24 — `audits/execution-integrity-baseline.txt`). Audit imutabilidade separada (`audit-baseline-immutability.sh` ou check inline) bloqueia removals.
- **Coordenação com `audit-execution-integrity.sh`:** ambos rodam em PRs para `develop`/`epic/*`; ordem é independente — gate falhar em ANY dos dois bloqueia merge.
- **Catalog entry (RULE-004):** dois nomes refletem a mesma realidade — entry referencia "audit-dep-policy.sh", layer "CI script", trigger "PR open/sync", exit codes 0..3, self-check yes.
- **Workflow CI:** integração com `.github/workflows/` é via `ScriptsAssembler`; projeto cliente herda o workflow via `CicdAssembler` (EPIC-0058 §sub-scope).
