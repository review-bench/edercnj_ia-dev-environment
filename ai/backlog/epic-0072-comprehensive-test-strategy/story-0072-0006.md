# História: CI script `audit-mutation-score.sh` + Rule 05 estendida (in-place — sem Rule número novo)

**ID:** story-0072-0006
**Status:** Refinada
**Refinement Verdict:** Approved (2026-04-30)

## 1. Visão

Como **developer on a generated project**, quero:
1. CI script `audit-mutation-score.sh` (Camada 2 — Rule 26) que verifica que mutation score atual do PR atinge `quality.mutation.threshold` declarado E não regrediu vs `governance/baselines/mutation-baseline.json`.
2. Extensão **in-place** de `targets/claude/rules/05-quality-gates.md` adicionando §"Mutation Score Threshold" e §"Performance Budget" (D-R3) — coverage + mutation viram **gate combinado**, não dois gates separados.

...para que weak tests with high line coverage but low mutation kill rate are caught pre-merge, reducing production defects caused by assertions that do not verify meaningful behavior.

## 2. Entrega de Valor

- **Valor primário:** Production defect rate caused by weak assertions drops measurably because PRs whose tests pass coverage thresholds but fail to kill mutations are blocked before merge.
- **Valor secundário:** Maintainers consult a single Rule (05) for all quality gates (coverage + mutation + perf-budget); no fragmentation across rules.
- **Métrica:** Zero PRs with mutation score below threshold merged post-rollout (measured by audit exit-code hits in CI logs). Secondary: revert rate for "test passed but behavior wrong" defects decreases by >= 30% within 2 releases of rollout.

## 3. Acceptance Criteria (Gherkin — 4 categorias mandatórias)

```gherkin
Cenario: Happy — score ≥ threshold + sem regressão
  DADO baseline 82% e PR atinge 85%
  E quality.mutation.threshold=80
  QUANDO audit-mutation-score.sh roda
  ENTÃO exit 0 (OK)

Cenario: Degenerate — primeiro run em projeto novo
  DADO governance/baselines/mutation-baseline.json não existe e quality.mutation.enabled=true
  E PR atinge score 78% (< threshold default 80%)
  QUANDO audit-mutation-score.sh roda no primeiro release pós-rollout
  ENTÃO exit 0 com WARN "first release — score below threshold tolerated for one cycle" (stage policy: WARN→FAIL — D-R3 §Stage Policy)
  E baseline é criada com score atual

Cenario: Error — score abaixo do threshold absoluto bloqueia
  DADO threshold=80 e PR atinge 72%
  QUANDO audit-mutation-score.sh roda no segundo release+ pós-rollout
  ENTÃO exit 1 (MUTATION_SCORE_VIOLATION) com mensagem "score 72% below threshold 80%"
  E reporta delta vs baseline (regressão? estabilidade?)

Cenario: Boundary — regression vs baseline com score acima do threshold
  DADO baseline 90%, PR atinge 82% (acima do threshold mas regrediu 8%)
  E quality.mutation.regression-tolerance-pct=5 (declarado no YAML)
  QUANDO audit-mutation-score.sh roda
  ENTÃO exit 1 (MUTATION_REGRESSION) com mensagem "regressão 8% > tolerance 5%"
  E reporta os top-20 mutações sobreviventes novas (presentes no PR, ausentes no baseline)

Cenario: Security — malformed mutation-report JSON rejected
  DADO mutation-report.json contém JSON inválido (truncado ou com campos ausentes: score, total_mutations, killed)
  QUANDO audit-mutation-score.sh tenta parsear o relatório
  ENTÃO exit 2 (OPERATIONAL_ERROR) com mensagem "malformed mutation report: missing required field 'score'"
  E NÃO escreve nem atualiza governance/baselines/mutation-baseline.json
  E NÃO segue symlinks no path do relatório (path traversal rejeitado)

Cenario: Security — baseline tampering detected via release_count inconsistency
  DADO governance/baselines/mutation-baseline.json existe com release_count=5
  E git tag list mostra apenas 3 releases tagged após mutation.enabled=true
  QUANDO audit-mutation-score.sh roda com --strict-baseline
  ENTÃO exit 2 (OPERATIONAL_ERROR) com mensagem "baseline release_count 5 inconsistent with tagged releases 3"

Cenario: Performance — audit completes within SLA
  DADO mutation-report.json com 10000 mutações (worst-case report size)
  E governance/baselines/mutation-baseline.json com 8000 mutações anteriores
  QUANDO audit-mutation-score.sh roda
  ENTÃO completa em < 5 segundos wall-clock
  E exit code é determinado normalmente (0 ou 1 conforme thresholds)
```

## 5. Typed Contracts

### 5.1 Input: `mutation-report.json` (consumed from story-0072-0003)

Schema owned by story-0072-0003 (`x-test-mutation` output). This story consumes the report read-only.

```json
{
  "score": 85.2,
  "total_mutations": 1200,
  "killed": 1022,
  "survived": 178,
  "no_coverage": 0,
  "timed_out": 0,
  "timestamp": "2026-04-30T12:00:00Z",
  "git_sha": "abc1234",
  "exclusions": ["com.example.generated.*", "com.example.legacy.*"],
  "survived_details": [
    { "mutator": "ConditionalsBoundary", "class": "com.example.Foo", "line": 42, "description": "..." }
  ]
}
```

Required fields for this audit: `score` (number, 0-100), `total_mutations` (integer >= 0), `killed` (integer >= 0), `survived` (integer >= 0). Missing any required field triggers exit 2 `OPERATIONAL_ERROR`.

### 5.2 Owned: `governance/baselines/mutation-baseline.json`

```json
{
  "timestamp": "2026-04-30T12:00:00Z",
  "git_sha": "abc1234",
  "score": 85.2,
  "total_mutations": 1200,
  "killed": 1022,
  "survived": 178,
  "release_count": 1,
  "exclusions": ["com.example.generated.*"]
}
```

Created on first successful audit run. Updated atomically (write to `.tmp` then `mv`) on each release tag. `release_count` increments monotonically.

### 5.3 Config YAML Paths

| Path | Type | Default | Description |
| :--- | :--- | :--- | :--- |
| `quality.mutation.enabled` | boolean | `false` | Enables mutation score gate |
| `quality.mutation.threshold` | integer (0-100) | `80` | Absolute floor for mutation score |
| `quality.mutation.regression-tolerance-pct` | integer (0-100) | `5` | Max allowed regression vs baseline before blocking |

### 5.4 Exit Code Enumeration

| Exit | Code | Condition |
| :--- | :--- | :--- |
| 0 | `OK` | Score >= threshold AND regression <= tolerance (or first-release WARN) |
| 1 | `MUTATION_SCORE_VIOLATION` | Score below absolute threshold |
| 1 | `MUTATION_REGRESSION` | Score above threshold but regression exceeds tolerance |
| 2 | `OPERATIONAL_ERROR` | jq missing, report malformed, baseline corrupt, path traversal attempt |
| 3 | `BASELINE_CORRUPT` | Baseline JSON unparseable or schema-invalid |

## 6. Risks

### Technical Risks

| Risk | Impact | Likelihood | Mitigation |
| :--- | :--- | :--- | :--- |
| **Report format drift from story-0072-0003** | Audit fails to parse mutation-report; false OPERATIONAL_ERROR | Medium | Pin schema version in report header field; audit validates `schema_version` before parsing |
| **Concurrent baseline write race** | Two parallel CI runs write mutation-baseline.json simultaneously; one write lost | Low | Atomic write via tmp+mv; baseline updates only happen on release tags (serialized by release flow) |
| **Dependency delay (story-0072-0003 not merged)** | This story cannot be integration-tested | High | Smoke test uses fixture JSONs; real integration deferred to story-0072-0009 E2E |
| **Malformed report JSON** | Script crashes or produces incorrect verdict | Medium | Strict jq schema validation upfront; missing field = exit 2 immediately |
| **Path traversal in report path argument** | Attacker-controlled path reads arbitrary file | Low | Normalize path, reject `..` and symlinks before any read (Rule 06 §Path operations) |

### Product Risks

| Risk | Impact | Likelihood | Mitigation |
| :--- | :--- | :--- | :--- |
| **Baseline tampering via release_count manipulation** | Stage policy WARN window artificially extended | Low | `--strict-baseline` cross-checks release_count against `git tag` count; discrepancy = exit 2 |
| **Adoption friction — sudden FAIL on existing projects** | Teams blocked on first mutation-enabled release | High | Stage policy WARN-then-FAIL (D-R3); first release is advisory only |

## 7. Alternatives Considered

### A1: Rule 05 in-place extension (CHOSEN)

Mutation threshold + performance budget added as new sections within the existing Rule 05 (Quality Gates). Single source of truth for all quality gates. Operator reads one rule. RULE-005-01 absolute-gate semantics apply uniformly to coverage + mutation.

### A2: New Rule NN "Quality Extended" (REJECTED)

Create a separate Rule for mutation and perf-budget gates. Rejected because: (a) fragments quality governance across two files; (b) creates precedent where each new gate type spawns a new Rule; (c) consumes a Rule number slot that may be needed for protocol rules.

### A3: Enforcement in skill layer (`x-test-mutation` exit code) instead of CI script (REJECTED)

Have `x-test-mutation` (story-0072-0003) directly enforce the threshold by failing with a non-zero exit code. Rejected because: (a) conflates report production with policy enforcement; (b) skill runs during implementation, not at PR gate time — timing mismatch; (c) CI scripts are the canonical Camada 2 enforcement point (Rule 26); (d) operator cannot tune threshold without re-running the full mutation analysis.

### A4: Third-party mutation gate integration (e.g., PIT Maven plugin enforcer, Stryker dashboard) (REJECTED)

Delegate score enforcement to the mutation tool's built-in CI integration. Rejected because: (a) couples gate to a specific tool vendor — violates cloud-agnostic constraint (Rule 01); (b) baseline management (release_count, stage policy) is project-specific and not supported by third-party dashboards; (c) audit script pattern (Rule 26 naming, exit codes, `--self-check`) would not be followed by external tools.

## 9. Decision Rationale

**Decisão:** Rule 05 ganha 2º + 3º thresholds (mutation + perf-budget) **in-place**; **NÃO** criar Rule número novo (D-R3). **Motivo:** Rule 05 já é o gate de quality (cobertura); agrupar mutation + perf-budget ali mantém o operador num só lugar, evita drift entre regras. RA8 (Rule 05) é mutável; não é Rule de protocolo (13/22/24/27) que é congelada por contrato. **Alternativa descartada:** criar Rule NN nova "quality-extended" — rejeitado por (a) viola "agrupar quality num só lugar"; (b) cria precedente perigoso (cada gate novo = nova Rule); (c) consume slot de Rule número que pode ser necessário para Rules de protocolo no futuro. **Consequência:** Rule 05 cresce ~80 linhas; CHANGELOG marca a extensão; toda referência a "quality gate" continua apontando para Rule 05.

## 10. Refinement Notes (consolidadas)

- **Tolerance de regression vs threshold absoluto:** os dois coexistem. Threshold absoluto = piso (não pode descer). Tolerance = vagal de stability (mesmo acima do piso, regressão > tolerance bloqueia).
- **Exclusões idiomáticas (legacy code, generated):** definidas pela skill `x-test-mutation` (story-0072-0003) — este audit consome o relatório, não decide escopo.
- **Stage policy WARN→FAIL:** `governance/baselines/mutation-baseline.json` carrega campo `release_count` que incrementa a cada release tagged em `main`; primeiro release com `enabled=true` é WARN (release_count=0→1), segundo+ é FAIL.
- **Integração com Rule 05:** D-R3 — a extensão in-place documenta 2 thresholds (cobertura existente + mutation NOVO) + 1 gate budget (perf — story-0072-0005 documenta separadamente como "Camada 2", aqui só o thresholds-na-Rule). RULE-005-01 (absolute-gate) aplica a ambos.
