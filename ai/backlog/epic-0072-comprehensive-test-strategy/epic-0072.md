## 1. Contexto & Escopo

### 1.1 Problema

A estratégia atual de testes do CLI cobre **Unit, Integration, API, E2E e Smoke** via `x-test-plan` (Double-Loop TDD em TPP order) e `x-test-tdd` (execução). Cobertura é gate absoluto (Rule 05: ≥95% line, ≥90% branch). Mas existem **três classes de teste ausentes do contrato gerado**, cada uma respondendo a uma pergunta que cobertura sozinha não responde:

**Lacuna 1 — Performance.**

`x-review-perf` faz **review estático** do código (N+1, pools, async, timeouts) — útil. Mas **não mede latência real**, **não mede throughput**, **não compara com SLO declarado**, **não detecta regressão entre releases**. Para um endpoint REST, ninguém roda Newman ou k6 antes do merge. Para gRPC, ninguém roda ghz. Para o próprio CLI, ninguém mede tempo de geração do `.claude/`. Quando aparece lentidão em produção, descobrimos por reclamação, não por gate.

**Lacuna 2 — Mutation testing.**

Cobertura ≥95% atesta que linhas são executadas, **não que asserts validam comportamento**. Um `assertNotNull(result)` é fraco — a mutação `return null` deveria fail, mas `assertNotNull` numa string que volta a ser `""` nem cobre o ponto correto. Mutation testing (PIT em Java, Stryker em JS/TS, mutmut em Python, go-mutesting em Go) injeta mutações sintáticas e mede quantas o test suite **mata**. Score baixo (< 80%) = test suite com asserts fracos. Hoje não medimos.

**Lacuna 3 — Contract testing.**

Quando uma API muda formato (rename de campo, mudança de tipo), os consumers quebram. Testes unit/integration do producer passam (não testam consumer); testes do consumer também passam (não há producer rodando). Contract testing (Pact, Spring Cloud Contract, OpenAPI breaking-change detector, proto-buf compat checker) preenche essa lacuna por **negociação de contrato versionado**. Hoje, nada gera/verifica contracts.

A consequência operacional aparece em três formas: (1) lentidão descoberta em produção, não em CI; (2) bugs sutis em código com cobertura alta (asserts não-discriminantes); (3) breaking changes em APIs descobertas pelo consumer rodando em prod. Os três são preveníveis em CI com ferramental adequado.

Como o CLI **gera projetos para várias stacks**, este épico precisa entregar skills que se adaptam ao YAML do projeto (REST → Newman; gRPC → ghz; CLI → hyperfine; etc.) — não apenas para o nosso projeto.

**Evidência empírica:** durante 48h de operação contínua com o CLI, o operador reportou 30+ ocorrências de problemas que cobertura de linha não preveniu — regressões de latência silenciosas, mutações sobreviventes em assertions fracas, e breaking changes de schema que passaram CI sem detecção. Estes incidentes motivaram a catalogação formal das 3 lacunas acima.

### 1.1b Persona

Operador-desenvolvedor que utiliza o CLI `ia-dev-env` para gerar e manter projetos. É quem executa `ia-dev-env generate`, invoca skills de implementação (`x-story-implement`, `x-task-implement`), e depende dos gates de CI para garantir que código mergeado em `develop`/`main` está livre de regressões. Este operador hoje confia na cobertura ≥95% como proxy de qualidade — mas não tem visibilidade sobre performance real, eficácia dos asserts, ou compatibilidade de contratos entre serviços.

### 1.2 Hipótese

> Se introduzirmos três skills sibling — `/x-test-performance`, `/x-test-mutation`, `/x-test-contract` — cada uma stack-aware (consome `interfaces` + `language` + `framework` do YAML), com SLOs/thresholds declarados em `quality.*` no YAML, e plugarmos os três como gates opcionais-por-default-mandatórios-quando-declarados em Phase 3 de `x-story-implement` e Phase 4 de `x-epic-implement`, então:
> - regressões de performance, asserts fracos e breaking changes em APIs deixam de chegar a `develop`/`main` sem detecção;
> - cada projeto-cliente herda a mesma estratégia respeitando sua stack;
> - o CLI continua sendo gerador (Rule 14): testes rodam no projeto-cliente quando o YAML declara, não no nosso projeto;
>
> **porque** cada gate introduz uma verificação ortogonal que cobertura de linha não substitui — mutation testing força asserts discriminantes (mata mutações sintáticas que `assertNotNull` ignora), performance testing compara medições reais contra SLO declarado (detecta regressão de p95 antes de chegar a produção), e contract testing valida compatibilidade inter-serviço por diff de schema (impede breaking changes invisíveis ao test suite do producer).

### 1.3 Escopo

Este épico entrega:

1. **Skill `/x-test-performance`** — stack-aware:
   - REST (`interfaces[].type=rest`) → Newman + `quality.performance.slo.rest.{p50,p95,p99}_ms` ou k6 quando `framework.k6=true`.
   - gRPC (`interfaces[].type=grpc`) → ghz + `quality.performance.slo.grpc.*`.
   - GraphQL (`interfaces[].type=graphql`) → Artillery.
   - CLI (`architecture.style=cli`) → hyperfine + `quality.performance.slo.cli.gen_time_p95_ms`.
   - Socket / event-driven → custom harness documentada em KP.
   - Saída: `plans/epic-XXXX/reports/perf-report-STORY-ID.md` + comparativo vs baseline (`governance/baselines/performance-baseline.json` por projeto).
2. **Skill `/x-test-mutation`** — stack-aware:
   - Java/Maven → PIT (`maven-surefire`).
   - Java/Gradle → PIT plugin.
   - JS/TS → Stryker.
   - Python → mutmut.
   - Go → go-mutesting.
   - Saída: `plans/epic-XXXX/reports/mutation-report-STORY-ID.md` + score.
   - Threshold via `quality.mutation.threshold` (default 80%).
3. **Skill `/x-test-contract`** — stack-aware:
   - REST/OpenAPI → openapi-diff (breaking change detector) + Pact provider tests quando `quality.contract.pact=true`.
   - gRPC/proto3 → buf breaking + buf lint.
   - Spring Boot → Spring Cloud Contract.
   - Eventos → schema registry compat check (Avro/JSON Schema).
   - Saída: `plans/epic-XXXX/reports/contract-report-STORY-ID.md`.
4. **Schema YAML novo `quality:`** (agrupa para evitar explosion):
   ```yaml
   quality:
     performance:
       enabled: true
       slo:
         rest: { p50_ms: 50, p95_ms: 200, p99_ms: 500, throughput_rps: 100 }
         grpc: { p50_ms: 30, p95_ms: 100, p99_ms: 250 }
         cli:  { gen_time_p95_ms: 3000 }
       baseline-tolerance-pct: 10
     mutation:
       enabled: true
       threshold: 80
       runtime-cap-min: 20
     contract:
       enabled: true
       pact: false
       openapi-breaking: true
       proto-breaking: true
   ```
5. **Templates novos**:
   - `_TEMPLATE-PERFORMANCE-PLAN.md` (auto-fill via YAML + manual: cenários de carga, resultados esperados).
   - `_TEMPLATE-MUTATION-PLAN.md` (escopo da mutação, exclusões, runtime cap).
   - `_TEMPLATE-CONTRACT-PLAN.md` (consumers conhecidos, provider state, versionamento).
6. **Capabilities** declarativas:
   - `quality.performance.{rest,grpc,cli,graphql,socket}.*`
   - `quality.mutation.{java-pit,stryker,mutmut,go-mutesting}.*`
   - `quality.contract.{openapi-diff,pact,buf,scc}.*`
   Skills declaram via `requires-any: [quality.performance.rest, quality.performance.grpc, ...]`.
7. **Rule 05 estendida** — adiciona threshold de mutation score (≥ 80% default) e gate de perf-budget (regressão > tolerance fail).
8. **Phase 3 de `x-story-implement` MODIFICADA** — quando `quality.performance.enabled=true`/`quality.mutation.enabled=true`/`quality.contract.enabled=true` no YAML, as skills correspondentes são MANDATORY TOOL CALLs.
9. **Smoke test E2E** (`Epic0072TestStrategySmokeIT`) cobrindo: perf-test fail por regressão > tolerance; mutation score < threshold bloqueia; contract breaking detectado bloqueia; opt-out via YAML `quality.X.enabled=false`.

### 1.4 Fora do escopo

- **Stress / chaos testing** (carga sustentada, falhas injetadas): coberto por EPIC-0073 (Regression Shell + DAST não cobre, mas o escopo de stress fica para épico futuro junto com chaos).
- **Property-based testing** (QuickCheck-style): valor secundário; pode entrar como skill futura `/x-test-property`.
- **Fuzz testing** (libfuzzer, jazzer): épico futuro.
- **Visual regression testing** (Percy, BackstopJS): não-aplicável a CLI/API.
- **Integração com observability platforms** (Datadog, NewRelic) — out of scope.

### 1.5 Entrega de Valor

- **Valor primário:** três classes de bug (perf regression, weak asserts, breaking change) ganham gate em CI.
- **Valor secundário:** projetos cliente herdam estratégia profissional sem ter que escolher ferramentas — o YAML decide.
- **Valor terciário:** test plans deixam de ser só TDD (unit/integration/AT) e passam a refletir o conjunto real de testes.
- **Métrica de sucesso primária:** ≥ 80% dos projetos novos gerados pós-rollout têm `quality.performance.enabled=true` (default flip em release seguinte). **Medição:** query em repositórios de projetos gerados pelo CLI (contagem de `quality.performance.enabled=true` vs total), janela de 30 dias pós-rollout.
- **Métrica de sucesso secundária:** mediana de mutation score em projetos rodando 0072 ≥ 75%. **Medição:** coleta de mutation-score do campo `score` em `reports/mutation-report-*.md` gerados por `/x-test-mutation` nos 3 primeiros projetos-piloto, janela de 60 dias pós-rollout.
- **Sinal qualitativo:** zero PRs merged com perf regression > 10% pós-rollout. **Medição:** `audit-perf-baseline.sh` em CI (exit 1 = regressão detectada), monitorado continuamente a partir do rollout, janela de 60 dias pós-rollout.

## 6. Decisões Arquiteturais

### 6.1 Por que 3 skills separadas e não uma `/x-test-quality`

Cada classe de teste (perf/mutation/contract) tem ferramenta diferente, runtime diferente, threshold diferente, target diferente. Skill única vira switch gigante.

**Decisão:** 3 skills sibling.

**Alternativa descartada:** skill única com `--type=...`. Rejeitado: alta coupling.

### 6.2 Por que stack-aware via capabilities e não via switch interno

Capabilities (EPIC-0064) é o vetor de extensibilidade. Adicionar nova stack (ex.: Rust com `cargo-mutants`) é só adicionar capability + KP, sem mexer na skill principal.

**Decisão:** capabilities families.

**Alternativa descartada:** switch dentro da skill. Rejeitado: viola Open/Closed.

### 6.3 Por que threshold default 80% e não 100% para mutation

100% é irreal e drena tempo. 80% é o sweet-spot industry (PIT default). Stories podem subir o threshold em sub-pacotes críticos (`mutation.thresholds.per-package`).

**Decisão:** 80% default, customizável.

**Alternativa descartada:** 90%. Rejeitado: alto false-positive.

### 6.4 Por que baseline de performance per-projeto e não shared

Cada projeto tem hardware-target diferente, padrões de uso diferentes. Comparar entre projetos não tem sentido.

**Decisão:** baseline em `governance/baselines/performance-baseline.json` no próprio projeto cliente.

**Alternativa descartada:** baseline compartilhado. Rejeitado.

### 6.5 Por que Pact opt-in (`quality.contract.pact=true`) mas openapi-diff sempre on

Pact requer infra (broker) e contrato negociado entre teams — alto custo de adoção. openapi-diff é leitura local e gratuita.

**Decisão:** openapi-diff e proto-diff sempre on (quando há OpenAPI/proto); Pact opt-in.

**Alternativa descartada:** Pact default-on. Rejeitado: barreira de adoção.

### 6.6 Por que MAJOR no CHANGELOG e não MINOR

Phase 3 contract change (gates novos quando YAML declara) afeta build dos projetos cliente. Documentação de migração obrigatória.

**Decisão:** MAJOR com migration notes.

**Alternativa descartada:** MINOR. Rejeitado: viola SemVer.

### 6.7 Tool-version pinning policy

External tools (Newman, k6, ghz, PIT, Stryker, mutmut, go-mutesting, openapi-diff, buf, hyperfine) vary in behavior across major versions. CI jitter and false positives arise when the tool version on the developer machine differs from CI.

**Decisão:** per-repository baselines. Tool versions are pinned in the `quality:` YAML block via an optional `tools:` sub-key:

```yaml
quality:
  performance:
    tools:
      rest: { name: newman, version: "6.2" }
      grpc: { name: ghz, version: "0.120" }
  mutation:
    tools:
      java: { name: pitest, version: "1.17" }
```

Version match is `semver major.minor` — patch drift is tolerated. When the tool on PATH does not match the pinned version, the skill emits a WARNING (not a hard fail) and proceeds. Future epics may promote the WARNING to a hard fail.

**Alternativa descartada:** global pinning via `.tool-versions` or `asdf`. Rejeitado: not all tools are in asdf registries; adds infra dependency outside the generator's scope.

## 12. Security Posture

### 12.1 Baseline Integrity

Performance baselines (`governance/baselines/performance-baseline.json`) and mutation baselines are per-project artifacts stored in the repository. Integrity is guaranteed by git's content-addressable object model — any tampering is detectable via `git diff` and CI audit. No external trust boundary is crossed for baseline storage.

### 12.2 Threat Model Scope for Generated Skills

The three new skills (`x-test-performance`, `x-test-mutation`, `x-test-contract`) generate SKILL.md files (markdown) — they do NOT execute arbitrary code in the generator itself (Rule 14). The generated SKILL.md instructs the target project's CI to invoke external tools (Newman, PIT, openapi-diff, etc.). Threat modeling for the generator is therefore limited to:

- **Template injection:** `_TEMPLATE-*-PLAN.md` files use `{{PLACEHOLDER}}` tokens resolved by the LLM at runtime; no server-side template engine is involved. Risk: LOW.
- **YAML parsing:** `quality:` block parsed by `ProjectConfig` via SnakeYAML SafeConstructor. Risk: mitigated by Rule 06 (secure defaults — explicit safe mode required for deserialization).

A full threat model for each generated skill's runtime behavior (e.g., Newman executing against a target API) is the responsibility of the target project, not the generator. This is consistent with Rule 14 (Project Scope Guard). **Recommendation:** add a `## Security Considerations` section to each of the 3 new SKILL.md files documenting which external tools are invoked and their trust boundaries.

### 12.3 External Tool Guidance

The three skills invoke external tools that must be installed on the target project's CI runner. The SKILL.md for each skill SHOULD include:

- Pinned tool version (see §6.7 Tool-version pinning policy).
- Checksum verification guidance for CI (e.g., `npm audit signatures` for Newman, GPG verification for PIT).
- Principle of least privilege: test tools run with read-only access to source and write access only to `reports/` output paths.
