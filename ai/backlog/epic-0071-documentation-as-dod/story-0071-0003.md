# História: `x-doc-generate` v2 (target-stack-aware + integração com `x-arch-system-update`)

**ID:** story-0071-0003
**Status:** Refinada
**Refinement Verdict:** approved

> ✅ **REFINEMENT APPROVED** — All 7 dimensions passed. Ready for implementation.

## 1. Visão

Como **operador**, quero `x-doc-generate` v2 que **substitui** o auto-detect uniforme do v1 por geração **target-stack-aware** (consome `documentation.targets` do `ProjectConfig` introduzido em story-0071-0001) — só atualiza targets relevantes ao stack do projeto cliente — **e** invoca `x-arch-system-update` (EPIC-0070) quando detecta mudança arquitetural, mantendo `docs/architecture/system.md` em sincronia.

A v2 mantém **fallback comportamental do v1** (sem flag → comportamento antigo); flag `--target-stack-aware` é o **default novo**, com `--legacy-v1` para preservar comportamento antigo durante 2 releases (Rule 19 §Skill Renaming).

## 2. Entrega de Valor

- **Valor primário:** geração de doc adapta-se à stack — projeto sem REST não recebe OpenAPI; projeto Node não recebe pom.xml-doc; etc.
- **Valor secundário:** integração com `x-arch-system-update` mantém `system.md` (EPIC-0070) sempre vivo quando arquitetura muda.
- **Métrica:** zero geração desnecessária medida em 5 perfis canônicos (Java/Spring, Java/CLI, Node/Express, Python/FastAPI, Go/gRPC) — cada perfil só recebe os targets declarados/auto-detectados.

## 3. Acceptance Criteria (Gherkin — 4 categorias mandatórias)

```gherkin
Cenario: Happy — stack-aware default em projeto Java/Spring/REST
  DADO projeto com interfaces[].spec=openapi declarado
  E .claude/skills/ existente
  E docs/architecture/system.md existente
  QUANDO /x-doc-generate roda em --target-stack-aware (default)
  ENTÃO atualiza README + OpenAPI + skill-docs + system.md
  E NÃO toca asyncapi (sem broker declarado)
  E NÃO toca grpc-proto (sem proto3)

Cenario: Degenerate — projeto sem doc.targets aplica auto-detect
  DADO projeto SEM bloco documentation.targets no YAML
  QUANDO /x-doc-generate roda
  ENTÃO defaults D-R/§7 da story 0001 são aplicados
  E geração só toca targets relevantes inferidos de interfaces[]

Cenario: Error — `--legacy-v1` com flag ambígua
  DADO operador roda /x-doc-generate --legacy-v1 --target-stack-aware
  QUANDO skill faz parse de args
  ENTÃO exit non-zero com FLAG_CONFLICT
  E stderr lista as duas flags como mutuamente exclusivas

Cenario: Boundary — detecção de mudança arquitetural dispara x-arch-system-update
  DADO PR adiciona novo módulo `application/integration/payment/`
  QUANDO /x-doc-generate roda em --target-stack-aware
  ENTÃO heurística detecta novo componente arquitetural (novo subdiretório de application/ com mais de 1 arquivo)
  E invoca Skill(skill: "x-arch-system-update", model: "sonnet", args: "--component payment")
  E system.md ganha entry sob ## Components
  SE EPIC-0070 indisponível
  ENTÃO skill loga WARN "x-arch-system-update indisponível — system.md não atualizado" e prossegue

Cenario: Performance — geração stack-aware completa em tempo aceitável
  DADO projeto com 20+ targets declarados em documentation.targets
  E 10+ arquivos de skill em .claude/skills/
  QUANDO /x-doc-generate roda em --target-stack-aware
  ENTÃO geração completa em < 60s
  E apenas targets relevantes ao stack são tocados

Cenario: Security — path traversal em documentation.targets rejeitado
  DADO YAML com documentation.targets contendo path "../../etc/passwd"
  QUANDO /x-doc-generate processa targets
  ENTÃO exit non-zero com PATH_TRAVERSAL_REJECTED
  E nenhum arquivo fora do diretório do projeto é lido ou modificado
  E skill NÃO segue symlinks em paths de targets
```

## 6. Decision Rationale

**Decisão:** Modificar v1 (não criar v3). **Motivo:** evolutivo — preserva contratos para callers existentes; flag `--legacy-v1` por 2 releases honra Rule 19 §Skill Renaming. **Alternativa descartada:** skill nova `x-doc-generate-v2` (nome diferente) — gera duplicação na slash-command menu e quebra muscle memory dos operadores. **Consequência:** v1 mantém fallback comportamental por 2 releases; remoção do fallback será PR follow-up sem necessidade de novo épico.

## 7. Refinement Notes (consolidadas)

- **Detecção de mudança arquitetural — heurística:** novo subdiretório em `application/` ou `domain/` ou `adapter/inbound/<protocol>/` ou `adapter/outbound/<technology>/` com ≥ 1 arquivo `.java`/`.ts`/`.py`/`.go`. Falsos positivos esperados em refactors que apenas movem código — mitigação: skip se `git log -p <new-dir>` mostra apenas `git mv` (rename detection).
- **Modo dry-run:** flag `--dry-run` lista o que seria atualizado sem escrever. Útil em CI para PR preview.
- **Integração com Phase 3:** Phase 3 modificada (story-0071-0006) invoca `x-doc-generate` ANTES de `x-doc-validate` — generate atualiza, validate confere.
- **Rule 13 Pattern usado:** INLINE-SKILL para `x-arch-system-update` (sub-skill direta com retorno usado). Quando EPIC-0070 indisponível, sub-skill é skipped com WARN — não bloqueia.
