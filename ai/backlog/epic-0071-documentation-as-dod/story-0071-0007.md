# História: Regenerar primeiro changelog híbrido para release atual (dogfood)

**ID:** story-0071-0007
**Status:** Refinada
**Refinement Verdict:** approved

> ✅ **REFINEMENT APPROVED** — All 7 dimensions passed. Ready for implementation.

## 1. Visão

Como **release manager**, quero gerar o **primeiro CHANGELOG híbrido** (Highlights + Keep-a-Changelog) para a release que entrega EPIC-0071 — **dogfood** do próprio formato novo. A story serve duplo propósito:

1. Validar que `x-release-changelog` v2 (story-0071-0004) produz output utilizável em release real (não só fixture sintética).
2. Comunicar a release de EPIC-0071 com Highlights bem escritos — auto-referencial intencional ("o que muda para você nesta release: documentação agora é DoD").

## 2. Entrega de Valor

- **Valor primário:** validação real do formato híbrido + comunicação clara da release que entrega doc-as-dod.
- **Valor secundário:** template para futuras releases — primeiro Highlights bem escrito vira referência de tom/tamanho para próximas execuções de `x-release-changelog`.
- **Métrica:** bloco `### Highlights` do release com EPIC-0071 cita 3+ valores entregues por EPIC-0071 (gate doc-as-dod, formato híbrido, dogfood); revisão humana aprova qualidade do output em ≤ 1 iteração.

## 3. Acceptance Criteria (Gherkin — 4 categorias mandatórias)

```gherkin
Cenario: Happy — dogfood gera entry híbrida
  DADO EPIC-0071 stories 0001..0006 mergeadas em epic/0071
  E EPIC-0070 disponível (pré-requisito hard D-R10)
  QUANDO operador roda /x-release-changelog vNEXT
  ENTÃO CHANGELOG.md ganha entry sem versão fixa (D-R12 — versão pinada por x-release)
  E entry inclui EPIC-0071 self-reference no bloco Highlights
  E entry tem 3-8 parágrafos derivados de "Entrega de Valor" do épico

Cenario: Degenerate — EPIC-0070 não disponível (modo degradado D-R10)
  DADO EPIC-0070 ainda não mergeado quando 0071 entra em release
  QUANDO /x-release-changelog roda
  ENTÃO Highlights vazio + WARN visível "EPIC-0070 não disponível — Highlights manual"
  E operador escreve Highlights manualmente lendo "Entrega de Valor" de epic-0071.md
  E entry final tem Highlights de qualidade equivalente

Cenario: Error — output de qualidade ruim (revisão humana rejeita)
  DADO Highlights gerado tem tom marketing ou foge do "o que muda para o usuário"
  QUANDO revisão humana inspeciona
  ENTÃO operador edita manualmente
  E story registra observação para refinamento de algoritmo (story follow-up)

Cenario: Boundary — entry sem versão fixa (D-R12)
  QUANDO story conclui
  ENTÃO CHANGELOG.md tem entry "## [Unreleased]" ou "## [vNEXT]" placeholder
  E `x-release` (em release-time) substitui placeholder pelo número real conforme Rule 08 SemVer

Cenario: Performance — geração do changelog dogfood completa em tempo aceitável
  DADO branch epic/0071 com 6+ stories mergeadas e 50+ commits
  QUANDO /x-release-changelog vNEXT roda
  ENTÃO geração completa em < 60s
  E entry híbrida é escrita em CHANGELOG.md sem timeout

Cenario: Security — Highlights gerado não contém referências a paths internos
  DADO epic-0071.md com Entrega de Valor que referencia paths internos do repo (ex.: java/src/main/...)
  QUANDO /x-release-changelog gera Highlights
  ENTÃO paths internos de implementação NÃO aparecem no bloco Highlights público
  E informações sensíveis (tokens, credenciais, env vars) NÃO são expostas no CHANGELOG
```

## 6. Decision Rationale

**Decisão:** Dogfood ANTES de marcar 0071 como Concluída (não pós-rollout). **Motivo:** validação real do formato em condições de release real, não fixture sintética; permite ajuste de algoritmo se output ruim. **Alternativa descartada:** dogfood pós-rollout — descobre problemas tarde demais, exige hotfix. **Consequência:** atrasa Phase 3 marginalmente (1-2 horas de revisão humana); aceitável dado o valor de validação.
