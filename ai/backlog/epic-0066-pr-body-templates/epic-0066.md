## 1. Contexto & Escopo

### 1.1 Problema

PRs atuais do repositório `ia-dev-environment` apresentam três deficiências sistêmicas:

1. **PRs de implementação** carregam paths para artefatos de plan/review em `## Orchestrator Evidence`, mas **não exibem o veredicto humano-legível** (specialist `Verdict: GO` / tech-lead `Decision: GO`). O reviewer humano precisa abrir 2-4 arquivos por PR para validar que reviews foram favoráveis.

2. **PRs de criação de épico/stories** (scaffold-only) **não têm template padronizado**. Cada operador inventa estrutura — PR #752 (epic-0063), #753 (epic-0064) e #754 (epic-0065) divergem em seções, ordem, e nível de detalhe.

3. **Telemetria** já carrega `epicId`/`storyId`/`taskId` em todo evento `tool.call` no NDJSON, mas **nada é consumido pelo body do PR**. Reviewer não vê tempo gasto por task ou por story sem rodar `/x-telemetry-analyze` manualmente.

Adicionalmente, **phase markers** (`phase.start` / `phase.end` exigidos por Rule 13) **não são emitidos em produção** — verificação em epics 0057-0060 mostra 0 ocorrências apesar do contrato. Isso impede agregação de telemetria por fase no template.

### 1.2 Escopo

Este epic entrega:

- **Dois templates Markdown** versionados sob `java/src/main/resources/shared/templates/`:
  - `_TEMPLATE-PR-IMPLEMENTATION.md` — para PR de implementação (story-PR para `epic/XXXX`; task-PR herda forma reduzida).
  - `_TEMPLATE-PR-BACKLOG.md` — para PR de scaffolding (epic + stories + IMPLEMENTATION-MAP, sem código de produção).
- **Skill nova `x-internal-pr-body-render`** (visibility: internal, model: haiku) que renderiza qualquer um dos dois templates a partir de fontes existentes (review artifacts, verify envelope, story-completion-report, telemetria, story markdown).
- **Script `scripts/telemetry-consolidate.sh`** (puro shell + jq) que agrega `events.ndjson` por escopo task/story/epic e emite JSON estruturado consumido pelo render skill.
- **Refactor de `x-pr-create`** (Phase 3) e da skill que cria backlog (`x-feature-create`, renomeada de `x-epic-decompose` por EPIC-0065) para invocarem o render skill.
- **Audit hard gate `audit-pr-template.sh`** que rejeita PRs sem o marcador `<!-- template-version:` no body.
- **Phase markers fix** em `x-story-implement` e `x-task-implement` para corrigir o gap de Rule 13 (story 0066-0009).
- **E2E smoke test** (`Epic0066PrTemplateSmokeTest`) cobrindo render + audit + integração com x-pr-create.

### 1.3 Fora do escopo (decisões D4 + D8)

- **Frontmatter YAML em reviews.** Decisão D4 do plano (`.claude/plans/pr-body-templates-plan.md`): reviews YAML estruturados ficam em **EPIC-0067** (sibling — pré-requisito deste epic). EPIC-0066 assume que ao iniciar implementação, reviews já emitirão YAML estruturado validado por `audit-review-frontmatter.sh`.
- **Backport de PRs já mergeados** para usar o novo template.
- **AI-based review quality scoring** — fora; consumimos veredicto declarado.
- **Templates para hotfix PRs** — fora; volume baixo justifica manual.

### 1.4 Entrega de Valor

- **Valor primário:** Reviewer humano consegue validar veredicto specialist + TL **sem abrir arquivos auxiliares** — só lendo o body do PR.
- **Valor secundário:** Telemetria por task/story aparece no body, dispensando `/x-telemetry-analyze` para review casual.
- **Valor terciário:** PRs de scaffolding ficam padronizados, reduzindo ruído de revisão e facilitando comparação cross-epic.
- **Métrica de sucesso primária:** 100% dos PRs criados via `x-pr-create` (após o epic) usam `_TEMPLATE-PR-IMPLEMENTATION.md`; 100% dos PRs criados via `x-feature-create` usam `_TEMPLATE-PR-BACKLOG.md`.
- **Métrica de sucesso secundária:** `audit-pr-template.sh` exit 0 em todos PRs novos (zero regressões).

## 3. Contratos & Endpoints

### 3.1 Contrato `_TEMPLATE-PR-IMPLEMENTATION.md`

Seções obrigatórias (na ordem):

1. `# {{title}}`
2. `## Summary`
3. `## Story / Task Context` (tabela com Story ID, Epic ID, Task IDs, flowVersion)
4. `## Acceptance Criteria` (lista handlebars `{{#each acceptanceCriteria}}`)
5. `## Review Status` (tabela com `Verdict`, `Decision`, paths dos artefatos)

### 8.2 Decisão arquitetural principal — dois templates separados

**Decisão:** dois templates independentes (`_TEMPLATE-PR-IMPLEMENTATION.md` e `_TEMPLATE-PR-BACKLOG.md`) ao invés de um template único condicional via handlebars `{{#if kind=implementation}}`.

**Motivo:** templates são consumidos por dois caminhos diferentes (x-pr-create vs x-feature-create) e têm seções não-sobrepostas (review status vs DAG structure). Um template condicional dobra a complexidade do parser e dificulta evolução independente.

**Alternativa descartada:** template único com todas as 13 seções condicionais (`{{#if kind == 'implementation'}}{{review-section}}{{/if}}`). Rejeitado porque:
- Aumenta carga cognitiva ao ler o template.
- Torna `audit-pr-template.sh` mais complexo (precisa decidir qual conjunto de seções validar).
- Cria acoplamento entre dois fluxos que evoluem em ritmos diferentes.

**Consequência:** dois arquivos em vez de um; duplicação aceita (~30 linhas comuns: header, footer, orchestrator evidence). O ganho em clareza supera o custo de duplicação. Ambos templates compartilham marcador `<!-- template-version: 1.0 -->` para audit unificado.

### 8.3 Decisão arquitetural secundária — render skill é INTERNAL

**Decisão:** `x-internal-pr-body-render` é internal (Rule 22), não public.

**Motivo:** não há valor em o usuário invocar `/x-internal-pr-body-render` diretamente. Sempre é wrapper de `x-pr-create` (implementation) ou `x-feature-create` (backlog).

**Alternativa descartada:** skill public (`x-pr-body-render`). Rejeitado porque:
- Aumenta superficie no `/help` sem benefício.
- Cria fluxo "manual" que pode bypassar `audit-pr-template.sh` se operador esquecer de chamar `x-pr-create` depois.

**Consequência:** segue padrão de Rule 22 §Migration Path (subroutine usado por ≥ 2 públicos). Vai para `java/src/main/resources/targets/claude/skills/internal/pr/`.

### 8.4 Decisão arquitetural sobre script vs Java

**Decisão:** `scripts/telemetry-consolidate.sh` é puro shell + jq, não classe Java.

**Motivo:** Rule 14 §Forbidden proíbe explicitamente "Telemetry collection or analysis" em código Java do gerador. Análise é runtime; gerador apenas embarca o script.

**Alternativa descartada:** classe `TelemetryAnalyzeCli` Java (já existente em `dev.iadev.telemetry.analyze`). Rejeitada porque consumir requer JVM startup (~600ms) — demasiado lento para ser chamado por hook ou render skill em cada PR.

**Consequência:** script duplica parcialmente lógica do `TelemetryAnalyzeCli`. Mitigação: ambos consomem mesmo NDJSON com mesmo schema; smoke test compara saídas. Manutenção em paralelo é aceitável dado custo de chamada.

### 8.5 Decisão sobre granularidade de tasks (D1 + D2)

**Decisão:** 9 stories (D1 completa + D2 phase markers).

**Motivo:** cada story tem responsabilidade isolada e File Footprint não-sobreposta (com 2 exceções: 0003+0004 sequencial, 0007 modifica audit existente).

**Alternativa descartada:** 5 stories magrinhas (variante §7.1 do plano). Rejeitada porque:
- Mescla 0003+0004 em uma só story criaria diff muito grande (~600 linhas SKILL.md).
- Mescla 0005+0006 acopla x-pr-create e x-feature-create — cada um deveria ter seu próprio PR de review.
- Remove story de audit (0007) — D5 explicitamente exige hard gate, então 0007 é mandatório.

**Consequência:** mais granularidade significa mais PRs (9 task PRs + 1 epic PR), mas cada PR é mais review-friendly. Caminho crítico permanece curto (4 phases lógicas).
