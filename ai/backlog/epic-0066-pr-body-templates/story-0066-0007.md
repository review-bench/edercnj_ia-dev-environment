## 1. Contexto & Escopo

Como **Operator de CI**, eu quero que todo PR mergeado em `epic/0066` ou `develop` seja
validado por um CI script `audit-pr-template.sh` (camada CI script, Rule 26 §Taxonomy),
invocado durante `mvn verify` por um Java audit harness `AuditPrTemplateAuditorTest`
(camada Java test layer, Rule 26 — convenção pós EPIC-0061 que removeu `audit.yml`),
que rejeita corpos de PR sem o marcador estrutural `<!-- template-version:`, para que
nenhum PR manual (criado sem `x-pr-create` ou `x-feature-create`) passe silenciosamente
pelo gate de lifecycle (Rule 27 §Non-bypass Contract — superfície 11).

> **Nota arquitetural — execução do gate:** EPIC-0061 (story-0061-0005) deletou
> `.github/workflows/audit.yml`. Auditorias de governance agora rodam inline via
> `mvn verify` através de classes Java `*AuditorTest` (Rule 26 §Java test layer +
> EPIC-0061 RULE-007/RULE-008). Esta story segue o mesmo padrão: o CI script é a
> implementação canônica (Rule 26 §CI script), e o `AuditPrTemplateAuditorTest`
> é o "harness" que o invoca durante o ciclo Maven, propagando exit codes como
> falhas de teste bloqueantes.

Adicionalmente, esta story estende `scripts/audit-pr-evidence.sh` para reconhecer a
variante backlog: quando `## Backlog Entregue` está presente no body, a seção
`## Orchestrator Evidence` sem Story IDs populados é válida por design (PRs de scaffolding
não carregam story-shaped evidence).

## 3. Contratos & Endpoints

### 3.1 CLI Contract `audit-pr-template.sh`

```bash
# Validar um PR específico
scripts/audit-pr-template.sh --pr <PR_NUMBER> [--repo <owner/repo>]

# Verificar pré-requisitos estruturais do próprio script
scripts/audit-pr-template.sh --self-check

# Exibir ajuda
scripts/audit-pr-template.sh --help
```

#### 3.1.1 Argparse

| Flag | Tipo | Obrigatório | Descrição |
| :--- | :--- | :--- | :--- |
| `--pr <N>` | integer | Sim (exceto `--self-check`) | Número do PR a validar |
| `--repo <owner/repo>` | string | Não | Repositório GitHub; padrão: inferido via `git remote` |
| `--hotfix-bypass` | flag | Não | Registra PR em baseline e sai 0; SOMENTE em `## Recovery` de SKILL.md chamador |
| `--self-check` | flag | Não | Verifica dependências e baseline; sai 0 ou 2 |
| `--help` | flag | Não | Exibe banner de uso |

#### 3.1.2 Fluxo de validação

1. Obter body do PR via `gh pr view <PR> --json body -q '.body'`.
2. Verificar se PR ID está em `governance/baselines/pr-template-baseline.txt` → se sim, exit 0 (avozado).
3. Verificar se PR body contém comment `<!-- audit-exempt: <reason> -->` → se sim e `<reason>` é não-vazio, exit 0.
4. Verificar se as primeiras 5 linhas contêm `<!-- template-version:` → se não, exit 1 `PR_TEMPLATE_VIOLATION`.
5. Detectar kind: linha `<!-- template-version:` contém token `--kind=backlog` → kind=backlog; caso contrário, kind=implementation.
6. Para kind=implementation: validar presença das 9 seções (§3.1.3).
7. Para kind=backlog: validar presença das 12 seções (§3.1.4).
8. Qualquer seção ausente → exit 1 `PR_TEMPLATE_VIOLATION` com nome da seção em stderr.
9. Todas as seções presentes → exit 0.

#### 3.1.3 Seções obrigatórias — kind=implementation (9 seções)

```
## Summary
## Story / Task Context
## Acceptance Criteria
## Review Status
## Verify Gate
## Telemetry
## Changes
## Orchestrator Evidence
```

Mais o title `# ` (linha com `^# ` no início do body). Total: 9 elementos verificados.

#### 3.1.4 Seções obrigatórias — kind=backlog (12 seções)

```
## Summary
## Backlog Entregue
## Lista de Stories
## Estrutura do DAG
## Coordenação com Epics em Andamento
## Métricas de Sucesso
## Test Plan
## Hard-Cut Authorization
## Out of Scope
## Origem (Plan Mode)
## Orchestrator Evidence
```

Mais o title `# `. Total: 12 elementos verificados.

### 3.2 Exit Codes (Rule 26 §Standardized Exit Codes — CI scripts only)

| Exit | Código (stderr) | Condição |
| :--- | :--- | :--- |
| 0 | — | Body conforme template, ou PR avozado em baseline, ou `audit-exempt` válido |
| 1 | `PR_TEMPLATE_VIOLATION` | Marcador ausente, kind desconhecido, ou seção obrigatória ausente |
| 2 | `OPERATIONAL_ERROR` | `gh` CLI ausente, PR não encontrado, jq ausente, baseline corrompida |
| 3 | `INVALID_EXEMPTION` | `<!-- audit-exempt: -->` sem reason, ou entrada de baseline malformada |

### 3.3 `--self-check` Contract (Rule 26 §self-check)

Verifica (saindo com exit 2 se qualquer check falhar):

1. `gh` CLI no PATH.
2. `jq` no PATH.
3. `governance/baselines/pr-template-baseline.txt` legível (ou ausente mas criável — warn only).
4. `scripts/audit-pr-template.sh` próprio tem hash de seção `--self-check` reachable.

## 8. Decision Rationale

**Decisão:** `audit-pr-template.sh` valida presença estrutural de seções (existência de `## Section Name`), não conteúdo semântico das seções.

**Motivo:** validação semântica (e.g., "Verify Gate tem coverage ≥ 95%") exigiria parse de Markdown estruturado, dependência de `pandoc` ou lógica complexa. A check de presença de seção é suficiente para detectar PRs manuais e é testável de forma determinística com fixtures simples.

**Alternativa descartada:** validação semântica de campos (e.g., verificar que `Coverage — Line` tem valor ≥ 95%). Rejeitada porque a render skill já é responsável por preencher corretamente; o audit é safety net para detectar bypass, não rerifica conteúdo já validado em outros gates.

**Consequência:** um PR poderia ter todas as seções vazias mas com headings presentes e passar na validação estrutural. Aceitável — o conteúdo é validado por Rule 24 / Rule 27 gates de artifact existence; este audit fecha o gap de "body totalmente sem estrutura".
