## 1. Contexto & Escopo

Como **Operador de PR**, eu quero que a skill interna `x-internal-pr-body-render --kind=implementation` gere automaticamente o corpo do PR em Markdown a partir de fontes já existentes em disco (artefatos de review, verify envelope, story-completion-report, telemetria e commits), para que o reviewer humano consiga validar veredicto specialist + tech-lead **sem abrir arquivos auxiliares** — lendo apenas o body do PR.

Esta story cria o arquivo `java/src/main/resources/targets/claude/skills/internal/pr/x-internal-pr-body-render/SKILL.md` do zero, cobrindo apenas o fluxo `--kind=implementation`. A extensão `--kind=backlog` fica para a story sequencial 0066-0004 (mesmo arquivo — hot-spot declarado na §9.3 File Footprint).

A skill:
- É **internal** (Rule 22) — invocada somente por `x-pr-create` e `x-feature-create` via INLINE-SKILL Pattern 1 (Rule 13).
- Usa **model: haiku** (Rule 23 §Haiku Eligibility — utility sem design reasoning).
- Implementa **fail-open**: dado ausente produz placeholder humano-legível (`(not yet run)` / `(pending)` / `(no telemetry)`) — nunca o placeholder de auditor `story-XXXX-YYYY` que acionaria `audit-pr-evidence.sh`.
- Canonicaliza e verifica o path `--out` para evitar path traversal (Rule 06 J6).
- Faz escape de caracteres Markdown perigosos antes da substituição handlebars (Rule 06).

### 3.4 Fontes de Dados — Phase 1 GATHER

A skill lê 7 fontes de dados na ordem abaixo. Cada fonte tem seu comportamento de falha-aberto definido:

| # | Fonte | Localização | Parse | Fallback (falha-aberto) |
| :--- | :--- | :--- | :--- | :--- |
| 1 | Story markdown | `ai/epics/*/story-{storyId}.md` ou `plans/epic-XXXX/story-{storyId}.md` (PathResolver) | Regex para seções Gherkin `Cenário:` (AC) | `acceptanceCriteria: []` |
| 2 | Review specialist | `ai/epics/epic-XXXX-*/plans/review-story-{storyId}.md` (v4) ou `plans/epic-XXXX/plans/review-story-{storyId}.md` (v3) — resolução via `PathResolver` | **YAML-when-available**: se EPIC-0067 mergeou e o arquivo abre com `---` (frontmatter), usar `yq '.verdict'`; senão, fallback regex `^\*\*Verdict:\s*(GO\|NO-GO)\*\*$` | `specialistVerdict: "(pending)"` |
| 3 | Review tech-lead | `ai/epics/epic-XXXX-*/plans/techlead-review-story-{storyId}.md` (v4) ou `plans/epic-XXXX/plans/techlead-review-story-{storyId}.md` (v3) — resolução via `PathResolver` | **YAML-when-available**: se frontmatter presente, `yq '.decision'`; senão, regex `^\*\*Decision:\s*(GO\|NO-GO)\*\*$` | `techleadDecision: "(pending)"` |
| 4 | Verify envelope | `plans/epic-XXXX/reports/verify-envelope-{storyId}.json` | jq `.testsResult`, `.coverageLine`, `.coverageBranch` | `"(not yet run)"` por campo |
| 5 | Story completion report | `plans/epic-XXXX/reports/story-completion-report-{storyId}.md` | Regex para tabela de tasks `| TASK-` | `taskIds: "(none)"` |
| 6 | Telemetria | `scripts/telemetry-consolidate.sh --story={storyId}` | JSON via stdout | `"(no telemetry available)"` se exit 1 |
| 7 | Commits | `git log develop..HEAD --oneline` | stdout linha a linha | `"(no commits)"` |

**Regra crítica de falha-aberto (RULE-004):** Nenhum placeholder gerado por ausência de dado pode ser `story-XXXX-YYYY`, `EPIC-XXXX`, ou qualquer padrão reconhecido por `audit-pr-evidence.sh` como token de auditoria. Placeholders válidos: `(pending)`, `(not yet run)`, `(no telemetry available)`, `(none)`, `(no commits)`.

**Detecção YAML-when-available (fontes 2 e 3):** primeira tentativa usa `head -1 <file>` para detectar `---` (frontmatter abre); se sim, parse YAML estruturado via `yq` (mais robusto, alinhado com EPIC-0067). Se o arquivo não tem frontmatter (situação esperada enquanto EPIC-0067 não mergear) ou se `yq` não está no PATH, cair para regex sobre o corpo Markdown. Esta detecção é por-arquivo, não global — EPIC-0066 pode entregar antes ou depois de EPIC-0067 sem mudança de código. Se ambos os métodos falharem (verdict não encontrado), usar o placeholder `(pending)` (RULE-004 — falha-aberto).

### 3.5 Fases da Skill

A skill tem 5 fases numeradas. Cada fase emite marcadores `phase.start` / `phase.end` (Rule 13 §Telemetry Markers).

**Phase 0 — ARGS:** Parsear e validar argumentos. Detectar `--kind`, `--story-id`, `--out`. Falhar com exit 1 se `--kind` ausente/inválido. Falhar com exit 3 se `--kind=implementation` e `--story-id` ausente. Canonicalizar `--out` e verificar que fica dentro de `${REPO_ROOT}` (Rule 06 J6 — sem path traversal).

**Phase 1 — GATHER:** Ler as 7 fontes de dados descritas em §3.4. Construir JSON envelope intermediário com todos os campos. Aplicar fallbacks de falha-aberto para cada campo ausente.

**Phase 2 — TELEMETRY:** Invocar `scripts/telemetry-consolidate.sh --story={storyId} --format=json` via Bash. Se exit 0: parsear e incorporar ao envelope. Se exit 1 (`NO_TELEMETRY`): preencher campos de telemetria com placeholder `(no telemetry available)`. Se exit 2 (`OPERATIONAL_ERROR`): emitir WARNING em stderr e continuar com placeholder (não abortar — telemetria é non-blocking por RULE-002).

**Phase 3 — RENDER:** Invocar `x-internal-report-write` via INLINE-SKILL (Rule 13 Pattern 1) passando o template `_TEMPLATE-PR-IMPLEMENTATION.md` e o JSON envelope. A skill existente realiza a substituição handlebars (`{{#each}}` / `{{#if}}`).

**Phase 4 — WRITE:** Escrever o Markdown renderizado no path `--out` de forma atômica (escrita em temp file + mv). Emitir o path em stdout (exit 0) ou `OPERATIONAL_ERROR` (exit 2) se escrita falhar.

### 3.6 Segurança

- **Path traversal em `--out`:** canonicalizar via `realpath --canonicalize-missing` + verificar que começa com `${REPO_ROOT}` (Rule 06 J6).
- **Markdown injection:** escapar `` ` ``, `|`, `\n` embutidos nos campos parseados antes da substituição handlebars.
- **Secrets em telemetria:** a skill NUNCA propaga `metadata.*` do NDJSON — apenas campos numéricos (`activeMs`, `elapsedMs`, `events`, `calls`, `totalMs`, `p95Ms`).

## 8. Decision Rationale

**Decisão:** 5 fases numeradas em vez de um bloco monolítico.

**Motivo:** Rule 13 exige marcadores de telemetria por fase numerada. Separar ARGS / GATHER / TELEMETRY / RENDER / WRITE em fases distintas permite observabilidade granular (operador vê qual fase está lenta) e facilita o teste unitário de cada fase com fixtures independentes.

**Alternativa descartada:** implementação em uma única fase com todo o pipeline inline. Rejeitada porque:
- `TelemetryMarkerLint` exige pelo menos um par `phase.start`/`phase.end` para skills de implementação.
- Dificulta testes: Phase 2 (telemetria) e Phase 3 (render) têm dependências distintas que precisam ser mockadas separadamente.

**Consequência:** 5 chamadas a `telemetry-phase.sh` adicionam ~5ms ao tempo de execução. Aceitável (dentro da faixa haiku).
