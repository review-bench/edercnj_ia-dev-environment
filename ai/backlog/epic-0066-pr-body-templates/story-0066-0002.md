## 1. Contexto & Escopo

Como **Render Skill de PR body** (skill `x-internal-pr-body-render` — story-0066-0003), eu quero invocar `scripts/telemetry-consolidate.sh --story=story-XXXX-YYYY` e receber um JSON estruturado com `activeMs`, `elapsedMs`, `events`, lista de tasks e top 5 ferramentas por duração, para que o template `_TEMPLATE-PR-IMPLEMENTATION.md` exiba métricas de telemetria no body de todo PR gerado.

Hoje o NDJSON em `plans/epic-XXXX/telemetry/events.ndjson` acumula centenas de eventos `tool.call`, `phase.start`/`phase.end`, e `subagent.*`, mas **nenhum consumidor os agrega por story/task/epic de forma estruturada e consumível por shell**. O `/x-telemetry-analyze` existente emite Mermaid Gantt para consumo humano interativo — não produz JSON consumível por script.

Esta story cria:
- `scripts/telemetry-consolidate.sh` — script puro shell + jq, argparse estilo `--story=`, `--task=`, `--epic=`, saída JSON (default), md, table.
- `java/src/main/resources/targets/claude/scripts/telemetry-consolidate.sh` — cópia source-of-truth embarcada via `ScriptsAssembler` (EPIC-0058), para que projetos gerados herdem o script.
- `src/test/java/dev/iadev/skills/Epic0066TelemetryConsolidateTest.java` — 5 fixtures JUnit (degenerate, happy, malformed, empty, large).

A story **não** cria qualquer classe Java de análise de telemetria (Rule 14 §Forbidden — "Telemetry collection or analysis"). O gerador embarca apenas o script; a lógica fica no shell.

### 1.1 Regras Transversais Aplicáveis

| ID | Título | Impacto |
| :--- | :--- | :--- |
| RULE-002 | Telemetria consumida como side-effect, not gate | Script nunca bloqueia; render skill falha-aberto se JSON ausente |

> **Nota sobre Rule 26 §Naming:** `telemetry-consolidate.sh` usa prefixo `telemetry-` (não `audit-`). Isso é correto: o script é uma ferramenta de agregação, **não** um audit gate CI. Portanto não está sujeito ao mandato `audit-` de Rule 26 §Naming. O `--self-check` é implementado voluntariamente (boa prática de scripts), não como obrigação de Rule 26.

### 1.2 Entrega de Valor

- **Valor primário:** render skill (story-0066-0003) recebe JSON estruturado para preencher a seção `## Telemetry` do `_TEMPLATE-PR-IMPLEMENTATION.md` sem processar NDJSON raw.
- **Valor secundário:** operadores conseguem rodar `scripts/telemetry-consolidate.sh --story=story-XXXX-YYYY --format=table` no terminal para review rápido sem abrir o PR.
- **Métrica de Sucesso:** `scripts/telemetry-consolidate.sh --story=story-0062-0005` retorna JSON válido (exit 0) com campos `scope`, `id`, `tasks[]`, `topTools[]` em < 2 s para arquivo com 10.000 eventos; `mvn test Epic0066TelemetryConsolidateTest` GREEN com 5 cenários passando.
- **Impacto no Negócio:** desbloqueia story-0066-0003 (render skill) — única dependência de dados de telemetria no caminho crítico do epic.

## 3. Contratos & Endpoints

### 3.1 CLI Contract

```bash
# Agregação por story
scripts/telemetry-consolidate.sh --story=story-XXXX-YYYY [--format=json|md|table]

# Agregação por task
scripts/telemetry-consolidate.sh --task=TASK-XXXX-YYYY-NNN [--format=json|md|table]

# Agregação por epic
scripts/telemetry-consolidate.sh --epic=epic-XXXX [--format=json|md|table]

# Self-check (valida dependências)
scripts/telemetry-consolidate.sh --self-check
```

**Regras de argparse:**
- Exatamente um dos três escopos (`--story`, `--task`, `--epic`) é obrigatório; múltiplos → exit 2 `OPERATIONAL_ERROR`.
- `--format` padrão: `json`.
- Flags desconhecidas → exit 2 `OPERATIONAL_ERROR`.

### 3.2 Saída JSON (format=json — default)

```json
{
  "scope": "story",
  "id": "story-0066-0002",
  "epicId": "EPIC-0066",
  "events": 87,
  "activeMs": 134560,
  "elapsedMs": 1820000,
  "tasks": [
    {
      "id": "TASK-0066-0002-001",
      "activeMs": 42100,
      "elapsedMs": 680000,
      "events": 31
    }
  ],
  "topTools": [
    {
      "tool": "Bash",
      "calls": 52,
      "totalMs": 78400,
      "p95Ms": 2539
    }
  ]
}
```

**Campos obrigatórios:** `scope`, `id`, `epicId`, `events`, `activeMs`, `elapsedMs`, `tasks`, `topTools`.

**Semântica de agregação:**
- `activeMs` = soma de `durationMs` de todos eventos `tool.call` no escopo.
- `elapsedMs` = `max(timestamp) - min(timestamp)` de todos eventos no escopo.
- `tasks[].activeMs` = soma de `durationMs` eventos cujo `metadata.taskId` casa com o ID da task.
- `topTools` = top 5 ferramentas ordenadas por `totalMs` descendente; P95 calculado como percentil 95 das durações individuais.
- Linhas NDJSON malformadas (não-parseable por `jq`) → ignoradas com WARNING em stderr; agregação continua.

### 3.3 Saída Markdown (format=md)

```markdown
## Telemetria — story-0066-0002

| Scope | Active time | Elapsed time | Events |
| :--- | :--- | :--- | :--- |
| Story `story-0066-0002` | 2 min | 30 min | 87 |
| Task `TASK-0066-0002-001` | 0.7 min | 11 min | 31 |

**Top tools:**
- `Bash`: 1307 s (52 calls, P95 2539 ms)
```

### 3.4 Saída Tabela (format=table)

Formato ascii-table simples, uma linha por escopo, adequado para terminal. Colunas: `SCOPE | ACTIVE_MIN | ELAPSED_MIN | EVENTS`.

### 3.5 Exit Codes (Rule 26 §Standardized Exit Codes — por analogia)

| Exit | Code | Significado |
| :--- | :--- | :--- |
| 0 | OK | JSON/md/table emitido com sucesso |
| 1 | NO_TELEMETRY | `events.ndjson` ausente ou vazio para o escopo; nenhum evento correspondente |
| 2 | OPERATIONAL_ERROR | jq ausente no PATH; argumento inválido; múltiplos escopos |

### 3.6 `--self-check` Behavior

```bash
scripts/telemetry-consolidate.sh --self-check
```

- Verifica `jq` no PATH → exit 2 se ausente.
- Verifica que diretório `plans/` existe (relativo ao PWD ou `$CLAUDE_PROJECT_DIR`) → exit 2 se ausente.
- Verifica que o próprio script tem bit de execução → exit 2 se ausente.
- Sucesso: exit 0 + mensagem `OK: telemetry-consolidate.sh self-check passed` em stdout.

- **OCP:** Novo `--format` (ex.: `csv`) adicionável sem modificar `aggregate_json` — só extende `format_output`.
- **DIP:** O script recebe o path do NDJSON via variável resolvida (não hardcoded); `ScriptsAssembler` é o binding point.

### 4.3 Estrutura Interna do Script

```bash
#!/usr/bin/env bash
set -euo pipefail

# parse_args() → preenche SCOPE, SCOPE_ID, FORMAT
# resolve_ndjson() → encontra plans/epic-XXXX/telemetry/events.ndjson
# aggregate_json() → pipeline jq que emite o JSON estruturado
# format_output() → converte JSON para md ou table se pedido
# self_check() → valida dependências
# main() → orquestra
```

Cada função: ≤ 25 linhas. Total do script: ≤ 150 linhas (excluindo comentários e linhas em branco).

## 8. Decision Rationale

### 8.1 Shell + jq vs. Java

**Decisão:** Script puro shell + jq, não classe Java.

**Motivo:** Rule 14 §Forbidden proíbe explicitamente "Telemetry collection or analysis" em código Java do gerador. Além disso, shell + jq startup time (~50 ms) é aceitável para uso em PR body render; JVM startup (~600 ms) seria custoso demais para ser chamado por hook.

**Alternativa descartada:** `TelemetryAnalyzeCli.java`. Rejeitada por Rule 14 + latência de JVM.

**Consequência:** duplicação parcial de lógica com o Gantt de `/x-telemetry-analyze`. Aceita: diferentes outputs, diferentes consumers, diferentes ciclos de evolução.

### 8.2 Fail-open (exit 0 quando nenhum dado relevante vs. exit 1)

**Decisão:** exit 1 `NO_TELEMETRY` quando nenhum evento do escopo for encontrado.

**Motivo:** o render skill (story-0066-0003) precisa distinguir "telemetria disponível" de "telemetria ausente" para renderizar placeholder `(telemetry not available)` vs. dados reais. Exit 1 é o sinal correto. O render skill trata exit 1 como fallback para placeholder — não aborta.

**Alternativa descartada:** exit 0 + JSON com campos zerados. Rejeitada porque um JSON com `"events": 0` parece dado válido ao consumidor, dificultando o tratamento de ausência de telemetria.

### 8.3 Top 5 vs. top N parametrizável

**Decisão:** top 5 hardcoded no script.

**Motivo:** o template `_TEMPLATE-PR-IMPLEMENTATION.md` exibe lista curta de ferramentas. N parametrizável adicionaria complexidade ao argparse sem benefício para o caso de uso principal.

**Consequência:** consumidor que precisar de top N diferente deve processar o JSON e re-filtrar. Documentado no `--help` do script.
