## 1. Visão

Como **operador de planejamento**, eu quero **uma skill que dispare múltiplas personas (PO, Tech Lead, Architect, Security, QA + condicionalmente Performance/SRE) em paralelo para refinar a história sob ângulos cruzados**, com perguntas consolidadas em um único batch e consolidação final pelo Architect, garantindo que o veredicto registrado seja prova de refinamento multi-perspectiva — não inquérito de uma só voz.

## 2. Persona & Cenário

**Persona principal:** operador de planejamento (PO/dev tech-lead misto). Invoca `/x-story-refine story-XXXX-YYYY` como single-entry; o dispatcher por baixo distribui análise para N persona-agents em paralelo.

**Cenário:** operador prestes a planejar uma story; quer cobertura cruzada (PO valida AC, Security identifica PII desprotegida, QA exige cenário de borda) sem precisar invocar 5 skills. Invoca a skill uma vez; recebe **um único batch consolidado** de perguntas (deduplicadas, agrupadas por categoria); responde tudo de uma vez; Architect consolida o resultado final no markdown da história.

## 3. Entrega de Valor

- **Valor primário:** stories deixam de chegar ao planning sem AC mensurável, persona genérica e contratos vagos.
- **Valor secundário:** o registro do diálogo (não só do checklist) fica auditável no markdown — ponto de retrospectiva pós-implementação.
- **Métrica primária:** ≥ 80% das stories pós-rollout têm `refinementVerdict.status="approved"` ao entrar em planning. Medido por `audit-refinement-gate.sh` (story-0006) semanalmente.
- **Métrica secundária:** redução de ≥ 30% no tempo médio de Phase 2 (TDD loop) — proxy de "quanto retrabalho de design entrou na implementação". Medido via `/x-telemetry-trend` comparando 5 épicos pré/pós rollout.

### 5.2 Phases A/B/C/D (contrato do dispatcher — D-R12..D-R15)

```
Phase A — Specialist analysis (paralelo, sem perguntas ao operador) [D-R12 + D-R15]
  Dispatcher emite N TaskCreate (1 por persona ativa) e despacha N sibling Agents EM UMA ÚNICA assistant message:

    Agent(subagent_type: "general-purpose", model: "sonnet",
          description: "PO refinement analysis for {STORY_ID}",
          prompt: "<carrega agents/core/product-owner.md + Rule 02/05/06/13 + story markdown> + <output schema: {questions: [...], blockers: [...], dimensions-owned: [persona, value, ac]}>")
    Agent(subagent_type: "general-purpose", model: "sonnet",
          description: "Tech Lead refinement analysis for {STORY_ID}",
          prompt: "<carrega agents/core/tech-lead.md + Rule 03/04 + story markdown> + <output schema com dimensions-owned: [contracts, dependencies]>")
    Agent(subagent_type: "general-purpose", model: "sonnet",
          description: "Architect refinement analysis for {STORY_ID}",
          prompt: "<carrega agents/core/architect.md + Rule 04 + story markdown> + <output schema com dimensions-owned: [alternatives, layer-ownership, adr-triggers]>")
    Agent(subagent_type: "general-purpose", model: "sonnet",
          description: "Security refinement analysis for {STORY_ID}",
          prompt: "<carrega agents/core/security-engineer.md + Rule 06 + story markdown> + <output schema com dimensions-owned: [threat-surface, sensitive-data, compliance-triggers]>")
    Agent(subagent_type: "general-purpose", model: "sonnet",
          description: "QA refinement analysis for {STORY_ID}",
          prompt: "<carrega agents/core/qa-engineer.md + Rule 05 + story markdown> + <output schema com dimensions-owned: [ac-categories, edge-cases, testability]>")

    # Condicionais (ativadas por capabilities):
    # - capability `compute.async.*` ou `data.observability.metrics` → Performance Engineer agent
    # - capability `infra.observability.*` ou `infra.deploy.*` → SRE/DevOps agent

  Cada agent retorna JSON estruturado: { questions: [...], blockers: [...], silent-rejections: [...], proposedSection: <draft> }.
  Dispatcher coleta todos os outputs e emite TaskUpdate(status: "in_progress") nas 5–7 tasks.

Phase B — Question consolidation (síncrono, ÚNICO batch) [D-R14]
  1. Dispatcher coleta `questions` de todas as personas.
  2. Aplica algoritmo de dedup: similaridade textual com normalização (lowercase, stopwords, lemma básico) — match >= 0.8 vira pergunta única.
  3. Agrupa por categoria: Persona/Valor, Contratos, Segurança, Qualidade, Performance, Operações.
  4. Apresenta em formato Markdown numerado, com indicação de qual(is) persona(s) fizeram a pergunta.
  5. Operador responde em um único bloco-texto (formato livre ou numerado correspondente).
  6. Dispatcher parseia respostas e distribui: cada persona recebe respostas relevantes ao seu escopo.
  Se zero perguntas no Phase A (todas as personas aprovaram em silêncio ou bloquearam): pula direto para Phase D.

Phase C — Specialist refinement (paralelo, com respostas) [D-R12]
  Dispatcher despacha NOVAMENTE os mesmos N sibling Agents em UMA ÚNICA assistant message, agora com:
  - persona definition (mesma do Phase A)
  - story markdown atualizada (caso operador tenha editado entre fases — refresh)
  - respostas relevantes do batch
  - output schema: { proposedSection: <reescrita>, dimensionVerdict: "approved" | "blocker", notes: <...> }

  Cada persona reescreve sua contribuição:
  - PO → Persona/Valor + AC clareza
  - Tech Lead → Contratos tipados + Dependências
  - Architect → Alternativas + Layer ownership + ADR triggers
  - Security → Riscos de segurança + Compliance triggers
  - QA → AC mensurável + Cenários (happy/borda/erro/regressão)
  - Performance (cond.) → Métricas/SLA
  - SRE (cond.) → Observabilidade/Deploy

Phase D — Architect consolidation [D-R13]
  Dispatcher invoca UM agent Architect dedicado em modo "consolidador":

    Agent(subagent_type: "general-purpose", model: "opus",
          description: "Architect consolidation for {STORY_ID}",
          prompt: "<carrega agents/core/architect.md + Rule 04 + ADR registry>
                  + <story markdown atual>
                  + <todas as proposedSection das 5–7 personas>
                  + <todos os blockers>
                  + INSTRUCTIONS: você está em modo CONSOLIDADOR. Aplique merge das contribuições nas seções correspondentes. Regenere o bloco '## Refinement Verdict' único, listando dimensions per-persona com status. Se houver blocker em qualquer dimensão → status final = 'rejected'. Caso contrário → 'approved'.")

  Architect retorna: markdown completo da história revisada + bloco Refinement Verdict canônico.

  Dispatcher dual-writes atomicamente:
    Skill(skill: "x-internal-status-update", model: "haiku",
          args: "--key refinementVerdict --value <json com dimensions per-persona, status, scope=story>")

  Dispatcher escreve markdown via Edit. Emite TaskUpdate(status: "completed") nas N tasks.
```

## 8. Decision Rationale

**Decisão D1 (atualizada por D-R12):** Dispatcher multi-persona com 4 phases (A: análise paralela; B: batch único; C: refinamento paralelo; D: consolidação Architect). NÃO mais inquérito linear de 6 dimensões.
**Motivo:** epic §6.7 — refinamento real cobre ângulos múltiplos (PO, Tech Lead, Architect, Security, QA + condicionais); uma só voz perde dimensões. Padrão reaproveita `x-internal-story-build-plan` Steps 1B–1F.
**Alternativa descartada (a):** N skills públicas (`x-story-refine-po`, ...) — taxonomia explode (D-R4).
**Alternativa descartada (b):** skill linear (modelo original) — falha exatamente no problema que o épico ataca.
**Consequência:** dispatcher precisa de tools `Skill` + `Agent`; pré-requisito é `agents/core/*.md` declararem §Rules explícita.

**Decisão D2:** Dual-write atômico (markdown + state) via INLINE-SKILL `x-internal-status-update`.
**Motivo:** Rule 13 (D-R9) + locality of control — o lock atômico do state já é responsabilidade de `x-internal-status-update`; skill nova reaproveita.
**Alternativa descartada:** escrever direto via Edit tool no state.
**Consequência:** dependência de `x-internal-status-update` ser invocável (já é, internal skill EPIC-0049).

**Decisão D3 (atualizada por D-R13):** `model: sonnet` no dispatcher e nos persona-agents de Phases A/C; `model: opus` apenas no Architect de Phase D (consolidador).
**Motivo:** Rule 23 — analistas individuais são Reviewer/Validator tier (perguntas Socráticas + heurísticas, Sonnet é suficiente); consolidação cross-cutting é Deep Planner tier (precisa de Opus para merge coerente de 5–7 contribuições com possível conflito).
**Alternativa descartada:** todos Opus (overspend); Architect também Sonnet (perde qualidade na consolidação cross-cutting).
**Consequência:** custo total da skill é ~5–7× Sonnet (Phase A) + Operador-time (Phase B) + ~5–7× Sonnet (Phase C) + 1× Opus (Phase D). Aceitável dado o valor; alternativa "operador faz na cabeça" custa mais em retrabalho silencioso.

**Decisão D4 (D-R14):** Perguntas em batch único (não loop iterativo per-persona).
**Motivo:** epic §6.9 — UX. Loop multiplica tempo por N e produz wizard hostil.
**Alternativa descartada:** loop per-persona; sem perguntas (perde input em ambiguidades genuínas).
**Consequência:** dispatcher implementa algoritmo de dedup textual + agrupamento por categoria.

**Decisão D5 (D-R15):** NO-GO inegociáveis aplicados silenciosamente; só ambiguidades viram pergunta.
**Motivo:** epic §6.10 — especialista que pergunta sobre o inegociável demonstra que não sabe o que é inegociável no seu domínio.
**Alternativa descartada:** todo NO-GO vira pergunta (wizard infinito).
**Consequência:** persona-agent recebe Rules relevantes no prompt; aplica heurísticas direto. NO-GO insuperável retorna `verdict.dimension.<persona> = blocker`.
