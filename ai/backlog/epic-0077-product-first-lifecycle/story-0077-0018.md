## 1. Contexto & Escopo

Como **Líder de QA**, eu quero reescrever charter de qa-engineer.md, enfatizando (1) AC measurability (cada AC deve ser testável), (2) error catalog (catálogo de erros esperados), (3) SLO harness (framework para validar SLOs), (4) success metrics (como medir que feature funcionou), garantindo que QA seja formalizado com rigor de EPIC-0077.

qa-engineer.md é document que define responsibilities e workflows de QA specialist. Rewrite adiciona:
- AC Measurability: cada AC em _TEMPLATE-STORY.md deve ter unidade de medida (ex: "latência < 200ms" not "rápido")
- Error Catalog: lista de erros esperados (ex: "InvalidToken", "RateLimitExceeded") que QA deve testar
- SLO Harness: framework para validar SLOs (uptime, latency, error rate) vs. RNFs Root
- Success Metrics: KPIs que QA monitora pós-deployment (ex: "< 0.1% error rate")

Valor: QA de EPIC-0077 é rigorosa, mensurável, rastreável; sucesso é quantificado.

## 8. Decision Rationale

**Decisão:** Error catalog é parte de charter, não implementação; QA deve conhecer erros esperados before testing.

**Motivo:** Força conversation entre dev e QA sobre error handling; evita surpresas de erros não testados.

**Alternativa descartada:** Erros descobertos durante testing (reactive).

**Consequência:** Requer input de dev; coordination overhead vale a pena.
