## 1. Contexto & Escopo

Como **Engenheiro de Produto**, eu quero criar _TEMPLATE-FEATURE.md com 7 seções canônicas, garantindo que cada feature seja documentada com requisitos claros, interfaces e critérios de aceite.

Uma Feature é o terceiro nível do Product-First Lifecycle: capabilities são decompostas em 4-8 features coerentes (ex: "Basic Auth", "OAuth2 Integration", "MFA Support"). As 7 seções (1: Feature Statement, 2: Casos de Uso, 3: Requisitos Funcionais, 4: Interfaces Exposed, 5: Acceptance Criteria Detalhados, 6: Estimativa & Roadmap, 7: Riscos & Mitigação) garantem clareza para implementação.

Valor: standardiza input para x-create-feature skill e downstream story planning (story-0077-0020), permitindo que 7 agentes paralelos processem features com confiança.

## 8. Decision Rationale

**Decisão:** AC são obrigatoriamente em Gherkin (não livre-text); não 3, não 20 — 10-20 expected.

**Motivo:** Gherkin garante testabilidade, evita ambiguidade de idioma natural. 10-20 AC cobrem happy path + 3+ error scenarios + boundary values (TPP).

**Alternativa descartada:** AC livre-text (falta de testabilidade), obrigatório 20+ (overhead).

**Consequência:** Requer treinamento em Gherkin; ferramenta de template com exemplos GH embedded.
