## 3. Contratos & Endpoints

### 3.1 Bloco Frontmatter Emitido por `x-review-pr`

Conforme schema `review-frontmatter-1.0.json` (epic-0067.md §3.1), campos específicos do TL:

```yaml
---
schema-version: "1.0"
generated-by: x-review-pr@<git rev-parse HEAD>
story-id: story-XXXX-YYYY
epic-id: EPIC-XXXX
date: <ISO-8601 UTC timestamp>
decision: GO | NO-GO | GO-WITH-RESERVATIONS
score: <inteiro 0-55>
score-max: 55
severity-counts:
  critical: <n>
  high: <n>
  medium: <n>
  low: <n>
  info: <n>
blocking-findings:
  - severity: high | critical
    title: "<título do finding>"
    file: "<path relativo ao repo>"
    line: <número de linha>
    recommendation: "<recomendação concisa>"
checklist:
  passed: <inteiro 0-45>
  total: 45
  failed-sections:
    - "<seção do checklist, ex: E.1>"
    - "<seção do checklist, ex: F.3>"
---
```

**Diferenças em relação ao frontmatter de `x-review` (story-0067-0002):**

| Campo | `x-review` (specialist) | `x-review-pr` (tech lead) |
| :--- | :--- | :--- |
| `generated-by` | `x-review@<sha>` | `x-review-pr@<sha>` |
| `score-max` | 50 | 55 |
| `reviewers` | presente (lista de roles) | **ausente** (TL é único reviewer) |
| `checklist` | ausente | **presente** (`passed`, `total: 45`, `failed-sections`) |

### 3.2 Mapeamento do Checklist de 45 Pontos

O checklist holístico do `x-review-pr` está organizado em seções (A a I). Cada ponto que **não passa** na revisão contribui com sua seção no campo `failed-sections`. Regra de mapeamento:

- `checklist.passed` = total de critérios avaliados positivamente (de 45).
- `checklist.total` = sempre `45` (fixo pelo schema).
- `checklist.failed-sections` = lista de strings no formato `"<Letra>.<Número>"` (ex: `"E.1"`, `"F.3"`) para cada critério reprovado ou marcado como não-aplicável-em-falha.

Critérios de não-aplicabilidade:
- Se um critério é "não aplicável" para o tipo de PR (ex: critério de migração de DB num PR sem banco), conta como **passado** (`checklist.passed++`). Não entra em `failed-sections`.
- Se um critério é "não aplicável" porque a feature não existe mas deveria (ex: ausência de health check quando health check é obrigatório), conta como **reprovado**. Entra em `failed-sections`.

### 3.3 Modificação `x-review-pr/SKILL.md` — Phase N

Adicionar a seguinte fase ao final do skill, imediatamente antes da seção `## Recovery` (se existir), ou ao final do documento:

```markdown
## Phase N — Emitir Frontmatter (MANDATORY — Rule 24 §Camada-1)

<!-- TELEMETRY: phase.start -->
Bash command: `$CLAUDE_PROJECT_DIR/.claude/hooks/telemetry-phase.sh start x-review-pr Phase-N-Frontmatter`

TaskCreate(
  subject: "story-XXXX-YYYY › Phase N › Frontmatter TL emission",
  activeForm: "Emitting TL review frontmatter",
  metadata: {
    "phase": "Phase N",
    "parentSkill": "x-review-pr",
    "expectedArtifacts": ["<path do techlead-review-story-XXXX-YYYY.md>"]
  }
)

**MANDATORY TOOL CALL — NÃO SIMULE, NÃO PULE (Rule 24).**

Invoke pre-gate (Rule 25 §Invariants 4):
    Skill(skill: "x-internal-phase-gate", model: "haiku", args: "--mode pre --phase 'Phase N' --skill x-review-pr")

Após produzir o corpo em prosa de `techlead-review-story-<STORY_ID>.md`, PREPEND o bloco de frontmatter YAML conformante com `governance/schemas/review-frontmatter-1.0.json`. Execute:

1. Obter SHA atual:
   Bash command: `git rev-parse HEAD`
   — Use o resultado como `<sha>` no campo `generated-by`.

2. Preencher os campos:
   - `schema-version: "1.0"` (fixo)
   - `generated-by: x-review-pr@<sha>`
   - `story-id`: conforme argumento `--story` passado à skill
   - `epic-id`: conforme argumento `--epic`
   - `date`: timestamp ISO-8601 UTC do momento de execução
   - `decision`: `GO` | `NO-GO` | `GO-WITH-RESERVATIONS` — derivado do veredicto holístico
   - `score`: soma dos critérios ponderados avaliados (0-55)
   - `score-max: 55` (fixo)
   - `severity-counts`: contagem de findings por severidade
   - `blocking-findings`: lista de findings severity ≥ HIGH (cada item com `severity`, `title`, `file`, `line`, `recommendation`)
   - `checklist.passed`: número de critérios aprovados (0-45)
   - `checklist.total: 45` (fixo)
   - `checklist.failed-sections`: lista de seções reprovadas no formato `"<Letra>.<Número>"`
   - **NÃO emitir** o campo `reviewers` (ausente no schema TL)

3. Validar o arquivo gerado:
   Bash command: `scripts/audit-review-frontmatter.sh --story <STORY_ID>`

   Se exit ≠ 0: abortar com código `REVIEW_FRONTMATTER_INVALID`.

Invoke post-gate (Rule 25 §Invariants 4 — verifica que o artefato foi emitido):
    Skill(skill: "x-internal-phase-gate", model: "haiku", args: "--mode post --phase 'Phase N' --skill x-review-pr --expected-artifacts <path do techlead-review-story-XXXX-YYYY.md>")

TaskUpdate(taskId: <id_da_TaskCreate_acima>, status: "completed")

<!-- TELEMETRY: phase.end -->
Bash command: `$CLAUDE_PROJECT_DIR/.claude/hooks/telemetry-phase.sh end x-review-pr Phase-N-Frontmatter ok`
```

## 8. Decision Rationale

### 8.1 Ausência de `reviewers` no frontmatter TL

**Decisão:** `x-review-pr` não emite o campo `reviewers`.

**Motivo:** `x-review-pr` é executada por um único revisor Tech Lead, não por múltiplos specialists. Incluir `reviewers: [tech-lead]` seria informação redundante e inconsistente com o schema (que define `reviewers` como lista de roles de specialists específicos como `qa`, `security`, `performance`). Consumers discriminam specialist vs TL pela presença/ausência de `checklist`.

**Alternativa descartada:** `reviewers: [tech-lead]`. Rejeitada porque `tech-lead` não é um dos valores permitidos pelo schema no campo `reviewers.items.enum`.

### 8.2 `checklist.failed-sections` como strings em vez de objetos

**Decisão:** `failed-sections` é `string[]` (ex: `["E.1", "F.3"]`), não array de objetos.

**Motivo:** Granularidade de string é suficiente para os consumers (EPIC-0066 render skill, audit script). Objetos adicionariam complexidade sem ganho no uso atual. Schema 1.1 pode enriquecer se necessário (OCP).
