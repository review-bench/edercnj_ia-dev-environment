## 1. Contexto & Escopo

### 1.1 Problema

Os artefatos `review-story-XXXX-YYYY.md` (produzidos por `x-review`) e `techlead-review-story-XXXX-YYYY.md` (produzidos por `x-review-pr`) hoje carregam veredictos em **prosa Markdown**:

- Specialist: `**Verdict: GO**` / `**Verdict: NO-GO**` na primeira linha do corpo
- Tech Lead: `**Decision: GO**` / `**Decision: NO-GO**` (idem)
- Severity counts: tabela manual com `Critical | Count | High | Count`
- Score: linha "00/55 | Status: Approved" parseada por regex frágil

Esse formato é parseável por `grep`, mas:
1. **Frágil:** depende de markdown bold + ordem específica de palavras.
2. **Não-tipado:** `Critical Count` é texto livre — números podem ser mal-formatados.
3. **Inconsistente:** PR #757 (specialist review) e PR #756 (techlead review) divergem em granularidade de findings.
4. **Não machine-readable:** `audit-review-frontmatter.sh` não consegue validar campos hoje.

### 1.2 Solução

Introduzir **frontmatter YAML estruturado v1.0** no topo de ambos artefatos de review. Schema:

```yaml
---
schema-version: "1.0"
generated-by: x-review@<sha> | x-review-pr@<sha>
story-id: story-XXXX-YYYY
epic-id: EPIC-XXXX
date: 2026-04-28T13:42:17Z
decision: GO | NO-GO | GO-WITH-RESERVATIONS
score: 42         # 0-50 (specialist) ou 0-55 (techlead)
score-max: 50     # specialist: 50; techlead: 55
severity-counts:
  critical: 0
  high: 0
  medium: 2
  low: 5
  info: 12
blocking-findings:
  - severity: high
    title: "SQL injection in UserRepository.findByName"
    file: "java/src/main/java/.../UserRepository.java"
    line: 42
    recommendation: "Use parameterized query (Rule 12 J1)"
reviewers:                # only for x-review
  - qa
  - security
  - performance
checklist:                # only for x-review-pr (45-point)
  passed: 41
  total: 45
  failed-sections: ["E.1", "F.3"]
---
# Specialist Review — story-XXXX-YYYY
... existing prose follows below ...
```

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$id": "https://iadev.dev/schemas/review-frontmatter-1.0.json",
  "type": "object",
  "required": ["schema-version", "generated-by", "story-id", "epic-id", "date", "decision", "score", "score-max", "severity-counts", "blocking-findings"],
  "properties": {
    "schema-version": { "const": "1.0" },
    "generated-by": { "type": "string", "pattern": "^(x-review|x-review-pr)@[0-9a-f]{40}$" },
    "story-id": { "type": "string", "pattern": "^story-[0-9]{4}-[0-9]{4}$" },
    "epic-id": { "type": "string", "pattern": "^EPIC-[0-9]{4}$" },
    "date": { "type": "string", "format": "date-time" },

      "type": "object",
```

## 8. Decision Rationale

### 8.1 Decisão arquitetural — frontmatter YAML único schema 1.0

**Decisão:** um schema único `review-frontmatter-1.0.json` cobre ambos `specialist` e `tech-lead` reviews via campos opcionais (reviewers vs checklist).

**Motivo:** ambos reviews compartilham 80% dos campos (decision, score, severity-counts, blocking-findings). Forçar dois schemas distintos cria duplicação e divergência futura.

**Alternativa descartada:** dois schemas (`specialist-review-frontmatter-1.0.json` + `techlead-review-frontmatter-1.0.json`). Rejeitada porque consumidores (EPIC-0066) acabariam tendo if-else por kind — schema único permite handling polimórfico (presença de `checklist` indica techlead).

**Consequência:** schema permite combinações ilegais (ex: `reviewers` + `checklist` simultaneamente). Mitigação: audit script emite WARN se ambos presentes simultaneamente; consumidores ignoram o campo "errado".

### 8.2 Decisão arquitetural — generated-by inclui SHA

**Decisão:** campo `generated-by: x-review@<40-char SHA>` é mandatório.

**Motivo:** rastreabilidade. Quando review for revisitado meses depois, é crítico saber qual versão da skill produziu o veredicto (skills evoluem — critérios mudam).

**Alternativa descartada:** apenas `generated-by: x-review` (sem SHA). Rejeitada porque skill versions divergem em critérios de severity classification — sem SHA, audit retroativo é impossível.

**Consequência:** SHA precisa ser obtido em runtime (`git rev-parse HEAD`) — adiciona dependência git às skills. Aceitável (skills já dependem de git para outras operations).

### 8.3 Decisão sobre baseline e deprecation

**Decisão:** baseline file `governance/baselines/review-frontmatter-baseline.txt` inicia VAZIO. Reviews já mergeados em `develop` antes deste epic NÃO são grandfathered; audit script só roda em PRs novos. Reviews em PRs `epic/*` em flight (epic-0063, epic-0064, epic-0065) recebem retrofit ou WARN-only durante deprecation window.

**Motivo:** evitar acúmulo de débito. Reviews legacy ficaram no histórico — mas qualquer review novo precisa ter frontmatter.

**Alternativa descartada:** popular baseline com todos reviews atuais (~50 arquivos). Rejeitada porque tornaria o gate sem efeito real (qualquer regressão futura teria precedente para entrar no baseline).

**Consequência:** se um epic legacy precisar revisitar uma review existente, deve atualizar para schema 1.0. Aceitável (custo low — reviewer LLM consegue regenerar).

### 8.4 Decisão sobre estrutura — 4 stories vs 5+

**Decisão:** 4 stories — Foundation (schema), Specialist (x-review), TechLead (x-review-pr), Audit+Verify.

**Motivo:** scope enxuto. Epic é prerequisito de EPIC-0066 e não há valor em granularidade adicional.

**Alternativa descartada:** 6 stories (split de templates de skills, split de audit/smoke). Rejeitada por overhead.

**Consequência:** stories médios em tamanho (~300-400 linhas de SKILL.md modificações). Aceitável.
