## 1. Contexto & User Story

### 1.1 Problema

O skill `x-review` produz `review-story-XXXX-YYYY.md` com veredicto em prosa Markdown (ex.: `**Verdict: GO**`). Esse formato não tem estrutura machine-readable: o campo `decision` não é tipado, `severity-counts` é texto livre em tabela, e `reviewers` não têm lista formal. O EPIC-0066 (PR Body Templates) precisa consumir esses dados de forma confiável, sem regex frágil sobre bold Markdown.

### 1.2 User Story

> Como **orquestrador `x-story-implement`** que invoca `x-review`,  
> quero que o artefato `review-story-XXXX-YYYY.md` produzido tenha **frontmatter YAML v1.0** no topo,  
> para que consumidores (EPIC-0066, `audit-review-frontmatter.sh`) possam ler `decision`, `score`, `severity-counts` e `reviewers` sem regex.

### 1.3 Escopo desta story

- Modificar `java/src/main/resources/targets/claude/skills/core/review/x-review/SKILL.md` para adicionar **Phase N — Emit Frontmatter (MANDATORY)** com marcadores de telemetria (Rule 13 §Telemetry Markers) e tag MANDATORY TOOL CALL (Rule 24 §Camada-1).
- Escrever `XReviewFrontmatterTest.java` validando que Phase N está presente com a estrutura correta.
- Regen de golden files afetados (`.claude/skills/x-review/SKILL.md` e golden dos 10 profiles: 9 stack profiles + `platform-claude-code`).

**Fora do escopo:** modificação de `x-review-pr` (story-0067-0003), criação do audit script (story-0067-0004), criação do schema JSON (story-0067-0001).

## 3. Contratos

### 3.1 Phase N — Emit Frontmatter (especificação completa)

A fase a ser adicionada ao final do corpo de `x-review/SKILL.md` (após todas as fases de invocação de specialists):

```markdown
## Phase N — Emit Frontmatter (MANDATORY — Rule 24 §Camada-1)

<!-- TELEMETRY: phase.start -->
Bash command: `$CLAUDE_PROJECT_DIR/.claude/hooks/telemetry-phase.sh start x-review Phase-N-Frontmatter`

> **MANDATORY TOOL CALL (Rule 24 §Camada-1):** Esta fase NÃO pode ser inlineada, simulada
> ou omitida. A LLM DEVE emitir o frontmatter populado no artefato de saída. Ausência do
> frontmatter é detectada por `audit-review-frontmatter.sh` (Camada 3 CI) e pelo Stop hook
> (Camada 2 runtime). Não há fallback quando a emissão do frontmatter falhar.

TaskCreate(
  subject: "<STORY_ID> › Phase N › Emit specialist review frontmatter",
  activeForm: "Emitting specialist review frontmatter",
  metadata: {
    "phase": "Phase N",
    "parentSkill": "x-review",
    "storyId": "<STORY_ID>",
    "epicId": "<EPIC_ID>",
    "expectedArtifacts": ["<path do review-story-XXXX-YYYY.md>"]
  }
)

Invoke pre-gate (Rule 25 §Invariants 4):
    Skill(skill: "x-internal-phase-gate", model: "haiku", args: "--mode pre --phase 'Phase N' --skill x-review")

After all specialist subagents have returned their findings and the prose body of
`review-story-<STORY_ID>.md` has been assembled, prepend the YAML frontmatter block
conforming to `governance/schemas/review-frontmatter-1.0.json`:

Populate each field as follows:

- `schema-version: "1.0"` — constante.
- `generated-by: x-review@$(git rev-parse HEAD)` — SHA do commit HEAD no momento da emissão.
- `story-id: <STORY_ID>` — ID canônico (ex.: `story-0067-0002`), obtido do argumento de invocação.
- `epic-id: <EPIC_ID>` — ID canônico (ex.: `EPIC-0067`), derivado do story-id.
- `date: $(date -u +%Y-%m-%dT%H:%M:%SZ)` — timestamp UTC ISO-8601 no momento de escrita.
- `decision: <DECISION>` — veredicto consolidado dos specialists: `GO` se nenhum specialist retornou NO-GO; `NO-GO` se qualquer specialist retornou NO-GO; `GO-WITH-RESERVATIONS` se qualquer specialist sinalizou reservas sem NO-GO.
- `score: <SCORE>` — soma de pontos atribuídos pelos specialists (inteiro 0-50).
- `score-max: 50` — constante para specialist review.
- `severity-counts.critical: <N>` — contagem de findings CRITICAL agregados de todos specialists.
- `severity-counts.high: <N>` — contagem de findings HIGH.
- `severity-counts.medium: <N>` — contagem de findings MEDIUM.
- `severity-counts.low: <N>` — contagem de findings LOW.
- `severity-counts.info: <N>` — contagem de findings INFO.
- `blocking-findings: [...]` — lista de findings com severity `critical` ou `high` (cada um com `severity`, `title`, `file`; `line` e `recommendation` quando disponíveis).
- `reviewers: [...]` — lista de roles de specialists invocados nesta execução (ex.: `["qa", "security", "performance"]`).

O artefato final deve ter a seguinte estrutura:

```
<!-- template-version: 1.0 -->
---
<frontmatter YAML populado>
---
# Specialist Review — <STORY_ID>
...prose body...
```

Após a escrita do artefato, validar:

    Bash command: `$CLAUDE_PROJECT_DIR/.claude/scripts/audit-review-frontmatter.sh --story <STORY_ID>`

Se o script retornar exit ≠ 0, abortar com código `REVIEW_FRONTMATTER_INVALID`. Não há fallback — frontmatter inválido é bloqueante.

Invoke post-gate (Rule 25 §Invariants 4 — verifica que o artefato foi emitido):
    Skill(skill: "x-internal-phase-gate", model: "haiku", args: "--mode post --phase 'Phase N' --skill x-review --expected-artifacts <path do review-story-XXXX-YYYY.md>")

TaskUpdate(taskId: <id_da_TaskCreate_acima>, status: "completed")

<!-- TELEMETRY: phase.end -->
Bash command: `$CLAUDE_PROJECT_DIR/.claude/hooks/telemetry-phase.sh end x-review Phase-N-Frontmatter ok`
```

| Campo | Fonte | Obrigatório? |
| :--- | :--- | :--- |
| `schema-version` | Constante `"1.0"` | Sim |
| `generated-by` | `git rev-parse HEAD` em runtime | Sim |
| `story-id` | Argumento de invocação `--story` | Sim |
| `epic-id` | Derivado de `story-id` (regex `story-(\d{4})-\d{4}` → `EPIC-$1`) | Sim |

| `score-max` | Constante `50` | Sim |
| `severity-counts.*` | Agregação dos findings por severity | Sim (todos 5 subcampos) |
| `blocking-findings` | Findings com severity `critical` ou `high` | Sim (lista vazia se nenhum) |
| `reviewers` | Lista de roles invocados nesta execução | Sim (lista vazia se nenhum) |

### 3.3 Regra de consolidação de `decision`

```
SE qualquer specialist retornou NO-GO → decision = "NO-GO"
SENÃO SE qualquer specialist sinalizou GO-WITH-RESERVATIONS → decision = "GO-WITH-RESERVATIONS"
SENÃO → decision = "GO"
```

Prioridade: NO-GO > GO-WITH-RESERVATIONS > GO.

### 3.5 Contrato MANDATORY TOOL CALL (Rule 24 §Camada-1)

O bloco `> **MANDATORY TOOL CALL (Rule 24 §Camada-1):**` DEVE estar presente na Phase N, imediatamente após o marcador `<!-- TELEMETRY: phase.start -->`. Esse bloco é a evidência normativa (Camada 1) de que a fase não pode ser inlineada. O audit `LifecycleIntegrityAuditTest` verifica presença do marcador.

### 3.6 Contrato Task Hierarchy + Phase Gate (Rule 25)

`x-review` é um dos 8 orquestradores canônicos da Rule 25 §Scope. Portanto a Phase N DEVE:

1. Emitir um `TaskCreate(...)` na entrada com `subject` no formato `"<STORY_ID> › Phase N › <descrição>"` (separador `›` U+203A — Rule 25 §Invariants 5) e `metadata.expectedArtifacts` listando o caminho do artefato a ser emitido.
2. Invocar `Skill(skill: "x-internal-phase-gate", model: "haiku", args: "--mode pre …")` antes da escrita.
3. Invocar `Skill(skill: "x-internal-phase-gate", model: "haiku", args: "--mode post --expected-artifacts …")` após a escrita.
4. Emitir `TaskUpdate(taskId: <id>, status: "completed")` quando o post-gate retornar passed.

Falha de qualquer gate retorna exit `12` (`PHASE_GATE_FAILED`); a skill propaga via `REVIEW_FRONTMATTER_INVALID` (semântica equivalente para o orquestrador chamador). O audit `audit-task-hierarchy.sh` (Rule 25 §Audit Contract — Layer 4) verifica balanço de `TaskCreate`/`TaskUpdate` e presença das chamadas PRE/POST.

### 3.7 Contrato Orchestrator Evidence (Rule 27 §Camada 1)

O PR body desta story DEVE conter a seção `## Orchestrator Evidence` listando:
- Caminho do `review-story-XXXX-YYYY.md` produzido como evidência da Phase N.

## 6. Segurança

| Área | Risco | Controle |
| :--- | :--- | :--- |
| YAML injection via conteúdo de findings | Finding com `title: "foo\n---\nmalicious: true"` poderia quebrar o YAML | Skills DEVEM usar YAML safe-emit (escapar caracteres especiais nos valores de string); não concatenação de strings |
| Path traversal em story-id | story-id usado para montar path do artefato | Regex `^story-[0-9]{4}-[0-9]{4}$` aplicada antes de qualquer I/O (Rule 06 §Path operations) |
| SHA spoofing | LLM pode inventar SHA em vez de executar git | `<!-- MANDATORY TOOL CALL -->` + audit verificam que o SHA tem exatamente 40 hex chars (schema pattern) |
| Dados sensíveis em recommendations | Skill J7 (Rule 12): exceções não devem expor paths internos | Recommendations são texto livre do reviewer (LLM); não expõem stack traces ou paths de sistema |

## 8. Decision Rationale

### 8.1 Ausência de fallback na Phase N

**Decisão:** frontmatter inválido → aborto com `REVIEW_FRONTMATTER_INVALID`; sem fallback silencioso.

**Motivo:** um review sem frontmatter derrota o propósito desta story. Consumidores (EPIC-0066) que dependem do frontmatter receberiam dados ausentes silenciosamente — bug difícil de diagnosticar. Falhar ruidosamente é preferível.

**Alternativa descartada:** emitir frontmatter vazio/placeholder quando git falha. Rejeitada porque `generated-by` sem SHA viola o contrato do schema 1.0 (campo `required`) e quebraria a rastreabilidade que justifica o campo.

**Consequência:** ambientes sem git (ex.: containers mínimos) precisam ter git instalado. Aceitável — skills `x-review` já dependem de git para outras operações (ex.: `x-git-commit`).

### 8.2 Posição da Phase N (após, não antes, da coleta de findings)

**Decisão:** Phase N é a fase final, após todos os specialists retornarem.

**Motivo:** o frontmatter precisa agregar dados de todos os specialists (decision consolidada, severity-counts, blocking-findings, reviewers). Emitir antes impossibilitaria a agregação.

**Alternativa descartada:** emitir frontmatter parcial e atualizar incrementalmente. Rejeitada por complexidade e risco de estado inconsistente se algum specialist abortar.

### 8.3 Sem flag `--skip-review-frontmatter`

**Decisão:** não criar flag de bypass para a Phase N.

**Motivo:** Rule 24 §Non-inlining Contract proíbe bypass de fases obrigatórias fora de `## Recovery`. Criar a flag abriria caminho para bypass sistemático em CI. O único caminho legítimo de bypass é `--legacy-flow` para epics pré-EPIC-0049.
