## 1. Contexto & Escopo

Como **Operador de Governança**, eu quero que todo `review-story-*.md` e `techlead-review-story-*.md` mergeado em `epic/*` ou `develop` seja verificado automaticamente pelo script `scripts/audit-review-frontmatter.sh`, e que um teste E2E (`Epic0067ReviewFrontmatterSmokeTest`) valide o ciclo ponta-a-ponta de geração e parsing do frontmatter YAML v1.0, para que a garantia de machine-readability dos reviews seja contínua, retroativa e fail-fast no CI — sem dependência de revisão manual.

Esta story é a **story final do EPIC-0067** — depende de 0067-0002 (x-review) e 0067-0003 (x-review-pr) para existirem artefatos com frontmatter para validar. Ela entrega dois ativos distintos:

1. **Camada 3 — CI script** (`scripts/audit-review-frontmatter.sh`): stateless check sobre artefatos do repositório, conforme a taxonomia do Rule 26 §Decision Matrix.
2. **Camada 2 — Java test** (`AuditReviewFrontmatterTest` + `Epic0067ReviewFrontmatterSmokeTest`): testes que requerem parsing estruturado de YAML e validação de schema — in-scope per Rule 14 §Allowed Code (`src/test/java/**/*AuditTest.java` e `**/*SmokeTest.java`).

Adicionalmente, a entrada de catálogo em `docs/audit-gates-catalog.md` (Rule 26 §Catalog-before-Add — RULE-004) é criada nesta story, junto com o registro de `ScriptsAssembler.java` para que projetos gerados herdem o script.

### 3.3 Estrutura interna do script

```bash
#!/usr/bin/env bash
set -u

REPO_ROOT="$(git rev-parse --show-toplevel 2>/dev/null || pwd)"
cd "${REPO_ROOT}"

BASELINE_DIR="${BASELINE_DIR:-governance/baselines}"
BASELINE_FILE="${BASELINE_DIR}/review-frontmatter-baseline.txt"
SCHEMA_FILE="governance/schemas/review-frontmatter-1.0.json"

# --self-check: verifica ferramentas e arquivos estruturais
case "${1:-}" in
  --self-check)
    exit_code=0
    for tool in yq jq; do
      if ! command -v "${tool}" >/dev/null 2>&1; then
        echo "OPERATIONAL_ERROR: ${tool} not found on PATH" >&2
        exit_code=2
      fi
    done
    if [[ ! -f "${SCHEMA_FILE}" ]]; then
      echo "OPERATIONAL_ERROR: schema file not found: ${SCHEMA_FILE}" >&2
      exit_code=2
    fi
    if [[ -f "${BASELINE_FILE}" && ! -r "${BASELINE_FILE}" ]]; then
      echo "OPERATIONAL_ERROR: baseline file not readable: ${BASELINE_FILE}" >&2
      exit_code=2
    fi
    exit "${exit_code}"
    ;;
esac

# parse restante de argumentos: --all | --epic <ID> | --story <ID>
# coleta candidatos em V3 (plans/epic-*/plans/) e V4 (ai/epics/*/plans/)
# para cada arquivo:
#   1. verifica presença de delimitadores --- / ---
#   2. extrai bloco frontmatter com yq
#   3. valida contra SCHEMA_FILE com jq (sem dependência de ajv)
#   4. verifica exemptions + baseline
```

### 3.4 Validação YAML + Schema (implementação jq-based)

O script NÃO depende de `ajv` para não introduzir runtime Node.js. Valida os campos `required` do schema via `yq` + `jq`:

```bash
# 1. Extrai frontmatter YAML -> converte para JSON
frontmatter_json=$(yq -o=json '.' <<< "${frontmatter_block}" 2>/dev/null)

# 2. Verifica campos obrigatórios via jq
required_fields=("schema-version" "generated-by" "story-id" "epic-id" "decision" "severity-counts")
for field in "${required_fields[@]}"; do
  if ! jq -e "has(\"${field}\")" <<< "${frontmatter_json}" >/dev/null 2>&1; then
    echo "REVIEW_FRONTMATTER_VIOLATION: ${file}: required field '${field}' missing" >&2
    violations+=("${file}")
  fi
done

# 3. Valida enum decision
decision_value=$(jq -r '."decision"' <<< "${frontmatter_json}")
case "${decision_value}" in
  GO|NO-GO|GO-WITH-RESERVATIONS) ;;
  *)
    echo "REVIEW_FRONTMATTER_VIOLATION: ${file}: invalid decision value '${decision_value}'" >&2
    violations+=("${file}")
    ;;
esac
```

## 6. Segurança

| Área | Controle | Implementação |
| :--- | :--- | :--- |
| **Path traversal no glob de varredura** | O script normaliza paths e rejeita `..` antes de qualquer leitura (Rule 06 §Path operations) | `realpath --relative-to="${REPO_ROOT}"` + rejeita paths fora de `REPO_ROOT` |
| **YAML injection no frontmatter lido** | `yq` processa o YAML como dado, nunca como código; `jq` opera sobre JSON serializado — nenhum `eval` de conteúdo do frontmatter | Não usar `eval "$(yq ...)"` — usar substituição de comando com result assignment |
| **Baseline file tampering** | Script verifica que baseline é legível (não vazio malformado) via `--self-check`; CI falha com `OPERATIONAL_ERROR` se arquivo ilegível | `[[ -r "${BASELINE_FILE}" ]]` no `--self-check` |
| **audit-exempt sem reason** | `<!-- audit-exempt: -->` sem motivo após `:` emite `INVALID_EXEMPTION` (exit 3) — previne bypass silencioso (Rule 27 §Forbidden) | Regex `audit-exempt:[[:space:]]*$` → exit 3 |

## 8. Decision Rationale

### 8.1 Decisão — yq + jq em vez de ajv para validação de schema

**Decisão:** `audit-review-frontmatter.sh` usa `yq` (YAML→JSON) + `jq` (validação de campos required + enum) em vez de `ajv` (JSON Schema validator for Node.js).

**Motivo:** `ajv` requer Node.js/npm no CI — dependência runtime não declarada em nenhum outro script do projeto. `yq` e `jq` já são pré-requisitos de scripts existentes (`audit-flow-version.sh`, `audit-epic-branches.sh`). Manter consistência de toolchain reduz fricção de onboarding.

**Alternativa descartada:** `ajv-cli` (full schema validation). Descartada porque o schema `review-frontmatter-1.0.json` tem apenas 6 campos required + 3 enums — validação manual via `jq` tem complexidade O(n_fields) trivial e é mais legível para auditors que não conhecem ajv.

**Consequência:** validações mais elaboradas (ex: pattern regex no `generated-by`) são verificadas apenas por `jq` com regex básico. Aceitável para v1.0; se o schema crescer, considera-se adicionar `ajv` em v2.

### 8.2 Decisão — baseline inicial vazio

**Decisão:** `governance/baselines/review-frontmatter-baseline.txt` é criado VAZIO (contém apenas um header de comentário). Nenhum review existente é grandfathered por default.

**Motivo:** conforme §8.3 do `epic-0067.md` — evitar acúmulo de débito. O audit só roda em PRs novos (não em histórico). Reviews em flight que não tiverem frontmatter devem ser atualizados pelo autor da story antes de abrir novo PR.

**Alternativa descartada:** popular o baseline com os ~50 reviews existentes. Rejeitada por tornar o gate inefetivo na prática.

**Consequência:** operator que tiver review legacy (sem frontmatter) em um PR que ainda não foi mergeado precisa regenerar o arquivo via `x-review --story <ID>` ou `x-review-pr --story <ID>` antes de abrir o PR após o merge do EPIC-0067.
