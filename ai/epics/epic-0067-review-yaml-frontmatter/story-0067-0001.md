## 1. Contexto & Escopo

Como **desenvolvedor do ia-dev-environment**, eu quero um JSON Schema versionado (`governance/schemas/review-frontmatter-1.0.json`) que defina a estrutura obrigatória do frontmatter YAML dos artefatos de review, e quero que os templates `_TEMPLATE-SPECIALIST-REVIEW.md` e `_TEMPLATE-TECH-LEAD-REVIEW.md` sejam modificados para incluir esse bloco de frontmatter no topo, para que todos os consumidores (EPIC-0066 render skill e `audit-review-frontmatter.sh`) possam parsear veredictos de review como dados estruturados em vez de regex-sobre-prosa.

Hoje os templates produzem artefatos com veredictos em **prosa Markdown** — frágil, não-tipado, e não machine-readable (ver epic §1.1). Esta story cria a fundação: o schema como fonte da verdade e os templates como ponto de injeção do frontmatter em runtime. Nenhuma skill é modificada nesta story (escopo: schema + templates somente).

A story **NÃO** depende de nenhuma outra story do epic — é o ponto de partida (Phase 0 do DAG). Bloqueia stories 0067-0002, 0067-0003 e 0067-0004.

## 3. Contratos & Endpoints

### 3.1 JSON Schema `review-frontmatter-1.0.json`

Arquivo criado em `governance/schemas/review-frontmatter-1.0.json` com o conteúdo exato conforme epic §3.1:

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$id": "https://iadev.dev/schemas/review-frontmatter-1.0.json",
  "type": "object",
  "required": ["schema-version", "generated-by", "story-id", "epic-id", "date", "decision", "score", "score-max", "severity-counts", "blocking-findings"],
  "properties": {
    "schema-version": { "const": "1.0" },
    "generated-by": { "type": "string", "pattern": "^(x-review|x-review-pr)@[0-9a-f]{40}$" },
    "story-id": { "type": "string", "pattern": "^story-[0-9]{4}-[0-9]{4}$" },
    "epic-id": { "type": "string", "pattern": "^EPIC-[0-9]{4}$" },
    "date": { "type": "string", "format": "date-time" },
    "decision": { "enum": ["GO", "NO-GO", "GO-WITH-RESERVATIONS"] },
    "score": { "type": "integer", "minimum": 0, "maximum": 55 },
    "score-max": { "type": "integer", "minimum": 1, "maximum": 55 },
    "severity-counts": {
      "type": "object",
      "required": ["critical", "high", "medium", "low", "info"],
      "properties": {
        "critical": { "type": "integer", "minimum": 0 },
        "high": { "type": "integer", "minimum": 0 },
        "medium": { "type": "integer", "minimum": 0 },
        "low": { "type": "integer", "minimum": 0 },
        "info": { "type": "integer", "minimum": 0 }
      }
    },
    "blocking-findings": {
      "type": "array",
      "items": {
        "type": "object",
        "required": ["severity", "title", "file"],
        "properties": {
          "severity": { "enum": ["critical", "high"] },
          "title": { "type": "string" },
          "file": { "type": "string" },
          "line": { "type": "integer", "minimum": 1 },
          "recommendation": { "type": "string" }
        }
      }
    },
    "reviewers": {
      "type": "array",
      "items": { "enum": ["qa", "security", "performance", "devops", "database", "api", "event", "observability"] }
    },
    "checklist": {
      "type": "object",
      "required": ["passed", "total"],
      "properties": {
        "passed": { "type": "integer", "minimum": 0 },
        "total": { "type": "integer", "minimum": 1 },
        "failed-sections": { "type": "array", "items": { "type": "string" } }
      }
    }
  }
}
```

**Observações:**
- 10 campos obrigatórios no root: `schema-version`, `generated-by`, `story-id`, `epic-id`, `date`, `decision`, `score`, `score-max`, `severity-counts`, `blocking-findings`.
- `blocking-findings` é required mas pode ser array vazio `[]` quando não houver findings de severity ≥ HIGH.
- `reviewers` (apenas specialist) e `checklist` (apenas techlead) são opcionais — o schema é superset.
- `blocking-findings[*].line` é opcional (campo `line` pode ser omitido por finding).
- `additionalProperties` não é declarado (default `true`) — campos extras são tolerados para extensibilidade futura.

### 3.2 Template `_TEMPLATE-SPECIALIST-REVIEW.md` modificado

O template DEVE conter o seguinte bloco no topo (antes do corpo de prosa existente), conforme epic §3.2:

```markdown
<!-- template-version: 1.0 -->
---
schema-version: "1.0"
generated-by: x-review@{{COMMIT_SHA}}
story-id: {{STORY_ID}}
epic-id: {{EPIC_ID}}
date: {{ISO_TIMESTAMP}}
decision: {{DECISION}}
score: {{SCORE}}
score-max: 50
severity-counts:
  critical: {{CRITICAL_COUNT}}
  high: {{HIGH_COUNT}}
  medium: {{MEDIUM_COUNT}}
  low: {{LOW_COUNT}}
  info: {{INFO_COUNT}}
blocking-findings:
{{BLOCKING_FINDINGS_YAML}}
reviewers:
{{REVIEWERS_YAML}}
---
# Specialist Review — {{STORY_ID}}

> **Decision:** {{DECISION}} | **Score:** {{SCORE}}/50

{{REVIEW_PROSE_BODY}}
```

O comentário `<!-- template-version: 1.0 -->` é posicionado imediatamente antes do delimitador `---` de abertura do frontmatter — consistente com a convenção EPIC-0066 (story-0066-0001 §3.1 e §3.2 usam `<!-- template-version: 1.0 ... -->` na linha 1).

## 8. Decision Rationale

**Decisão:** Schema único `review-frontmatter-1.0.json` cobre ambos os tipos de review (specialist e tech lead) via campos opcionais.

**Motivo:** 80% dos campos são compartilhados entre os dois tipos. Dois schemas distintos criariam duplicação e divergência futura. Consumidores distinguem o tipo pela presença de `reviewers` (specialist) ou `checklist` (techlead) — polimorfismo via presença de campo.

**Alternativa descartada:** dois schemas `specialist-review-frontmatter-1.0.json` + `techlead-review-frontmatter-1.0.json`. Rejeitada porque consumidores (EPIC-0066) acabariam com if-else por kind — schema único permite handling polimórfico.

**Consequência:** schema permite combinação ilegal `reviewers` + `checklist` simultaneamente. Mitigação documentada em epic §8.1: audit script emite WARN; consumers ignoram campo "errado".
