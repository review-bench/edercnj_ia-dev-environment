## 1. Visão & Problema

Bugs are first-class planning artifacts — distinct from features in intent (regression vs.
new value), in template shape (reproduction steps, root-cause analysis, regression tests),
and in lifecycle pressure (bugs often demand faster cycle times than greenfield work). Today
in `ia-dev-environment`, bugs are forced through the same `/x-create-feature` chain as
features: authors invent ad-hoc directory names like `ai/epics/epic-XXXX-fix-Y/`, story
templates lack reproduction-step sections, the refinement gate has no bug-specific
acceptance dimensions (e.g., "is the regression test included before the fix?"), and PR
review templates do not differentiate "this PR introduces a feature" from "this PR closes
a bug — verify the regression test is red without the fix."

The result is silent quality erosion. Bug fixes ship without regression coverage because
the template never asked for it. Tech leads cannot quickly answer "how many critical bugs
are open?" because bugs hide inside epic folders. Cycle-time KPIs cannot separate
feature delivery from defect remediation. And new contributors mistake bug folders for
feature folders, introducing scope creep.

EPIC-0080 elevates bugs to a parallel first-class planning hierarchy with their own
directory tree (`ai/bugs/bug-XXXXXX/`), their own creation skill (`/x-create-bug`), their
own refinement skill (`/x-refine-bug`), their own implementation map, and their own
governance rules. The flow mirrors the feature/epic chain in shape but is tuned for the
defect-remediation domain: every bug carries a reproduction recipe, a regression test that
must be authored RED before the fix, a root-cause classification, and a refinement verdict
gating implementation. PR review for bugs explicitly checks "regression test exists,
runs without the fix, and is RED before the fix lands."

By making bugs first-class, we restore visibility (a tech lead can `ls ai/bugs/` and see
the open queue), we enforce regression-first TDD (the template demands the failing
test as a deliverable, not a side-effect), and we enable separate cycle-time
measurement (defect MTTR vs. feature lead time become independent metrics computable
from `ai/bugs/` vs. `ai/epics/` directory creation/closure timestamps).

## 2. Persona & Stakeholders

| Persona                          | Role / Interest                                                                  |
| :------------------------------- | :------------------------------------------------------------------------------- |
| **Developer (primary)**          | Authors bug reports, runs `/x-create-bug`, implements fixes via the bug-aware story chain. |
| **Tech Lead (primary)**          | Refines bugs via `/x-refine-bug`, gates implementation, reviews bug PRs.         |
| **Orchestrator / SRE**           | Ensures the refinement gate, lifecycle audit, and PR-merge gates apply uniformly to bug PRs. |
| **QA Engineer**                  | Verifies regression tests exist and were RED before the fix.                     |
| **Product Owner (stakeholder)**  | Consumes defect MTTR and open-bug-count metrics for release readiness decisions. |

The primary persona is the **Developer who just discovered a regression and needs to file
it with full reproduction context within 5 minutes**. The Tech Lead persona consumes
the same artifacts during refinement and PR review but does not author them.

> as first-class fields, the refinement gate validates them before implementation begins,

## 4. Alternativas Consideradas

### Alt-A: Treat bugs as a label on existing epic/feature artifacts

Add a `type: bug` frontmatter field to existing epic/story templates; reuse the
`/x-create-feature` chain unchanged. **Rejected** because it does not solve the template
gap (no reproduction steps, no regression-test field), the refinement gate cannot apply
bug-specific dimensions without bifurcating, and tech-lead visibility (`ls ai/bugs/`) is
not achieved. Labels are opt-in and silently omitted under deadline pressure.

### Alt-B: Dedicated `bugfix/*` git branch convention only (no planning artifacts)

Mirror `hotfix/*` semantics — skip planning entirely, go straight to a fix branch with PR
review enforcing regression tests. **Rejected** because (a) hotfix branches are
single-file critical-fix bypasses (Rule 19 Exception 2) and inappropriate for normal-priority
defects, (b) skipping planning loses reproduction context that the original reporter holds
but the implementer does not, (c) tech-lead refinement of "is this really a bug or a missing
feature?" disappears, and (d) cycle-time tooling cannot distinguish bug vs. feature work
from branch names alone (false positives from "fix typo" feature branches).

### Alt-C: First-class `ai/bugs/bug-XXXXXX/` with parallel skill chain (chosen)

Mirror feature/epic chain shape, diverge in template content. **Chosen** because it is the
minimum-disruption path that gives all four target outcomes: full reproduction context
captured at creation, regression-first TDD enforced at refinement, tech-lead visibility
via directory listing, and independent MTTR measurement via timestamp scoping. Cost: 6
new skills, 6 new rules, 1 new template family, 4 new audit scripts. Benefit: defect
governance becomes structurally visible and mechanically enforced rather than aspirational.

### Alt-D — Store canônico externo (Jira)

Avaliar o Jira como store canônico de bugs, com `ai/bugs/` atuando como cache local ou stub.
**Rejeitada** porque: (1) dependência de conectividade externa viola o modelo offline-first;
(2) `ai/bugs/` como first-class artifact mantém coerência com o modelo `ai/epics/`;
(3) sincronização bidirecional Jira ↔ `ai/bugs/` introduz conflito de estado sem benefício
proporcional; (4) skills existentes já cobrem exportação opcional para Jira. A integração
Jira permanece viável como camada de exportação futura.

## 5. Escopo & Fora-de-Escopo

### In Scope

1. New `ai/bugs/bug-XXXXXX/` directory structure with `bug.md`, story files, refinement verdict, and reports/.
2. `/x-create-bug` skill — scaffolds the bug folder from a brief description with template-driven population.
3. `/x-refine-bug` skill — multi-persona refinement (developer + tech-lead + QA) producing a refinement verdict gating implementation.
4. Auto-generation of implementation stories from a bug (`/x-create-bug` produces 1-N stories under `ai/bugs/bug-XXXXXX/story-NN.md`).
5. Bug-specific implementation map (`ai/bugs/bug-XXXXXX/IMPLEMENTATION-MAP.md`).
6. Refinement-gate enforcement extended to bug stories (Camada 0 hook + Camada 2 audit).
7. PR review and merge gates extended to bug PRs (regression-test-before-fix invariant).
8. 6 new governance rules covering the above lifecycle.

### Out of Scope (≥ 3 items required)

1. **Cross-project bug import** — pulling bugs from external trackers (Jira, GitHub Issues) into `ai/bugs/`. Future epic.
2. **Automated root-cause analysis** — LLM-driven RCA on stack traces. Treated as a separate research epic.
3. **Bug deduplication / similarity detection** — surfaces during creation. Deferred to a later epic post-baseline.
4. **MTTR analytics dashboard skill** — `/x-analyze-bug-trends` or equivalent. KPI-3 measurement is computable manually post-merge; tooling is a separate concern.
5. **Migration of historical defect-remediation epics** (`epic-XXXX-fix-*`) into `ai/bugs/`. New convention applies forward only.
6. **Hotfix branch unification** — `hotfix/*` semantics (Rule 19 Exception 2) remain distinct from `bug/*` and are not changed by this epic.

## 6. Riscos de Produto & Mitigações

### Risk-1 (Product) — Adoption resistance: developers continue ad-hoc bug filing

Developers under deadline pressure may bypass `/x-create-bug` and file bugs as feature
epics or as direct git branches, defeating the directory-scoping benefit.

**Mitigation:** Camada 0 PreToolUse hook detects `feat:` or `epic-XXXX-fix-*` patterns
and surfaces an advisory pointing to `/x-create-bug`. Camada 2 audit script
`audit-bug-classification.sh` flags merged PRs whose title matches `fix:`/`bug:` but
which originate from non-`bug/*` branches. Rule 19-style 2-release adoption window
with WARN before HARD-FAIL.

### Risk-2 (Product) — Refinement bottleneck: tech-lead becomes a queue

Mandatory `/x-refine-bug` before implementation may stall urgent fixes if the tech lead
is unavailable.

**Mitigation:** `/x-refine-bug` accepts an `--auto-approve-trivial` flag for bugs
classified `severity: low + scope: single-file + has-regression-test: true` at creation
time, producing an auto-approved verdict signed by `automation`. Critical/high-severity
bugs always require human refinement. Hotfix path (`hotfix/*`) remains the escape valve
for production incidents (Rule 19 Exception 2).

### Risk-3 (Technical) — Refinement-gate hook complexity: dual artifact discovery

`enforce-refinement-gate.sh` (Camada 0) currently looks for `ai/epics/.../execution-state.json`.
Extending it to also discover `ai/bugs/.../execution-state.json` risks regressions in the
existing epic gate.

**Mitigation:** Add a small dispatcher function `find-refinement-target` that returns
`{kind: epic|bug, path: ...}`; existing call sites consume the dispatcher. Story-0080-0005
ships a golden-file regression test covering both kinds plus an absent-file negative case.
Hook fail-open contract preserved: dispatcher errors degrade to existing epic-only behavior
with WARN, never blocking unrelated work.

**TechLead feasibility refinement (Phase C):** A implementação de `find-refinement-target`
adota um contrato de fail-open estritamente limitado ao cenário path-not-found: quando o
arquivo `execution-state.json` simplesmente não existe no path calculado, o dispatcher
degrada para o comportamento legado (epic-only) com WARN, sem bloquear operações não
relacionadas. Qualquer outro erro — parse inválido do JSON, chave `kind` ausente, valor
fora do enum `epic|bug`, ou falha de I/O que não seja ENOENT — é tratado como hard failure
com saída não-zero, impedindo que um state file corrompido ou malformado produza um verdict
silenciosamente errado. Essa delimitação garante KPI-4 (zero violações do gate em CI):
um arquivo malformado jamais será interpretado como `approved`.

A ordenação da cadeia de dependências é corrigida para refletir a precedência lógica entre
R-080-6 e story-0080-0005: story-0080-0006 (enforce merge-commit para `bug/*` PRs) deve ser
aprovada e ativa **antes** que story-0080-0005 (extensão do hook Camada 0 e do audit
Camada 2 do refinement-gate para bugs) seja implementada. O `IMPLEMENTATION-MAP.md` deve
refletir: 0080-0001 → 0080-0002 → 0080-0003 → 0080-0004 → 0080-0006 → 0080-0005.

A detecção de bugs mal classificados é endereçada pelo `audit-bug-classification.sh`
(Camada 2), que cruzará diff count vs `severity:low` auto-approved. Quando um PR
auto-aprovado com `severity: low` excede o threshold single-file, o audit emite
`BUG_MISCLASSIFICATION_WARNING`.

### Risk-4 (Security) — Path traversal and injection via free-form bug fields

Free-form input to `/x-create-bug` (slug, title, reporter identity, reproduction steps)
is written to `ai/bugs/bug-XXXXXX/bug.md` and used to compose branch names and shell
commands inside hooks. Without validation, malicious or careless input could traverse
outside `ai/bugs/`, inject shell metacharacters into hook helpers, or smuggle PII into
governance artifacts.

**Mitigation:** story-0080-0001 implementa validação e escape de todos os campos livres do
`/x-create-bug` antes de qualquer gravação. Slug validado via regex `^bug-[0-9]{6}$`
seguida de normalização de caminho + verificação de prefixo contra `ai/bugs/` para
eliminar path traversal. Hook advisório usa `printf '%q'` para toda interpolação de
strings controladas pelo usuário. `ai/bugs/` captura apenas identidade do autor git;
sem dados adicionais de PII; satisfaz LGPD art. 6º, III.

### Risk-5 (Technical) — Regression-test-before-fix audit false positives

`audit-bug-regression-coverage.sh` checks that a `test:` commit precedes a `fix:` commit
in the bug PR's history. Authors who squash-merge or amend commits will appear as
violations even when the test was authored RED first.

**Mitigation:** Audit operates on the **unsquashed branch history** of the merged PR
fetched via `gh pr view --json commits`. PRs that lose history to amend/squash receive
a CI WARN (not FAIL) with operator instructions to use merge-commit strategy on bug PRs.
Story-0080-0006 documents the merge-commit convention for `bug/*` → `develop` PRs and
extends `x-merge-pr` to default `--merge` (not `--squash`) when source branch matches `bug/*`.

### Smoke Test Strategy

End-to-end lifecycle validation is declared via `BugLifecycleSmokeIT` (a sandboxed git repo, executed as part of `mvn verify`). The smoke suite covers the full `/x-create-bug → /x-refine-bug → implementation gate → PR review` chain with 4 mandatory scenarios:

| Scenario | Trigger | Assertion |
| :------- | :------ | :-------- |
| **S-1 — Scaffold** | Run `/x-create-bug "checkout total wrong when promo applied"` with piped stdin (severity=high, scope=single-module) in a sandboxed repo | `ai/bugs/bug-000001/bug.md` exists; frontmatter contains `requires-capabilities: [governance.bug-lifecycle]`; branch `bug/000001-checkout-total-promo` created from `develop`; docs PR opened with label `bug-scaffold`; stdout JSON envelope valid (shape: `{bugId, branch, prUrl, scaffoldPath, elapsedMs, status}`); elapsed ≤ 90s |
| **S-2 — Refinement** | Run `/x-refine-bug bug-000001` on the scaffolded + manually completed `bug.md` (reproduction steps, observed vs. expected, regression test slot filled) | `## Refinement Verdict` in `bug.md` has `status: approved`; `verdictHash` is a 64-hex-char SHA-256; `execution-state.json` `storyRefinements` map updated with matching hash |
| **S-3 — Gate block** | Run `Skill(skill: "x-implement-story", args: "ai/bugs/bug-000001/story-02-fix.md")` before `/x-refine-bug` is invoked (verdict `status: pending`) | `enforce-refinement-gate.sh` exits 33 `REFINEMENT_REQUIRED`; no implementation worktree created; stderr contains pointer to `/x-refine-bug bug-000001` |
| **S-4 — PR review gate** | Create bug PR from `bug/000001-*` branch with only a `fix:` commit (no prior `test:` commit) and invoke `x-review-pr` on the PR | Checklist item BR-PR-2 evaluates FAIL; Tech-Lead verdict surface receives NO-GO; `## Bug Lifecycle Evidence` in PR body records `BR-PR-2: FAIL — order: [fix:...]; expected [test:..., fix:...]`; PR cannot be merged |

Smoke suite is gated: `BugLifecycleSmokeIT` MUST pass on every PR targeting `develop` or `epic/*` that touches any `bug-lifecycle` capability artifact. Failure = CI exit 1.
