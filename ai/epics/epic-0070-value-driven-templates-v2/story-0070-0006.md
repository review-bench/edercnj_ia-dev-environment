# História: Skill `/x-arch-system-update`

**ID:** story-0070-0006
**Status:** Refinada
**Refinement Verdict:** approved

## 1. Visão

Como **arquiteto / orquestrador**, quero skill `/x-arch-system-update <epic-id>` que atualiza `docs/architecture/system.md` incrementalmente após cada épico — adiciona componentes, integrações, e decisões ao Decision Log do Sistema (§11 do template).

## 2. Entrega de Valor

- `system.md` permanece **vivo** + sincronizado com decisões arquiteturais por épico.
- Decision Log acumula histórico navegável.
- **Métrica:** 100% dos épicos pós-rollout invocam `x-arch-system-update` na Phase 3 (validação por audit em PR para `develop` — pode ser delegada a EPIC-0071/Doc-as-DoD).

## 3. Acceptance Criteria (Gherkin — 4 categorias mandatórias)

```gherkin
Cenario: Happy — update incremental
  DADO docs/architecture/system.md existe (criado por story-0070-0004)
  E EPIC-0099 acabou com decisão "adoção Hibernate Search" registrada em ADR-NNNN
  QUANDO operador invoca /x-arch-system-update epic-0099
  ENTÃO seção "Persistência" ganha bloco sobre Hibernate Search
  E seção "Decision Log do Sistema" ganha entry vinculada à ADR-NNNN
  E nenhuma outra seção é tocada (skill é cirúrgica, não regen)

Cenario: Degenerate — épico sem decisões arquiteturais
  DADO EPIC-0099 não introduziu decisões arquiteturais novas (épico só de docs/refactor)
  QUANDO operador invoca /x-arch-system-update epic-0099
  ENTÃO skill termina com exit 0 + mensagem "no architectural decisions detected"
  E system.md não é modificado

Cenario: Error — system.md não existe
  DADO docs/architecture/system.md ausente
  QUANDO operador invoca /x-arch-system-update epic-0099
  ENTÃO skill aborta com SYSTEM_MD_MISSING + sugere "rode ia-dev-env generate primeiro"

Cenario: Boundary — idempotência
  DADO /x-arch-system-update epic-0099 já rodou (Hibernate Search já no system.md)
  QUANDO operador roda novamente /x-arch-system-update epic-0099
  ENTÃO system.md fica idêntico bytewise ao estado anterior (idempotente)
```

## 6. Decision Rationale

**Decisão:** Skill incremental — não regenera `system.md` do zero. **Motivo:** preserva narrativa manual escrita por operadores em §10 (Integrações Externas) e em parte §11 (Decision Log). **Alternativa descartada:** regen completa (apaga narrativa). **Consequência:** lógica de merge precisa ser cuidadosa — usar `x-internal-report-write --append` quando possível (já tem dedup) e `Edit` cirúrgico quando não (auto-fill seções 1-9).

## 7. Refinement Notes (consolidadas)

- **Estratégia de merge — escolha definitiva:** **Append-with-dedup** via `x-internal-report-write --append` para o Decision Log (§11) — bloco anexado carrega marker `## ID: <epic-id>` (ou `## ID: <epic-id>-<adr-id>` quando múltiplas decisões), e a skill já dedupa por esse marker (interface documentada). Para inserções em seções 1-10 (auto-fill), usar `Edit` localizado por marker HTML `<!-- AUTO-FILL: <key> -->` no template.

