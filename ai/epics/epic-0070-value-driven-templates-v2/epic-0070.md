## 1. Contexto & Escopo

### 1.1 Problema

Os templates atuais de Epic e Story (`_TEMPLATE-EPIC.md`, `_TEMPLATE-STORY.md`, ambos derivados do trabalho de RA9 9-seções planejado pelo EPIC-0056) sofrem de **três disfunções entrelaçadas**:

**Disfunção 1 — Mistura de valor de negócio com arquitetura técnica em uma só estrutura.**

A seção 1 ("Contexto & Escopo") pede uma "descrição concisa (3-5 frases)". As seções 2 ("Packages — Hexagonal"), 3 ("Contratos & Endpoints") e 4 ("Materialização SOLID") exigem detalhes técnicos profundos. O autor, na prática, escolhe entre escrever um épico raso na seção 1 (e profundo nas técnicas) ou um épico técnico-pesado que não comunica valor. Não há espaço narrativo para problema, persona, hipótese, alternativas — informações que **definem o valor que o épico entrega** e que o time (e LLMs futuras) precisa para tomar decisões coerentes meses depois.

**Disfunção 2 — Arquitetura técnica espalhada por épicos, sem visão de sistema.**

Cada épico declara seus packages hexagonais, mas o **sistema como um todo** — stack escolhida, banco, comunicação (REST / gRPC / Socket / Event), observabilidade, resilience, performance budget, segurança baseline — vive disperso entre rules (Rule 04 — arquitetura summary), o YAML do projeto, e fragmentos de épicos antigos. Quem entra no projeto reconstrói esse mapa pela leitura de 60+ arquivos.

**Disfunção 3 — Descrição "concisa" perde substância narrativa irrecuperável.**

3-5 frases não cabem hipótese de impacto, nem persona detalhada, nem alternativas consideradas, nem trade-offs estratégicos. O custo dessa síntese excessiva aparece **6 meses depois**, quando o time ou uma LLM futura tenta entender por que o épico foi escrito daquele jeito — a informação não está em lugar nenhum.

EPIC-0056 (RA9, em planejamento) tentou padronizar 9 seções fixas, mas mantém a mistura valor/técnica. Este épico resolve as três disfunções de uma vez, e por isso **substitui** EPIC-0056.

### 1.2 Hipótese

> Se separarmos o template de épico/story em **"valor de negócio puro"** (problema, persona, hipótese, OKRs, alternativas, riscos de produto, escopo) e movermos toda arquitetura técnica do sistema para um **único `docs/architecture/system.md` vivo**, alimentado parcialmente pelo YAML do projeto e atualizado a cada épico, então:
> - épicos e histórias ficam legíveis para stakeholders não-técnicos sem perder rigor;
> - decisões técnicas são tomadas uma vez no nível do sistema, não re-litigadas em cada épico;
> - LLMs futuras (e novos devs) recuperam o "porquê" de qualquer feature ao ler o markdown, não escavando código + ADRs + commits;
> - a arquitetura hexagonal continua sendo materializada via **rules** (não duplicada nos templates) —
> **porque** a separação elimina a ambiguidade estrutural: autores não conseguem popular seções técnicas §2-7 quando essas seções não existem no template, e leitores futuros localizam a rationale estratégica em um arquivo dedicado sem precisar escanear 7+ seções técnicas.

### 1.3 Escopo

Este épico entrega:

1. **`_TEMPLATE-EPIC.md` v2** — reescrito do zero, foco em valor:
   - 1. Visão & Problema (narrativa, sem limite de tamanho — recomendado 3-8 parágrafos)
   - 2. Persona & Stakeholders
   - 3. Hipótese de Valor & OKRs/KPIs
   - 4. Alternativas Consideradas (≥ 2, com motivo de descarte)
   - 5. Escopo & Fora-de-Escopo
   - 6. Riscos de Produto & Mitigações
   - 7. Stories (índice; bloqueia / é bloqueada por; entrega de valor por story)
   - 8. Quality Gates (DoR/DoD herdados do projeto, com possíveis adições por épico)
   - 9. Origem & Referências (decision rationale, links, ADRs, memória de IA)
   - **Sem seções 2-7 do v1** (Packages, Contratos, SOLID, Quality Gates técnicas, Segurança, Observabilidade) — migram para o `system.md`.
2. **`_TEMPLATE-STORY.md` v2** — reescrito, foco em valor:
   - 1. Visão (Como X, eu quero Y, garantindo Z) + Contexto narrativo
   - 2. Persona & Cenário de Uso
   - 3. Entrega de Valor (métrica, impacto)
   - 4. Critérios de Aceite (Gherkin, 4 categorias mandatórias: degenerate / happy / error / boundary)
   - 5. Contratos (request/response/event tipados — input para spec sync, EPIC-0071)
   - 6. Tasks (3-8 tasks, mesmas regras do v1)
   - 7. Dependências (Blocked By / Blocks)
   - 8. Decision Rationale (≥ 1 micro-template 4-linhas)
   - 9. Refinement Verdict (anexado por `/x-story-refine`, EPIC-0069)
   - **Sem seções de Packages, SOLID, Coding Constraints, Observabilidade técnica** — vivem no `system.md` e são governadas por rules.
3. **`_TEMPLATE-ARCHITECTURE-SYSTEM.md` (NEW)** — template do markdown vivo `docs/architecture/system.md`:
   - 1. Stack Resolvida (auto-fill via YAML: language, framework, build tool, native build)
   - 2. Persistência (auto-fill via YAML: database type/version, migration tool, cache, message broker)
   - 3. Comunicação (auto-fill via YAML: interfaces — REST/gRPC/Event/Socket/CLI — com spec format)
   - 4. Observabilidade (auto-fill via YAML: standard, backend, SLOs, structured logging fields)
   - 5. Resilience (auto-fill via YAML + manual: circuit breakers, retries, timeouts, fallbacks, idempotency)
   - 6. Performance Budget (auto-fill via YAML quando `quality.performance.slo` declarado, EPIC-0072; manual quando não)
   - 7. Segurança Baseline (auto-fill via YAML: compliance, encryption; manual: threat surface, sensitive data classification)
   - 8. Dependency Policy (auto-fill via YAML quando `dependencies.policy` declarado, EPIC-0074; manual quando não)
   - 9. Documentação Targets (auto-fill via YAML, EPIC-0071: README, OpenAPI, asyncapi, ADR, skill-docs)
   - 10. Integrações Externas (manual: APIs, webhooks, MCP servers do YAML)
   - 11. Decision Log do Sistema (acumulativo: cada épico adiciona suas decisões via `x-arch-system-update`)
4. **Skill `/x-arch-system-update`** — atualiza `docs/architecture/system.md` incrementalmente, lendo épico recém-implementado + YAML + ADRs novos.
5. **Atualização das skills `x-epic-create` e `x-story-create`** — passam a usar v2 templates por padrão; flag `--legacy-template-v1` para opt-out durante deprecation window.
6. **Skill `/x-template-migrate`** — assiste migração de épicos v1 para v2 (parser inteligente: extrai narrativa do "Contexto & Escopo" v1 e empurra para "Visão & Problema" v2; extrai packages/contratos/SOLID e pergunta se devem ir para `system.md` ou ficar como ADR).
7. **Marcar EPIC-0056 como Superseded** — preserva histórico mas redireciona para EPIC-0070.
8. **Capability `governance.value-driven-templates`** (universal) + Rule 30 atualizada (compartilhada com EPIC-0071, ambas se referenciam) ou Rule nova específica (decisão na story-0070-0001).
9. **Smoke test E2E** (`Epic0070ValueTemplatesSmokeIT`) cobrindo: gerar epic v2, gerar story v2, atualizar `system.md` via `x-arch-system-update`, migrar epic v1 com `x-template-migrate` e diff vs golden.

### 1.4 Fora do escopo

- **Reescrever épicos existentes em massa**: skill `x-template-migrate` é opt-in; baseline imune. Migração ad-hoc.
- **Substituir Rule 04 (Architecture Summary)**: rule continua governando direção de dependência hexagonal. Templates apenas deixam de duplicá-la.
- **Mexer em `_TEMPLATE-TASK.md`**: task fica como está (consumida por `x-task-implement`, escopo task-first).
- **Reescrever templates de planning** (`_TEMPLATE-IMPLEMENTATION-PLAN.md`, `_TEMPLATE-TEST-PLAN.md`, etc.): permanecem por agora; refatoração futura, escopo separado.
- **Internacionalização do template** (i18n): templates ficam em PT-BR (Rule 02). Tradução é épico futuro.

### 1.5 Entrega de Valor

- **Valor primário:** épicos passam a comunicar o **porquê** sem ofuscar com **como**. Stakeholders não-técnicos leem épicos sem precisar de tradutor; técnicos consultam `system.md` quando querem o como.
- **Valor secundário:** decisões de arquitetura do sistema vivem em **um arquivo só**, vivo, navegável. Onboarding de novo dev passa de "leia 60 arquivos" para "leia 1 arquivo + rules + YAML".
- **Valor terciário:** memória de IA (EPIC-0075) tem âncora estável — `system.md` é o melhor candidato a single source of truth para retrieval.
- **Métrica de sucesso primária:** ≥ 90% dos épicos novos pós-rollout usam template v2 (sem `--legacy-template-v1`). Medido automaticamente por `audit-template-version.sh` escaneando NDJSON de telemetria; verificado a cada release.
- **Métrica de sucesso secundária (proxy mensurável):** zero invocações de `--legacy-template-v1` após 2 releases do GA v2 — medido por `audit-template-version.sh --check=no-legacy-flag` (exit 1 `LEGACY_FLAG_VIOLATION` em qualquer ocorrência).
- ~~**Sinal qualitativo**~~ *removido* — não falsificável; substituído pela métrica proxy acima.

## 6. Decisões Arquiteturais

### 6.1 Por que substituir EPIC-0056 e não estender

EPIC-0056 (RA9 9-seções) **mantém a mistura valor/técnica**, apenas padroniza-a. Estender significaria 9-seções-melhoradas que ainda misturam, ou 9-seções + 9-seções-extras. Substituir é mais limpo: 0056 vira histórico, 0070 é o caminho ativo.

**Decisão:** substituição.

**Alternativa descartada:** estender 0056 com flag de modo. Rejeitado: dois templates conviventes geram drift e revisão dupla.

**Consequência:** EPIC-0056 vai para "Superseded"; trabalhos pré-rollout são imunes (baseline). PRs no 0056 que não foram mergeados ainda devem ser fechados.

### 6.2 Por que `system.md` único e não `system/<feature>.md`

Multiplos arquivos é o estado atual disperso (cada épico fala da sua parte). Single file força uma visão coerente. Para escala, conforme o sistema cresce, o `system.md` pode ser dividido por seção (ex: `system/persistence.md`, `system/messaging.md`) — mas só quando justificado, e apenas como split do mesmo template.

**Decisão:** single `system.md` v1.

**Alternativa descartada:** modular desde o início (`system/*.md`). Rejeitado: complexidade prematura; `x-arch-system-update` opera em um arquivo.

**Consequência:** quando `system.md` ultrapassar ~800 linhas, abrir épico de "split modular do system.md".

### 6.3 Por que auto-fill via YAML mas não 100%

Stack escolhida (Java + Spring) é determinística (do YAML). Decisão de Hibernate Search vs JPA Criteria é narrativa (manual). Misturar é a forma certa: o YAML traz o "o quê", o operador escreve o "como/por quê" no mesmo arquivo.

**Decisão:** template com **placeholders** preenchidos pelo `TemplatesAssembler` na geração inicial, e seções narrativas para preenchimento manual via `x-arch-system-update`.

**Alternativa descartada:** 100% auto-fill (gerar tudo). Rejeitado: vira XML rendido — sem narrativa.

**Consequência:** template carrega convenções de placeholder bem documentadas; story-0070-0004 normatiza.

### 6.4 Por que skill de migração e não script bash

Migração v1→v2 não é mecânica — bloco "Packages (Hexagonal)" pode virar update no `system.md` ou ADR ou descartado. Decisão depende do contexto. Skill interativa pergunta; script faria errado.

**Decisão:** `/x-template-migrate` interativa, com diff + perguntas por bloco.

**Alternativa descartada:** script bash auto-merge. Rejeitado: gera resultados ruins em ~40% dos casos pelo nosso teste manual.

**Consequência:** migração é opt-in e custosa (5-15min por épico). Operador escolhe quais épicos vale migrar; baseline pré-rollout fica imune.

### 6.5 Por que Rule 30 e não fundir com Rule 22

Rule 22 (Lifecycle Integrity) governa **estados** de artefatos. Templates governam **forma**. Conceitos ortogonais.

**Decisão:** Rule 30 separada — "Value-Driven Templates Contract".

**Alternativa descartada:** seção em Rule 22. Rejeitado: pollui rule existente.

**Consequência:** rule a mais para manter; mas escopo claro.

### 6.6 Por que template-v1 ainda existe em deprecation window

Projetos no meio do ciclo de vida (épicos abertos com v1) não devem ser forçados a migrar mid-flight. Window é 2 releases.

**Decisão:** flag `--legacy-template-v1` com warning. Removida no 3º release.

**Alternativa descartada:** breaking imediato. Rejeitado: viola Rule 19.

**Consequência:** janela curta + warning; comunicar bem no CHANGELOG.
