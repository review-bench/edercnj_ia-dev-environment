## 1. Visão & Problema

O generator ia-dev-env entrega 29 arquivos de agente sob `src/main/resources/targets/claude/agents/` (divididos em `core/`, `conditional/`, `checklists/`, `developers/`), mas nenhuma das ~114 skills existentes usa o mecanismo nativo de dispatch de subagente do Claude Code — ou seja, nenhuma skill chama `Agent(subagent_type: "<agent-name>", ...)` referenciando um agente registrado. Toda dispatch com persona cai em `Agent(subagent_type: "general-purpose", ...)` com a persona duplicada inline no argumento `prompt:`. Os arquivos `agent.md` são documentação inerte que o runtime nunca carrega.

As **5 skills** que aludem a personas específicas o fazem via prosa inline: `x-plan-story` (7 personas), `x-refine-epic` (5), `x-refine-story` (7), `x-internal-build-story-plan` (6), e `x-review-codebase` (8 — via subskills, não dispatch Agent). Isso produz três consequências concretas:

1. **Duplicação de persona.** Arquiteto/QA/TechLead/Security/PO/Performance vivem como ~30–60 linhas de prosa dentro do `prompt:` de cada skill de planejamento paralelo. Quando a definição de papel evolui, quatro skills devem ser editadas em sincronia — drift inevitável.

2. **Violação de Rule 23 por default.** Subagentes `general-purpose` herdam o modelo da sessão pai, que é Opus hoje. Revisores/QA também roteiam por Opus por acidente — exatamente a baseline de 84% Opus que o EPIC-0050 se propôs a corrigir. Declarações `model:` por agente são o mecanismo que permite que cada tier aterrise no modelo correto independentemente do pai.

3. **Agentes órfãos geram sinal falso.** Um novo colaborador lendo `.claude/agents/sre-engineer.md` razoavelmente assume que a persona SRE está conectada a alguma skill. Não está. 16 dos 29 agentes (55%) são completamente órfãos — incluindo toda a família `checklists/` (11 arquivos que são estruturalmente conteúdo de checklist, não personas de orquestração).

**Se não fizermos nada:** o token baseline permanece inflado (Opus em 84%), a manutenção de personas escala com O(N*skills) em vez de O(agents), e os 29 arquivos de agente continuam sendo documentação morta sem nenhum valor operacional.

## 2. Persona & Stakeholders

### Persona-1: Engenheiro de Software mantendo skills de planejamento

- **Papel:** Skill Maintainer responsável por x-plan-story, x-refine-epic, x-refine-story, x-internal-build-story-plan
- **Dor atual:** Quando a definição de papel do Architect evolui, é necessário editar 4 skills em lockstep — e ainda assim há risco de drift entre elas
- **Ganho com este épico:** A persona vive em um único arquivo `architect.md`; as skills apenas referenciam `subagent_type: "architect"` — zero duplicação
- **Critério de sucesso pessoal:** "Posso evoluir a persona do Architect editando um único arquivo e confiar que todas as skills usam a versão atualizada"

### Persona-2: CI Maintainer adicionando novo agente

- **Papel:** Engenheiro responsável pela integridade do pipeline CI
- **Dor atual:** Nenhum gate verifica se novas skills introduzem personas inline em vez de usar o dispatch nomeado
- **Ganho com este épico:** `audit-agent-skill-wiring.sh` captura `INLINE_PERSONA_VIOLATION` em cada PR, com baseline file para gerenciar exceções
- **Critério de sucesso pessoal:** "PRs com `You are a Senior Architect` inline no prompt: são bloqueados automaticamente"

### Persona-3: Arquiteto avaliando custo de token

- **Papel:** Architect / Tech Lead analisando otimização de custo
- **Dor atual:** Revisores e QA rodam em Opus por herança silenciosa — custo ~2x desnecessário
- **Ganho com este épico:** Cada agente declara `model: sonnet` ou `model: opus` explicitamente; o tier correto é garantido por contrato
- **Critério de sucesso pessoal:** "% de chamadas Opus cai de 84% para ≤50% após a migração"

## 3. Hipótese & OKRs

### Hipótese de Valor

**Se** formalizarmos o frontmatter dos agentes, migrarmos as 4 skills de planejamento paralelo e as 8 skills de review especializado para dispatch nomeado, removermos os 11 pseudo-agentes de checklist, e adicionarmos um gate CI que detecta personas inline,
**então** a persona de cada papel viverá em um único arquivo canônico, o tier de modelo de cada subagente será determinístico, e novas violações serão detectadas automaticamente em PRs,
**porque** o mecanismo `subagent_type: "<agent-name>"` do Claude Code carrega a persona do arquivo .md registrado — eliminando a necessidade de duplicar o corpo da persona no argumento `prompt:` de cada skill.

## 4. Alternativas Consideradas

### Alternativa 1 — Manter inline personas mas documentar via convenção

**Descrição:** Não migrar para named subagent dispatch; em vez disso, estabelecer uma convenção de documentação para que inline personas referenciem o agent.md de origem via comentário.

| Prós | Contras |
| :--- | :--- |
| Zero esforço de migração de skills | Drift inevitável — nenhum mecanismo de enforcement |
| Compatível com qualquer versão do Claude Code | Rule 23 permanece violada por default (herança silenciosa de modelo) |
| Rollback trivial | 29 agentes permanecem inoperantes; custo de token não melhora |

**Decisão de rejeição:** Convenção sem enforcement é documentação que decai. A duplicação de persona (dor #1) e a violação de Rule 23 (dor #2) não são resolvidas. O objective principal — operacionalizar o mecanismo agent.md — não seria atingido.

### Alternativa 2 — Deletar todos os agentes e não migrar para named dispatch

**Descrição:** Como os agentes são inoperantes, simplesmente removê-los e manter o padrão inline atual.

| Prós | Contras |
| :--- | :--- |
| Elimina documentação morta imediatamente | Perde o mecanismo de custo de token (model: por agente) |
| Simplifica a estrutura do repositório | Piora a manutenibilidade — personas ficam ainda mais fragmentadas |

**Decisão de rejeição:** Deletes sem migration destroem o valor potencial do mecanismo. O objetivo é operacionalizar, não deletar.

### Alternativa 3 — Migrar apenas as parallel-planning skills (scope reduzido)

**Descrição:** Limitar a migração a x-plan-story, x-refine-epic, x-refine-story, x-internal-build-story-plan; deixar as 8 review skills para um épico futuro.

| Prós | Contras |
| :--- | :--- |
| Entrega mais rápida de parte do valor | Checklists e orphans continuam gerando falso sinal |
| Menor risco de regressão | Gate CI deve ser adicionado de qualquer forma para o subset |

**Decisão de rejeição:** As review skills e os checklists são igualmente urgentes — deixar metade do trabalho pendente cria um estado intermediário inconsistente que complica o gate de auditoria.
