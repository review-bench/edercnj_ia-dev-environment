## 1. Visão

Como **gate operator (LLM ou CI)**, quero a skill `/x-doc-validate` que valida **freshness** de **6 dimensões** de documentação — README, API specs (OpenAPI/AsyncAPI agrupados), gRPC proto, ADR, skill-docs e `docs/architecture/system.md` — retornando **exit non-zero** quando staleness é detectada e produzindo um relatório em `_TEMPLATE-DOC-VALIDATE-REPORT.md` consumível por orquestradores (Phase 3 de `x-story-implement`).

A skill é **target-stack-aware** (consome `documentation.targets` do `ProjectConfig` introduzido em story-0071-0001) — só valida o que foi declarado/auto-detectado.

## 2. Entrega de Valor

- **Valor primário:** gate de freshness pré-merge — bloqueia PR cujo código tocou features que requerem doc-update sem que docs tenham sido atualizadas.
- **Valor secundário:** relatório estruturado (`_TEMPLATE-DOC-VALIDATE-REPORT.md`) é o **artefato evidência** registrado em Rule 24 §Mandatory Evidence Artifacts.
- **Métrica:** ≥ 95% PRs pós-rollout passam sem violation; false-positive rate ≤ 5% medido contra PRs históricos do próprio repo (validação em Marco de Validação Arquitetural — IMPLEMENTATION-MAP §7).

## 6. Decision Rationale

**Decisão:** Skill separada de `x-doc-generate` (não flag `--validate-only`). **Motivo:** SRP — generate cria/atualiza, validate confere; outputs diferentes (geração modifica arquivos, validação é read-only + report); orquestradores consomem `validate`, hooks consomem `validate`, dev consome `generate`. **Alternativa descartada:** flag `--validate-only` em `x-doc-generate` — quebra contrato existente da v1 e mistura responsabilidades. **Consequência:** 2 SKILLs a manter; KP comum em `knowledge/documentation/targets.md` para não duplicar lista de dimensões.

## 7. Refinement Notes (consolidadas)

- **Heurísticas de "endpoint detectado vs OpenAPI sync":** parser detecta `@RestController` / `@RequestMapping` / `@GetMapping` (Spring) ou `app.get()`/`app.post()` (Express) novos no diff; cruza com OpenAPI `paths:` para identificar endpoints sem entrada. Lista de detectores cresce por stack — começar com Java/Spring + Node/Express.
- **False-positive tolerance:** ≤ 5% medido contra PRs históricos. Se medido > 5%, ajustar heurística ou subir freshness-window-hours como mitigação temporária.
- **`freshness-window-hours` semântica:** 0 = imediato (default); >0 = tolerância em horas para casos especiais (releases, hotfix grace period). Configurável em `documentation.freshness-window-hours`.
- **Integração com `x-arch-system-update` (EPIC-0070):** quando dimensão `system-architecture` valida e detecta drift, skill invoca `x-arch-system-update --validate-only`; ausência de EPIC-0070 → dimensão registrada como "skipped (EPIC-0070 indisponível)".
- **Rule 24 evidência:** relatório `_TEMPLATE-DOC-VALIDATE-REPORT.md` salvo em `plans/epic-XXXX/reports/doc-validate-STORY-ID.md` (caminho integrado em Rule 24 §Mandatory Evidence Artifacts em story-0071-0006).
