# História: `x-release-changelog` v2 (formato híbrido) + `_TEMPLATE-CHANGELOG-ENTRY.md`

**ID:** story-0071-0004
**Status:** Refinada
**Refinement Verdict:** approved

> ✅ **REFINEMENT APPROVED** — All 7 dimensions passed. Ready for implementation.

## 1. Visão

Como **release manager**, quero `x-release-changelog` v2 que gera **formato híbrido** no `CHANGELOG.md`:

1. Bloco `### Highlights` narrativo de 3-8 parágrafos (derivado de `## Entrega de Valor` dos épicos v2 do range desde último tag — EPIC-0070 é hard prereq, **D-R10**).
2. Seções Keep-a-Changelog rigorosas mantidas (`### Added`, `### Changed`, `### Fixed`, `### Breaking`, `### Deprecated/Removed`) agregadas via Conventional Commits (`feat:` → Added, `fix:` → Fixed, `refactor:` → Changed, `feat!:`/`BREAKING CHANGE:` → Breaking).

A v2 também entrega `_TEMPLATE-CHANGELOG-ENTRY.md` (template em `java/src/main/resources/shared/templates/`) que `x-release-changelog` consome via `x-internal-report-write`.

## 2. Entrega de Valor

- **Valor primário:** changelog passa a ser **legível por stakeholders** — bloco Highlights responde "o que mudou para mim?" sem leitura cruzada de PRs.
- **Valor secundário:** rigor SemVer mantido — Keep-a-Changelog ainda alimenta tooling existente (parsers, releases automáticas, dependabot).
- **Métrica:** bloco `### Highlights` citado em ≥ 3 comunicações de release (Slack/email) em 1 trimestre — sinal de adoção real.

## 3. Acceptance Criteria (Gherkin — 4 categorias mandatórias)

```gherkin
Cenario: Happy — changelog híbrido com Highlights de epic-value
  DADO 3 épicos merged no range desde último tag
  E cada épico v2 com seção "## Entrega de Valor" preenchida
  QUANDO /x-release-changelog v3.10.0 roda
  ENTÃO CHANGELOG.md ganha entry "## [v3.10.0] — YYYY-MM-DD"
  E sub-bloco "### Highlights" com 3-8 parágrafos derivados das entregas
  E sub-blocos "### Added/Changed/Fixed/Breaking" agregam Conventional Commits

Cenario: Degenerate — range sem épicos v2 (modo degradado D-R10)
  DADO range desde último tag contém apenas commits sem épico v2 declarado
  QUANDO /x-release-changelog roda
  ENTÃO entry é gerada com Highlights vazio + WARN visível "EPIC-0070 não disponível ou nenhum épico v2 no range — Highlights manual ou degradado"
  E exit 0 (não bloqueia release)

Cenario: Error — `format=invalid` no YAML
  DADO documentation.changelog.format=foo no YAML
  QUANDO /x-release-changelog roda
  ENTÃO exit non-zero com INVALID_CHANGELOG_FORMAT
  E stderr lista valores válidos {hybrid, keep-a-changelog, conventional-only}

Cenario: Boundary — Highlights tamanho fora do range 3-8 parágrafos
  DADO range com 1 épico v2 que tem Entrega de Valor curta (1 parágrafo)
  QUANDO /x-release-changelog roda
  ENTÃO Highlights é gerado com mínimo 3 parágrafos (expansão automática com bullets de Conventional Commits)
  SE > 8 parágrafos seriam gerados
  ENTÃO truncamento com "..." + WARN visível "Highlights truncado — revisar manualmente"

Cenario: Performance — geração de changelog completa em tempo aceitável
  DADO range com 100+ commits e 10 épicos merged desde último tag
  QUANDO /x-release-changelog roda
  ENTÃO geração completa em < 60s
  E todas seções (Highlights + Added/Changed/Fixed/Breaking) estão presentes

Cenario: Security — conteúdo de Entrega de Valor sanitizado antes de inserir no CHANGELOG
  DADO epic markdown com Entrega de Valor contendo sequências de escape ou referências a paths internos do CI
  QUANDO /x-release-changelog gera Highlights
  ENTÃO conteúdo é sanitizado (escape de caracteres especiais de markdown)
  E nenhum path absoluto do filesystem aparece no CHANGELOG.md gerado
  E nenhum token ou credencial do ambiente de CI é exposto
```

## 6. Decision Rationale

**Decisão:** Highlights derivado de "## Entrega de Valor" dos épicos v2 (não escrito manualmente). **Motivo:** single source of truth — esse campo já é obrigatório nos épicos v2 (EPIC-0070); reusar evita duplicação ("escreva valor no épico **e** no changelog"). **Alternativa descartada:** operador escreve Highlights manualmente — gera dual write e drift; campo "Entrega de Valor" do épico fica desatualizado vs Highlights do release. **Consequência:** EPIC-0070 é hard prereq; sem ele, fallback degradado (Highlights vazio + WARN) preserva fluxo de release sem bloquear.

## 7. Refinement Notes (consolidadas)

- **Tamanho do Highlights (3-8 parágrafos):** range arbitrário mas tested em 3 releases reais antes de fixar. Se output ruim em > 50% dos casos, abrir story de refinamento de algoritmo.
- **Tom do Highlights:** formal-objetivo (não marketing); foco em "o que muda para o usuário" e "métricas de impacto se medidas". Tom é responsabilidade do épico v2 (campo Entrega de Valor); changelog é fiel ao texto original.
- **Integração com release notes externas:** out of scope nesta story (newsletter/blog post); changelog é a fonte para release notes.
- **Fallback degradado D-R10:** se EPIC-0070 não disponível OU range sem épicos v2, Highlights vazio + WARN visível + exit 0. NÃO bloquear release. Quando EPIC-0070 mergea, fallback é removido em PR follow-up.
