## 1. Contexto & Escopo

### 1.1 Problema

Documentação é tratada como **subproduto opcional** no fluxo atual. Isso aparece em três sintomas observáveis:

**Sintoma 1 — `x-doc-generate` é opcional em `x-story-implement` Phase 3.** A skill existe, sabe gerar README/ADR/OpenAPI/changelog, mas é invocada **se sobrar tempo**. PRs merged sem doc-update passam pelo CI sem fricção.

**Sintoma 2 — README, OpenAPI, asyncapi, ADRs ficam desatualizados silenciosamente.** Nada em CI checa freshness. Um endpoint novo entra na API sem entrada na OpenAPI spec; um ADR é referenciado em um PR sem ser publicado em `docs/adr/`. Esse débito acumula. Quando alguém vai usar a documentação, descobre que está errada — e perde confiança em qualquer outra parte.

**Sintoma 3 — `CHANGELOG.md` é mecânico. Atualmente `x-release-changelog` agrega por commit type (`feat:`, `fix:`, `refactor:`), produzindo entries técnicas como `- expand X interface` sem dizer **o que muda para o usuário** ou **qual valor entrou**. Releases viram catálogo de commits, não narrativa de produto. Stakeholders não conseguem ler o changelog e entender o que mudou em termos de capacidade entregue.

A consequência cumulativa é cara: novos contribuidores aprendem o sistema lendo código, não documentação; usuários do CLI não entendem o que cada release entrega; auditoria pós-incidente reconstrói fluxo a partir de logs e PRs porque a doc não acompanha. **Documentação que não é DoD vira documentação que não existe**.

Importante: este projeto é **um gerador de CLI para projetos cliente em várias stacks**. O que documentamos no nosso projeto vale como exemplo, mas o épico precisa entregar um sistema que se aplique a qualquer projeto cliente — o conjunto de artefatos a manter freshness varia por stack (README sempre; OpenAPI quando há REST; asyncapi quando há eventos; gRPC proto quando há gRPC; ADRs quando há decisões; skill-docs quando há skills).

### 1.2 Hipótese

> Se transformarmos atualização de documentação em **etapa bloqueante** do `x-story-implement` (Phase 3 com `--skip-doc` removido), com **target stack-aware** (README + OpenAPI + asyncapi + ADR + skill-docs conforme YAML do projeto declara), e se reescrevermos o changelog em **formato híbrido** (bloco "## Highlights" narrativo no topo + Keep-a-Changelog rigoroso em baixo) alimentado pelo campo "Entrega de Valor" dos épicos/stories v2 (EPIC-0070), então documentação acompanha código por design e o changelog vira ferramenta de comunicação.

### 1.3 Escopo

Este épico entrega:

1. **Skill `/x-doc-validate`** — gate bloqueante que verifica freshness por target stack-aware:
   - **README** sempre validado: presença de seções esperadas (Overview, Setup, Usage, Configuration, Skills) e diff vs git mtime.
   - **OpenAPI/asyncapi** validado quando `interfaces[].spec` declara `openapi`/`asyncapi`: schema válido + cobertura de endpoints/eventos novos vs implementados.
   - **gRPC proto** validado quando `interfaces[].type=grpc`: contracts mantidos + breaking-change detection (delegado a `x-test-contract` em EPIC-0072 quando disponível; standalone caso contrário).
   - **ADRs** validados: cada `Decision Rationale` em story v2 com `## ADR Reference: ADR-XXXX` deve ter o ADR publicado em `docs/adr/`.
   - **Skill-docs** validado: cada skill nova/modificada tem o frontmatter v3.0 + `## Triggers` + `## Examples` atualizados.
   - **`docs/architecture/system.md`** (EPIC-0070) validado: se o épico introduz novo componente/integração e `x-arch-system-update` não foi invocado, gate falha.
2. **Phase 3 de `x-story-implement` MODIFICADA** — invocação `Skill(skill: "x-doc-generate", model: "sonnet", ...)` + `Skill(skill: "x-doc-validate", model: "sonnet", ...)` passa a ser **MANDATORY TOOL CALL** (Rule 24). Flag `--skip-doc` removida; mantida apenas em `## Recovery` block.
3. **`x-release-changelog` v2** — reescrita para gerar formato híbrido:
   ```
   ## [v3.10.0] — 2026-XX-XX

   ### Highlights

   <Bloco narrativo de 3-8 parágrafos: o que entrou nesta release, o que muda
    para o usuário, métricas de impacto se medidas, breaking changes destacadas.
    Construído lendo "Entrega de Valor" dos épicos merged + git log entre tags.>

   ### Added
   - <Conventional Commits feat: agregados>

   ### Changed
   - <Conventional Commits refactor: agregados>

   ### Fixed
   - <Conventional Commits fix: agregados>

   ### Breaking
   - <Itens com `feat!:` / `fix!:` / `BREAKING CHANGE:`>

   ### Deprecated / Removed
   ```
4. **Skill `/x-doc-generate` v2** — mantém auto-detect do v1, ganha:
   - Modo `--target-stack-aware` (default): consome YAML do projeto e atualiza só os targets relevantes (REST → OpenAPI; gRPC → proto; events → asyncapi; sempre → README + skill-docs + system.md update).
   - Integração com `x-arch-system-update` (EPIC-0070) — chama-a quando detecta mudança arquitetural.
5. **Schema YAML novo** — `documentation.targets`:
   ```yaml
   documentation:
     targets:
       - readme              # sempre
       - openapi             # auto-detect via interfaces.spec=openapi
       - asyncapi            # auto-detect via interfaces.broker
       - grpc-proto          # auto-detect via interfaces.spec=proto3
       - adr                 # sempre
       - skill-docs          # sempre se .claude/skills/ existir
       - system-architecture # sempre se docs/architecture/system.md existir
     freshness-window-hours: 0   # 0 = imediato; >0 = tolerância (raro)
     changelog:
       format: hybrid          # hybrid (default) | keep-a-changelog | conventional-only
       highlights-source: epic-value   # epic-value (default) | git-log-only | manual
   ```
6. **Capability `governance.doc-as-dod`** (universal) declarada em `capabilities/governance/doc-as-dod.yaml`.
7. **Rule normativa `Documentation Freshness Gate`** (numeração TBD — palpite vigente: Rule 31; story-0071-0001 verifica gap real conforme **D-R3**) + **ADR** correspondente (numeração TBD — palpite vigente: ADR-0020; verificação em **D-R4**).
8. **CI script `audit-doc-freshness.sh`** (camada CI script — Rule 26) — varre PRs e falha se artefatos esperados (por target) não foram tocados quando código fonte foi tocado em diff que requer documentação. Exit codes seguem Rule 26 §Standardized (ver **D-R5**).
9. **Smoke test E2E** (`Epic0071DocAsDoDSmokeIT`) cobrindo: PR sem README update bloqueado; PR com OpenAPI desatualizada bloqueada; CHANGELOG híbrido gerado corretamente; opt-out via `## Recovery` honrado; integração com `x-arch-system-update`.

### 1.4 Fora do escopo

- **Geração automática de manuais de usuário em prosa longa** (gitbook, mkdocs sites complexos): permanece manual.
- **Tradução automática de README** (i18n): épico futuro.
- **Geração de diagramas (PlantUML/Mermaid)** automatizada: permanece como atualização manual no `system.md`.
- **Modificar formato Keep-a-Changelog**: o formato continua; só ganha o bloco "## Highlights" no topo.
- **Newsletter / publicação externa do changelog**: escopo separado.

### 1.5 Entrega de Valor

- **Valor primário:** documentação acompanha código. Se um endpoint entrou, está na OpenAPI; se um padrão arquitetural mudou, está no `system.md`; se uma decisão foi tomada, há ADR.
- **Valor secundário:** changelog passa a ser **legível por stakeholders** sem leitura cruzada de PRs. Cada release responde "o que mudou para mim?".
- **Valor terciário:** memória de IA (EPIC-0075) tem material confiável para indexar — documentação que reflete o estado atual, não o estado de 6 meses atrás.
- **Métrica de sucesso primária:** ≥ 95% dos PRs merged pós-rollout passam por `audit-doc-freshness.sh` sem violation. Medido semanalmente.
- **Métrica de sucesso secundária:** changelog "## Highlights" é citado em ≥ 3 comunicações de release (Slack/email) em 1 trimestre — sinal de adoção real.
- **Sinal qualitativo:** zero requests de "alguém atualizou o README com isso?" pós-rollout em 1 sprint.

## 6. Decisões Arquiteturais

### 6.1 Por que CHANGELOG híbrido e não substituir Keep-a-Changelog

Keep-a-Changelog tem rigor que serve a SemVer e a tooling existente (parsers, releases automáticas). Substituir quebra. Adicionar bloco "## Highlights" no topo, **antes** das seções rigorosas, dá legibilidade narrativa **sem** quebrar o contrato.

**Decisão:** híbrido. Highlights primeiro (humano), Keep-a-Changelog depois (mecânico).

**Alternativa descartada:** substituir. Rejeitado: quebra parsers existentes.

**Consequência:** CHANGELOG fica mais longo. Aceitável.

### 6.2 Por que target stack-aware e não check uniforme

Projeto Java + Spring + REST tem OpenAPI. Projeto Node sem REST não tem. Forçar OpenAPI universal seria absurdo. Stack-aware é a única forma que escala.

**Decisão:** YAML `documentation.targets` declara explicitamente. Auto-detect quando ausente.

**Alternativa descartada:** check único. Rejeitado.

**Consequência:** mais código no audit script (cases por target). Aceitável.

### 6.3 Por que Highlights derivados do "Entrega de Valor" do épico v2

Esse campo já é obrigatório nos épicos v2 (EPIC-0070). Reusar evita duplicação ("escreva valor no épico **e** no changelog"). Single source of truth.

**Decisão:** `x-release-changelog` v2 lê `## Entrega de Valor` dos épicos merged no range.

**Alternativa descartada:** operador escreve Highlights manualmente. Rejeitado: dual write.

**Consequência:** EPIC-0070 é pré-requisito hard. Sem v2, fallback para git log (modo degradado).

### 6.4 Por que doc-validate skill separada de doc-generate

`generate` cria/atualiza. `validate` confere. Misturar viola SRP. Hooks consomem `validate`; orquestradores consomem `generate`. Outputs diferentes.

**Decisão:** 2 skills sibling.

**Alternativa descartada:** flag `--validate-only` em `x-doc-generate`. Rejeitado: muda contrato existente.

**Consequência:** 2 SKILL.md a manter. KP comum em `knowledge/documentation/targets.md`.

### 6.5 Por que Phase 3 modificada e não Phase 4 nova

`x-story-implement` tem 4 fases. Adicionar Phase 4 quebraria orquestradores que dependem da estrutura. Fortalecer Phase 3 (incluir doc-generate + validate como mandatory tool calls dentro dela) é cirúrgico.

**Decisão:** Phase 3 absorve doc obligation.

**Alternativa descartada:** Phase 4 nova. Rejeitado: blast radius alto.

**Consequência:** Phase 3 fica mais densa. Extrair sub-fases internas se passar de 250 linhas.
