## 1. Visão

Como **gate operator**, quero a skill `/x-dep-policy-validate` que:
1. Lê `dependencies.policy` do YAML do projeto via `DependencyPolicyConfig` (story-0074-0001).
2. Invoca `x-dependency-audit --policy` (modificação aditiva — story consome a flag) e `x-supply-chain-audit` para coletar findings (CVEs, licenses, versions, freshness).
3. Aplica a matriz `block-on` (D-R10) cruzando cada finding com a policy declarada.
4. Gera `plans/epic-XXXX/reports/dep-policy-validation-STORY-ID.md` via template `_TEMPLATE-DEP-POLICY-REPORT.md` (matriz finding × policy × ação × severidade).
5. Retorna exit code consistente: `0` (OK ou warnings only), `1` (`DEP_POLICY_VIOLATION` se qualquer `block-on: any-violation` é satisfeito ou `denied-cve` aciona).

…para que o gate SCA seja executável e auditável, não review-only.

## 2. Entrega de Valor

- **Valor primário:** gate runtime aplicado tanto em Phase 3 (story-0074-0005) quanto em CI (story-0074-0004) compartilha esta skill — single source of truth do "qual finding bloqueia".
- **Valor secundário:** report markdown padronizado entra como artefato evidência da Rule 27 (surface 13 — D-R7) na Phase 3.
- **Valor terciário:** modificação aditiva de `x-dependency-audit` (não wrapper novo) preserva backward-compat — chamadas sem `--policy` continuam comportamento atual.
- **Métrica primária:** zero PRs com finding HIGH/CRITICAL não-mitigado pós-rollout (medido por `audit-dep-policy.sh` em CI — story-0074-0004).
- **Métrica secundária:** report markdown gerado sob ≤ 30s para projetos com ≤ 200 deps diretas (alvo razoável; PRs lentos investigados).

## 6. Decision Rationale

**Decisão:** modificar `x-dependency-audit` (adicionar `--policy`) em vez de criar wrapper novo. **Motivo:** `x-dependency-audit` já parseia dep tree, fetch CVEs, calcula freshness — duplicar isso num wrapper novo viola DRY e cria drift. **Alternativa descartada:** skill `x-dep-validate-with-policy` paralela. Rejeitada — duas skills com 80% de código compartilhado é red flag arquitetural. **Consequência:** `x-dependency-audit` ganha modo "report-only" (sem `--policy`) e modo "report+policy-cross-check" (com `--policy`); SKILL.md documenta ambos claramente.

## 7. Refinement Notes (consolidadas)

- **Granularidade da matriz `block-on` (D-R10):** report markdown DEVE explicitar qual cláusula `block-on` foi acionada por finding (não apenas "violation"); operador precisa saber se a falha veio de severity-cve, denied-cve, license, ou min-version.
- **Integração com baseline:** quando `audits/dep-policy-baseline.txt` existe (story-0074-0004), findings já registrados são marcados como "GRANDFATHERED" no report e NÃO entram em "Blocking findings". Linha de baseline tem formato `<dep-coordinate>::<finding-id>  # reason — YYYY-MM-DD`.
- **Recovery se finding crítico aparece em transitiva:** report deve sugerir mitigation paths (override Maven `<dependencyManagement>`, npm `resolutions`, pip constraint file, go mod replace) — pacote KP `dependency-policy-playbook.md` documenta receitas.
- **Performance:** parsing de dep tree grande (≥ 500 deps transitivas) deve evitar O(N²); lookup `Map<coord, finding>` é mandatório.
- **Modificação aditiva de `x-dependency-audit`:** flag `--policy` é opcional; ausência preserva 100% do comportamento legado. SKILL.md documenta a flag em `## Examples` + `## Integration Notes`.
- **Skill model tier (D-R6):** `sonnet` por Rule 23 (Reviewer/Validator — aplica matriz a findings, não gera código novo). Frontmatter v3.0 obrigatório.
