## 1. Contexto & Escopo

### 1.1 Problema

A skill `x-dependency-audit` cobre **CVE detection, license check, outdated detection, SBOM generation** — bom escopo, mas opera contra **defaults internos** e sem **policy declarada pelo projeto**. Resultado: cada projeto cliente tem comportamento ligeiramente diferente; nenhum tem policy explícita registrada como contrato.

Quatro lacunas concretas:

**Lacuna 1 — Sem `min-version` declarado.** Um projeto pode permitir Spring Boot 2.x (EOL desde 2025) silenciosamente. Não há declaração "Spring Boot ≥ 3.x mandatory". Quando vulnerabilidade aparece em versão antiga, não há gate dizendo "esse projeto declarou min-version, esta dependência viola".

**Lacuna 2 — Sem `max-version` policy.** Um time pode aceitar Spring Boot 4.x quando aparecer (não testado, breaking changes pendentes) por engano. Sem max-version policy, upgrades automáticos via Dependabot caem em main sem revisão.

**Lacuna 3 — Sem `allowed-licenses` whitelist.** AGPL/SSPL/proprietary pode entrar como transitiva sem ninguém perceber até auditoria de compliance externa.

**Lacuna 4 — Sem **gate final** pré-merge consolidado.** `x-dependency-audit` é invocado em Phase 1 de planning, gera relatório, mas **não bloqueia merge** se um findings HIGH aparece sem mitigação. O gate é review-only ("o reviewer decide"), não automatizado.

A consequência é que a postura SCA do projeto é **declarativa sem ser executável**: "nós nos preocupamos com supply chain" sem nada que prove. Para o CLI, que **gera projetos cliente em várias stacks** (Java/Maven, Java/Gradle, Node/npm, Python/pip, Go), a falta de policy uniforme significa que cada projeto reinventa o controle, e nenhum tem controle real.

### 1.2 Hipótese

> Se introduzirmos um schema YAML `dependencies.policy` com `min-versions`, `max-versions`, `allowed-licenses`, `denied-cves`, `freshness-window-days`, e plugarmos `/x-dep-policy-validate` como **gate final** mandatório em Phase 3 de `x-story-implement` quando `dependencies.policy.enabled=true`, então:
> - cada projeto cliente declara policy explicitamente; auditoria passa de "cada um tem o seu" para "todo projeto tem o mesmo contrato com valores diferentes";
> - upgrades silenciosos por Dependabot ficam contidos pelo max-version;
> - findings HIGH/CRITICAL em deps bloqueiam merge sem ação manual;
> - LGPD/PCI compliance fica comprovável via license whitelist + SBOM.

### 1.3 Escopo

Este épico entrega:

1. **Schema YAML novo `dependencies.policy`**:
   ```yaml
   dependencies:
     policy:
       enabled: true
       min-versions:
         - { groupId: org.springframework.boot, artifactId: "*", version: "3.2.0" }
         - { groupId: com.fasterxml.jackson.core, artifactId: "*", version: "2.18.0" }
         - { name: lodash, version: "4.17.21" }   # cross-stack syntax — depende do build tool
       max-versions:
         - { groupId: org.springframework.boot, artifactId: "*", version: "3.x" }   # pin major
       allowed-licenses:
         - Apache-2.0
         - MIT
         - BSD-3-Clause
         - BSD-2-Clause
         - ISC
         # explicitly excluded: AGPL-3.0, SSPL-1.0, proprietary
       denied-cves:
         - CVE-2024-12345   # finding aceitavelmente bloqueado mesmo se patch disponível
       freshness-window-days: 365
       block-on:
         severity-cve: HIGH      # block se CVE >= HIGH (CRITICAL implícito)
         license: any-violation  # block se license fora da whitelist
         min-version: any-violation
         max-version: warn-only  # max é proteção contra upgrade automático, não block hard
         freshness: warn-only    # outdated > 365 days = warning, não block
   ```
2. **Skill `/x-dep-policy-validate`** — gate final:
   - Lê `dependencies.policy` do YAML.
   - Invoca `x-dependency-audit` + `x-supply-chain-audit` para coletar findings.
   - Aplica policy: cada finding cruzado com `block-on` thresholds.
   - Gera `plans/epic-XXXX/reports/dep-policy-validation-STORY-ID.md` com matriz finding × policy × ação.
   - Exit non-zero se qualquer `block-on: any-violation` é violado.
3. **`x-dependency-audit` MODIFIED** — passa a aceitar `--policy` para receber policy do YAML; retorna findings já cruzados com a policy.
4. **Phase 3 de `x-story-implement` MODIFIED** — quando `dependencies.policy.enabled=true`, invocação de `/x-dep-policy-validate` é **MANDATORY TOOL CALL** (Rule 24). Sai como artefato evidência (Rule 27 surface adicional).
5. **CI script `audit-dep-policy.sh`** (Camada 2) — varre PRs para `develop`/`epic/*` e re-roda policy validation pra defesa em profundidade.
6. **Capability `governance.dependency-policy`** + sub-capabilities por build tool (`governance.dependency-policy.{maven,gradle,npm,pip,gomod}`).
7. **Rule 32 — Dependency Policy Gate** + **ADR-0023**.
8. **Templates novos**:
   - `_TEMPLATE-DEP-POLICY-DECLARATION.md` — sub-template do `system.md` (EPIC-0070 §8) para declarar policy de forma humana antes de codificar no YAML.
   - `_TEMPLATE-DEP-POLICY-REPORT.md` — saída de `/x-dep-policy-validate`.
9. **Smoke test E2E** (`Epic0074DepPolicySmokeIT`) cobrindo 6 cenários: min-version violation bloqueia, max-version violation warning-only, license fora da whitelist bloqueia, CVE HIGH bloqueia, denied-cve bloqueia mesmo com patch, opt-out via `dependencies.policy.enabled=false`.

### 1.4 Fora do escopo

- **Auto-upgrade de dependências**: Dependabot/Renovate continua. Policy é validação, não upgrade.
- **Geração automática de patches**: out of scope.
- **Fork/mirror de dependências em registry interno**: out of scope.
- **Análise de dependências transitivas profundas (≥ 5 níveis)**: limitado a `x-dependency-audit` capability — máximo 3 níveis.
- **Deps de dev-time** (test-only, build-time): policy aplica só em runtime/compile scope. Test scope é warning-only.
- **License compatibility analysis** (multi-license combination): difícil; limita-se a whitelist/blacklist por license.

### 1.5 Entrega de Valor

- **Valor primário:** projetos passam a ter policy SCA explícita e executável, não declarativa.
- **Valor secundário:** auditoria externa de compliance (LGPD/PCI) tem evidência objetiva — `_TEMPLATE-DEP-POLICY-DECLARATION.md` no `system.md` + relatório de validação por release.
- **Valor terciário:** upgrades silenciosos (Dependabot mergeando major bumps) ficam contidos.
- **Métrica de sucesso primária:** 100% dos projetos novos pós-rollout declaram `dependencies.policy.enabled=true` (ou explicit opt-out documentado).
- **Métrica de sucesso secundária:** zero PRs merged com finding CVE HIGH/CRITICAL não-mitigado pós-rollout.
- **Sinal qualitativo:** time pára de fazer "auditoria SCA pré-release" manualmente — o gate cobre.

## 6. Decisões Arquiteturais

### 6.1 Por que policy no YAML e não em arquivo dedicado

Policy é configuração de projeto. YAML do projeto é o single source of truth da configuração. Adicionar arquivo separado (`dependency-policy.yaml`) cria duas fontes; usuário esquece de manter sync.

**Decisão:** sub-bloco `dependencies.policy` no YAML principal.

**Alternativa descartada:** arquivo dedicado. Rejeitado: drift garantido.

**Consequência:** YAML cresce. Tolerável dado o agrupamento sob `dependencies:`.

### 6.2 Por que `block-on` granular e não block-all

Diferentes findings têm pesos diferentes. CVE HIGH é hard block; max-version é warning (alta probabilidade de false positive em upgrades intencionais); freshness é só warning. Uniformizar leva a alarm fatigue.

**Decisão:** matriz `block-on` por categoria.

**Alternativa descartada:** "block on any". Rejeitado.

### 6.3 Por que `freshness-window-days` warning e não block

Deps "abandonadas" às vezes são propositais (libs estáveis, ex.: `commons-lang3`). Block silencioso causa fricção desnecessária.

**Decisão:** warning-only no default. Operador customiza para hard-block em projetos high-compliance (PCI).

**Alternativa descartada:** block default. Rejeitado.

### 6.4 Por que sub-capabilities por build tool

Maven, Gradle, npm, pip, go.mod têm parsers/sintaxes diferentes. Cada um precisa de implementação específica. Sub-capabilities permitem skill principal degradar quando tooling não está disponível.

**Decisão:** `governance.dependency-policy.{maven,gradle,npm,pip,gomod}` como sub-capabilities.

**Alternativa descartada:** capability monolítica. Rejeitado: viola Open/Closed.

### 6.5 Por que x-dependency-audit modificado e não wrapper novo

`x-dependency-audit` já consome dependency tree. Adicionar `--policy` flag preserva interface, evita skill duplicada.

**Decisão:** modificação `--policy`.

**Alternativa descartada:** skill nova `x-dep-validate-with-policy`. Rejeitado: redundância.
