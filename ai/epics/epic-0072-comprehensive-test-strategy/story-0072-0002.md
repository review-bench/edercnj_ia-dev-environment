# História: Skill `/x-test-performance` (stack-aware: REST/gRPC/CLI/GraphQL/Socket) + `_TEMPLATE-PERFORMANCE-PLAN.md` + KP

**ID:** story-0072-0002
**Status:** Refinada
**Refinement Verdict:** approved

## 1. Visão

Como **desenvolvedor de projeto gerado pelo ia-dev-env**, quero uma skill stack-aware `/x-test-performance` que:
1. Lê `interfaces[].type` + `architecture.style` + `framework` do YAML do projeto.
2. Despacha para a ferramenta correta por stack (REST → Newman, gRPC → ghz, CLI → hyperfine, GraphQL → Artillery, Socket/event-driven → harness custom documentada em KP).
3. Honra `quality.performance.slo.<stack>.{p50,p95,p99}_ms` + `quality.performance.baseline-tolerance-pct` declarados em `QualityConfig`.
4. Compara contra baseline persistente em `governance/baselines/performance-baseline.json` (per-projeto — D-R8) e bloqueia merge quando regressão > tolerance.

…para que regressão de performance seja detectada em CI antes de chegar a `develop`/`main`, em vez de aparecer como reclamação em produção (§1.1 Lacuna 1 do epic).

## 2. Entrega de Valor

- **Valor primário:** regressão de p95/p99 ganha gate em CI; perf SLA deixa de depender de boa-vontade humana.
- **Valor secundário:** projetos cliente herdam baseline format + tooling-pinning sem decidir manualmente.
- **Métrica:** ≥ 80% dos projetos novos pós-rollout têm `quality.performance.enabled=true` (medido por contagem em `config-templates/` + projetos vivos via flag).

```gherkin

  E gera relatório de medição sem comparativo a SLO
  E NÃO bloqueia merge

Cenario: Error — perf regression > tolerance fail PR
  DADO YAML do projeto declara quality.performance.slo.rest.p95_ms=200 e baseline-tolerance-pct=10
  E baseline atual mede p95=180ms
  E PR introduz mudança que mede p95=220ms (+22% vs baseline)

Cenario: Performance/SLA — skill execution latency
```

## 3.1. Typed Contracts

### QualityConfig.performance (Java record — declared in story-0072-0001, consumed here)

```java
public record PerformanceConfig(
    boolean enabled,
    int baselineTolerancePct,
    Map<String, StackSlo> slo  // key = stack name: "rest", "grpc", "cli", "graphql", "socket"
) {
    public record StackSlo(
        int p50Ms,
        int p95Ms,
        int p99Ms
    ) {}
}
```

### Baseline JSON Schema (`governance/baselines/performance-baseline.json`)

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "object",
  "additionalProperties": {
    "description": "Key = stack name (rest, grpc, cli, graphql, socket)",
    "type": "object",
    "additionalProperties": {
      "description": "Key = endpoint/method/command identifier",
      "type": "object",
      "required": ["p50Ms", "p95Ms", "p99Ms", "throughputRps", "measuredAt", "gitSha"],
      "properties": {
        "p50Ms":         { "type": "integer", "minimum": 0 },
        "p95Ms":         { "type": "integer", "minimum": 0 },
        "p99Ms":         { "type": "integer", "minimum": 0 },
        "throughputRps": { "type": "number",  "minimum": 0 },
        "measuredAt":    { "type": "string",  "format": "date-time" },
        "gitSha":        { "type": "string",  "pattern": "^[0-9a-f]{40}$" }
      }
    }
  }
}
```

### Performance Report Output (`reports/perf-report-STORY-ID.md`)

The report template `_TEMPLATE-PERFORMANCE-PLAN.md` produces a Markdown file with the following typed sections:

| Section | Content | Format |
|---------|---------|--------|
| `## Summary` | Overall pass/fail, stack tested, SLO compliance | Prose + table |
| `## Results per Endpoint` | Per-endpoint: measured p50/p95/p99, baseline p50/p95/p99, delta %, verdict | Markdown table |
| `## Baseline Comparison` | Tolerance threshold, exceeded endpoints, recommended action | Markdown table |
| `## Tooling` | Tool used, version, command executed, container image (if applicable) | Key-value list |

No absolute filesystem paths, hostnames, IP addresses, or credentials appear in the report (sanitization contract).

## 6. Decision Rationale

### 6.1 Alternatives

| Alternative | Decision | Rationale |
|-------------|----------|-----------|
| **A1: Stack-awareness via `requires-any` capabilities (chosen)** | Adopted | Open/Closed — adding a new stack (e.g., Rust with `cargo-criterion`) means creating a new capability YAML + KP, without modifying `x-test-performance/SKILL.md`. Tool default per stack is a KP convention, not skill code. |
| **A2: Internal `if/elif` switch in the skill** | Rejected | Violates Open/Closed; duplicates detection logic across sibling skills; each new stack requires modifying the skill body. |
| **A3: Unified tooling (k6 for all stacks)** | Rejected | k6 supports HTTP, gRPC, and WebSocket natively and could simplify to a single tool. However: (1) k6 lacks native CLI benchmarking (hyperfine is purpose-built); (2) k6's gRPC support is less mature than ghz for proto3 service discovery; (3) locking all stacks to one vendor creates single-point-of-failure risk for the entire perf gate; (4) per-stack KP approach allows teams to swap tooling via capability override without touching the skill. |
| **A4: Baseline stored in execution-state.json instead of dedicated file** | Rejected | execution-state.json is per-epic, transient; baseline is per-project, permanent. Mixing concerns would bloat the state file and break the append-only contract. Dedicated `governance/baselines/performance-baseline.json` provides clear ownership and auditability. |

### 6.2 Risks

#### Technical Risks

| # | Risk | Impact | Likelihood | Mitigation |
|---|------|--------|------------|------------|
| T1 | **CI tooling availability** — Newman/ghz/hyperfine/Artillery may not be pre-installed in target CI environments | Skill fails with unclear error; blocks merge | Medium | Skill emits `TOOL_NOT_FOUND` with actionable install instructions; smoke tests use containers (`--platform=linux/amd64`) to avoid binary dependency; KP documents container fallback per tool. |
| T2 | **Baseline concurrent writes** — parallel CI jobs for the same project could race on `performance-baseline.json` writes | Corrupted baseline; false positives/negatives on subsequent runs | Low | Baseline is append-only by contract; write restricted to explicit `task-perf-baseline-update` with file-level lock advisory. Concurrent reads are safe (JSON is immutable once written for a given git SHA). |
| T3 | **Proto3 service discovery for gRPC** — ghz requires `.proto` file paths or reflection endpoint to enumerate methods | Skill cannot generate load plan for gRPC stack; exits with unhelpful error | Medium | KP documents two discovery modes: (a) proto file path from project config, (b) gRPC server reflection. Skill checks both before failing. Smoke test validates at least one path. |
| T4 | **EPIC-0073 baseline format compatibility** — EPIC-0073 (regression+DAST) also writes to `governance/baselines/` | Schema collision; one epic breaks the other's parser | Medium | Baselines use separate files (`performance-baseline.json` vs `regression-baseline.json`). JSON schema uses stack-scoped top-level keys, no namespace collision. Story-0072-0001 ADR documents the compatibility contract. |
| T5 | **Container image size and pull latency** — smoke tests using containers add cold-start latency in CI | CI timeout; slow developer feedback loop | Low | Pin specific image tags (not `latest`); use multi-stage images where possible; document expected pull times in KP. |

#### Product Risks

| # | Risk | Impact | Likelihood | Mitigation |
|---|------|--------|------------|------------|
| P1 | **Low adoption** — teams may not enable `quality.performance.enabled=true` if setup cost is perceived as high | Feature delivers zero value; investment wasted | Medium | Default SLO templates per stack in KP; `x-test-performance` degrades gracefully (smoke-only mode when no SLO declared); generator sets `enabled=true` when capability is present. |
| P2 | **False positive rate** — overly tight default tolerance (10%) may cause merge blocks on benign variance | Developer frustration; teams disable the gate | Medium | Default `baseline-tolerance-pct=10` is configurable per-project in YAML; KP documents tuning guidance; degenerate scenario (no SLO) runs smoke-only without blocking. |
| P3 | **Tooling version drift** — pinned versions become stale; new features/fixes unavailable | Security vulnerabilities in perf tooling; incompatibility with newer runtimes | Low | Renovate integration (EPIC-0074) automates major version pinning; KP documents minimum versions with CVE monitoring guidance. |

## 7. Refinement Notes (consolidadas)

- **Cenários de carga padrão por stack:** documentados no KP correspondente. REST: 100 req/s sustained 30s + spike-test. gRPC: 50 RPS sustained 30s. CLI: 100 invocações em série + 10 paralelas. GraphQL: query simples + query nested (3 níveis).
- **Baseline lock vs append:** baseline é **append-only por default** (cada PR que muda comportamento cria nova entry com timestamp + git_sha); update explícito requer task `task-perf-baseline-update.md` com justificativa (otimização legítima vs regressão). Lock ⇒ baseline não-mutável a menos que task aprovada.
- **Tooling pinning policy:** versões mínimas no KP; smoke usa containers; pinning major automatizado em Renovate quando 0074 (deps) entregar.
- **Integração com EPIC-0073 (regression+DAST):** EPIC-0073 também usa `governance/baselines/` para baseline de regressão funcional — formato JSON estendível compatibilmente.
