# História: CI script `audit-perf-baseline.sh` + entry no audit-gates-catalog

**ID:** story-0072-0005
**Status:** Refinada
**Refinement Verdict:** Approved

## 1. Visão

Como **developer contributing to a generated project**, quero CI script `audit-perf-baseline.sh` (Camada 2 — Rule 26 §Taxonomy) que:
1. Verifica integridade de `governance/baselines/performance-baseline.json` (D-R8): JSON parse-válido + schema atendido + sem campos obrigatórios faltando.
2. Detecta sobrescrita silenciosa de baseline (cada update DEVE ter justificativa via task explícita — Refinement Notes da story-0072-0002).
3. Cruza baseline com último `perf-report-STORY-ID.md` produzido na branch — se relatório indica regressão > tolerance e não há entry em `governance/baselines/perf-baseline-updates.log`, bloqueia.
4. Implementa `--self-check` (Rule 26 §--self-check Flag) — exit 2 (`OPERATIONAL_ERROR`) quando dependências (`jq`) ou baseline-file ausentes.
5. Entry simultânea em `docs/audit-gates-catalog.md` (RULE-004 — Catalog-before-Add).

…porque without baseline integrity protection, performance regressions introduced by my PRs can silently reach production: a corrupted baseline file yields no comparison, and an unjustified baseline overwrite erases the only evidence of prior acceptable thresholds.

## 2. Entrega de Valor

- **Valor primário:** Developers are protected from merging PRs that silently degrade performance — a corrupted or unjustifiably overwritten baseline is caught before merge, ensuring regressions are always surfaced.
- **Valor secundário:** Generated projects inherit a consistent baseline-integrity guardrail without each team needing to define their own update-log format or audit convention.
- **Métrica retrospectiva:** zero PRs with silently overwritten baseline in 90 days post-rollout (measured by log + audit history).
- **Métrica per-run (p95):** script execution completes in < 2s on a repo with up to 50 baseline entries.
- **Métrica per-run (false-positive rate):** < 1% false-positive rate over 30-day rolling window (measured by manual override count / total audit runs).

## 3. Acceptance Criteria (Gherkin — 6 categorias)

```gherkin
Cenario: Happy — baseline válida + sem regressão pendente
  DADO governance/baselines/performance-baseline.json é JSON válido + schema OK
  E nenhum perf-report-*.md no PR indica regressão
  QUANDO audit-perf-baseline.sh roda (sem args)
  ENTÃO exit 0 (OK)

Cenario: Degenerate — baseline ausente em projeto novo
  DADO governance/baselines/performance-baseline.json não existe (projeto recém-gerado)
  QUANDO audit-perf-baseline.sh roda
  ENTÃO exit 0 (OK) com WARN "no baseline yet — first run will create it"
  E NÃO bloqueia merge

Cenario: Error — baseline corrompida fail
  DADO governance/baselines/performance-baseline.json com JSON malformado (parse-error em line 12)
  QUANDO audit-perf-baseline.sh roda
  ENTÃO exit 3 (BASELINE_CORRUPT) com mensagem identificando file + linha
  E sugere reverter para a baseline da branch develop

Cenario: Boundary — sobrescrita sem justificativa bloqueia
  DADO baseline foi sobrescrita no PR (novo timestamp, novo git_sha)
  E NÃO há entry em governance/baselines/perf-baseline-updates.log com razão
  QUANDO audit-perf-baseline.sh roda
  ENTÃO exit 1 (PERF_BASELINE_VIOLATION) com mensagem "baseline updated without justification"
  E reporta diff entre baseline anterior (git show HEAD~1) e atual

Cenario: Security — path traversal in baseline file path rejected
  DADO a variável de ambiente PERF_BASELINE_PATH é definida como "../../etc/passwd"
  QUANDO audit-perf-baseline.sh roda
  ENTÃO exit 2 (OPERATIONAL_ERROR) com mensagem "path traversal attempt rejected"
  E o script NÃO abre nem lê o arquivo apontado
  E o script valida que o resolved path está dentro do repo root (realpath + startsWith guard)

Cenario: Performance/SLA — script completes within execution time budget
  DADO governance/baselines/performance-baseline.json com 50 entries (worst-case size)
  E perf-baseline-updates.log com 200 lines (worst-case log)
  QUANDO audit-perf-baseline.sh roda
  ENTÃO exit 0 ou 1 (resultado depende do conteúdo)
  E tempo de execução total < 2 segundos (wall-clock, medido via `time`)
```

## 4. Typed Contracts

### 4.1 `performance-baseline.json` — JSON Schema (consumed, not owned)

> **Source of truth:** story-0072-0002 owns the schema definition. This story consumes it read-only.

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$id": "performance-baseline-v1",
  "type": "object",
  "required": ["version", "entries"],
  "properties": {
    "version": { "type": "string", "pattern": "^1\\.0$" },
    "entries": {
      "type": "array",
      "items": {
        "type": "object",
        "required": ["stack", "p50", "p95", "p99", "timestamp", "git_sha"],
        "properties": {
          "stack":     { "type": "string", "minLength": 1 },
          "endpoint":  { "type": "string" },
          "p50":       { "type": "number", "minimum": 0 },
          "p95":       { "type": "number", "minimum": 0 },
          "p99":       { "type": "number", "minimum": 0 },
          "timestamp": { "type": "string", "format": "date-time" },
          "git_sha":   { "type": "string", "pattern": "^[0-9a-f]{40}$" }
        },
        "additionalProperties": false
      }
    }
  },
  "additionalProperties": false
}
```

### 4.2 `perf-baseline-updates.log` — Typed Format

Tab-delimited, one line per update, append-only. Fields:

| # | Field | Type | Format | Example |
|---|-------|------|--------|---------|
| 1 | `timestamp` | string | ISO-8601 UTC (`YYYY-MM-DDTHH:MM:SSZ`) | `2026-04-30T14:22:00Z` |
| 2 | `git_sha` | string | 40-char hex (full SHA) | `a1b2c3d4...` |
| 3 | `author` | string | No tabs, no newlines | `eder.nunes` |
| 4 | `reason` | string | Double-quoted, internal quotes escaped as `\"` | `"Optimized DB queries — TASK-0072-0005-003"` |

**Delimiter:** horizontal tab (`\t`, 0x09). **Line terminator:** `\n` (LF). **Encoding:** UTF-8.

Example line:
```
2026-04-30T14:22:00Z	a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2	eder.nunes	"Optimized DB queries — TASK-0072-0005-003"
```

### 4.3 Exit codes (public contract — Rule 26 §Standardized)

| Exit | Code | Condition |
|------|------|-----------|
| 0 | `OK` | Baseline valid + no unjustified overwrite |
| 1 | `PERF_BASELINE_VIOLATION` | Baseline overwritten without log justification |
| 2 | `OPERATIONAL_ERROR` | `jq` missing, baseline unreadable, path traversal, or `--self-check` failure |
| 3 | `BASELINE_CORRUPT` | JSON parse error or schema validation failure |

## 7. Decision Rationale

**Decisão:** Baseline per-projeto em `governance/baselines/performance-baseline.json` (D-R8) — não shared entre projetos. **Motivo:** cada projeto tem hardware-target diferente, padrões de uso diferentes; comparar entre projetos não tem sentido (preservada de §6.4 do epic). **Alternativa descartada:** baseline compartilhada em uma central remote — rejeitado por (a) viola Rule 14 (cloud-agnostic, sem dependência de serviço externo); (b) baselines diferem por hardware do CI runner. **Consequência:** baseline vive no repo do projeto cliente, versionada via git; updates explicitos via task + log entry.

## 8. Alternatives Considered

| # | Alternative | Considered | Rejected because |
|---|-------------|-----------|-----------------|
| 1 | **Git pre-commit hook** (Camada 0 instead of Camada 2) | Catches corruption at commit time, before push | (a) Hooks are optional — developers can `--no-verify`; (b) no CI-level enforcement means silent bypass is possible; (c) pre-commit hooks add latency to every commit, not just baseline-touching commits |
| 2 | **Java auditor test** (`PerfBaselineAuditTest.java`, Camada 3) | Structured parsing via Jackson; compile-time schema validation; co-located with other `*AuditTest` classes | (a) Requires `mvn verify` — heavier than a shell script for a JSON-only check; (b) generated projects without Maven cannot use it; (c) Rule 26 decision matrix says "no structured code parsing needed" → CI script is the correct layer |
| 3 | **Embed justification inside baseline JSON** (add `_lastUpdateReason` field) | Single file to check; no separate log file | (a) Pollutes the baseline schema with audit metadata; (b) git history only shows latest reason — previous reasons are lost unless the entire history is traversed; (c) append-only log is simpler to audit and grep |

## 9. Risks

### Technical Risks

| # | Risk | Impact | Likelihood | Mitigation |
|---|------|--------|-----------|-----------|
| T1 | **Shallow clone `git show HEAD~1` failure** — CI runners using `--depth=1` cannot access prior baseline version for diff comparison | Audit cannot detect silent overwrite; exits with false-negative (exit 0 when it should be exit 1) | Medium (GitHub Actions default fetch-depth=1 for PRs) | Check `git rev-parse HEAD~1 2>/dev/null`; if it fails, fetch one more commit via `git fetch --deepen=1`; if still fails, emit WARN and skip diff check (fail-open for that specific check only) |
| T2 | **Concurrent PR baseline race** — two PRs simultaneously update baseline; both pass audit on their own branch but conflict on merge | Baseline ends up with one PR's values, silently discarding the other's | Low (baseline updates are rare — tied to explicit rebaseline tasks) | Document in Refinement Notes that baseline updates must be serialized (merge-train or rebase before merge); audit cannot prevent this at CI level — it is a merge-order concern |
| T3 | **`--self-check` vs degenerate AC contradiction** — `--self-check` exits 2 when baseline is absent, but degenerate AC says exit 0 when baseline is absent | Confusion about which exit code applies when baseline does not exist | Medium (first-run scenario for every generated project) | `--self-check` validates tooling prerequisites only (jq on PATH, baseline dir writable); absence of baseline file is a runtime condition handled by the main flow (exit 0 + WARN), not a prerequisite failure |
| T4 | **Schema source-of-truth conflict** — this story and story-0072-0002 both reference baseline JSON structure; schema drift between stories | Audit validates against a stale schema; false positives or missed corruption | Low (stories are in the same epic, sequential dependency) | story-0072-0002 is the canonical owner of the schema. This story consumes the schema read-only. If the schema changes, this story's audit must be updated in the same PR (enforced by dependency order: 0072-0002 merges first) |
| T5 | **Shell injection in log-append path** — if `reason` field contains shell metacharacters and the script uses unquoted expansion during log parsing | Arbitrary command execution during audit | Medium (reason field is developer-authored free text) | Parse log with `read -r` + IFS=tab; never eval or unquoted-expand reason field; validate reason matches regex `^"[^"]*"$` (double-quoted, no unescaped internal quotes) |
| T6 | **`jq` resource exhaustion** — maliciously large baseline JSON (~100MB) causes jq to OOM | CI runner killed; audit never completes | Low (baseline is committed to git; PR review catches large files) | Check file size before parsing: `wc -c < baseline.json`; reject files > 1MB with exit 2 (OPERATIONAL_ERROR) |
| T7 | **Symlink attack on baseline path** — `performance-baseline.json` is a symlink to a sensitive file | Audit reads and potentially leaks sensitive file contents in error messages | Low (git does not follow symlinks by default; PR review catches symlink additions) | Check `test -L "$baseline_path"` before reading; reject symlinks with exit 2 (OPERATIONAL_ERROR) + message "symlink rejected — baseline must be a regular file" |

### Product Risks

| # | Risk | Impact | Likelihood | Mitigation |
|---|------|--------|-----------|-----------|
| P1 | **Developer friction from false positives** — legitimate baseline updates flagged as violations because developer forgot the log entry | Developer bypasses audit or adds `--no-verify` to their workflow | Medium | Clear error message with actionable fix: "Add entry to perf-baseline-updates.log with format: <template>"; provide a helper script or task template in Refinement Notes |
| P2 | **Adoption resistance** — teams see baseline audit as overhead for a feature they did not ask for | Teams disable the audit or never enable performance testing | Low (audit is generated by default; disabling requires explicit action) | Audit is fail-open for first-run (degenerate AC: exit 0 when no baseline exists); teams only see enforcement after they opt into performance testing |

## 10. Refinement Notes (consolidadas)

- **Estratégia de baseline update (PR explícita):** update da baseline requer task aprovada (`task-perf-baseline-update.md`) + entry em `perf-baseline-updates.log` com razão. Audit verifica os dois.
- **Fluxo de rebaseline pós-otimização legítima:** task documenta a otimização; baseline é regenerada; log registra; audit aceita. Sem essa documentação, é tratada como sobrescrita silenciosa.
- **Threshold de regression vs threshold absoluto:** este audit valida a integridade da baseline, NÃO a regressão (a regressão é detectada pela skill `x-test-performance` em runtime). Separação de concerns.
- **Stage policy:** este audit já entra como FAIL no primeiro release (não há razão para ser advisory — baseline corrompida é sintoma claro).
- **Schema source of truth:** story-0072-0002 owns the `performance-baseline.json` schema. This story (0072-0005) consumes it read-only. Schema changes require updating the audit in the same PR.
