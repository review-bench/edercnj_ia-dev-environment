# História: Skill `/x-test-mutation` (stack-aware: PIT/Stryker/mutmut/go-mutesting) + `_TEMPLATE-MUTATION-PLAN.md` + KP

**ID:** story-0072-0003
**Status:** Pendente
**Refinement Verdict:** approved (2026-04-30T17:55:00Z)

## 1. Visão

Como **desenvolvedor de um projeto gerado por `ia-dev-env`**, quero uma skill stack-aware `/x-test-mutation` que:
1. Detecta `language` + `framework` (Java/Maven → PIT; Java/Gradle → PIT plugin; JS/TS → Stryker; Python → mutmut; Go → go-mutesting).
2. Executa mutation testing escopo `application + domain` (excluindo `test`, `generated`, `infrastructure/adapter` por default — ajustável).
3. Valida `quality.mutation.threshold` (default 80%) com `quality.mutation.runtime-cap-min` (default 20 min) — abort se exceder o cap.
4. Bloqueia merge quando score < threshold.

…porque cobertura ≥95% atesta que linhas executam, NÃO que asserts validam comportamento (§1.1 Lacuna 2 do epic). Mutation testing é o único gate que detecta `assertNotNull(result)` em string que voltou a ser `""`.

## 2. Entrega de Valor

- **Valor primário:** asserts fracos detectados em CI; cobertura passa a ter qualidade real.
- **Valor secundário:** projetos cliente herdam a tooling default por stack sem decidir entre PIT/muJava/Stryker/mutmut/go-mutesting.
- **Métrica:** mediana de mutation score nos 3 primeiros projetos pós-rollout ≥ 75% (medida no smoke do epic 0009).

## 3.1. Typed Contracts

### MutationConfig (capability YAML → Java record)

```java
/**
 * Resolved from quality.mutation.* keys in the project YAML.
 * Assembled by MutationConfigResolver during CapabilityAwareComposer pipeline.
 */
public record MutationConfig(
    boolean enabled,                        // quality.mutation.enabled (default: true)
    int thresholdPercent,                    // quality.mutation.threshold (default: 80, range: [0, 100])
    int runtimeCapMinutes,                  // quality.mutation.runtime-cap-min (default: 20, range: [1, 120])
    List<String> excludePackages,           // quality.mutation.exclude-packages (default: ["**/test/**", "**/generated/**", "**/infrastructure/adapter/**"])
    Map<String, Integer> perPackageThresholds, // quality.mutation.thresholds.per-package (optional, default: empty)
    MutationTool tool                       // resolved from language + framework; not user-settable
) {
    public MutationConfig {
        if (thresholdPercent < 0 || thresholdPercent > 100)
            throw new IllegalArgumentException("threshold must be in [0, 100]");
        if (runtimeCapMinutes < 1 || runtimeCapMinutes > 120)
            throw new IllegalArgumentException("runtime-cap-min must be in [1, 120]");
        for (String pkg : excludePackages) {
            if (pkg.contains("..") || pkg.startsWith("/"))
                throw new IllegalArgumentException("path traversal detected in exclude-packages: " + pkg);
        }
    }
}

public enum MutationTool {
    PIT,        // Java/Maven, Java/Gradle
    STRYKER,    // JS/TS (Node)
    MUTMUT,     // Python
    GO_MUTESTING // Go
}
```

### Exit Code Enumeration

| Exit code | Named constant | Condition |
|-----------|---------------|-----------|
| 0 | `SUCCESS` | Score >= threshold within runtime cap |
| 1 | `MUTATION_SCORE_BELOW_THRESHOLD` | Score < threshold |
| 2 | `MUTATION_RUNTIME_CAP_EXCEEDED` | Execution exceeded `runtime-cap-min` |
| 3 | `MUTATION_CONFIG_INVALID` | Invalid config (path traversal, out-of-range values) |
| 4 | `MUTATION_TOOL_NOT_FOUND` | Resolved tool binary not on PATH |
| 5 | `MUTATION_STACK_UNDETECTED` | No language/framework declared; `enabled=true` |

### Runtime Cap Enforcement Mechanism

The runtime cap is enforced via a **process-level watchdog timer**:
1. Skill spawns the mutation tool process (PIT/Stryker/mutmut/go-mutesting) with `timeout(1)` (Unix) or equivalent platform command.
2. `timeout --signal=TERM <cap_minutes>m <tool-command>` ensures the child process receives SIGTERM at cap boundary.
3. If SIGTERM is ignored, SIGKILL follows after 30s grace period.
4. On cap exceeded: skill collects partial results (PIT writes incremental XML; Stryker writes partial JSON), computes partial score, and exits with `MUTATION_RUNTIME_CAP_EXCEEDED`.
5. Partial results are reported with a `verdict: "ABORTED"` marker in the report frontmatter and a list of packages not yet mutated.

## 6. Decision Rationale

**Decisão:** Threshold default 80% (não 90%, não 100%). **Motivo:** 100% é irreal e drena tempo; 90% gera alta taxa de false-positive (mutações equivalentes que não há como matar sem refactor estrutural); 80% é o sweet-spot industry — PIT ships com 80% como default, Stryker com 80%. **Alternativa descartada (threshold 90%):** rejeitado pelo histórico de força bruta documentado no PIT changelog (≥ 50% das mutações sobreviventes em projetos saudáveis são equivalent mutants ou test-quality). **Consequência:** projetos críticos (módulos de domínio com regras de negócio densas) podem subir o threshold via `thresholds.per-package` — feature documentada mas opcional. **Consequência adicional:** Rule 05 ganha um segundo threshold de quality (cobertura + mutation) — modelagem in-place via D-R3 (sem Rule número novo).

### 6.1. Alternatives (strategic)

| Alternative | Description | Rejection rationale |
|-------------|-------------|---------------------|
| **Property-based testing** (jqwik/QuickTheory for Java, fast-check for JS, Hypothesis for Python) | Generate random inputs to find edge cases that fixed tests miss. Detects specification gaps rather than assertion gaps. | Complementary but orthogonal to mutation testing: PBT finds missing test scenarios, mutation testing finds weak assertions in existing tests. PBT does not detect `assertNotNull(result)` on a non-null but semantically wrong value. Would require a separate story (`x-test-property`) and does not close Lacuna 2. |
| **Assertion linters** (AssertJ assertions checker, custom Checkstyle rules, eslint-plugin-jest `no-standalone-expect`) | Static analysis to flag weak assertion patterns (`assertTrue(true)`, `assertNotNull` without value check). Zero runtime cost. | Catches only syntactic anti-patterns, not semantic weakness. A test with `assertEquals("", result)` passes the linter but is meaningless if the contract says the method should return the user's name. Mutation testing detects this because mutating the return value to `"foo"` would still pass the test. Linters are a useful complement (low cost, fast feedback) but insufficient as the sole gate. |
| **Threshold-only alternative (no tooling, manual review)** | Rely on code review to catch weak assertions; set no automated gate. | Human reviewers consistently miss `assertNotNull`-only tests in large PRs (> 300 lines). The epic's Lacuna 2 analysis showed 12 instances across 3 sample projects that passed review. Automated mutation testing is the only scalable detection mechanism. |

## 6.2. Risks

### Technical Risks

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| **Equivalent mutants false-positive:** PIT/Stryker generate mutations that are semantically equivalent to the original code (e.g., changing `i < n` to `i != n` when `i` is always incremented by 1). These inflate the survived-mutant count and make the score appear lower than reality. | HIGH | MEDIUM — developers waste time investigating unkillable mutants, eroding trust in the gate | Document equivalent mutant patterns per stack in KP playbooks. PIT's `STRONGER` mutator set (not `ALL`) reduces equivalent mutants by ~30%. Add `mutation.exclude-equivalent-mutators` config key (roadmap, not this story) for per-project tuning. |
| **Tooling version pinning:** PIT 1.16+, Stryker 8.x+, mutmut 2.x+, go-mutesting v0.0.x+ are the tested versions. Upgrading tools may change mutation operators, altering scores across runs. | MEDIUM | MEDIUM — score regressions on tool upgrade confuse developers | Pin tool versions in KP playbooks. SKILL.md `## Integration Notes` documents version compatibility matrix. Future story may add `quality.mutation.tool-version` config key. |
| **Partial run score misleading:** When runtime cap is exceeded, the partial score is computed only from mutants processed so far. If the skipped packages have higher survival rates, the partial score overstates quality. | MEDIUM | LOW — partial results carry `verdict: "ABORTED"` and list unprocessed packages | Report clearly marks partial results. Suggest operator increase cap or reduce scope. Do not use partial score as a pass/fail gate (exit code is `MUTATION_RUNTIME_CAP_EXCEEDED`, not `SUCCESS` or `FAIL`). |
| **Python/Go smoke gap:** Smoke tests (task-007) cover only Java/Maven (PIT) and Node (Stryker). Python (mutmut) and Go (go-mutesting) are validated via KP documentation review only, not automated smoke. | MEDIUM | MEDIUM — undiscovered integration issues on Python/Go stacks | Document gap explicitly in task-007. Add Python/Go smoke fixtures as a follow-up task in a future story (not blocking this story). SKILL.md emits WARN for unsmoked stacks. |
| **Supply-chain risk:** PIT, Stryker, mutmut, and go-mutesting are third-party dependencies. A compromised release could execute arbitrary code during mutation testing. | LOW | HIGH — code execution in CI pipeline | Skill resolves tool binaries from the project's own dependency tree (Maven plugin for PIT, npm devDependency for Stryker, pip package for mutmut, go install for go-mutesting). No ad-hoc downloads from external URLs. KP playbooks document expected artifact checksums for pinned versions. `x-dependency-audit` (Rule 24 surface #08) covers these dependencies in its regular scan. |
| **Input sanitization for exclude-packages:** User-supplied glob patterns in `quality.mutation.exclude-packages` could contain path traversal sequences or shell metacharacters. | MEDIUM | HIGH — arbitrary file access or command injection | `MutationConfig` record constructor validates no `..` or absolute paths. SKILL.md Phase 0 (config validation) rejects invalid patterns before spawning any process. AC "Security — exclude-packages rejeita path traversal" covers this. |

### Product Risks

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| **Adoption friction:** Developers on generated projects may perceive mutation testing as slow and noisy, leading to `quality.mutation.enabled=false` across the board. | MEDIUM | HIGH — gate becomes useless if universally disabled | Stage policy: first release emits WARN only; second release enforces FAIL. 20-min runtime cap prevents worst-case CI stalls. Per-package thresholds let teams lower the bar on adapter layers while keeping domain strict. |
| **Stage policy friction:** The WARN-then-FAIL rollout requires coordination between releases. If the second release ships before teams have addressed warnings, CI breaks unexpectedly. | LOW | MEDIUM — developer frustration, potential rollback of the gate | CHANGELOG documents the transition timeline. `quality.mutation.enforcement-mode` config key (values: `warn`, `fail`; default follows stage policy) gives teams an explicit override during the transition window. |

## 7. Refinement Notes (consolidadas)

- **Runtime cap (mutation testing é caro):** 20 min cap default protege CI de timeouts. Tooling como PIT permite `--mutationUnitSize` para limitar escopo; Stryker tem `concurrency`. Cap exceeded ⇒ abort com sinal claro (não silent-skip).
- **Exclusões idiomáticas:** test/generated/adapter excluídos por default para evitar ruído. Domain/application sempre incluídos.
- **Integração com Rule 05:** D-R3 — Rule 05 ganha §"Mutation Score Threshold" in-place. Não criar Rule NN nova. Audit `audit-mutation-score.sh` (story-0072-0006) é o gate operacional.
- **Stage policy (warn primeiro release, fail no segundo):** documentado em CHANGELOG do epic 0009 — `quality.mutation.enabled=true` no primeiro release emite WARN apenas; segundo release vira FAIL. Mitiga adoção brusca.
