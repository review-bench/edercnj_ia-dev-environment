## 1. Visão

Como **mantenedor de qualidade**, quero uma skill stack-aware `/x-test-mutation` que:
1. Detecta `language` + `framework` (Java/Maven → PIT; Java/Gradle → PIT plugin; JS/TS → Stryker; Python → mutmut; Go → go-mutesting).
2. Executa mutation testing escopo `application + domain` (excluindo `test`, `generated`, `infrastructure/adapter` por default — ajustável).
3. Valida `quality.mutation.threshold` (default 80%) com `quality.mutation.runtime-cap-min` (default 20 min) — abort se exceder o cap.
4. Bloqueia merge quando score < threshold.

…porque cobertura ≥95% atesta que linhas executam, NÃO que asserts validam comportamento (§1.1 Lacuna 2 do epic). Mutation testing é o único gate que detecta `assertNotNull(result)` em string que voltou a ser `""`.

## 2. Entrega de Valor

- **Valor primário:** asserts fracos detectados em CI; cobertura passa a ter qualidade real.
- **Valor secundário:** projetos cliente herdam a tooling default por stack sem decidir entre PIT/muJava/Stryker/mutmut/go-mutesting.
- **Métrica:** mediana de mutation score nos 3 primeiros projetos pós-rollout ≥ 75% (medida no smoke do epic 0009).

## 3. Acceptance Criteria (Gherkin — 4 categorias mandatórias)

```gherkin
Cenario: Happy — score ≥ threshold passa
  DADO quality.mutation.threshold=80 e quality.mutation.runtime-cap-min=20
  E PR atinge score 86%
  QUANDO x-test-mutation roda em projeto Java/Maven
  ENTÃO PIT executa em ≤ 20 min
  E skill exit 0 (SUCCESS)
  E reporta mutações sobreviventes em plans/epic-XXXX/reports/mutation-report-STORY-ID.md (lista filtrável por package)

Cenario: Degenerate — projeto sem language declarado
  DADO YAML sem language ou framework
  E quality.mutation.enabled=true
  QUANDO x-test-mutation roda
  ENTÃO skill emite WARN "no language declared — skipping mutation" e exit 0
  E plano gera entry "skipped — undetectable stack"
  E NÃO bloqueia merge

Cenario: Error — score abaixo do threshold bloqueia
  DADO quality.mutation.threshold=80
  E PR atinge score 72%
  QUANDO x-test-mutation roda
  ENTÃO skill exit non-zero MUTATION_SCORE_BELOW_THRESHOLD
  E reporta os top-20 sobreviventes com classe/método/linha

Cenario: Boundary — runtime-cap excedido aborta com sinal claro
  DADO quality.mutation.runtime-cap-min=10 e PIT estimado em 25 min
  QUANDO x-test-mutation roda
  ENTÃO skill aborta após 10 min com exit non-zero MUTATION_RUNTIME_CAP_EXCEEDED
  E reporta nome dos packages que ainda faltavam
  E sugere subir cap ou reduzir escopo via mutation.exclude-packages
```

## 6. Decision Rationale

**Decisão:** Threshold default 80% (não 90%, não 100%). **Motivo:** 100% é irreal e drena tempo; 90% gera alta taxa de false-positive (mutações equivalentes que não há como matar sem refactor estrutural); 80% é o sweet-spot industry — PIT ships com 80% como default, Stryker com 80%. **Alternativa descartada:** 90% — rejeitado pelo histórico de força bruta documentado no PIT changelog (≥ 50% das mutações sobreviventes em projetos saudáveis são equivalent mutants ou test-quality). **Consequência:** projetos críticos (módulos de domínio com regras de negócio densas) podem subir o threshold via `thresholds.per-package` — feature documentada mas opcional. **Consequência adicional:** Rule 05 ganha um segundo threshold de quality (cobertura + mutation) — modelagem in-place via D-R3 (sem Rule número novo).

## 7. Refinement Notes (consolidadas)

- **Runtime cap (mutation testing é caro):** 20 min cap default protege CI de timeouts. Tooling como PIT permite `--mutationUnitSize` para limitar escopo; Stryker tem `concurrency`. Cap exceeded ⇒ abort com sinal claro (não silent-skip).
- **Exclusões idiomáticas:** test/generated/adapter excluídos por default para evitar ruído. Domain/application sempre incluídos.
- **Integração com Rule 05:** D-R3 — Rule 05 ganha §"Mutation Score Threshold" in-place. Não criar Rule NN nova. Audit `audit-mutation-score.sh` (story-0072-0006) é o gate operacional.
- **Stage policy (warn primeiro release, fail no segundo):** documentado em CHANGELOG do epic 0009 — `quality.mutation.enabled=true` no primeiro release emite WARN apenas; segundo release vira FAIL. Mitiga adoção brusca.
