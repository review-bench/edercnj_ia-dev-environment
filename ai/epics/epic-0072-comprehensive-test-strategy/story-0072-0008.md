# História: Phase 3 de `x-story-implement` MODIFIED — invocação MANDATORY conditional dos 3 testes

**ID:** story-0072-0008
**Status:** Refinada

## 1. Visão

Como **developer on a generated project**, quero que `Phase 3` de `x-story-implement` invoque `/x-test-performance`, `/x-test-mutation`, `/x-test-contract` como **MANDATORY conditional** (Rule 24 §Non-inlining Contract):
1. **MANDATORY** quando `quality.<sub>.enabled=true` no YAML do projeto.
2. **No-op com WARN** quando `quality.<sub>.enabled=false`.
3. Sequência: **perf → mutation → contract** (D-R11; *fast-fail* — se perf reprovou, cancela mutation/contract; reduz custo em CI).
4. Cada falha mapeia para código específico (`PERF_REGRESSION_DETECTED` / `MUTATION_SCORE_BELOW_THRESHOLD` / `CONTRACT_BREAKING_CHANGE`) propagado pelo orquestrador.
5. Atualizar Rule 24 §Mandatory Evidence Artifacts adicionando os 3 novos relatórios (`perf-report-STORY-ID.md`, `mutation-report-STORY-ID.md`, `contract-report-STORY-ID.md`) como artefatos exigidos quando o gate correspondente está ativo.

…porque sem este modify, as 3 skills das stories 0002/0003/0004 ficam disponíveis mas não são acionadas pelo orquestrador — gates ficam decorativos.

## 2. Entrega de Valor

- **Valor primário:** Production defect rate from untested quality dimensions drops measurably because PRs are blocked when performance regresses, mutations survive, or API contracts break — defects that previously reached `develop` undetected are now caught at the story-implement gate.
- **Valor secundário:** Projects inherit the behavior automatically via YAML opt-in — developers do not need to remember manual invocations.
- **Métrica de execução:** 100% dos PRs em projetos com `quality.X.enabled=true` passam pelas 3 skills (medido por `events.ndjson` — toda execução de `x-story-implement` deve emitir 3 `tool.call` para `x-test-{performance,mutation,contract}` quando enabled).
- **Métrica de resultado:** Number of post-merge quality regressions (performance, mutation survivorship, contract breakage) per release drops to zero for projects with `quality.*.enabled=true`. **Unit:** regression count per release. **Target:** 0. **Measurement:** compare `PERF_REGRESSION_DETECTED` / `MUTATION_SCORE_BELOW_THRESHOLD` / `CONTRACT_BREAKING_CHANGE` exit events in `events.ndjson` (gate-caught) against post-merge defect reports (escaped). Baseline: first release with gates active.

## 4. Typed Contracts

### 4.1 QualityConfig Java Record

```java
public record QualityConfig(
    QualitySubConfig performance,
    QualitySubConfig mutation,
    QualitySubConfig contract
) {
    /** Returns a no-op config where all gates are disabled. */
    public static QualityConfig disabled() {
        return new QualityConfig(
            QualitySubConfig.disabled(),
            QualitySubConfig.disabled(),
            QualitySubConfig.disabled()
        );
    }
}

public record QualitySubConfig(
    boolean enabled,
    Map<String, Object> params
) {
    public static QualitySubConfig disabled() {
        return new QualitySubConfig(false, Map.of());
    }
}
```

- Source: parsed from project YAML `quality:` block by `QualityConfigParser`.
- Validation: `params` values are validated for type safety (boolean fields must be boolean, paths must pass `Path.normalize().startsWith(base)` check). Invalid values cause `OPERATIONAL_ERROR` (exit 2).

## 6. Risks

### Technical Risks

| # | Risk | Impact | Likelihood | Mitigation |
| :--- | :--- | :--- | :--- | :--- |
| T1 | **Flaky perf baseline false-positive** — performance baselines are environment-sensitive; CI runners with noisy neighbors produce jitter, triggering `PERF_REGRESSION_DETECTED` on unchanged code | HIGH — blocks legitimate PRs; erodes trust in gate | MEDIUM | Use percentile-based tolerance (p95 with configurable `tolerance_pct` in `quality.performance.params`); require 2 consecutive failures before hard block; document warm-up iteration count |
| T2 | **Mutation test duration blocks pipeline** — PIT/pitest on large codebases can run 10-30 minutes, blocking CI and developer flow | MEDIUM — slows feedback loop | HIGH | Scope mutation to changed files only (`quality.mutation.params.scope=diff`); set wall-clock timeout per gate (default 5min); fast-fail ordering (perf first) means mutation only runs on perf-clean code |
| T3 | **Backward compat for projects without `quality.*` config** — generated projects pre-EPIC-0072 have no `quality:` YAML block; Phase 3 must degrade gracefully | HIGH — would break all existing projects | LOW | `QualityConfig.disabled()` factory returns all-disabled config when YAML block absent; no new behavior for legacy projects; zero behavioral change on `flowVersion < 4` |
| T4 | **Exit code collision with existing orchestrator codes** — codes 14/17/18 must not collide with Rule 20 (15=WORKTREE_AMBIGUOUS), Rule 25 (12=PHASE_GATE_FAILED), Rule 45 (10-70 range) | HIGH — dispatch logic breaks silently | LOW | Verified against existing code tables in Rules 20/24/25/27/45; documented in §4.2; CI lint `audit-exit-code-collisions.sh` proposed for EPIC-0072-0009 |
| T5 | **Phase 3 ordering change breaks telemetry phase markers** — inserting 3 new sub-phases (Phase-3-Quality-Perf/Mutation/Contract) into existing Phase 3 may confuse `/x-telemetry-analyze` consumers | MEDIUM — Gantt charts misrender | LOW | Use sub-phase naming convention (Phase-3-Quality-*) distinct from existing Phase-3 marker; update `TelemetryMarkerLint` to recognize compound phase IDs |

### Product Risks

| # | Risk | Impact | Likelihood | Mitigation |
| :--- | :--- | :--- | :--- | :--- |
| P1 | **Adoption friction** — developers enabling `quality.performance.enabled=true` for the first time encounter unexpected blocking on existing code that never had perf baselines | MEDIUM — frustration, rollback | MEDIUM | First execution with no existing baseline produces WARN, not FAIL (establishes baseline); subsequent runs compare against it; document in generated project README |

## 8. Decision Rationale

**Decisão:** Conditional via YAML (`quality.<sub>.enabled=true`), NÃO sempre-on. **Motivo:** projetos sem SLA (CLI internos, ferramentas de devops, scripts) não devem ser forçados a manter baseline de performance ou rodar mutation testing (caro). Opt-in declarativo respeita a heterogeneidade dos projetos cliente. **Alternativa descartada:** sempre-on com `--skip-perf`/`--skip-mutation`/`--skip-contract` flags — rejeitado por (a) viola Rule 24 §Forbidden (`--skip-*` outside `## Recovery` é violation); (b) opt-out via flag é frágil (pode ser esquecido), opt-in via YAML é explícito. **Consequência:** Rule 24 §Mandatory Evidence Artifacts ganha 3 entries condicionais (artefato exigido SE gate enabled).

**Decisão complementar:** Sequência sequencial perf → mutation → contract (D-R11). **Motivo:** (a) mutation drena CPU e gera jitter no perf p95 — paralelizar invalida medição; (b) fast-fail reduz custo em CI quando uma falha; (c) ordering reflete custo crescente (perf é segundos, mutation é minutos, contract é segundos — perf primeiro é o "smoke fast"); (d) abort-code mapping é trivial (1 falha por etapa).
