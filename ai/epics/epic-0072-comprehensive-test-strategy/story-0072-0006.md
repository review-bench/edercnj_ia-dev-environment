## 1. Visão

Como **CI guardian**, quero:
1. CI script `audit-mutation-score.sh` (Camada 2 — Rule 26) que verifica que mutation score atual do PR atinge `quality.mutation.threshold` declarado E não regrediu vs `governance/baselines/mutation-baseline.json`.
2. Extensão **in-place** de `targets/claude/rules/05-quality-gates.md` adicionando §"Mutation Score Threshold" e §"Performance Budget" (D-R3) — coverage + mutation viram **gate combinado**, não dois gates separados.

…porque cobertura ≥95% sem mutation testing é gate falso (§1.1 Lacuna 2 do epic). A Rule 05 já é o lugar canônico de quality gates — agrupar mutation lá evita drift entre Rule 05 e uma hipotética "Rule NN — quality-extended".

## 2. Entrega de Valor

- **Valor primário:** Camada 2 + Rule 05 fortalecidas; gate de cobertura + mutation passa a ser combinado (RULE-005-01 absolute-gate aplica a ambos).
- **Valor secundário:** mantenedor lê uma única Rule (05) para entender quality gates; sem fragmentação.
- **Métrica:** zero PRs com mutation score < threshold mergeados pós-rollout (medido por audit hits + revert rate).

## 3. Acceptance Criteria (Gherkin — 4 categorias mandatórias)

```gherkin
Cenario: Happy — score ≥ threshold + sem regressão
  DADO baseline 82% e PR atinge 85%
  E quality.mutation.threshold=80
  QUANDO audit-mutation-score.sh roda
  ENTÃO exit 0 (OK)

Cenario: Degenerate — primeiro run em projeto novo
  DADO governance/baselines/mutation-baseline.json não existe e quality.mutation.enabled=true
  E PR atinge score 78% (< threshold default 80%)
  QUANDO audit-mutation-score.sh roda no primeiro release pós-rollout
  ENTÃO exit 0 com WARN "first release — score below threshold tolerated for one cycle" (stage policy: WARN→FAIL — D-R3 §Stage Policy)
  E baseline é criada com score atual

Cenario: Error — score abaixo do threshold absoluto bloqueia
  DADO threshold=80 e PR atinge 72%
  QUANDO audit-mutation-score.sh roda no segundo release+ pós-rollout
  ENTÃO exit 1 (MUTATION_SCORE_VIOLATION) com mensagem "score 72% below threshold 80%"
  E reporta delta vs baseline (regressão? estabilidade?)

Cenario: Boundary — regression vs baseline com score acima do threshold
  DADO baseline 90%, PR atinge 82% (acima do threshold mas regrediu 8%)
  E quality.mutation.regression-tolerance-pct=5 (declarado no YAML)
  QUANDO audit-mutation-score.sh roda
  ENTÃO exit 1 (MUTATION_REGRESSION) com mensagem "regressão 8% > tolerance 5%"
  E reporta os top-20 mutações sobreviventes novas (presentes no PR, ausentes no baseline)
```

## 6. Decision Rationale

**Decisão:** Rule 05 ganha 2º + 3º thresholds (mutation + perf-budget) **in-place**; **NÃO** criar Rule número novo (D-R3). **Motivo:** Rule 05 já é o gate de quality (cobertura); agrupar mutation + perf-budget ali mantém o operador num só lugar, evita drift entre regras. RA8 (Rule 05) é mutável; não é Rule de protocolo (13/22/24/27) que é congelada por contrato. **Alternativa descartada:** criar Rule NN nova "quality-extended" — rejeitado por (a) viola "agrupar quality num só lugar"; (b) cria precedente perigoso (cada gate novo = nova Rule); (c) consume slot de Rule número que pode ser necessário para Rules de protocolo no futuro. **Consequência:** Rule 05 cresce ~80 linhas; CHANGELOG marca a extensão; toda referência a "quality gate" continua apontando para Rule 05.

## 7. Refinement Notes (consolidadas)

- **Tolerance de regression vs threshold absoluto:** os dois coexistem. Threshold absoluto = piso (não pode descer). Tolerance = vagal de stability (mesmo acima do piso, regressão > tolerance bloqueia).
- **Exclusões idiomáticas (legacy code, generated):** definidas pela skill `x-test-mutation` (story-0072-0003) — este audit consome o relatório, não decide escopo.
- **Stage policy WARN→FAIL:** `governance/baselines/mutation-baseline.json` carrega campo `release_count` que incrementa a cada release tagged em `main`; primeiro release com `enabled=true` é WARN (release_count=0→1), segundo+ é FAIL.
- **Integração com Rule 05:** D-R3 — a extensão in-place documenta 2 thresholds (cobertura existente + mutation NOVO) + 1 gate budget (perf — story-0072-0005 documenta separadamente como "Camada 2", aqui só o thresholds-na-Rule). RULE-005-01 (absolute-gate) aplica a ambos.
