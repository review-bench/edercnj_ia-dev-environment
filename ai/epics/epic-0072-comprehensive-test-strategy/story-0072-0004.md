# História: Skill `/x-test-contract` (stack-aware: openapi-diff/Pact/buf/SCC) + `_TEMPLATE-CONTRACT-PLAN.md` + KP

**ID:** story-0072-0004
**Status:** Pendente
**Refinement Verdict:** approved

## 1. Visão

Como **developer on a generated project**, quero uma skill stack-aware `/x-test-contract` que:
1. Detecta `interfaces[].type` + `framework` (REST/OpenAPI → openapi-diff; gRPC/proto3 → buf breaking; Spring Boot → Spring Cloud Contract; eventos → schema registry compat check).
2. Compara contrato (openapi.yaml / *.proto / *.avsc) na branch base vs PR.
3. Reporta breaking changes com classificação (campo removido, tipo trocado, enum value removido, etc.).
4. Bloqueia merge quando breaking change detectado, exceto se PR documenta migração via CHANGELOG/`_TEMPLATE-CHANGELOG-ENTRY.md` (integração com EPIC-0071 — Doc-as-DoD).
5. Pact é **opt-in** via `quality.contract.pact=true` — runtime contract negotiation requer infra (broker) + co-design entre teams; default off.

...so that contract breaking changes are detected pre-merge and never surface as consumer bugs in production (epic section 1.1 Gap 3). Contract testing pre-merge is the only deterministic gate for API/proto/event-schema compatibility.

## 2. Entrega de Valor

- **Valor primário:** breaking changes em API contracts detectados pré-merge (REST/proto/event), deixam de surgir como reclamação do consumer em produção.
- **Valor secundário:** projetos cliente herdam openapi-diff + buf breaking sem decidir entre ferramentas; Pact fica disponível mas opt-in para teams maduras.
- **Métrica primária:** number of contract-breaking PRs merged without CHANGELOG documentation drops to 0 within 30 days of rollout (measured by `audit-contract-breaking.sh` exit code on merged PRs).
- **Métrica secundária:** skill execution time p95 < 30 seconds for single-contract comparison (measured via telemetry NDJSON phase.end - phase.start delta).
- **Métrica de qualidade:** false-positive rate (PRs flagged as breaking that are actually compatible) < 5% over first 60 days (measured by operator override count in contract reports).

## 6. Decision Rationale

**Decisão:** openapi-diff e buf breaking **sempre on** (quando há `openapi.yaml`/`*.proto`); Pact **opt-in** via `quality.contract.pact=true`. **Motivo:** openapi-diff/buf são leitura local + zero infra (apenas binário no PATH ou container) — adoção sem fricção. Pact requer broker, co-design entre teams, processo de versioning negociado — alto custo de adoção. **Alternativa descartada:** Pact default-on — rejeitado por barreira de adoção; teams pequenas seriam forçadas a manter um broker. **Consequência:** Pact disponível para teams maduras que já têm infra; default-off mantém o épico aplicável a 90% dos projetos. **Consequência adicional:** false-positive em refactors compatíveis (renomear campo + adicionar deprecation) é tratado pela integração com CHANGELOG (Cenario Boundary): breaking documentado passa com WARN, breaking não-documentado bloqueia.

### Alternatives Considered

| # | Alternative | Verdict | Rationale |
|---|------------|---------|-----------|
| 1 | **Schema Registry as single source of truth** — rely exclusively on Confluent Schema Registry compatibility modes (BACKWARD, FORWARD, FULL) for all contract types, not just events | Rejected | Only covers Avro/Protobuf/JSON-Schema registered in a schema registry. REST OpenAPI contracts and gRPC `.proto` files used without a registry would be uncovered. Forces infrastructure dependency (running registry) on all projects regardless of stack. |
| 2 | **Pact default-on for all projects** | Rejected | Pact requires broker infrastructure, co-design between consumer/provider teams, and ongoing negotiation. High adoption barrier for small teams; 90% of projects would never configure the broker. |
| 3 | **buf lint + buf breaking as separate invocations** — split proto validation into two distinct skill phases | Rejected | `buf breaking` is the core contract check (detects incompatible changes). `buf lint` is a style/hygiene check orthogonal to contract compatibility. Combining them in one phase conflates concerns. Decision: `x-test-contract` invokes only `buf breaking` for contract compatibility; `buf lint` belongs in `x-code-lint` (style layer, not contract layer). |
| 4 | **openapi-diff + buf + SCC per-format tools (chosen)** | Accepted | Each tool is best-in-class for its format. Local execution, zero infrastructure. Stack-aware capability resolution ensures only relevant tools activate. CHANGELOG integration provides documented-breaking escape hatch. |

### Skill Exit Codes

| Exit | Code | Condition |
|------|------|-----------|
| 0 | `SUCCESS` | No breaking changes detected, or breaking change documented in CHANGELOG |
| 1 | `CONTRACT_BREAKING_CHANGE` | Breaking change detected without CHANGELOG documentation |
| 2 | `OPERATIONAL_ERROR` | Tool not found on PATH, invalid configuration, file read failure |
| 3 | `CONTRACT_ARTIFACT_INVALID` | Contract file exists but is malformed (unparseable YAML/proto/avsc) |

### Report Schema (`contract-report-STORY-ID.md`)

Output path: `ai/epics/epic-XXXX/reports/contract-report-STORY-ID.md`

| Section | Content |
|---------|---------|
| `## Summary` | Overall verdict (PASS/FAIL/WARN), tool used, execution time |
| `## Changes Detected` | Table: field, change-type (ADDED/REMOVED/TYPE_CHANGED/ENUM_VALUE_REMOVED/NULLABLE_CHANGED/DEFAULT_CHANGED), severity (BREAKING/NON_BREAKING), location |
| `## CHANGELOG Integration` | Whether CHANGELOG "## Breaking" entry was found; regex match details |
| `## Recommendations` | Migration guidance for breaking changes |

### CHANGELOG Detection Regex

The skill detects documented breaking changes via the following regex applied to `CHANGELOG.md` diff in the PR:

```regex
^##\s+(Breaking(\s+Changes?)?|BREAKING)\s*$
```

This matches: `## Breaking`, `## Breaking Change`, `## Breaking Changes`, `## BREAKING`. When EPIC-0071 delivers `_TEMPLATE-CHANGELOG-ENTRY.md`, the detection migrates to `Skill(skill: "x-changelog-validate")` invocation.

### SCC Stub-Repository Guard

When `quality.contract.scc=true` and `scc.stub-repository-url` is absent or unreachable:
- Skill emits WARN: `"SCC stub repository not configured or unreachable — skipping Spring Cloud Contract verification"`
- Exit 0 (fail-open) — does not block merge for missing infrastructure
- Report records `scc_skipped` with reason

## 7. Risks

### Technical Risks

| # | Risk | Likelihood | Impact | Mitigation |
|---|------|-----------|--------|------------|
| T1 | **Tool version drift** — openapi-diff, buf, or SCC binary on developer PATH is incompatible with skill expectations | Medium | Medium | Skill validates tool version at startup (`openapi-diff --version`, `buf --version`). Minimum versions declared in `ContractConfig`. Mismatch → exit 2 `OPERATIONAL_ERROR` with actionable message. |
| T2 | **SCC stub-repository missing** — Spring Cloud Contract requires a stub repository that may not exist for new projects | High | Low | Fail-open guard (see §6.1): skill skips SCC check with WARN when stub repo is absent. No merge block. |
| T3 | **EPIC-0071 delay** — `_TEMPLATE-CHANGELOG-ENTRY.md` and `x-changelog-validate` not available at implementation time | Medium | Low | Skill uses local regex detection for CHANGELOG "## Breaking" entries (self-contained). Future-wired integration documented in KP; skill migrates to Skill invocation when 0071 merges. No functional dependency on 0071 for story completion. |
| T4 | **Supply-chain binary risk** — openapi-diff and buf are external binaries executed via Bash | Low | High | Skill does NOT download binaries at runtime. Binaries must be pre-installed on PATH (developer responsibility). Skill validates binary exists and version matches before execution. No network calls to fetch tooling. |
| T5 | **False-positive rate exceeds target** — aggressive breaking-change classification flags compatible refactors | Medium | Medium | CHANGELOG integration provides escape hatch. Operator override count tracked in contract reports. Classification rules documented in KP and reviewable by tech lead before activation (DoR item). |

### Product Risks

| # | Risk | Likelihood | Impact | Mitigation |
|---|------|-----------|--------|------------|
| P1 | **CHANGELOG bypass abuse** — developers document fake "## Breaking" entries to pass the gate without actual migration paths | Low | High | `audit-contract-breaking.sh` (story-0072-0007) cross-validates CHANGELOG entry content against actual breaking changes. Empty or boilerplate entries flagged. Tech-lead review gate on PRs with WARN exits. |
| P2 | **Schema registry auth** — event contract checks require authenticated schema registry access that varies per environment | Medium | Medium | Fail-open on auth failure (security scenario). No credentials stored in skill config. Auth delegated to environment variables (`SCHEMA_REGISTRY_USER`, `SCHEMA_REGISTRY_PASSWORD`). |

## 8. Refinement Notes (consolidadas)

- **Políticas de versioning (semver-aware):** quando contrato declara versão (openapi `info.version: 2.0.0`), bump MAJOR no contrato + CHANGELOG entry "## Breaking" satisfaz o gate. Bump MINOR/PATCH com breaking change continua bloqueando.
- **Integração com OpenAPI sync (EPIC-0071):** quando 0071 entregar `_TEMPLATE-CHANGELOG-ENTRY.md` + audit `audit-changelog-presence.sh`, integração migra de regex local para invocação Skill (`x-changelog-validate`). Documentado como "future-wired" no KP.
- **False-positive em refactors compatíveis:** rename com deprecation marker é categorizado como breaking; CHANGELOG documenta a migração; gate passa com WARN. Reduz fricção sem perder o sinal.
- **Schema registry compat check (eventos):** skill consulta `quality.contract.events.{schema-registry-url, subject-name-strategy}`; se não declarado, gate passa com WARN.
