## 6. Decision Rationale

**Decisão:** Schema agrupado sob `quality:` top-level (não 3 chaves top-level separadas). **Motivo:** evita YAML explosion no `ProjectConfig`; mantém os 3 sub-blocos próximos semanticamente (todos são "quality gates"); facilita iteração (operador lê uma seção, não três espalhadas). **Alternativa descartada:** 3 sub-blocos top-level (`performance:`, `mutation:`, `contract:`) — rejeitado por (a) cada uma seria "uma chave a mais no nível raiz" complicando o schema YAML; (b) drift entre as 3 inevitável quando alguma evoluir. **Consequência:** futuras dimensões de quality (chaos, fuzz, property) entram como `quality.<sub>:` sem novo top-level.

## 7. Refinement Notes (consolidadas)

- **Granularidade SLO per-endpoint vs global:** SLO global por `interfaces[].type` (ex.: `quality.performance.slo.rest.p95_ms` aplica-se a TODOS endpoints REST). Per-endpoint via override `quality.performance.slo.per-endpoint: { "/api/v1/users": { p95_ms: 100 } }` — feature opcional, ENTREGUE EM EPIC FUTURO (não escopo desta story).
- **Defaults sãos por stack:** REST p95=200ms, gRPC p95=100ms, CLI gen-time-p95=3000ms (já no §1.3 do epic); mutation threshold=80; contract.openapi-breaking=true / pact=false. Bloco ausente ⇒ todos os `enabled=false` (Rule 19 backward-compat — projetos legados não quebram).
- **Integração com EPIC-0073 (regression+DAST):** EPIC-0073 também desce sob `quality.*` (`quality.regression.*`, `quality.security.*`). Nomenclatura compatível por design — schema desta story permite extensão.
