## 1. Contexto & Escopo

Como **Auditor de Compliance**, eu quero auditar os *fan-outs paralelos* (Rule 13 Pattern 2 — múltiplos `Agent(...)` siblings em uma única mensagem do orquestrador) garantindo que **todos** os N agents declarados foram realmente lançados, não somente um subset que o LLM decidiu invocar.

Hoje `x-review` declara 8 sub-reviewers paralelos (qa, perf, devops, security, observability, db, api, event) e `x-internal-story-build-plan` declara 5 agents (impl, tests, tasks, security, compliance). O audit telemetry de Rule 24 valida apenas que `x-review` foi invocado (parent skill), **não** que os 8 children foram lançados. LLM pode emitir só 1-2 agents e sumarizar o restante — comportamento que não é detectável por `audit-execution-integrity.sh --scope=telemetry` atual.

Esta história introduz `audit-wave-dispatch.sh` que cruza:

- **Declaração estática** — extrai do SKILL.md o conjunto canônico de agents/sub-skills esperados em cada wave (parsing de blocos `## Phase N — Batch A` ou markers explícitos).
- **Execução real** — conta eventos `agent.start` ou `tool.call subagent_type=...` no NDJSON dentro da janela do parent skill.

Wave matching é por **subject prefix** (Rule 25 §3): para `x-review` da story-XXXX-YYYY, espera 8 eventos `agent.start` com `subject` matching `^story-XXXX-YYYY › Review › (qa|perf|devops|security|observability|db|api|event)$`.

Inclusão na declaração estática vem de duas fontes possíveis:

1. **Marker `## Wave: <name>`** dentro de phase, listando explicitamente os children:
   ```markdown
   ### Wave: specialist-review
   - x-review-qa
   - x-review-perf
   - x-review-devops
   - x-review-security
   - x-review-observability
   - x-review-db
   - x-review-api
   - x-review-event
   ```
2. **Heurística** — múltiplos `Agent(...)` siblings em uma única mensagem do orquestrador documentada via Rule 13 Pattern 2 são contados como wave.

Quando uma wave declarada tem N members e o NDJSON tem M < N eventos matching, audit retorna `WAVE_DISPATCH_INCOMPLETE` (exit 1) listando os children ausentes.

Esta história também adiciona Rule 13 §Wave Convention (extension) formalizando o marker `### Wave:` como contrato.

## 3. Contratos & Endpoints

### 3.1 Wave marker grammar

```markdown
### Wave: <wave-name>
- <skill-or-agent-name>
- <skill-or-agent-name>
...
```

Marker DEVE aparecer dentro de uma `## Phase N` section. Múltiplas waves por phase permitidas (e.g., specialist-review + observability-review). `<wave-name>` é regex `[a-z][a-z0-9-]+`.

### 3.2 audit-wave-dispatch.sh contract

| Campo | Tipo | M/O | Validações | Exemplo |
| :--- | :--- | :--- | :--- | :--- |
| `--mode` | enum `static\|dynamic\|both` | M | — | `--mode=both` |
| `--story-id` | regex | O (M se dynamic) | strict | `--story-id=0063-0014` |
| `--epic-id` | regex | O | — | `--epic-id=0063` |
| `--skills-root` | path | O | default `java/src/main/resources/targets/claude/skills/` | — |
| `--self-check` | flag | O | — | — |

### 3.3 Exit codes

| Exit | Code | Condição |
| :--- | :--- | :--- |
| 0 | `OK` | Todas waves completas |
| 1 | `WAVE_DISPATCH_INCOMPLETE` | M < N eventos para alguma wave declarada `[required]`-equivalente |
| 2 | `WAVE_MARKER_MALFORMED` | Marker inválido em SKILL.md |
| 3 | `WAVE_TELEMETRY_AMBIGUOUS` | Múltiplas waves overlapping no NDJSON sem distinção |
| 4 | `INVALID_ARGS` | argv malformado |

### 3.4 Static check

Para cada SKILL.md sob `--skills-root`:

1. Localizar todas seções `### Wave: <name>`.
2. Validar marker (regex §3.1).
3. Listar items da wave.
4. Cruzar com Rule 23 (model selection) — agents na wave devem ter model declarado.

### 3.5 Dynamic check

Para a story-id passada:

1. Ler `events.ndjson` via PathResolver.
2. Para cada wave declarada no orquestrador chamado: contar eventos `agent.start` ou `tool.call` matching subject prefix da wave dentro da janela temporal do parent skill (de `phase.start` até `phase.end`).
3. Se count < N → exit 1 com lista de children ausentes.
4. Se count > N → log INFO (extra agent dispatched, não falha).

### 3.6 Baseline

Skills pré-EPIC-0063 sem wave marker são grandfathered via `audits/wave-dispatch-baseline.txt`. Imutável após merge.

## 8. Decision Rationale

**Decisão:** Marker explícito `### Wave:` ao invés de inferir de Rule 13 Pattern 2 (múltiplos Agent siblings).
**Motivo:** Heurística-só introduz ambiguidade — quantos siblings bastam para virar wave? Marker explícito é determinístico.
**Alternativa descartada:** Inferir de blocos de código com múltiplos `Agent(...)`. Rejeitado por fragilidade (espaço em branco, comentários quebram).
**Consequência:** Skill author precisa declarar marker. Custo único por skill com fan-out.

**Decisão:** Janela temporal definida pelo phase boundary (Rule 25 phase-gate eventos).
**Motivo:** Phase eventos já existem; reutilização é zero-custo.
**Alternativa descartada:** Janela fixa de 60s. Rejeitado por waves longas.
**Consequência:** Wave audit depende de Rule 25 task hierarchy ativo (`taskTracking.enabled=true`). Falha gracefully em legacy epics (skipped).
