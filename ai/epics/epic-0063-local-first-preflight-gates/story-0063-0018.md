## 1. Contexto & Escopo

Como **Operations Engineer**, eu quero que cada `.claude/hooks/*.sh` tenha um modo `--self-check` que valida pré-condições do hook (fonte presente, dependências disponíveis, hook registrado em settings.json) — análogo ao contrato Rule 26 que já vale para `audit-*.sh` —, e que `verify-hooks-integrity.sh` rode esses self-checks em CI, garantindo que **hook quebrado = bypass detectado**, não silente.

Hoje Rule 26 exige `--self-check` para audit scripts. Hooks (`stage-telemetry.sh`, `enforce-preflight-gates.sh`, `verify-story-completion.sh`, `verify-phase-gates.sh`, `enforce-phase-sequence.sh`) **não têm contrato análogo**. Resultado: hook que silenciosamente para de funcionar (binário ausente, jq quebrado, regex que não casa, settings.json desregistrou) vira bypass invisível. Isso é particularmente perigoso para hooks fail-CLOSED (Rule 005 do épico): se o hook é o gate, o gate pode estar vazio sem ninguém perceber.

A história introduz:

1. **Convenção `--self-check` para hooks** — extensão da Rule 26 (§Hooks Self-Check). Cada hook deve responder a `--self-check` mesmo não sendo seu modo de invocação principal (Claude Code passa JSON via stdin, não argv). Convenção: hook detecta se primeiro arg é `--self-check` e bypass-a o stdin reading. Exit 0 / 1 / 2 conforme schema.
2. **Auditor consolidado** — `scripts/verify-hooks-integrity.sh` itera sobre `.claude/settings.json` registered hooks, invoca cada `--self-check`, e produz relatório consolidado. Falha se qualquer hook falhar self-check.
3. **CI gate** — `verify-hooks-integrity.sh` roda em CI no `audit.yml` workflow + invocação local pelo `preflight.sh` como gate 9. Hook quebrado bloqueia o release.

Pré-condições mínimas que cada self-check verifica:

| Hook | Pré-condições self-check |
| :--- | :--- |
| `stage-telemetry.sh` | git presente, telemetry-lib.sh source-able, write access em `.claude/` |
| `enforce-preflight-gates.sh` | preflight.sh presente + executável, jq presente, telemetry-lib presente, settings.json registra este hook em PreToolUse |
| `enforce-preflight-gates.sh` (extended v2) | matchers v2 carregáveis, vector catalog em sync com `docs/preflight-bypass-vectors.md` |
| `verify-story-completion.sh` | git, jq, plans/epic-* path resolver, settings.json registra Stop event |
| `verify-phase-gates.sh` | execution-state.json schema válido, x-internal-phase-gate disponível |
| `enforce-phase-sequence.sh` | mesmos de verify-phase-gates |

## 3. Contratos & Endpoints

### 3.1 Hook self-check protocol

```bash
#!/usr/bin/env bash
set -euo pipefail

if [[ "${1:-}" == "--self-check" ]]; then
  # 1. Check binary deps
  command -v jq >/dev/null 2>&1 || { echo "MISSING_DEP: jq" >&2; exit 1; }
  # 2. Check related files
  [[ -x scripts/preflight.sh ]] || { echo "MISSING_FILE: scripts/preflight.sh" >&2; exit 1; }
  # 3. Check hook is registered in settings.json
  if ! jq -e '.hooks.PreToolUse[]? | select(.hooks[]?.command == "...")' .claude/settings.json >/dev/null; then
    echo "HOOK_NOT_REGISTERED: PreToolUse" >&2
    exit 2
  fi
  echo "OK"
  exit 0
fi

# normal hook flow reads stdin
...
```

### 3.2 Self-check exit codes (per hook)

| Exit | Code | Condição |
| :--- | :--- | :--- |
| 0 | `OK` | Pré-condições verdes |
| 1 | `HOOK_DEPENDENCY_MISSING` | jq, git, ou outro binário ausente |
| 2 | `HOOK_NOT_REGISTERED` | hook não consta em `.claude/settings.json` |
| 3 | `HOOK_CONFIG_DRIFT` | settings.json registra hook mas com path diferente |

### 3.3 verify-hooks-integrity.sh contract

| Campo | Tipo | M/O | Validações | Exemplo |
| :--- | :--- | :--- | :--- | :--- |
| `--mode` | enum `summary\|verbose\|json` | O | default summary | `--mode=verbose` |
| `--settings` | path | O | default `.claude/settings.json` | — |
| `--self-check` | flag | O | recursivo — checa o auditor próprio | — |

### 3.4 verify-hooks-integrity exit codes

| Exit | Code | Condição |
| :--- | :--- | :--- |
| 0 | `OK` | Todos hooks verdes |
| 1 | `HOOKS_INTEGRITY_FAILED` | ≥1 hook falhou self-check |
| 2 | `SETTINGS_MALFORMED` | settings.json inválido |
| 3 | `HOOK_SELF_CHECK_MISSING` | hook registrado mas não suporta `--self-check` |

## 8. Decision Rationale

**Decisão:** `--self-check` como primeiro arg detectado antes de stdin read.
**Motivo:** Hooks Claude Code recebem JSON via stdin; CLI invocation precisa de path alternativo para validação. Detectar arg primeiro é simples.
**Alternativa descartada:** Hook separado `<name>-self-check.sh`. Rejeitado por duplicação.
**Consequência:** Cada hook tem ~10 linhas de boilerplate self-check. Aceito (DRY via `hooks/lib/self-check-helpers.sh`).

**Decisão:** Auditor consolidado (`verify-hooks-integrity.sh`) ao invés de N audits separados.
**Motivo:** Operador quer visão única "todos hooks OK?" — N audits separados poluem CI.
**Alternativa descartada:** Um audit por hook. Rejeitado.
**Consequência:** verify-hooks-integrity precisa parsear settings.json — sem grande complexidade dado jq disponível.
