## 1. Contexto & Escopo

Como **Compliance Officer**, eu quero um documento `docs/audit-bypass-catalog.md` listando para cada uma das 11 skills bypassáveis: nome, tipo de evidência hoje (file/telemetry/both), padrão de bypass observado ou possível, e plano de blindagem (FR17 do SPEC, AC10 do épico).

A causa raiz do EPIC-0062 demonstrou: bypass não é uma vulnerabilidade isolada — é uma **classe** de problema que afeta múltiplas skills. Cada skill que produz evidência file-based pode ter o mesmo problema de stub. Sem catalogar sistematicamente, vamos descobrir bypasses one-by-one ad hoc.

A história produz um documento estruturado com 11 entries (tabela ou subsection per skill). Cada entry tem 4 campos:

1. **Nome da skill**
2. **Tipo de evidência hoje:** `file` (apenas markdown/json) | `telemetry` (apenas NDJSON) | `both`
3. **Padrão de bypass observado/possível:** descrição concreta (ex: "review com 2 linhas e Verdict: GO")
4. **Plano de blindagem:** ação concreta (ex: "audit content (story-0063-0002) + audit telemetry (story-0063-0003)")

As 11 skills mínimas (FR17):
1. `x-review` — content + telemetry
2. `x-review-pr` — content + telemetry
3. `x-internal-story-verify` — schema + telemetry
4. `x-dependency-audit` — output validation (real `mvn dependency:analyze` output)
5. `x-arch-plan` — schema + telemetry (when scope=STANDARD+)
6. `x-test-tdd` — commit-order audit (test-first)
7. `x-task-plan` — exists per task before x-task-implement
8. `x-threat-model` — required for stories tocando auth/network/persistence
9. `x-test-run` — JaCoCo report committable
10. `x-spec-drift` — periodic gate
11. `x-code-audit` — release branch gate

O documento NÃO implementa as blindagens (essas são EPICs futuros). Esta história APENAS catalogue + plan. Saída é input para roadmap de governance subsequente.

## 8. Decision Rationale

**Decisão:** Catalog APENAS lista 11 skills da FR17 (não tenta ser exaustivo).
**Motivo:** Catálogo exaustivo é trabalho infinito (cada nova skill expande o catalog). FR17 é a baseline acionável. Atualização contínua é responsabilidade do owner de cada skill via revisão periódica.
**Alternativa descartada:** Auto-discovery via grep nos SKILLs. Rejeitado por gerar ruído (skills puramente lexical sem evidência).
**Consequência:** Skills futuras adicionadas ao repo NÃO entram no catalog automaticamente. Mitigação: smoke test em CI alerta nova skill sem entry (epic futuro).

**Decisão:** Plans são descritivos (texto) ao invés de structured data (YAML).
**Motivo:** Plans dependem de contexto épico-by-épico; YAML rigid não capta nuance.
**Alternativa descartada:** YAML schema com campos blindagem_steps[]. Rejeitado por overhead de manutenção.
**Consequência:** Test valida apenas estrutura mínima (4 sub-sections), não semântica. Aceito.
