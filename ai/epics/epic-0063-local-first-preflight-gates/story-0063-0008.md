## 1. Contexto & Escopo

Como **Repo Admin**, eu quero estender `scripts/setup-branch-protection.sh` com flag `--apply-strict` que aplica configuração GitHub-side strict (require reviews, status checks, linear history, no force-push), garantindo a 4ª camada de defesa em profundidade — última linha de defesa caso Camadas 0-3 sejam contornadas.

Camada 0 (PreToolUse hook) bloqueia tool calls localmente. Camadas 1-3 (rule normativa, Stop hook, CI audit) detectam e auditam. Camada 4 (branch protection) é a última linha de defesa: mesmo se LLM ou operator contornar todas anteriores, GitHub-side rejeita o push/merge se config strict está aplicada.

A história estende o script existente (`setup-branch-protection.sh` se já existir; criar caso não) com uma nova flag `--apply-strict` que via `gh api` configura:

**develop branch:**
- `required_pull_request_reviews=1` (1+ approval)
- `required_status_checks=all` (todos checks listados em FR16)
- `required_linear_history=true`
- `enforce_admins=true`
- `allow_force_pushes=false`
- `allow_deletions=false`

**epic/* branches:**
- `required_status_checks=all`
- `enforce_admins=true`
- `allow_force_pushes=false`
- (sem `required_reviews` pois epic é integration branch — story PRs são as gated)

Required status checks (FR16):
1. `Build + verify (mvn -B verify)`
2. `audit-self-check`
3. `audit-matrix (audit-execution-integrity.sh)`
4. `audit-matrix (audit-flow-version.sh)`
5. `audit-matrix (audit-review-content.sh)` (NEW — story-0063-0002)
6. `audit-matrix (audit-execution-integrity.sh --scope=telemetry)` (NEW — story-0063-0003)
7. `Pre-commit Chain (format/lint/compile)`

Idempotente: re-execução é no-op. Modo dry-run via `--dry-run` mostra config sem aplicar. Operador executa manualmente uma vez (FR15 Open Question 3 — manual mas gated em PR review).

## 8. Decision Rationale

**Decisão:** Required status checks contém nomes literais ("Build + verify (mvn -B verify)") ao invés de IDs.
**Motivo:** GitHub Actions identifica checks por display name. IDs mudam entre runs; nomes são estáveis.
**Alternativa descartada:** Job IDs do workflow. Rejeitado porque IDs não são públicos via API.
**Consequência:** Renomear workflow quebra config. Mitigação: documentação em `docs/branch-protection.md` lista nomes literais; teste smoke valida match.

**Decisão:** Aplicação manual (operator runs uma vez) ao invés de automação CI.
**Motivo:** Branch protection é meta-config; aplicá-la em CI cria infinite loop (CI altera config → CI re-run → ...). Manual + auditável é seguro.
**Alternativa descartada:** Auto-apply em CI nightly. Rejeitado pelo argumento acima.
**Consequência:** Drift possível se admin manually altera config. Mitigação: smoke test em CI valida config esperada (sem aplicar).
