## 1. Contexto & Escopo

Como **Project Owner**, eu quero implementar o rollout em 2 fases (RULE-010 do épico) — primeiro release WARN-only, segundo release FAIL-mode — via **feature toggle explícito** (`CLAUDE_PREFLIGHT_PHASE` env var + `.claude/preflight.phase` file), calendário documentado e ADR de transição, garantindo que operadores tenham 1 release para calibrar antes de bloqueio físico.

RULE-010 promete o rollout, mas nenhuma story do escopo original (0001-0011) implementa **a execução** desse rollout. Sem feature toggle e calendário explícitos, o rollout vira ad-hoc — operadores ficam sem visibilidade da fase atual e equipes que dependem do projeto recebem fail-mode sem aviso.

A história introduz 3 artefatos:

1. **Feature toggle** — env var `CLAUDE_PREFLIGHT_PHASE` (`warn` | `fail`, default `fail`). Override por arquivo `.claude/preflight.phase` (precedence: env > file > default). Hooks (story-0063-0004 e -0013) lêem o toggle: em `warn`, log + permitem; em `fail`, bloqueiam.
2. **Calendário & rollout doc** — `docs/preflight-rollout.md` documenta calendário concreto: data de release que ativa WARN, data de release que vira FAIL, métricas de saída (recovery rate < 5%, false positive count = 0 antes de virar FAIL).
3. **ADR-0016** — `docs/adr/ADR-0016-preflight-rollout.md` registra decisão de 2-phase rollout, alternativas (big-bang vs gradual), critérios de saída.

A história também adiciona **smoke test de rollout** que verifica: (a) toggle padrão é fail; (b) `.claude/preflight.phase=warn` desativa bloqueio; (c) métricas de recovery_mode_used (story-0063-0017) acima do limiar bloqueiam transição para FAIL.

A transição WARN→FAIL é **gated**: `scripts/audit-rollout-readiness.sh` (NEW) valida que critérios de saída foram atingidos antes do release que ativa FAIL ser cortado. Roda em CI da release branch.

## 3. Contratos & Endpoints

### 3.1 Feature toggle precedence

```
CLAUDE_PREFLIGHT_PHASE env var
  → if set, value used (validated: warn|fail)
  → else: read .claude/preflight.phase
    → if exists, value used
    → else: default = "fail"
```

Valores aceitos: `warn`, `fail`. Outros → exit 2 `INVALID_PHASE`.

### 3.2 Hook behavior por fase

| Fase | Bypass detectado | Ação |
| :--- | :--- | :--- |
| `warn` | qualquer | log WARNING em stderr + emit evento `preflight.warn_mode` em NDJSON + exit 0 (permite) |
| `fail` | qualquer | log ERROR + emit evento `preflight.bypass_blocked` + exit 1 (bloqueia) |
| `fail` + `CLAUDE_RECOVERY_MODE=1` | qualquer | log WARN + emit `recovery_mode_used` + exit 0 (permite com audit log) |

### 3.3 audit-rollout-readiness.sh contract

| Campo | Tipo | M/O | Validações | Exemplo |
| :--- | :--- | :--- | :--- | :--- |
| `--target-phase` | enum `warn\|fail` | M | — | `--target-phase=fail` |
| `--window-days` | int | O | default 30 | `--window-days=30` |
| `--self-check` | flag | O | — | — |

### 3.4 Exit codes

| Exit | Code | Condição |
| :--- | :--- | :--- |
| 0 | `OK` | Todos critérios de saída atingidos |
| 1 | `ROLLOUT_NOT_READY` | recovery_mode rate >= 5% OR false-positive count > 0 |
| 2 | `INVALID_PHASE` | toggle value malformado |
| 3 | `INSUFFICIENT_DATA` | janela < window-days OR sem dados telemetry suficientes |
| 4 | `INVALID_ARGS` | argv malformado |

### 3.5 Critérios de saída para FAIL

- `recovery_mode_used` rate < 5% das stories nos últimos 30d
- 0 false-positives reportados (issues label `false-positive`)
- Min 10 stories merged em fase WARN

### 3.6 Calendário (template em `docs/preflight-rollout.md`)

```markdown
# Preflight Rollout Calendar

| Phase | Tag | Date | Behavior |
|:--|:--|:--|:--|
| WARN | v3.X.0 | 2026-MM-DD | Hooks log WARNING, do not block |
| READINESS GATE | (CI gate) | 30d after WARN | audit-rollout-readiness checks metrics |
| FAIL | v3.Y.0 | 2026-MM-DD+30d | Hooks block; CLAUDE_RECOVERY_MODE=1 only escape |
```

## 8. Decision Rationale

**Decisão:** Default = `fail` (não `warn`) após release inicial.
**Motivo:** Default `warn` arrasta o problema indefinidamente. `fail` força correção; `warn` é opt-in via toggle explícito durante janela de calibração.
**Alternativa descartada:** Default `warn` indefinido. Rejeitado por inverter o ônus de prova.
**Consequência:** Release inicial precisa coordenar com equipe para opt-in `warn` durante 30d. Aceito.

**Decisão:** Toggle file (`.claude/preflight.phase`) além de env var.
**Motivo:** Env vars não são committed; precisamos de override visível em CI (committed file).
**Alternativa descartada:** Só env var. Rejeitado porque CI sem env var herda default = fail e quebra rollout.
**Consequência:** File entra em git. Mudanças requerem PR (controle adicional).
