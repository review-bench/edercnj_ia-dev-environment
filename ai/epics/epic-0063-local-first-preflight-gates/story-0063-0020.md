## 1. Contexto & Escopo

Como **Tech Lead**, eu quero que o `x-review` em scope=epic (Phase 4.5 da story-0063-0006) faça **cross-check** entre findings declarados no `review-epic-XXXX.md` consolidado e os findings de cada `review-story-XXXX-YYYY.md` original, garantindo que (a) findings críticos de stories não desaparecem na consolidação e (b) findings novos do epic-level review não sobrescrevem os de story sem reconciliação explícita.

Story-0063-0006 (Phase 4.5) introduz epic-level review. Mas o consume de N reviews de story em 1 review consolidado é um ponto natural de "perda de evidência": se uma story passou content audit por edge case com 50 linhas verbosas mas vazias (Decision Rationale do épico admite ~80% catch rate), o epic review **herda** esse stub e propaga. Pior: epic review pode "smooth over" findings críticos das stories — `x-review` em scope=epic poderia decidir "esses 3 NO-GO findings não são críticos no contexto agregado" sem rastreabilidade.

A história introduz `scripts/audit-review-reconciliation.sh` que valida cross-check entre os dois níveis:

1. **Findings de story enumerados** — para cada `review-story-XXXX-YYYY.md`, extrai findings (regex `^### Finding \d+:` ou similar) e severidade.
2. **Findings de epic enumerados** — mesmo extract para `review-epic-XXXX.md`.
3. **Reconciliation map obrigatório** — epic review precisa conter seção `## Findings Reconciliation` listando, para CADA finding crítico/alto de story:
   - `inherited` — finding propagado para epic review
   - `resolved` — finding resolvido por implementação subsequente (com ref ao commit)
   - `superseded` — finding substituído por outro mais amplo no epic-level (com cross-ref)
   - `dropped` — finding descartado com justificativa explícita (≥30 chars)
4. **Findings críticos não reconciliados** → audit fail `RECONCILIATION_INCOMPLETE` (exit 1).

A história também adiciona ao `_TEMPLATE-CONSOLIDATED-REVIEW-DASHBOARD.md` (template existente de epic review) uma seção obrigatória "Findings Reconciliation" e a `x-review` Phase 4.5 (story-0063-0006) é estendido para preencher essa seção.

### 1.2 Entrega de Valor

- **Valor Principal:** Findings críticos não desaparecem silenciosamente na consolidação story → epic.
- **Métrica de Sucesso:** AC do épico estendido — 100% dos epic-reviews mergeados pós-rollout têm seção Findings Reconciliation cobrindo todos critical/high de stories filhas.
- **Impacto no Negócio:** Epic-level review é trustworthy — não é um "smooth over" do story-level.

### 3.3 Exit codes

| Exit | Code | Condição |
| :--- | :--- | :--- |
| 0 | `OK` | Todos findings ≥ severity-floor reconciliados |
| 1 | `RECONCILIATION_INCOMPLETE` | ≥1 finding sem entry no map |
| 2 | `RECONCILIATION_INVALID_STATUS` | status fora do enum |
| 3 | `RECONCILIATION_INSUFFICIENT_JUSTIFICATION` | dropped sem justificativa ≥30 chars |
| 4 | `INVALID_ARGS` | argv malformado |

### 3.4 Findings extraction algorithm

Regex tolerante para findings em story review (refinement — aceita variações do template histórico):

```
^(##|###)\s+(Finding\s+)?(?P<id>F-\d+):\s*(?P<title>.+)$
^\*\*Severity:\*\*\s+(?P<sev>low|medium|high|critical)$
```

Aceita formatos:
- `### Finding F-1: Title`
- `## Finding F-1: Title`
- `### F-1: Title`
- `## F-1: Title`

Match em `review-story-XXXX-YYYY.md` produz lista `[(story_id, F-id, severity, title)]`.

Reconciliation map parser tolerante a whitespace:

```
^\|\s*(?P<story>[^|]+?)\s*\|\s*(?P<finding>F-\d+)\s*\|\s*(?P<sev>\w+)\s*\|\s*(?P<status>\w+)\s*\|.+$
```

Cross-check: para cada (story, F-id, severity≥severity-floor) deve existir linha no map.

## 8. Decision Rationale

**Decisão:** Status enum fechado (`inherited`/`resolved`/`superseded`/`dropped`) com justificativa exigida em `dropped`.
**Motivo:** Reduz ambiguidade. `dropped` é o status que precisa de revisão humana; outros têm semântica forte.
**Alternativa descartada:** Status livre. Rejeitado por inconsistência.
**Consequência:** Tech Lead precisa categorizar cada finding. Marginal overhead, ganho substancial em rastreabilidade.

**Decisão:** severity-floor default = high (não critical).
**Motivo:** Findings high são frequentes o suficiente para causar regressões mas raros o suficiente para reconciliar manualmente. Default critical seria muito permissivo.
**Alternativa descartada:** Default critical. Rejeitado.
**Consequência:** Reviews de epic ficam mais detalhados. Aceito.
