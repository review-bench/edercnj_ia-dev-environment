## 1. Contexto & Escopo

Como **Story Implementer (LLM/Operator)**, eu quero que `x-story-implement` execute reviews especialistas + tech-lead ANTES de criar o PR (Phase 2.5), garantindo que o PR seja "publicação de código já validado" e não "let's see if CI passes".

Hoje a ordem é: Phase 0 (context) → 1 (plan) → 2 (implement) → 3 (verify + review + report). Reviews executam DEPOIS do PR aberto, descobrindo problemas em CI/post-PR — multiplica time-to-merge porque ciclo "implement → push → PR → CI red → fix → push" repete N vezes.

A nova ordem (FR11 do SPEC):
```
Phase 0  → context
Phase 1  → plan
Phase 2  → implement tasks (x-task-implement loop)
Phase 2.5 → REVIEW (x-review + x-review-pr) — NEW POSITION
Phase 2.6 → x-internal-story-verify — moved up
Phase 2.7 → preflight gate runs
Phase 2.8 → x-pr-create (only if 2.5 + 2.6 + 2.7 all PASS)
Phase 3  → post-merge cleanup + x-internal-story-report
```

Phase 2.5 emite eventos `tool.call x-review` e `tool.call x-review-pr` no NDJSON (FR12) — via PreToolUse telemetry hook já existente. Esta é a evidência primária consumida por `audit-execution-integrity.sh --scope=telemetry` (story-0063-0003).

A história modifica o SKILL.md fonte em `java/src/main/resources/targets/claude/skills/core/dev/x-story-implement/SKILL.md` e regenera o output `.claude/skills/x-story-implement/SKILL.md`. Mudança é estrutural (Rule 13 / 24 / 25 mandatory tool calls preservados); apenas a ordem das phases muda.

### 1.2 Entrega de Valor

- **Valor Principal:** PR é evento de publicação, não validação. Time-to-merge médio reduzido em ~30% (estimativa).
- **Métrica de Sucesso:** `Epic0063LocalFirstSmokeTest` AC5 verde — eventos `x-review` precedem `x-pr-create` no NDJSON; nenhuma story passa Phase 2.8 sem 2.5 + 2.6 + 2.7 GREEN.
- **Impacto no Negócio:** Operator/LLM corrige feedback de reviewer ANTES do PR ser visível ao time → reduz noise em PR queue.

## 8. Decision Rationale

**Decisão:** Mover reviews para Phase 2.5 (entre impl e PR) ao invés de adicionar passo separado pré-Phase 2.
**Motivo:** Reviews precisam do código implementado para serem significativos. Mover para 2.5 (depois de impl, antes de PR) preserva utilidade da review enquanto inverte o fluxo PR.
**Alternativa descartada:** Reviews como Phase 0.5 (pré-impl, focando arch). Rejeitado porque mistura escopo com x-arch-plan já existente.
**Consequência:** SKILL.md fica ~150 lines mais longo. Phase 3 (post-merge) reduz escopo (apenas report). Refactor futuro pode renomear Phase 3 para 4 e Phase 2.5/6/7/8 para 3/4/5/6 — mas mudança de nomes quebra fila de epics legacy. Mantemos sub-decimal por compat.
