## 1. Contexto & Escopo

Como **Tech Lead**, eu quero auditar por **conteúdo** (não só presença) os 6 artefatos de Phase 1 que `x-internal-story-build-plan` produz — `arch-`, `plan-`, `tests-`, `tasks-`, `security-`, `compliance-` — aplicando heurística sintática equivalente à de `audit-review-content.sh` (story-0063-0002), garantindo que o LLM não pode produzir os 6 arquivos com 5 linhas vazias cada e passar.

Story-0063-0002 cobriu `review-story-*.md` e `verify-envelope-*.json` porque eles foram a porta de entrada do problema do EPIC-0062. Mas a mesma classe de bypass aplica-se aos 6 planning artifacts: hoje `audit-execution-integrity.sh` valida apenas presença, então um LLM que invoca `x-internal-story-build-plan` mas internamente sumariza o trabalho dos 5 sub-agents pode produzir 6 markdowns/jsons mínimos e passar Camada 3.

A história introduz `scripts/audit-planning-content.sh` que aplica heurísticas calibradas por tipo de artefato:

| Artefato | Heurísticas mínimas |
| :--- | :--- |
| `arch-story-*.md` | ≥120 linhas; ≥5 seções H2; ≥1 mermaid diagram (`\`\`\`mermaid`); ≥3 mini-ADRs; tabela NFR presente |
| `plan-story-*.md` | ≥80 linhas; ≥4 seções H2; ≥3 fases declaradas; lista de arquivos a tocar (≥3 entries) |
| `tests-story-*.md` | ≥60 linhas; ≥1 seção "Acceptance Tests" (Gherkin); ≥1 seção "Unit Tests" (TPP order); ≥3 cenários |
| `tasks-story-*.md` | ≥60 linhas; ≥3 tasks com TASK-XXXX-YYYY-NNN id; cada task com **Files:** e **Acceptance Criteria:** |
| `security-story-*.md` | ≥40 linhas; ≥3 ameaças listadas; mitigation por ameaça; OWASP/CWE refs ≥2 |
| `compliance-story-*.md` | ≥30 linhas; ≥1 referência a Rule específica do projeto; checklist DoR/DoD |

Heurística NÃO usa LLM-judge. Calibrada contra artefatos legítimos do histórico (epics 0049-0062). Falsos positivos baixos via marker `<!-- audit-exempt-content: <reason> -->` para SCOPE=SIMPLE legítimos.

Também valida **dual-evidence rule** (RULE-003 do épico): cada artefato presente DEVE ter evento `tool.call` matching skill no NDJSON. `audit-planning-content.sh --scope=both` faz ambas checagens (content + telemetry); modo `--scope=content` faz só content; `--scope=telemetry` só cross-check.

- **Valor Principal:** Estende anti-stub de reviews/envelope para os 6 artefatos de Phase 1 — fecha 6 vetores adicionais de evidência fabricada.

## 3. Contratos & Endpoints

### 3.1 Request

| Campo | Tipo | M/O | Validações | Exemplo |
| :--- | :--- | :--- | :--- | :--- |
| `--story-id` | regex `[0-9]{4}-[0-9]{4}` | M | strict | `--story-id=0063-0015` |
| `--scope` | enum `content\|telemetry\|both` | O | default `both` | `--scope=both` |
| `--artifact` | enum `arch\|plan\|tests\|tasks\|security\|compliance\|all` | O | default `all` | `--artifact=arch` |
| `--strict` | flag | O | desativa exempt markers | `--strict` |
| `--self-check` | flag | O | — | — |

### 3.2 Exit codes

| Exit | Code | Condição |
| :--- | :--- | :--- |
| 0 | `OK` | Todos artefatos passam |
| 1 | `PLANNING_CONTENT_INSUFFICIENT` | ≥1 artefato falha heurística |
| 2 | `PLANNING_TELEMETRY_MISSING` | ≥1 artefato presente sem evento `tool.call` matching |
| 3 | `PLANNING_BASELINE_CORRUPT` | baseline malformado |
| 4 | `INVALID_ARGS` | argv malformado |

### 3.3 Heurísticas detalhadas (algoritmo)

Para `arch-story-*.md`:
- `wc -l` ≥ 120 (excluindo linhas vazias)
- `grep -c "^## "` ≥ 5
- `grep -c "^\`\`\`mermaid"` ≥ 1
- `grep -c "ADR-" + "Mini-ADR"` combinados ≥ 3
- regex de tabela NFR (`\| NFR \|.*\|.*\|`) presente

Para `tasks-story-*.md`:
- regex `TASK-[0-9]{4}-[0-9]{4}-[0-9]{3}` ≥ 3 matches (com prefixo `TASK-` literal)
- para cada TASK detectada, verificar `**Files:**` e `**Acceptance Criteria:**` na seção dela

(Demais regras seguem o mesmo padrão.)

### 3.4 SCOPE awareness

Lê `scope` do `execution-state.json.storyClassification[story-id]`:

- `SIMPLE` → security + compliance permitem `<!-- audit-exempt-content -->` legítimo
- `STANDARD` → todos artefatos exigidos com heurística completa
- `COMPLEX` → adiciona threshold extra de +30% nas linhas mínimas

### 3.5 Dual-evidence cross-check

Para cada artefato presente, verifica NDJSON tem evento:

| Artefato | Skill esperada |
| :--- | :--- |
| `arch-story-*.md` | `x-arch-plan` |
| `plan-story-*.md` | `x-internal-story-build-plan` (Step 1B) |
| `tests-story-*.md` | `x-test-plan` |
| `tasks-story-*.md` | `x-lib-task-decomposer` ou `x-task-plan` |
| `security-story-*.md` | `x-internal-story-build-plan` (Step 1E) |
| `compliance-story-*.md` | `x-internal-story-build-plan` (Step 1F) |

## 8. Decision Rationale

**Decisão:** Heurística sintática (não LLM-judge), igual a story-0063-0002.
**Motivo:** Consistência arquitetural com Decision Rationale do épico (custo+latência).
**Alternativa descartada:** LLM-judge per artefato. Rejeitado.
**Consequência:** ~80% catch rate. Aceito como faixa 1; LLM-judge fica como tier-2 para futuro.

**Decisão:** SCOPE awareness embutido (SIMPLE/STANDARD/COMPLEX adjusta thresholds).
**Motivo:** Heurística uniforme penaliza stories SIMPLE com falsos positivos. Adjuste é determinístico via execution-state.json.
**Alternativa descartada:** Threshold único. Rejeitado.
**Consequência:** Audit precisa ler execution-state.json (já necessário para storyId resolution).
