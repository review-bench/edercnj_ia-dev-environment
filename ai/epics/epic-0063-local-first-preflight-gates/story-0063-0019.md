# História: NDJSON Integrity — Hash Chain

**ID:** story-0063-0019
**Chave Jira:** —
**Status:** Pendente

---

## 1. Contexto & Escopo

Como **Auditor de Compliance**, eu quero que cada evento gravado em `events.ndjson` carregue um campo `prev_hash` formando uma **hash chain** ligando o evento N ao hash SHA-256 do evento N-1, garantindo que edição manual ou reordenação de eventos seja detectável estaticamente — fechando a janela entre Stop hook (que escreve no disco) e o próximo commit (que stage-telemetry adiciona).

Story-0063-0003 (telemetry-as-evidence) re-introduz `stage-telemetry.sh` que faz `git add` do NDJSON ao final de cada turno. Isso garante que NDJSON é commitado, mas **não impede** que o LLM ou operator edite o arquivo antes do `git add` final do turno. Como os eventos são append-only do ponto de vista de design, qualquer edição de eventos passados é uma manipulação que invalida a evidência.

Hash chain fecha essa janela:

- Cada evento NDJSON ganha campos `seq` (integer monotônico) e `prev_hash` (SHA-256 hex do evento N-1 inteiro como JSON canonical).
- Primeiro evento da sessão tem `seq=1` e `prev_hash="0000...0000"` (genesis).
- `telemetry-emit.sh` (helper existente) é estendido para calcular hash e popular campos.
- `audit-execution-integrity.sh --scope=telemetry` (story-0063-0003) é estendido com `--check-chain` que recomputa hash de cada evento e valida match com `prev_hash` do próximo.
- Mismatch → `EIE_TELEMETRY_CHAIN_BROKEN` (exit 5).

Edição manual quebra a chain: alterar evento N invalida o hash → evento N+1 tem `prev_hash` apontando para hash antigo, não bate. Reordenação quebra: seq não é monotônico OU prev_hash não casa.

Eventos pré-EPIC-0063 (sem chain fields) são grandfathered: chain check skip-a até encontrar primeiro evento com `seq` populated. Após esse marker, chain é obrigatória.

A história também adiciona **session boundary marker** — `event=session.start` e `event=session.end` claramente delimitando início/fim de sessão Claude Code, facilitando análise multi-sessão e prevenindo cross-session chain confusion.

## 3. Contratos & Endpoints

### 3.1 Event schema (extended)

Antes:
```json
{"timestamp": "...", "event": "tool.call", "session_id": "...", "pid": 12345, "skill": "x-arch-plan"}
```

Depois:
```json
{
  "seq": 42,
  "prev_hash": "a3f2e8...c1b9",
  "timestamp": "...",
  "event": "tool.call",
  "session_id": "...",
  "pid": 12345,
  "skill": "x-arch-plan"
}
```

`prev_hash` = SHA-256 do **evento anterior** (linha completa NDJSON minus trailing newline). Genesis: `0000...0000` (64 zeros).

### 3.2 telemetry-emit.sh extended contract

Toda emissão lê última linha de `events.ndjson` da story atual, computa hash, popula `seq` e `prev_hash`, anexa nova linha. Atomicidade: `flock` no NDJSON file durante emit (evita race em stories paralelas).

### 3.3 audit-execution-integrity.sh --check-chain extended

| Campo | Tipo | M/O | Validações | Exemplo |
| :--- | :--- | :--- | :--- | :--- |
| `--scope` | enum `full\|telemetry\|chain\|all` | M | chain = só validate chain | `--scope=chain` |
| `--story-id` / `--epic-id` | regex | O | filter | — |
| `--strict` | flag | O | desabilita grandfather (baseline) | — |

### 3.4 Exit codes (extended)

Adiciona aos existentes (story-0063-0003):

| Exit | Code | Condição |
| :--- | :--- | :--- |
| 5 | `EIE_TELEMETRY_CHAIN_BROKEN` | hash mismatch ou seq non-monotonic |
| 6 | `EIE_TELEMETRY_GENESIS_INVALID` | primeiro evento sem genesis hash correto |

### 3.5 Chain validation algorithm

```
prev_hash = "0000..."
prev_event = null
for each line in events.ndjson (in order):
  parsed = JSON.parse(line)
  if parsed.seq != (prev_event?.seq ?? 0) + 1:
    fail SEQ_NON_MONOTONIC
  if parsed.prev_hash != prev_hash:
    fail HASH_MISMATCH
  prev_hash = sha256(line)
  prev_event = parsed
```

### 3.6 Baseline (grandfather)

`audits/telemetry-chain-baseline.txt` lista per epic-id o primeiro `seq` em que chain foi adotada. Eventos antes desse seq são skipped pelo chain check. Append-only (CI valida imutabilidade); novos epics começam com seq=1 + chain.

## 8. Decision Rationale

**Decisão:** SHA-256 via sha256sum (binário) ao invés de OpenSSL ou libcrypto.
**Motivo:** Disponibilidade universal; zero dep adicional.
**Alternativa descartada:** SHA-1 (mais barato). Rejeitado por colisão conhecida.
**Consequência:** Cada emit gasta ~1-2ms para hash. Aceito (telemetry path já tem overhead de I/O).

**Decisão:** Hash sobre linha inteira (string JSON), não estrutura canonicalized.
**Motivo:** Linha é exatamente o que vai pro disco — hash do que está committado é mais robusto.
**Alternativa descartada:** JSON canonicalization. Rejeitado por complexidade (e telemetry-emit já produz JSON estável).
**Consequência:** Reformatação espacial do JSON quebra chain. Aceito (NDJSON é uma-linha-uma-evento por contrato).

**Decisão:** Genesis 64 zeros ao invés de hash determinístico do session_id.
**Motivo:** Simplicidade — genesis é constante, não exige estado adicional.
**Alternativa descartada:** Genesis = hash(session_id). Rejeitado por adicionar coupling sem benefício forense.
**Consequência:** Múltiplas sessões na mesma story têm chains independentes (delimitadas por session.start markers).
