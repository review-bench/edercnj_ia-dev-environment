## 8. Decision Rationale

**Decisão D1:** Dual-write (markdown + state), não só markdown.
**Motivo:** hooks precisam de leitura O(1) via `jq` em < 500ms; markdown parsing é caro e frágil.
**Alternativa descartada:** só markdown.
**Consequência:** sincronização exige cuidado — auditoria detecta divergência via `verdictHash` (sha256 do bloco markdown).

**Decisão D2:** `refinementVerdict` é **campo opcional** (Rule 19 — additive change).
**Motivo:** ausência → status implícito "tbd" → hook no-op em legacy. Não quebra `flowVersion=1`.
**Alternativa descartada:** campo obrigatório com default.
**Consequência:** sem migração forçada de state files antigos.

**Decisão D3:** Status `Refinada` publicado dentro da Rule 29 (não Rule separada).
**Motivo:** D-R3 (b) — cohesion: Rule 29 define o estado e suas transições. Não há Rule canônica preexistente para Story Status enum, e criar uma só para 1 estado novo é overkill.
**Alternativa descartada:** Rule nova "Story Lifecycle".
**Consequência:** Rule 29 tem 2 escopos (gate + máquina de estados), ambos intrinsecamente ligados.

**Decisão D4:** `verdictHash` (sha256 do bloco markdown) registrado no state.
**Motivo:** detecção de divergência state↔markdown (operador editou markdown manualmente sem rerun da skill).
**Alternativa descartada:** sem hash — confia que markdown e state ficam sincronizados.
**Consequência:** audit-refinement-gate.sh (story-0006) consegue flagar divergência objetivamente.
