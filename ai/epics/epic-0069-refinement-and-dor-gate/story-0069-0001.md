## 8. Decision Rationale

**Decisão D1:** Capability universal (sem `requires-capabilities` próprio) — D-R5.
**Motivo:** refinement é processo (humano), não tecnologia. Stack do projeto cliente (Java, Python, Node) não muda o que é uma persona ou um AC bem-formado.
**Alternativa descartada:** capability por stack (`governance.refinement-gate.java`, etc.) — artificial.
**Consequência:** todo projeto gerado pelo `ia-dev-env` herda o gate por default; opt-out explícito via `governance.refinement-gate: false` no YAML do projeto.

**Decisão D2:** Status `Refinada` publicado dentro da Rule 29, não em Rule separada — D-R3 (b).
**Motivo:** cohesion — a regra que **define** o estado também documenta as transições; criar Rule separada apenas para 1 status novo + 2 transições é overkill.
**Alternativa descartada:** Rule nova "Story Lifecycle" separada de Rule 29.
**Consequência:** Rule 29 tem 2 escopos — gate runtime + máquina de estados — mas ambos são intrinsecamente ligados.

**Decisão D3:** Numeração de Rule e ADR são working-titles — D-R6.
**Motivo:** memory feedback consolidado em refinement passes anteriores — não pinar números antecipadamente; verificar contra branches em voo no momento da implementação.
**Alternativa descartada:** pinar Rule 29 / ADR-0018 no scaffold.
**Consequência:** primeira task da story é a verificação; se colidir, atualização de referências cruzadas é parte do escopo.
