## 1. Visão

Como **arquiteto de governança**, eu quero **um CI script (Camada 2 — Rule 26) que verifique pós-merge se cada story implementada teve `refinementVerdict.status="approved"`** ou está coberta por exceção válida (hotfix, baseline, audit-exempt), garantindo defesa em profundidade contra bypass do hook (Camada 0) — operador pode desabilitar hook localmente; CI não.

## 2. Persona & Cenário

**Persona principal:** revisor/maintainer responsável pelo gate de PR; e CI agent rodando o pipeline.

**Cenário:** PR aberto contra `develop` ou `epic/*` dispara `audit-refinement-gate.sh`. Script percorre commits desde o merge-base; para cada story merged identificada, verifica `refinementVerdict.status` no commit final. Se algum violou, exit 1 e build falha.

## 3. Entrega de Valor

- **Valor primário:** Camada 2 (CI script — Rule 26) defendendo o contrato em profundidade — hook sozinho é insuficiente porque dev pode desativar hook local.
- **Valor secundário:** detecta divergência state↔markdown via `verdictHash` (introduzido em story-0004) — operador editando markdown manualmente é flagado.
- **Métrica primária:** zero falsos positivos em 10 PRs pós-rollout (audit testado contra histórico).
- **Métrica secundária:** zero falsos negativos em 1 sprint pós-rollout (story merged com refinement rejected → CI deve falhar).
- **Métrica terciária:** performance — varrer 200 PRs em < 30s.

## 4. Acceptance Criteria (Gherkin — esboço)

```gherkin
Cenario: PR sem refinement aprovado falha
  DADO PR abre merge de story-X com refinementVerdict.status="rejected"
  E story-X nao esta na baseline nem tem audit-exempt marker
  QUANDO audit-refinement-gate.sh roda em CI
  ENTAO exit 1 com REFINEMENT_GATE_VIOLATION
  E stderr nomeia story-X e o motivo

Cenario: PR com refinement aprovado passa
  DADO PR abre merge de story-Y com refinementVerdict.status="approved"
  QUANDO audit roda
  ENTAO exit 0

Cenario: divergencia state vs markdown eh detectada
  DADO state tem verdictHash="abc123" mas hash atual do bloco markdown eh "xyz789"
  QUANDO audit roda
  ENTAO exit 1 com REFINEMENT_GATE_VIOLATION sub-codigo "verdict-mismatch"

Cenario: hotfix bypass eh tolerado (Rule 27 Exception 2)
  DADO PR abre de hotfix/CRIT-XXX para main
  QUANDO audit roda
  ENTAO exit 0 (hotfix exception)
  E log registra a excecao

Cenario: baseline grandfathers stories pre-rollout
  DADO story-Z merged antes do rollout do gate
  E story-Z esta listada em governance/baselines/refinement-gate-baseline.txt
  QUANDO audit roda
  ENTAO exit 0
  E log mostra "story-Z grandfathered"

Cenario: --self-check valida pre-requisitos (Rule 26)
  QUANDO audit-refinement-gate.sh --self-check roda
  ENTAO exit 0 se jq na PATH e governance/baselines/refinement-gate-baseline.txt legivel
  E exit 2 (OPERATIONAL_ERROR) se faltam pre-requisitos
```

## 5. Contratos & Endpoints

- **Path source-of-truth:** `java/src/main/resources/targets/claude/scripts/_default/audit-refinement-gate.sh` — D-R2.
- **Output path (gerado):** `scripts/audit-refinement-gate.sh` no projeto cliente (via ScriptsAssembler).
- **Camada:** 2 (CI script — Rule 26).
- **Exit codes** (Rule 26 §Standardized — D-R7):
  - `0` — OK.
  - `1` — `REFINEMENT_GATE_VIOLATION` (com sub-códigos no stderr: `missing-verdict`, `rejected-verdict`, `verdict-mismatch`).
  - `2` — `OPERATIONAL_ERROR` (jq ausente, baseline ilegível, etc.).
  - `3` — `BASELINE_CORRUPT` ou `INVALID_EXEMPTION`.
- **Baseline:** `governance/baselines/refinement-gate-baseline.txt` — formato uma `STORY-ID` por linha + `# reason` comment. **Immutable post-merge** (CI separado garante via diff de baseline).
- **`--self-check` flag** — obrigatório (Rule 26 §--self-check Flag).
- **`audit-exempt` per-line marker** — `<!-- audit-exempt: <reason> -->` no markdown da story (rara — exception revisada).
- **Catalog entry obrigatório:** `docs/audit-gates-catalog.md` ganha linha para `audit-refinement-gate.sh` (Rule 26 RULE-004 catalog-before-add) **e** para `enforce-refinement-gate.sh` da story-0005 (mesma PR ou separada).

## 8. Decision Rationale

**Decisão D1:** CI script (Camada 2) complementa hook (Camada 0).
**Motivo:** defesa em profundidade — hook roda na máquina dev (pode ser desativado localmente); CI roda em PR (operador não controla).
**Alternativa descartada:** só hook.
**Consequência:** dois pontos de implementação a manter sincronizados — mas semântica é a mesma (`refinementVerdict.status == "approved"` OR exception).

**Decisão D2:** `verdictHash` para detectar divergência state↔markdown.
**Motivo:** dual-write da story-0004 introduz risco de drift se operador editar markdown manualmente; hash força detecção objetiva.
**Alternativa descartada:** comparação textual full do bloco (frágil contra whitespace).
**Consequência:** dependência hard de story-0004 ter introduzido o campo `verdictHash`.

**Decisão D3:** Baseline immutable post-merge.
**Motivo:** Rule 24 / Rule 27 padrão — baseline grandfathers stories pré-rollout, não cobre stories novas.
**Consequência:** CI separado precisa garantir imutabilidade (diff de `refinement-gate-baseline.txt` em PRs deve falhar).

**Decisão D4:** Exit codes seguem Rule 26 §Standardized (0/1/2/3) — D-R7.
**Motivo:** consistência com todos os outros CI scripts do projeto.
**Consequência:** sub-códigos de violação ficam no stderr (e.g., "REFINEMENT_GATE_VIOLATION sub-code missing-verdict"), não no exit code.
