## 1. Contexto & Escopo

### 1.1 Problema

EPIC-0063 (Local-First Pre-Flight Gates) prevê 21 stories que fecharão a classe "skill pula etapa declarada" em **boundaries**: `git push`, `gh pr create`, `Skill x-pr-create`, e — via a rule de Tool-Call Grammar (`story-0063-0012`; rule number TBD) — invocações estaticamente declaradas em SKILL.md auditadas contra NDJSON pós-merge. PR #752 mergeou o scaffold do EPIC-0063 (21 markdown files de planejamento), mas `execution-state.json` em `develop` rastreia apenas as 11 stories da v1 inicial (`0001..0011`, todas `PENDING`); a expansão v2 (`0012..0021`) ainda não foi incorporada ao state file. EPIC-0061 `story-0061-0001` (Non-Interactive Default + Working-Tree Guard, **mergeada em 2026-04-28** — PRs #755/#756/#757) tornou `--non-interactive` o default dos 8 orquestradores Anexo B.

A junção de ambos cria uma **janela cega** que nenhum dos dois epics fecha:

> Em modo `--non-interactive`, o LLM, no meio de uma `## Phase N` aberta, emite prosa em vez da próxima tool call mandatória — sem chegar a boundary algum (push/PR/Skill explícito) e sem completar a fase.

Os hooks existentes não capturam esse estado:

- `verify-story-completion.sh` (Stop hook, Rule 24 Camada 2) checa **evidência ao final** do orquestrador, não progresso intra-fase.
- `enforce-preflight-gates.sh` (PreToolUse, EPIC-0063 stories 0004/0013) bloqueia bypass em push/PR/Skill, mas só dispara se o LLM emite tool call.
- `enforce-phase-sequence.sh` (PreToolUse, Rule 25 Camada 3) bloqueia invocações fora de ordem, mas só dispara em invocação.
- `verify-phase-gates.sh` (Stop hook, Rule 25 Camada 2) checa gate ao final da fase, não no meio.
- `audit-tool-call-grammar.sh` (CI, **planejado** por EPIC-0063 `story-0063-0012` — rule number TBD; ainda não materializado em `develop`) detectará `[required]` ausente no NDJSON, mas só pós-merge.

Sintoma operacional documentado: durante execução de EPIC-0061 story-0061-0001, após `TaskUpdate(completed)` da sub-fase 3.1 (specialist reviews), o LLM parou e aguardou ~2-5 minutos por confirmação humana antes que o operador percebesse o silêncio. Esse padrão se repete há vários sprints sob diferentes orquestradores e modelos — é a motivação direta dos EPICs 0061 e 0063, e este epic fecha o gap residual.

### 1.2 Escopo

Este epic entrega:

- **Field `interactiveMode`** em `execution-state.json` (`"interactive"` | `"non-interactive"`), escrito pelos 8 orquestradores Anexo B na inicialização (Rule 19 fallback: ausência = `"interactive"`).
- **Hook novo `enforce-continuous-flow.sh`** (Stop hook, Rule 26 layer "Hook runtime") — distinto de `verify-story-completion.sh`, com responsabilidade única: detectar progresso intra-fase em modo non-interactive.
- **Integração com a Tool-Call Grammar rule** (introduzida por EPIC-0063 `story-0063-0012`; rule number TBD): o hook deriva `next-mandatory-call` lendo o SKILL.md ativo e identificando a próxima invocação `[required]` ainda não emitida no NDJSON da fase corrente. Implementação acopla aos markers (sintaxe), não ao número da rule.
- **`--self-check` flag** (Rule 26) com 3 validações (state-file path resolvable, NDJSON parser ok, dependencies on PATH).
- **E2E smoke test** (`Epic0068ContinuousFlowSmokeTest`) cobrindo 5 cenários: NUDGE em fase aberta, no-NUDGE em modo interactive, no-NUDGE em finding HIGH pendente, no-NUDGE em fase completa, no-NUDGE em hotfix branch.

### 1.3 Fora do escopo

- **Reescrever orquestradores para subagent-per-phase** — analisado e rejeitado (custo alto, risco de regressão; existing skill structure preserved).
- **Auto-retry quando NUDGE não destrava** — caso `recovery_mode_used` tradicional (EPIC-0063-0017).
- **Telemetria de "tempo morto" entre eventos** — pode ser feature do `/x-telemetry-analyze` em outro escopo.
- **Backport para `flowVersion: "1"` (legacy)** — hook é no-op para legacy state files (Rule 19 fallback).
- **Modificar `verify-story-completion.sh`** — separação de responsabilidades preservada (SRP — Rule 03).

### 1.4 Entrega de Valor

- **Valor primário:** elimina silenciosamente a classe "LLM travado mid-fase" — o operador recebe nudge automático no próximo turno em vez de precisar intervir manualmente com "estamos travados?".
- **Valor secundário:** unifica três sinais existentes (Tool-Call Grammar markers + `execution-state.json` + telemetria NDJSON) em um único hook acionável, fechando a lacuna de detecção em tempo real.
- **Métrica de sucesso primária:** P95 do gap entre `tool.call` consecutivos em modo `non-interactive` < 30s para 95% das stories merged pós-rollout.
- **Métrica de sucesso secundária:** zero reports operacionais de "estamos travados?" em sessões pós-rollout (target qualitativo).
- **Impacto no negócio:** elimina padrão de fricção operacional que vem afetando produtividade há ≥6 sprints.

## 6. Decisões Arquiteturais

### 6.1 Por que Stop hook e não PostToolUse

PostToolUse só dispara após tool call. Quando o LLM emite **prosa**, não há PostToolUse — não há gancho para interceptar. Stop é o único evento que captura "fim de turno" independente do conteúdo do turno (tool call ou prosa).

### 6.2 Por que separar de `verify-story-completion.sh`

Single Responsibility (Rule 03):
- `verify-story-completion.sh` checa **evidência ao final** do orquestrador (artefatos no disco para Rule 24 surfaces).
- `enforce-continuous-flow.sh` checa **progresso intra-fase** (delta de tool calls entre turnos).

Misturar viola SRP, complica testes, e dificulta evolução independente. Os dois hooks são complementares e podem rodar no mesmo `Stop` event sem conflito.

### 6.3 Por que não Rule nova

A Tool-Call Grammar rule (EPIC-0063 `story-0063-0012`; rule number TBD) já cobre o contrato de invocação obrigatória (`[required]` markers). Este hook é a Camada 2 (runtime) dessa rule, não uma rule nova. Reduz proliferação normativa. Nota: o número final da rule só será fixado quando o conflito com `28-capability-frontmatter-contract.md` (EPIC-0064 em refinamento) for resolvido — uma das duas precisará ser renumerada.

### 6.4 Por que não bloquear (exit ≠ 2)

Stop hook com exit 2 emite WARNING ao LLM via stderr (Claude Code surfaca para o LLM no próximo turno). Isso é **nudge**, não block. Para block físico, seria PreToolUse — mas LLM não emite tool call pra interceptar. Nudge é o vetor cirúrgico aqui.

### 6.5 Por que `interactiveMode` em state e não em env var

State file é a fonte de verdade do orquestrador ativo (Rule 25). Env var seria sessão-scoped e não sobreviveria a `/clear`. State persiste e é resumível.
