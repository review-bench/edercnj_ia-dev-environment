## 1. Contexto & Escopo

### 1.1 Problema

Existem **duas zonas de teste** que ferramentas formais (PIT, Pact, JUnit, Newman) não cobrem bem e que ainda assim são parte do contrato de qualidade:

**Zona 1 — Regressão Shell (testes de regressão pragmáticos).**

Para o nosso CLI, regressão é **gerar projetos com cada perfil canônico e diff vs golden**. Hoje isso existe parcialmente em Java (`AssemblerRegressionSmokeTest`), mas:
- não cobre o caminho real do operador (`./setup.sh --config X.yaml`);
- não exercita scripts de hooks gerados;
- não testa migração entre versões (ex.: v3 → v4 layout, EPIC-0060/0062);
- não exercita comandos `/skill` simulados em sandbox.

Para projetos cliente (REST/gRPC/event), regressão pragmática é **rodar um conjunto de cenários nomeados** via cURL/grpcurl/wscat e checar status + payload sem precisar montar framework de testes para cada cenário-de-fumaça. Hoje, projetos gerados não recebem esse harness — cada time inventa o seu, ou pior, não tem.

**Zona 2 — DAST (Dynamic Application Security Testing).**

`x-security-pipeline` referencia OWASP ZAP **passive scan** (read-only). Mas pentest dinâmico real é **ZAP active scan** (envia payloads de injeção, XSS, traversal) + **Nuclei templates** (CVE-templates curados pela comunidade). Hoje, nada disso roda. Quando aparece vulnerabilidade DAST-detectável em prod, descobrimos por bug bounty ou incidente, não por gate.

Como o CLI é **gerador para várias stacks**, o épico precisa entregar:
- **Modo "self"**: harness de regressão pra **o nosso projeto** (gerar todos os perfis, diff vs golden, smoke após geração).
- **Modo "service"**: template de regressão **para projetos cliente** stack-aware (cURL pra REST, grpcurl pra gRPC, wscat pra Socket).
- **DAST tier**: smoke (ZAP passive + lightweight Nuclei) em PR; full (ZAP active scan + Nuclei completo) em nightly.

### 1.2 Hipótese

> Se introduzirmos `/x-test-regression-shell` (com modo dual: self e service) e `/x-pentest-dynamic` (com tier smoke/full), e plugarmos os dois como gates condicionais (regression-shell sempre quando declarado; DAST smoke em PR + full nightly), então:
> - regressões funcionais pegáveis com cURL/grpcurl deixam de chegar a `develop`;
> - vulnerabilidades DAST-detectáveis ganham gate de detecção em CI;
> - projetos cliente recebem ambos os harnesses por padrão (com opt-out explícito), eliminando a era do "cada time inventa o seu smoke".

### 1.3 Escopo

Este épico entrega:

1. **Skill `/x-test-regression-shell`** com 2 modos:
   - **Modo `--self`** (para o nosso CLI): gera todos os 9 perfis canônicos, diff cada um vs golden, executa smoke pós-geração (`./setup.sh` simulado em sandbox + verificação de hooks instalados).
   - **Modo `--service`** (para projeto cliente): consome `tests/regression/scenarios.yaml` declarado pelo time, executa cenários cURL/grpcurl/wscat conforme `interfaces[]`, valida status + payload + headers.
   - Saída: `plans/epic-XXXX/reports/regression-shell-report-STORY-ID.md` ou `tests/regression/results/regression-YYYY-MM-DD.md`.
2. **Skill `/x-pentest-dynamic`** com 2 tiers:
   - **Tier `--smoke`** (default, roda em PR): ZAP passive scan + Nuclei lightweight templates (top-50 CVE templates).
   - **Tier `--full`** (nightly): ZAP active scan completo + Nuclei full templates + custom payloads conforme `security.compliance` declarada (PCI/LGPD specific).
   - Saída: SARIF 2.1.0 + Markdown report em `results/security/dast/dast-{smoke|full}-YYYY-MM-DD.md`.
3. **Schema YAML novo** sob `quality:` (compartilhado com EPIC-0072):
   ```yaml
   quality:
     regression:
       enabled: true
       mode: service              # self (CLI próprio) | service (projeto cliente)
       scenarios-file: tests/regression/scenarios.yaml
     dast:
       enabled: true
       tier-pr: smoke
       tier-nightly: full
       zap:
         enabled: true
         active-scan-policy: default
       nuclei:
         enabled: true
         templates-version: v9.x
   ```
4. **Templates novos**:
   - `_TEMPLATE-REGRESSION-SHELL.md` — descreve cenários (request/response esperado).
   - `_TEMPLATE-PENTEST-PLAN.md` — escopo, ambiente, payloads, exclusions, ações pós-finding.
   - `tests/regression/scenarios.yaml.template` — esqueleto stack-aware do scenario file (gerado pelo `ScriptsAssembler`).
5. **Capabilities** declarativas:
   - `quality.regression.{self,service}.*`
   - `quality.dast.{zap-passive,zap-active,nuclei}.*`
6. **CI workflow MODIFIED** (Camada 4):
   - PR: `audit-regression-shell.sh` + `dast-smoke.yml`.
   - Nightly: `dast-full.yml` (cron schedule).
7. **KP novo**: `knowledge/security/dast-playbook.md` — quando rodar smoke vs full, como interpretar findings, mitigation patterns por categoria OWASP.
8. **Phase 3 de `x-story-implement` MODIFIED** — quando `quality.regression.enabled=true`, `/x-test-regression-shell` é MANDATORY TOOL CALL conditional. DAST smoke é invocado em CI (não em Phase 3 — separação clara: skill orchestrada vs CI-only).
9. **Smoke test E2E** (`Epic0073RegressionDastSmokeIT`) cobrindo: regression-shell self mode, regression-shell service mode, DAST smoke detecta finding HIGH, DAST full diferenciado de smoke, opt-out via YAML.

### 1.4 Fora do escopo

- **Pentest manual humano**: skill é automação; pentest manual não substitui (e vice-versa).
- **Bug bounty platform integration**: escopo separado.
- **Fuzz testing** (libfuzzer, jazzer): EPIC futuro junto com property-based.
- **Chaos engineering** (Litmus, Chaos Mesh, Gremlin): épico futuro.
- **WAF rule generation a partir de findings**: escopo separado.
- **Geração automática de PoC para findings**: skill produz Markdown + SARIF; PoC é manual.

### 1.5 Entrega de Valor

- **Valor primário:** vulnerabilidades DAST-detectáveis e regressões funcionais pegáveis-com-cURL ganham gate em CI.
- **Valor secundário:** projetos cliente recebem harness de regressão e DAST sem precisar inventar.
- **Valor terciário:** o nosso projeto ganha regressão shell própria que cobre o caminho real do operador (`./setup.sh`).
- **Métrica de sucesso primária:** ≥ 1 finding HIGH/CRITICAL detectado e mitigado nos 3 primeiros projetos rodando 0073 (sinal de que DAST está rodando de verdade).
- **Métrica de sucesso secundária:** zero PRs merged com regressão funcional pegável-com-cURL pós-rollout.
- **Sinal qualitativo:** time pára de pedir "alguém pode rodar Postman pra confirmar?" pré-merge.

## 6. Decisões Arquiteturais

### 6.1 Por que regression-shell modo dual (self + service)

Dois casos de uso reais e diferentes (CLI gerador vs projeto cliente). Skill única com modos é mais econômica que duas skills similares.

**Decisão:** modo dual numa skill.

**Alternativa descartada:** 2 skills (`x-test-regression-self`, `x-test-regression-service`). Rejeitado: duplicação de lógica.

### 6.2 Por que DAST tiered (smoke em PR + full nightly)

ZAP active + full Nuclei = 10-15min. Rodar em todo PR é caro e atrasa o ciclo. Smoke (passive + lightweight) = 2-3min, pegável em PR. Full em nightly preserva profundidade sem onerar.

**Decisão:** tiered. Smoke em PR como gate; full nightly como informativo.

**Alternativa descartada:** full em PR. Rejeitado: custo proibitivo.

### 6.3 Por que DAST não em Phase 3 mas em CI

Phase 3 roda na máquina do dev (Claude Code). DAST exige target ambiente rodando (preview env, staging). Roda em CI apenas, onde infra está disponível.

**Decisão:** DAST em CI workflow, não em skill orchestrada por dev.

**Alternativa descartada:** DAST em Phase 3 com docker-compose local. Rejeitado: complexidade alta, dependência externa.

### 6.4 Por que Nuclei templates pinned version

Nuclei templates evoluem (CVE novos surgem). Versão pinned evita "PR quebrou porque template novo bateu" + permite upgrade controlado.

**Decisão:** `quality.dast.nuclei.templates-version: v9.x` no YAML. Upgrade via PR explícito.

**Alternativa descartada:** sempre latest. Rejeitado: instabilidade.

### 6.5 Por que scenarios.yaml e não DSL própria

YAML é universal, lido por jq/yq, reusável. DSL própria seria custoso de manter.

**Decisão:** `tests/regression/scenarios.yaml` simples (interface, request, expected response).

**Alternativa descartada:** Karate / Gauge DSL. Rejeitado: dependência adicional.
