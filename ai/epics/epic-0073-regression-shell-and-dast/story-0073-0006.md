# História: CI workflow `dast-full.yml` (nightly cron + manual dispatch)

**ID:** story-0073-0006
**Status:** Pendente
**Refinement Verdict:** approved

## 1. Visão

Como **security guardian**, quero o workflow `dast-full.yml.template` rodando em **cron diário** (02:00 UTC) + **manual dispatch** (`workflow_dispatch`) + **workflow_call** (consumível por release pipelines), executando DAST tier `--full` (ZAP active + Nuclei full templates) com saída **informativa** — relatório consumido por review humano, **NÃO bloqueador** de PRs em curso.

## 2. Entrega de Valor

- **Valor primário:** DAST profundo (active scan) roda em ritmo regular — captura findings que o tier smoke (passive) não encontra (SQL injection blind, time-based, payload-driven).
- **Valor secundário:** workflow é **consumível por release pipelines** (workflow_call) — `x-release` pode invocar `dast-full` antes de tagear `main` para confirmação.
- **Valor terciário:** comparação entre runs cria uma **série temporal** (artifact retention 30 dias) — permite identificar findings novos entre runs.
- **Métrica primária:** ≥ 1 finding `active-only` (não detectável por smoke) reportado em sprint 1 pós-rollout — valida que o tier full agrega sinal.
- **Métrica secundária:** runtime P95 ≤ 15min (nightly cap aceitável).

## 3. Acceptance Criteria (Gherkin — 4 categorias mandatórias)

```gherkin
Cenario: Happy — cron 02:00 UTC dispara workflow
  DADO repositório com quality.dast.enabled=true e tier-nightly=full
  QUANDO cron 02:00 UTC ocorre
  ENTÃO dast-full.yml dispara automaticamente
  E job sobe target conforme quality.dast.target (D-R9)
  E invoca /x-pentest-dynamic --full
  E SARIF + Markdown report uploaded como artifact (retention 30 dias)
  E workflow status é independente — não afeta PR checks vivos

Cenario: Happy — manual dispatch via workflow_dispatch
  DADO operador acessa Actions UI e clica "Run workflow" em dast-full
  QUANDO operador escolhe branch + opções
  ENTÃO workflow dispara on-demand
  E inputs aceitos: target-override (URL custom), nuclei-version-override (pin temporário)
  E logs marcam claramente "manual dispatch by <user>"

Cenario: Happy — workflow_call consumido por x-release
  DADO release pipeline (x-release) precisa de validação DAST pré-tag
  QUANDO release-pipeline.yml chama dast-full.yml via workflow_call
  ENTÃO dast-full executa com inputs herdados (ref, target, version)
  E retorna outputs: findings-count + sarif-artifact-id
  E release pipeline pode dispatch decisão (proceed / abort) com base nos outputs

Cenario: Degenerate — opt-out via YAML em projeto não-DAST
  DADO projeto declara quality.dast.enabled=false
  QUANDO cron dispara
  ENTÃO workflow detecta flag no primeiro step e termina exit 0 com log "DAST_DISABLED — skipping nightly"
  E nenhum SARIF é gerado

Cenario: Error — target inacessível em ambiente nightly
  DADO quality.dast.target=staging
  E STAGING_BASE_URL retorna 503 ou timeout
  QUANDO workflow dispara
  ENTÃO step "verify target reachable" falha
  E job termina com DAST_TARGET_UNREACHABLE
  E (opcional, se Slack webhook configurado) notificação Slack é enviada
  E workflow run fica vermelho mas NÃO afeta PRs em curso

Cenario: Boundary — runtime cap nightly
  DADO --full executa por > 30min (anomalia)
  QUANDO timeout (configurado 35min) é atingido
  ENTÃO job é cancelado pelo GitHub Actions
  E SARIF parcial é uploaded com findings já coletados
  E sumário lista endpoints NÃO cobertos (transparência)
```

## 6. Decision Rationale

**Decisão:** **nightly informativo, NÃO gate de PR**. **Motivo:** ZAP active scan + Nuclei full = 10-15min wallclock; rodar em todo PR é proibitivo (latência) e em projetos com 100+ PRs/dia gerariam custo de runner alto. Como gate efetivo é o `dast-smoke` (story-0073-0005), `dast-full` complementa com profundidade sem onerar fluxo. **Alternativa descartada:** `dast-full` em PR como gate. **Rejeitado por:** custo proibitivo. **Consequência:** findings active-only podem demorar até 24h para serem detectados (cron diário), o que é aceitável para a categoria (não são exploits zero-day em produção, são vulnerabilidades em código pré-merge).

**Decisão complementar:** triple trigger (cron + workflow_dispatch + workflow_call). **Motivo:** cron cobre cadência regular; workflow_dispatch cobre investigação ad-hoc + hotfix audits; workflow_call permite reuso por release pipeline (x-release pode chamar dast-full antes de tag main). **Alternativa descartada:** apenas cron. **Rejeitado por:** perde flexibilidade de manual run + não consumível por outros workflows. **Consequência:** workflow ganha 3 paths de invocação; testes do smoke E2E precisam cobrir os 3.

**Decisão complementar:** Slack webhook é **opcional** (secret-driven). **Motivo:** projetos podem ou não ter Slack — não fazer dependência rígida. **Alternativa descartada:** notificação obrigatória. **Rejeitado por:** força adoção de Slack; sem secret, ruído ou falha. **Consequência:** projeto com Slack ganha visibilidade ativa; sem Slack, time consulta artifact diretamente em GitHub Actions.

## 7. Refinement Notes (consolidadas)

- **Retention policy:** artifacts retidos por **30 dias** (dentro do free tier do GitHub para repos públicos; ajustável via `actions/upload-artifact@v4` `retention-days: 30`). Para repos privados com plano Enterprise, considerar 90 dias.
- **Comparison-between-runs (stretch):** download artifacts dos últimos 7 runs (`actions/download-artifact@v4` listing via API), parse SARIF de cada um, diff vs run atual, destaque "findings new this run". Stretch — implementar só se aplicável post-MVP.
- **Cron schedule timezone:** 02:00 **UTC** (não local) para consistência cross-region. Ajustável via `quality.dast.cron-utc-hour` no YAML se time pede 03:00 ou 23:00.
- **Manual hotfix audit:** flag `enabled-override=true` permite rodar workflow mesmo com `enabled=false` no YAML — caso de uso: investigação ad-hoc após incidente em produção.
