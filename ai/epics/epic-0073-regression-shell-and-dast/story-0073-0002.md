## 1. Visão

Como **operador**, quero a skill `/x-test-regression-shell` com dois modos:

- **`--self`** (para o nosso CLI gerador): gera os 9 perfis canônicos em sandbox temporária, diff cada um vs golden, executa smoke pós-geração (`./setup.sh` simulado em sandbox + verificação de presença de hooks instalados).
- **`--service`** (para projeto cliente): consome `tests/regression/scenarios.yaml` declarado pelo time, executa cenários cURL (REST) / grpcurl (gRPC) / wscat (Socket) conforme `interfaces[]` declarado, valida status code + payload + headers.

…produzindo um relatório markdown navegável que **não exige montar framework de testes só para um smoke pré-merge**.

## 2. Entrega de Valor

- **Valor primário:** regressão pragmática cobre 2 contextos reais (gerador + cliente) sem inventar DSL nova.
- **Valor secundário:** projetos cliente recebem harness pronto via story-0073-0004 (scenarios.yaml.template stack-aware) e usam **a mesma skill** que o gerador, eliminando "cada time faz o seu".
- **Métrica primária:** ≥ 1 regressão pegável-com-cURL detectada e bloqueada em PR nos 3 primeiros projetos pós-rollout (sinal de que o gate está rodando de verdade).
- **Métrica secundária:** zero regressões funcionais pegáveis-com-cURL chegando a `develop` em 2 sprints pós-rollout.
- **Métrica terciária:** tempo médio do `--self` < 90s em CI (não é gargalo no PR pipeline).

```gherkin
  OU em tests/regression/results/regression-self-YYYY-MM-DD.md (modo standalone)

  E tests/regression/scenarios.yaml com 3 cenários REST (GET /health, POST /users, GET /users/{id})
  QUANDO operador invoca /x-test-regression-shell --service
  ENTÃO 3 cenários executam (cURL com timeout, headers e auth conforme YAML)

  E relatório em tests/regression/results/regression-service-YYYY-MM-DD.md
  E exit 0 quando todos passam; exit 1 quando ≥ 1 falha

Cenario: Degenerate — scenarios.yaml ausente em modo service
  DADO projeto cliente com quality.regression.enabled=true E mode=service
  E tests/regression/scenarios.yaml NÃO existe
  QUANDO operador invoca /x-test-regression-shell --service
  ENTÃO skill aborta com erro REGRESSION_SCENARIOS_MISSING
  E mensagem orienta: "rode ia-dev-env generate ou crie tests/regression/scenarios.yaml a partir do template"
  E exit 2 (OPERATIONAL_ERROR)

Cenario: Error — interfaces[] e scenarios.yaml divergentes
  DADO YAML projeto declara interfaces=[rest, grpc]
  E scenarios.yaml contém apenas cenários REST (sem grpc)
  QUANDO skill --service roda
  ENTÃO WARN INTERFACES_COVERAGE_PARTIAL é emitido (não fatal)
  E relatório destaca cobertura: "rest: 3 cenários | grpc: 0 cenários (cobertura parcial)"
  E exit 0 se cenários rest passam (não bloqueia por cobertura parcial — opt-in time decide quando expandir)

Cenario: Boundary — self mode com goldens dessincronizados (drift)
  DADO 1 dos 9 perfis tem golden desatualizado vs código vigente
  QUANDO skill --self roda
  ENTÃO diff é detectado e relatório mostra +/- linhas
  E skill emite REGRESSION_GOLDEN_DRIFT (exit 1)
  E mensagem orienta: "rode mvn process-resources && GoldenFileRegenerator se a mudança é intencional"
```

## 6. Decision Rationale

**Decisão:** modo dual numa skill (`--self` + `--service`). **Motivo:** lógica compartilhada (parse YAML, render report, exit codes) representa ~60% do código; duas skills duplicariam essa parte. **Alternativa descartada:** 2 skills (`x-test-regression-self`, `x-test-regression-service`). **Rejeitado por:** drift entre as duas + onerar `/help` com 2 entradas próximas. **Consequência:** SKILL.md ganha um `case "$mode"` no Phase 1 dispatch; documentação separa claramente os 2 modos via `## Modes` section.

**Decisão complementar:** `model: sonnet` (Rule 23 — Reviewer/Validator tier). **Motivo:** skill orquestra tools externos (cURL/grpcurl/wscat), faz parse YAML, formata relatório markdown — sem deep design reasoning inline. **Alternativa descartada:** `opus` (overkill para this orchestration). **Consequência:** custo ~5× menor por execução; aceitável dado que skill roda em CI + ad-hoc.

  ```yaml
    - id: get-health
      interface: rest

        headers: { Accept: "application/json" }

        status: 200
        headers: { Content-Type: "application/json" }

          json-path: $.status
  ```
