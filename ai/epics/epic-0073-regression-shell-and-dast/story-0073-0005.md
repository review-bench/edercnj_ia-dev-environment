# História: CI workflow `dast-smoke.yml` (gate de PR) + CI script `audit-regression-shell.sh`

**ID:** story-0073-0005
**Status:** Pendente
**Refinement Verdict:** approved

## 1. Visão

Como **CI guardian**, quero entregar dois artefatos complementares de Camada 4 (workflow) + Camada 2 (CI script):

1. **`dast-smoke.yml.template`** — workflow GitHub Actions que dispara em `pull_request: opened|synchronize` e invoca `/x-pentest-dynamic --smoke`. Cobre `quality.dast.enabled=true` (skip silencioso quando false). Sobe target conforme `quality.dast.target` (D-R9), executa skill, faz upload de SARIF + Markdown report como artifacts.
2. **`audit-regression-shell.sh`** — CI script Camada 2 (Rule 26) que verifica que `quality.regression.enabled=true && mode=service` implica `tests/regression/scenarios.yaml` presente E `/x-test-regression-shell --service` foi executado no PR (via telemetria NDJSON ou marker artifact). Exit codes Rule 26 (0/1/2/3) + `--self-check` mandatório.

…para que **DAST + regression-shell tenham gate efetivo em PR**, não apenas opt-in confiando que o time lembra.

## 2. Entrega de Valor

- **Valor primário:** DAST + regression-shell viram gate sintético — PRs falham se DAST encontra HIGH/CRITICAL ou se regression-shell foi declarado mas não rodou.
- **Valor secundário:** SARIF artifact é consumível pelo GitHub Security tab (visualização nativa de findings).
- **Métrica primária:** 100% dos PRs em projetos com `quality.dast.enabled=true` rodam `dast-smoke.yml` (medido pelo presence do workflow run nos PRs do mês pós-rollout).
- **Métrica secundária:** 100% dos PRs em projetos com `quality.regression.enabled=true && mode=service` passam por `audit-regression-shell.sh` (script lança `REGRESSION_SHELL_VIOLATION` se não rodou).
- **Métrica terciária:** dast-smoke runtime P95 ≤ 5min em CI (não vira gargalo de PR).

## 3. Acceptance Criteria (Gherkin — 4 categorias mandatórias)

```gherkin
Cenario: Happy — workflow dast-smoke dispara em PR e gera SARIF
  DADO PR aberto em projeto com quality.dast.enabled=true
  E quality.dast.target=local-container e docker-compose.yml presente
  QUANDO PR é aberto/sincronizado
  ENTÃO dast-smoke.yml workflow dispara automaticamente
  E job sobe target (docker compose up -d), aguarda healthy (≤ 60s)
  E invoca /x-pentest-dynamic --smoke (ZAP passive + Nuclei lightweight)
  E artifact SARIF (results/security/dast/dast-smoke-*.sarif) é uploaded
  E artifact Markdown (results/security/dast/dast-smoke-*.md) é uploaded
  E exit code do job mapeia para CI status (PR check) — verde quando 0; vermelho quando 1

Cenario: Happy — audit-regression-shell.sh valida execução obrigatória
  DADO projeto com quality.regression.enabled=true && mode=service
  E PR continha invocação de /x-test-regression-shell --service registrada em telemetria
  QUANDO audit-regression-shell.sh roda no CI
  ENTÃO exit 0 (OK)
  E nada é emitido em stderr

Cenario: Degenerate — opt-out via YAML resulta em workflow no-op
  DADO projeto com quality.dast.enabled=false
  QUANDO PR é aberto
  ENTÃO dast-smoke.yml ainda dispara (presença incondicional)
  E job detecta flag e emite "DAST_DISABLED — skipping (opt-out)"
  E job termina exit 0 em < 30s
  E nenhum SARIF é gerado

Cenario: Error — audit-regression-shell.sh detecta omissão
  DADO projeto com quality.regression.enabled=true && mode=service
  E PR NÃO contém invocação de /x-test-regression-shell registrada
  QUANDO audit-regression-shell.sh roda
  ENTÃO exit 1 com REGRESSION_SHELL_VIOLATION
  E mensagem orienta: "regression-shell declared in YAML but not executed in PR — invoque /x-test-regression-shell --service"

Cenario: Error — script --self-check falha quando jq ausente
  QUANDO audit-regression-shell.sh --self-check roda em ambiente sem jq
  ENTÃO exit 2 (OPERATIONAL_ERROR)
  E mensagem cita "jq required on PATH" (Rule 26 §--self-check template)

Cenario: Boundary — workflow timeout cap
  DADO dast-smoke executa por > 8min (anomalia — target lento)
  QUANDO o workflow atinge timeout (configurado 10min)
  ENTÃO job é cancelado pelo GitHub Actions
  E artifact parcial é uploaded
  E PR check fica vermelho com mensagem timeout
```

## 6. Decision Rationale

**Decisão:** workflow separado (`dast-smoke.yml`) — não estender `ci.yml`. **Motivo:** DAST tem dependências externas (ZAP, Nuclei), runtime potencialmente longo (até 5min), e ciclos de update independentes (Nuclei templates) — manter isolado evita poluir `ci.yml`. **Alternativa descartada:** job adicional em `ci.yml`. **Rejeitado por:** acopla update de DAST tooling ao update de CI principal. **Consequência:** dois workflows distintos com triggers idênticos para PR, mas que evoluem independentemente.

**Decisão complementar:** `audit-regression-shell.sh` é **CI script (Camada 2)** — não Hook runtime. **Motivo:** valida artefatos do PR (telemetria + arquivo `scenarios.yaml`); não precisa rodar durante turno do LLM (Rule 26 §Decision Matrix). **Alternativa descartada:** Hook PostToolUse. **Rejeitado por:** latência adicional em todo turno LLM, mesmo quando irrelevante. **Consequência:** validação ocorre 1x por PR (suficiente).

**Decisão complementar:** `dast-smoke.yml` dispara **incondicionalmente** (toda vez que PR é aberto), com short-circuit no primeiro step quando `enabled=false`. **Motivo:** garantir presença do gate na infra (não esperar o time "lembrar de habilitar"). **Alternativa descartada:** `if: ${{ env.DAST_ENABLED == 'true' }}` no nível de workflow. **Rejeitado por:** se YAML está corrompido, workflow nem dispara — perda de sinal. **Consequência:** workflow sempre dispara mas terminal exit 0 em < 30s quando opt-out.

## 7. Refinement Notes (consolidadas)

- **Cache Nuclei templates:** `actions/cache@v4` com key derivada de `quality.dast.nuclei.templates-version` (D-R8). Cobertura ~95% dos runs (cache hit) economiza ~30s.
- **Secrets management para ZAP:** ZAP API key (se usado active mode futuro) vive em `secrets.ZAP_API_KEY` — workflow não imprime no log.
- **DAST target URL injection (D-R9):** workflow tem step condicional:
  - `local-container`: `docker compose up -d && DAST_TARGET_URL=http://localhost:8080`.
  - `preview-env`: lê output de workflow upstream (`needs.preview-deploy.outputs.url`).
  - `staging`: `DAST_TARGET_URL=${{ secrets.STAGING_BASE_URL }}`.
- **Concurrency group:** cancela run anterior quando novo push acontece no mesmo PR (`cancel-in-progress: true`) — evita acumular runs zumbis.
