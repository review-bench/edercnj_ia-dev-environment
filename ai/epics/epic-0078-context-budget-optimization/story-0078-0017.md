### 3.1.1 Baseline Contract (`release-elapsed-baseline.json`) — operator Q5=a

| Campo | Tipo | Sempre presente | Descrição |
| :--- | :--- | :--- | :--- |
| `stubMergeCommit` | String (commit-sha) | Sim | SHA do merge-commit de story-0078-0013 em `develop` (o "tracking origin"). |
| `trackingSince` | String (ISO-8601) | Sim | Timestamp da gravação do baseline (informativo; não usado no algoritmo). |

**Algoritmo de contagem (commit-based, NOT date-based):**

1. Resolver `<stubMergeCommit>` do baseline.
2. Listar tags `vX.Y.Z` em `main` (`git tag --list 'v*' --merged main`).
3. Para cada tag, verificar `git merge-base --is-ancestor <stubMergeCommit> <tag-commit>`. Tag é elegível se o commit-de-merge da story-0078-0013 é ancestral do tag.
4. Need ≥ 2 such tags → exit 0; senão exit 1 `RELEASE_WINDOW_NOT_REACHED`.

### 3.1.2 Equivalência Bash ↔ Java (operator Q4=c)

| Implementação | SoT para | Localização |
| :--- | :--- | :--- |
| `audit-release-elapsed.sh` | CI workflow shell (declarado em RULE-011) | `src/main/resources/targets/claude/scripts/audit-release-elapsed.sh` |
| `ReleaseWindowVerifier.java` | `mvn verify` integration | `src/main/java/dev/iadev/audit/ReleaseWindowVerifier.java` |

Ambos:
- Leem o **mesmo** baseline `governance/baselines/release-elapsed-baseline.json`.
- Computam o **mesmo** resultado (mesmo conjunto de tags elegíveis, mesmo exit code).
- Coexistem por design (operator Q4=c). Equivalência verificada por `ReleaseElapsedEquivalenceTest.java` que invoca ambos sobre o mesmo input e asserts mesmo exit code + mesmo conjunto de tags consideradas.

## 8. Decision Rationale

**Decisão:** Manter como story explícita (não automatizar via cron/scheduler).
**Motivo:** Operação sensível (deleção de 4 rules + regeneração de 11 perfis); requer revisão humana e PR explícito; menor risco de regressão silenciosa.
**Alternativa descartada:** Cron job que detecta janela de release e abre PR automaticamente. Rejeitado: aumenta superfície de automação para benefício marginal; story-0078-0017 é one-shot por épico.
**Consequência:** Operador deve invocar manualmente após release n+2 — gating temporal documentado em DoR previne erro.

**Decisão:** Gating temporal verificável por `git tag --list` (não por data).
**Motivo:** Releases podem se atrasar; data wall-clock seria injusto. Tag-count reflete intenção real ("dois ciclos de release passaram").
**Alternativa descartada:** Gating por data (ex.: "90 dias após merge"). Rejeitado: desacopla da cadência real do projeto.
**Consequência:** Se projeto entrar em hiato sem releases, story permanece bloqueada — comportamento desejado.
