## 1. Contexto & Escopo

Como **Tech Lead**, eu quero (a) elevar `audit-context-budget.sh` de advisory para hard-fail com limite 25.000 tokens always-loaded, (b) publicar ADR documentando "rules são contratos curtos", e (c) entregar `_TEMPLATE-RULE.md` com 4 blocos canônicos (Purpose, Invariants/Forbidden, Enforcement, Reference), garantindo que a convenção introduzida pelo EPIC-0078 fique cristalizada e bloqueie regressão futura.

Esta é a história de "fechamento do contrato": stories anteriores (0078-0001 a 0078-0015) entregaram o tooling, slimming, KPs, audits e pruning. Esta consolida tudo em invariantes mecânicos (CI hard-fail) e documentais (ADR + template). Após esta story, qualquer rule nova que ultrapasse o budget é bloqueada antes do merge; qualquer autor de rule pega o template e segue automaticamente o padrão.

## 3. Contratos & Endpoints

### 3.1 Audit Script Behavior

| Modo | Limite efetivo | Exit code |
| :--- | :--- | :--- |
| Advisory (anterior) | warn em > baseline.limit | 0 |
| Hard-fail (nova) | falha em > baseline.limit | 1 |

**Limit precedence (resolves contradiction):**
1. `--limit <N>` flag (CLI) — overrides para validação ad-hoc / debug.
2. `baseline.limit` (campo do JSON) — fonte primária; permite ADR/operador override sem mudança de código.
3. Default `25000` — usado quando `baseline.limit` ausente. Equivalente a "novo baseline ainda não publicado".

A regra "Hard-fail when measured > baseline.limit (default 25000)" substitui a leitura literal do número em código.

## 8. Decision Rationale

**Decisão:** Hard-fail com limite 25000 tokens (não 22000 ou 30000).
**Motivo:** Headroom de ~3000 tokens sobre a medição esperada pós-slim (~22000) para acomodar crescimento orgânico saudável; bem abaixo do baseline pré-épico (~52000).
**Alternativa descartada:** Limite dinâmico (baseline + N%). Rejeitado: limite estático é mais legível, menos surpresa em CI; revisões periódicas via PR.
**Consequência:** Após 2-3 releases, pode ser necessário renegociar limite para acomodar novas rules — explícito via PR ao baseline JSON.

**Decisão:** Template `_TEMPLATE-RULE.md` com 4 blocos canônicos (não 5+).
**Motivo:** 4 blocos = núcleo mínimo. Mais blocos viram cargo culture; menos perde estrutura.
**Alternativa descartada:** Template livre + checklist. Rejeitado: checklist sem estrutura textual perde valor pedagógico.
**Consequência:** Rules complexas precisam encaixar conteúdo extenso em "Reference" (link para KP) — alinha com RULE-001.

### 8.1 Riscos & Interações

| ID | Risco | Mitigação |
| :--- | :--- | :--- |
| R-1 | Pruned-by-advisory rules (story-0078-0014) NÃO são contadas no budget — composer só emite quando capability presente. Audit mede o que assembler outputs para o canonical "core minimal" profile. | Documentado explicitamente. `audit-context-budget.sh` opera sobre output do composer (não sobre source-of-truth completo). |
| R-2 | Em hard-prune mode (ativado nesta story per Q2=a), pruned rules desaparecem inteiramente do output do default profile. Métrica reflete carga real, não potencial. | Esta é a propriedade desejada. CHANGELOG `## Changed` documenta a transição advisory→hard. |
| R-3 | Operador renegociar `baseline.limit` para um valor maior dribla o gate. | Mudança a `baseline.limit` requer PR + revisão; ADR obrigatório quando >25000. Documentado em DoR. |

**Decisão:** Composer flip de advisory → hard-prune (operator Q2=a).
**Motivo:** Após validar capability annotation em story-0078-0014 (modo advisory), esta story ativa o hard-prune como default — capability-aware rules são fisicamente excluídas do output `.claude/` quando capability não está presente no perfil.
**Alternativa descartada:** Permanecer advisory + log. Rejeitado: advisory deixa rules carregadas mesmo em perfis que não as usam, defeating o propósito do épico.
**Consequência:** Em hard-prune, `audit-context-budget.sh` mede apenas o que o assembler emite para o "core minimal" profile (sem capabilities estendidas) — números refletem baseline real always-loaded.
