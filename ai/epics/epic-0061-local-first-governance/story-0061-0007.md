## 1. Contexto & Escopo

Como **operador de projetos `.claude/` já gerados pré-EPIC-0061**, eu quero (a) um discriminador `flowVersion: "3"` em `execution-state.json` que marca epics nascidos no lifecycle local-first e (b) um script `migrate-to-local-first.sh` idempotente que copia os novos templates de audit + atualiza configs em projetos `.claude/` existentes, garantindo que não preciso regenerar o projeto inteiro do zero para receber o lifecycle local-first.

Esta é a **story terminal** do épico. Adiciona o terceiro valor à matriz `flowVersion` da Rule 19 (`"1"` legacy, `"2"` EPIC-0049, `"3"` EPIC-0061 local-first). Backward compat preservada — epics em flight com `flowVersion: "2"` continuam funcionando inalterados; apenas epics novos nascem com `"3"` e engajam o lifecycle local-first integralmente.

O migration script `scripts/migrate-to-local-first.sh` é gerado (sob `targets/claude/scripts/_default/migrate-to-local-first.sh.tpl`) e copiado para `.claude/scripts/` em cada projeto. Operadores com projetos pré-EPIC-0061 rodam o script em modo `--dry-run` primeiro, depois `--apply`. Tag `local-first-lifecycle-frozen` é criada em develop após merge, marcando o ponto de "épico fechado" e habilitando releases MINOR.

- **Valor Principal:** Discriminador formal `"3"` permite orchestrators dispatcharem comportamento por flowVersion. Projetos legados ganham migration script idempotente.

- **Impacto no Negócio:** Adoção do lifecycle local-first sem regen completa. Releases MINOR podem prosseguir.

## 3. Contratos & Endpoints

### 3.1 `flowVersion` Matrix (Rule 19 update)

| Valor | Significado | Comportamento dos orchestrators |
| :--- | :--- | :--- |
| `"1"` | Legacy (pre-EPIC-0049) | Story PRs target `develop`; sem epic branch; menus interativos default |
| `"2"` | EPIC-0049 | Story PRs target `epic/XXXX`; manual gate; menus interativos default (até EPIC-0061) |
| `"3"` (NOVO) | EPIC-0061 local-first | Story PRs target `epic/XXXX`; menus opt-in via `--interactive`; Java audit no CI; bash audits no projeto-alvo |

### 3.2 `migrate-to-local-first.sh` Contract

| Modo | Comportamento | Exit code |
| :--- | :--- | :--- |
| `--dry-run` | Reporta diff esperado (arquivos a copiar/atualizar). Sem efeitos. | 0 (preview OK), 1 (preview vazio = nada a fazer) |
| `--apply` | Aplica mudanças idempotentemente. | 0 (success), 1 (parcial — alguma mudança falhou), 2 (operacional) |
| `--self-check` | Verifica deps (jq, git). | 0 (OK), 2 (deps faltando) |

Mudanças aplicadas pelo `--apply`:

1. Copia `.claude/scripts/audit-*.sh` da stack detectada (lê `ProjectConfig` ou heurística por arquivo: `pom.xml` → java-maven, `package.json` → node, etc.)
2. Atualiza `.github/workflows/ci.yml` para invocar `bash .claude/scripts/audit-all.sh`
3. Atualiza `execution-state.json` em `plans/epic-*/` (epics em flight) — adiciona `flowVersion: "2"` se ausente; epics NOVOS criados após o script nascem com `"3"`
4. Imprime checklist de "manual review" para itens que demandam atenção humana (CHANGELOG, ADRs cruzados, etc.)

### 3.3 `ExecutionState` Schema Update

```java
public record ExecutionState(
    String flowVersion,    // "1" | "2" | "3"
    String epicId,
    Map<String, StoryStatus> storyStatuses,
    TaskTracking taskTracking,
    Boolean localFirstLifecycle  // NOVO — true quando flowVersion="3"
) {}
```

`localFirstLifecycle` é **derivado** de `flowVersion="3"` mas explicitado em JSON para facilitar grep e auditoria.

## 8. Decision Rationale

**Decisão:** Adicionar campo `localFirstLifecycle: bool` em `execution-state.json` mesmo sendo derivado de `flowVersion="3"`.

**Motivo:** Operadores e scripts de auditoria que fazem `grep "localFirstLifecycle" plans/*/execution-state.json` ganham resposta imediata sem precisar parsear flowVersion. Trade-off: pequena duplicação semântica para grande ganho de discoverability.

**Alternativa descartada:** Apenas `flowVersion: "3"` sem campo derivado. Descartada porque grep direto vira mais elegante e auditoria via `jq` é mais simples (`.localFirstLifecycle`).

**Consequência:** Inconsistência entre `flowVersion: "2"` e `localFirstLifecycle: true` (impossível por design) seria um bug. Mitigação: validator em `ExecutionState.parse` rejeita combinação inválida com mensagem clara.
