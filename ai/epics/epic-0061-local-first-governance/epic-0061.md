## 1. Contexto & Escopo

**Chave Jira:** —

O repositório `ia-dev-environment` é um **gerador de projetos** que produz `.claude/` para um stack-alvo (Java/Maven, Spring Boot, Node, Python, Go). Três sintomas operacionais expõem uma confusão arquitetural na governança atual: (a) `scripts/audit-*.sh` vivem no raiz do gerador e referenciam Maven/JaCoCo, ficando órfãos quando o CLI gera para Spring/Node/Python — o projeto-alvo não recebe governança equivalente; (b) o workflow `.github/workflows/audit.yml` bloqueia PRs do gerador rodando 8 audits bash em paralelo ao `ci.yml` Java, duplicando custo de runner e introduzindo flakiness por dependências (jq, yq, gh, bash); (c) orchestrators (`x-epic-implement`, `x-story-implement`, `x-release`, `x-review-pr`) têm gates 3-opções (Rule 20) com **default = interativo**, o que trava sessões LLM em menus que ninguém responde. Adicionalmente, o agente entra em "confirmação defensiva" ao detectar working tree suja ou branch divergente.

Este épico **separa três layers** que estão hoje misturados: hooks locais (Camada 0, preventivo durante sessão LLM — permanecem como estão); audits de template/runtime (são gerados como bash por stack via `ScriptsAssembler` e servem o projeto-alvo); validação interna do gerador (rodando como `*AuditTest.java` em `mvn verify`, sem `audit.yml` paralelo). Como consequência, o CLI passa a entregar governança apropriada para cada stack gerado, o CI do gerador roda apenas `mvn verify` (1 job único), e orchestrators executam non-interactive por padrão (`--interactive` vira opt-in explícito).

## 3. Contratos & Endpoints

Épico de governança e geração. Nenhum endpoint REST/gRPC. Artefatos gerados:

- **Bash scripts** sob `.claude/scripts/audit-*.sh` no projeto-alvo (renderizados por stack)
- **Wrapper único** `.claude/scripts/audit-all.sh` que roda os 8 audits e agrega exit codes

- **Java classes** `dev.iadev.audit.*Auditor` no gerador apenas (não exportadas)

## 8. Decision Rationale

**Decisão:** Manter os audits implementados em **bash como forma canônica** (gerada por stack para o projeto-alvo) e **Java como espelho** (apenas no gerador, validado por smoke equivalence test).

**Motivo:** Bash é portável entre stacks (Java/Spring/Node/Python/Go todos têm bash + jq + gh disponíveis em qualquer CI runner). Java seria ideomatico só para projetos Java — quebraria a portabilidade. Java no gerador acelera feedback (sem dependência de bash em developer machines Windows) e dá veredicto único no log do `mvn verify`. O custo da duplicação é amortizado pelo `AuditEquivalenceSmokeIT` que prova paridade.

**Alternativa descartada:** Polyglot via "Java CLI + bash wrapper" (audit é uma classe Java executada por `java -cp .claude/audit/audit.jar dev.iadev.audit.AuditCli`). Descartada porque exigiria runtime Java em projetos Node/Python/Go — quebra premissa de stack agnostic.

**Consequência:** Toda mudança em lógica de audit demanda edição em **dois lugares** (bash + Java) e regeneração do golden corpus. Isso é mitigado pelo smoke test de equivalência que falha o build se uma das duas for esquecida. Stack-mismatch (ex.: `audit-maven-coverage.sh` em projeto Node) é resolvido por templates por stack — não vai existir audit Maven em projeto Node.
