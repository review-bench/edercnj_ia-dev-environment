## 1. Contexto & Escopo

Como **arquiteto de governança**, eu quero que Rule 26 (Audit Gate Lifecycle) reflita a arquitetura local-first do épico, formalizando a separação entre **Camada 0 (Local Hooks Preventivos)** que rodam DURANTE sessão LLM e **Camadas 2-4 (CI script, Java test, Workflow)** que rodam DEPOIS (detectivos), garantindo que operadores e contributors entendam onde cada gate vive e por que.

Hoje Rule 26 documenta 4 camadas mas as trata como mecanicamente equivalentes — uma pode substituir a outra. Esta story estende para 5 camadas com uma distinção semântica explícita: Camada 0 (preventiva, durante turn LLM) vs Camadas 2-4 (detectivas, após o fato). ADR-0017 (Local-First Lifecycle Convention) publica a decisão arquitetural e explica trade-offs (preventivo é melhor mas não substitui detectivo defense-in-depth).

Adicionalmente, a story formaliza o contrato dos hooks `verify-*.sh` existentes: contrato de exit codes, formato de mensagens stderr, integração com `ProcessRunner` para testabilidade. Hoje os hooks existem mas seus contratos vivem espalhados em comentários — Rule 26 §Camada 0 passa a ser source of truth.

## 3. Contratos & Endpoints

### 3.1 Rule 26 Updated Taxonomy

| Camada | Trigger | Localização | Quando roda | Reação |
| :--- | :--- | :--- | :--- | :--- |
| **0 — Local Hooks Preventivos (NOVO)** | Eventos Claude Code (PreToolUse, Stop, SessionStart) | `.claude/hooks/verify-*.sh` | DURANTE sessão LLM | Bloqueia tool call ou emite WARNING via stderr |
| **1 — Normative** | Loaded into context | `.claude/rules/*.md` + `CLAUDE.md` | Cada conversa | LLM consciente de regras |
| **2 — CI Script** | PR open/sync | `.claude/scripts/audit-*.sh` (no projeto-alvo) | Após push | Falha o build |
| **3 — Java Test** | `mvn verify` | `framework/src/test/java/dev/iadev/audit/` (no gerador) | Build do gerador | Falha o build |
| **4 — CI Workflow** | GitHub Actions | `.github/workflows/*.yml` | Orchestrate Camadas 2/3 | Falha o job |

### 3.2 Hook Contract (Camada 0)

Todo `verify-*.sh` em `.claude/hooks/` MUST:

- Aceitar argumentos via env vars passadas pelo Claude Code (sem args posicionais)
- Retornar exit 0 (OK), 2 (WARNING — surfacing para LLM), ou outro código fail-fast
- Stderr emite mensagem human-readable; stdout reservado para evento Claude Code consumir
- Latência típica < 500ms (não bloquear UX da sessão)
- `CLAUDE_TELEMETRY_DISABLED=1` desliga emissão de telemetria mas não desliga o hook em si

### 3.3 ADR-0017 Outline

```markdown
# ADR-0017 — Local-First Lifecycle Convention

## Status
Accepted (2026-04-27, EPIC-0061)

## Context
Pre-EPIC-0061: governance lived in two places — hooks locais (preventivo)
e scripts/audit-*.sh + audit.yml (detectivo, redundante com hooks).

## Decision
Adopt 5-layer taxonomy: Camada 0 (preventivo, durante LLM turn) +
Camadas 1-4 (detectivos, after-the-fact).

## Consequences
+ Onboarding mais claro (contributors veem onde colocar novo gate)
+ CI mais rápido (Camada 4 mais leve, sem duplicação com Camada 0)
- Hooks locais não rodam em CI runners (não substituem Camada 2/3 — defense in depth)

## Related
- Rule 26 §Camada 0 (extended)
- EPIC-0061 RULE-006
```

- [ ] **`verify-story-completion.sh` heurística refinada** (Rule 25 §False-Positive Storm fix). Hoje o hook combina Signal A (`gh pr create` em até 500 eventos antigos da telemetria) com Signal B (`story-XXXX-YYYY` em qualquer parte do `git log -1 --format=%B`) — combinação cria loop infinito quando branch tem PR mergeado mas nenhum commit foi feito na sessão atual. Refinamento: substituir Signal A por **commit count delta da sessão** (`git log --since="$SESSION_START_TIMESTAMP" --oneline | wc -l > 0`), e Signal B por **match em commit DA SESSÃO** (não no HEAD pré-existente). Variável `SESSION_START_TIMESTAMP` populada via `SessionStart` hook gravando timestamp em `.claude/state/session-start-{pid}.txt`.
- [ ] Smoke test do refinamento: rodar hook duas vezes consecutivas em fixture sem commits novos → ambas exit 0 silenciosamente. Rodar uma vez em fixture com commit novo de story sem evidence → exit 2 com warning correto.

## 8. Decision Rationale

**Decisão:** Renumerar para "Camada 0" em vez de "Camada 5" (no final da lista existente).

**Motivo:** Camadas 0-4 forma uma sequência **temporal lógica**: 0 (preventivo, durante turn) → 1 (normativo, contexto) → 2 (CI script local-ish) → 3 (Java test no build) → 4 (orquestração). Numeração crescente reflete "quão tarde no lifecycle o gate dispara". Renumeração quebra referências a "Camada 1-4" em ADRs antigos — mitigação: ADR-0017 explicita o mapping (antiga Camada 1 → nova Camada 1; nova Camada 0 é adição).

**Alternativa descartada:** Renomear sem renumerar (manter Camadas 1-4, usar nomes descritivos "Preventive Layer" + "Layers 1-4"). Descartada por inconsistência: nomeação mista ("Layer 0" vs "Preventive Layer") é mais confusa que numérica uniforme.

**Consequência:** Documentação histórica (CHANGELOG, ADRs antigos) que mencionam "Camada 1" agora referem-se ao que era "Camada 1" pré-EPIC-0061 (Normative). Sem renumeração — apenas adição de Camada 0 antes. Sem breaking change.
