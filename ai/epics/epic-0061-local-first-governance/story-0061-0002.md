## 1. Contexto & Escopo

Como **gerador de projetos `.claude/`**, eu quero que os 8 audit scripts sejam materializados como templates por stack-alvo (java-maven, java-gradle, spring-boot, node, python, go, _default), garantindo que projetos Spring/Node/Python recebam governança apropriada em vez de scripts hardcoded para Maven que ficariam inúteis.

Hoje (pós-EPIC-0058), `ScriptsAssembler` existe e copia scripts genericamente. Esta story estende-o para resolver templates **por stack**: ao gerar um projeto-alvo Spring, o `ScriptsAssembler` lê de `targets/claude/scripts/spring-boot/` (que herda os 8 audits comuns + adiciona `audit-actuator-exposure.sh` específico de Spring); ao gerar para Node, lê de `targets/claude/scripts/node/` (com adaptações para `package.json` em vez de `pom.xml`). Stacks desconhecidas caem para `_default/` (apenas os 5 audits markdown — runtime audits exigem conhecimento de stack).

Templates carregam placeholders (`{{BUILD_TOOL}}`, `{{COVERAGE_REPORT_PATH}}`, `{{LOCK_FILE}}`) resolvidos em geração. Os scripts atuais sob `scripts/audit-*.sh` raiz do gerador servem como **semente** para `targets/claude/scripts/java-maven/` (cópia 1:1 com placeholders). Demais stacks adaptam a partir da semente.

### 1.1 Regras Transversais Aplicáveis

| ID | Título |
| :--- | :--- |

| RULE-003 | Templates por Stack |

### 1.2 Entrega de Valor

- **Valor Principal:** Projetos gerados em qualquer stack suportado recebem governança apropriada via 8 audit scripts adaptados.
- **Métrica de Sucesso:** 7 stacks (`java-maven`, `java-gradle`, `spring-boot`, `node`, `python`, `go`, `_default`) com templates funcionais. `Stack{X}AuditSmokeIT` verde para cada um.
- **Impacto no Negócio:** Permite usar o CLI `ia-dev-env` para gerar projetos não-Java sem sacrificar governança de lifecycle.

## 3. Contratos & Endpoints

### 3.1 `StackResolver` API

| Método | Parâmetros | Retorno | Comportamento |
| :--- | :--- | :--- | :--- |
| `resolveTemplateDir(stack)` | `String stack` (ex.: "spring-boot") | `Path` | `targets/claude/scripts/{stack}/` ou `_default/` se desconhecida |
| `supportedStacks()` | — | `List<String>` | Lista hardcoded das 6 stacks com runtime audits |

### 3.2 Placeholder Resolution Contract

| Placeholder | Java/Maven | Java/Gradle | Spring Boot | Node | Python | Go |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| `{{BUILD_TOOL}}` | `mvn` | `gradle` | `mvn` | `npm` | `pip` | `go` |
| `{{COVERAGE_REPORT_PATH}}` | `target/site/jacoco/jacoco.xml` | `build/reports/jacoco/test/jacocoTestReport.xml` | `target/site/jacoco/jacoco.xml` | `coverage/lcov.info` | `coverage.xml` | `coverage.out` |
| `{{LOCK_FILE}}` | `pom.xml` | `gradle.lockfile` | `pom.xml` | `package-lock.json` | `requirements.txt` | `go.sum` |
| `{{TEST_COMMAND}}` | `mvn verify` | `./gradlew check` | `mvn verify` | `npm test` | `pytest` | `go test ./...` |

### 3.3 Audit Catalog per Stack

Os 5 audits de Template (markdown scan) existem em **todas** as stacks (são stack-agnostic):
- `audit-model-selection.sh`
- `audit-skill-visibility.sh`
- `audit-bypass-flags.sh`
- `audit-task-hierarchy.sh`
- `audit-phase-gates.sh`

Os 3 audits de Runtime existem em todas exceto `_default`:
- `audit-flow-version.sh`
- `audit-epic-branches.sh`
- `audit-execution-integrity.sh`

Audits stack-específicos:
- `spring-boot/audit-actuator-exposure.sh` — Verifica que `application.yml` não expõe `/actuator/env`, `/heapdump` em produção
- `node/audit-package-lock-integrity.sh` — Verifica `npm audit` + integridade de `package-lock.json`
- `python/audit-requirements-pin.sh` — Verifica que dependências em `requirements.txt` têm `==` (pin) e não `>=`
- `go/audit-go-mod-tidy.sh` — Verifica que `go.mod` está tidy (sem deps espúrias)

## 4. Materialização SOLID

### 4.1 Regras Aplicáveis do Épico

| ID | Título | Impacto |
| :--- | :--- | :--- |
| RULE-002 | ScriptsAssembler como SoT | `ScriptsAssembler` é a única rota; outros assemblers não copiam scripts diretamente |
| RULE-003 | Templates por Stack | Implementação direta — 7 diretórios de templates |

### 4.2 Princípios SOLID

- **SRP:** `ScriptsAssembler` apenas copia + resolve placeholders. `StackResolver` apenas mapeia stack → path.
- **OCP:** Nova stack = novo diretório `targets/claude/scripts/{stack}/` + entrada em `StackResolver.supportedStacks()`. Sem modificação no `ScriptsAssembler`.
- **DIP:** `ScriptsAssembler` recebe `StackResolver` via construtor.

### 4.3 Coding Constraints

- `StackResolver.java` ≤ 100 linhas
- `ScriptsAssembler.java` ≤ 200 linhas (após extensão)
- Templates `.sh.tpl` carregam shebang `#!/usr/bin/env bash` + `set -euo pipefail`

## 6. Segurança

| Área | Controle | Status |
| :--- | :--- | :--- |
| Path operations no assembler | `StackResolver.resolveTemplateDir` rejeita stack com `../` ou caracteres não-alfanuméricos. Regex `^[a-z][a-z0-9-]*$`. | Required |
| Placeholder substitution | Substituição via `String.replace` (literal, não regex). Zero risco de injection via valor de placeholder. | Required |
| Templates gerados | Cada `.sh.tpl` carrega `set -euo pipefail`. Variáveis sempre quoted (`"$VAR"`). | Required |

## 8. Decision Rationale

**Decisão:** Usar diretório por stack (`targets/claude/scripts/{stack}/`) em vez de single-file template com `if [[ stack == "..." ]]` blocks.

**Motivo:** Templates por stack mantêm cada audit script focado e legível (~50 linhas). Single-file com branches viraria 600+ linhas de bash com nested conditionals — alta dificuldade de manutenção. Diretórios também permitem `git diff` claro quando uma stack precisa de adaptação.

**Alternativa descartada:** Generator usando templating engine (Mustache, Handlebars) com partials por stack. Descartada porque introduz dependência runtime adicional e complica debugging quando algo dá errado na geração. Placeholder simples (`String.replace`) é suficiente para os 4 placeholders identificados.

**Consequência:** Adicionar uma nova stack exige criar um diretório + copiar/adaptar 5-9 templates. Esforço estimado: ~1 hora por stack para alguém familiarizado. `_default` fallback elimina necessidade de cobrir long-tail de stacks raras.
