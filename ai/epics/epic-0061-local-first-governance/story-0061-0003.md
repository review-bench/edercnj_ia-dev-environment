## 1. Contexto & Escopo

Como **gerador de projetos**, eu quero que `docs/audit-gates-catalog.md` seja renderizado dinamicamente pelo `DocsAssembler` baseado na stack do projeto-alvo, garantindo que o catálogo de governança liste exatamente os audits que cada projeto recebe (ex.: catálogo de Spring lista 9 audits incluindo actuator-exposure; Node lista 9 incluindo package-lock-integrity; `_default` lista 5).

Hoje, `docs/audit-gates-catalog.md` no raiz do gerador é mantido manualmente e cobre apenas o cenário Java/Maven do gerador. Quando alguém usa o CLI para gerar um projeto Spring, o catálogo gerado seria desincronizado com os scripts realmente entregues. Esta story introduz um template `_TEMPLATE-AUDIT-GATES-CATALOG.md` com placeholders dinâmicos (`{{#each audit}}`) renderizados pelo `DocsAssembler` em geração, lendo o inventário de scripts produzidos pelo `ScriptsAssembler` (Story 2). A versão estática em `docs/` raiz do gerador é deletada — fonte única de verdade vira o template.

## 3. Contratos & Endpoints

### 3.1 `DocsAssembler.renderCatalog` API

| Método | Parâmetros | Retorno | Comportamento |
| :--- | :--- | :--- | :--- |
| `renderCatalog(stack, scriptInventory)` | `String stack`, `List<AuditScript> inventory` | `String` (markdown) | Renderiza `_TEMPLATE-AUDIT-GATES-CATALOG.md` substituindo placeholders e iterando sobre `inventory` |

### 3.2 `AuditScript` data class

| Campo | Tipo | Exemplo |
| :--- | :--- | :--- |
| `name` | `String` | `audit-model-selection.sh` |
| `category` | `String` | `Template` ou `Runtime` ou `Stack-Specific` |
| `validates` | `String` | `"frontmatter de SKILL.md declara model:"` |
| `guarantees` | `String` | `"custo de tokens dentro do orçamento"` |
| `ruleAnchor` | `String` | `"Rule 23"` |
| `exitCodes` | `Map<Integer,String>` | `{0: "OK", 1: "MODEL_SELECTION_VIOLATION", 2: "OPERATIONAL_ERROR"}` |

### 3.3 Template Placeholders

| Placeholder | Tipo | Substituição |
| :--- | :--- | :--- |
| `{{STACK}}` | scalar | `"spring-boot"` |
| `{{TOTAL_AUDITS}}` | scalar | `9` |
| `{{#each audit}}...{{/each}}` | loop | Bloco repetido por audit |
| `{{audit.name}}` | scalar (loop) | `"audit-model-selection.sh"` |
| `{{audit.validates}}` | scalar (loop) | descrição |
| `{{audit.exitCodes}}` | tabela (loop) | renderizada como tabela markdown |

## 8. Decision Rationale

**Decisão:** Renderizar catálogo dinamicamente em geração em vez de manter por stack templates estáticos pré-prontos (`docs/audit-gates-catalog-spring.md`, `-node.md`, etc.).

**Motivo:** Templates estáticos por stack divergem rapidamente — adicionar um novo audit comum exigiria editar 7 arquivos. Single template + render dinâmico mantém **um lugar** onde a estrutura do catálogo vive; conteúdo é derivado do inventory canônico do `ScriptsAssembler`.

**Alternativa descartada:** Catálogo gerado runtime pelo próprio `audit-all.sh` na primeira execução. Descartada porque move responsabilidade de doc generation para runtime do projeto-alvo, e exigiria invocar audit em modo "describe-only" (complicação desnecessária).

**Consequência:** Mudança em qualquer audit (nova validação, novo exit code) demanda atualizar (a) template `_TEMPLATE-AUDIT-GATES-CATALOG.md` se mudou estrutura, (b) `AuditScript` populator no `ScriptsAssembler` se mudou metadata. Drift entre catálogo e scripts é detectado por smoke test que compara nomes de arquivos em `.claude/scripts/` com nomes listados no catálogo gerado.
