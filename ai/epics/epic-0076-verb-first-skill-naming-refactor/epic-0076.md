## 1. Contexto & Escopo

### 1.1 Problema

O catálogo de skills ainda combina padrões semânticos diferentes: parte já está em formato aceitável para operadores (`x-review-security`, `x-release`), parte segue `substantivo + ação` (`x-epic-implement`, `x-arch-plan`, `x-pr-fix`) e parte continuará mudando em épicos anteriores (`x-feature-create`, `x-story-refine`, `x-memory-search`). Isso dificulta descoberta, documentação e previsibilidade.

EPIC-0076 estabelece a segunda onda de padronização: **verbo primeiro**, com objeto explícito e intencional. O padrão alvo é:

- públicas: `x-<verbo>-<objeto>`
- internas: `x-internal-<verbo>-<objeto>`
- libs: `x-lib-<verbo>-<objeto>`

### 1.2 Escopo incluído

- congelar a gramática do rename
- fechar a matriz canônica `de -> para` pós-EPIC-0075
- renomear skills públicas
- renomear skills internas e libs
- atualizar referências em source of truth, Java, templates, docs e testes
- adicionar guard CI contra nomes legados

### 1.3 Fora do escopo

- knowledge packs `*-kp`
- retroedição de épicos já concluídos
- aliases permanentes
- transição longa com dupla nomenclatura

## 4. Regras Transversais

| ID | Título | Descrição |
| :--- | :--- | :--- |
| **RULE-001** | Verbo primeiro | Toda skill pública usa `x-<verbo>-<objeto>`; o verbo responde imediatamente “o que esta skill faz?”. |
| **RULE-002** | Internal preserva namespace | Toda internal segue `x-internal-<verbo>-<objeto>`; `internal` nunca muda de posição. |
| **RULE-003** | Lib preserva namespace | Toda lib segue `x-lib-<verbo>-<objeto>`. |
| **RULE-004** | Baseline pós-epics anteriores | Quando um épico anterior já planejou renome ou criação de skill, EPIC-0076 trabalha sobre esse nome futuro consolidado. |
| **RULE-005** | Nome intencional | O rename não é inversão mecânica; clareza de propósito vence simetria. |
| **RULE-006** | Escopo do catálogo | Entram skills públicas, internas e `x-lib-*`; knowledge packs ficam fora. |
| **RULE-007** | Rename por cluster | Os renames são executados por clusters coerentes para reduzir conflitos e facilitar revisão. |
| **RULE-008** | Atualização cross-surface obrigatória | Cada rename exige atualização atômica em source of truth, docs, Java, templates e testes. |
| **RULE-009** | Sem aliases | O catálogo final é único; nomes antigos só sobrevivem em changelog, ADRs históricos e allow-list explícita do guard. |
| **RULE-010** | Guard anti-legado | CI falha se nome antigo reaparecer fora das localizações permitidas. |
