## 1. Contexto

JSON Schema (Draft 2020-12) que valida cada arquivo `capabilities/<category>/<id>.yaml`. Define formato canônico de uma capability declarada no catálogo.

Campos obrigatórios: `id`, `category`, `kind`. Campos opcionais: `version`, `status`, `description`, `parameters`, `requires`, `provides`, `excludes`, `tags`, `expands-to`. Categorias top-level são lista fechada (13 namespaces: language, framework, interface, data, messaging, architecture, observability, deployment, security, compliance, testing, cloud, governance).

Constraint condicional: `kind=profile` ⇒ `expands-to` obrigatório, sem `requires`/`provides`/`excludes`/`parameters`. `kind=atomic|composite` ⇒ sem `expands-to`.

## 2. Acceptance Criteria

```gherkin
Scenario: Schema validates a Postgres capability
  Given file capabilities/data/database/postgres.yaml with id, category=data, kind=atomic, version=16
  When validated against governance/schemas/capabilities-1.0.json
  Then validation passes

Scenario: Schema rejects unknown category
  Given file with category=unknown-cat
  When validated
  Then validation fails (enum violation)

Scenario: Schema validates profile expansion
  Given file with kind=profile and expands-to=[language.java, framework.spring-boot]
  When validated
  Then validation passes

Scenario: Schema rejects profile with requires field
  Given file with kind=profile, expands-to=[...], requires=[...]
  When validated
  Then validation fails (allOf constraint)

Scenario: Schema rejects atomic with expands-to
  Given file with kind=atomic and expands-to=[...]
  When validated
  Then validation fails (allOf constraint)
```
