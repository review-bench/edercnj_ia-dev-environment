Scenario: Resolver feliz com profile java-cli-picocli (happy)

  Given mesmo profile, mesmo catálogo
  When CapabilityResolver.resolve() chamado 3 vezes consecutivas
  Then todas as 3 produzem ResolvedCapabilitySet com SHA idêntico (serialized JSON canonical)

Scenario: Profile vazio (boundary — degenerate)
  Given profile com capabilities: []
  When CapabilityResolver.resolve(profile)
  Then returns ResolvedCapabilitySet com Set vazio
  And no error

## 6. Decision Rationale

**Decisão:** Fixtures versionadas (capabilities reais em `capabilities/runtime/jvm.yaml` etc.) em vez de mocks ou test-only fixtures.
**Motivo:** Stories de Phase 3 (composer integration) e Phase 4 (framework split) reusam exatamente esses fixtures. Versioná-los uma vez economiza duplicação. Fixtures também são as primeiras capabilities reais do catálogo.
**Alternativa descartada:** Mocks por test class. Rejeitada por (a) duplicação cross-tests, (b) divergência de schema entre mocks e produção quando catálogo evoluir.
**Consequência:** Smoke test é fragile a mudanças no schema das capabilities — mudança em `runtime/jvm.yaml` quebra smoke test, sinalizando review necessário.

## 7. Implementation Notes

Fixtures versionados em `capabilities/` e `profiles/` — são os primeiros arquivos reais do catálogo e servem tanto ao smoke quanto às stories de Phase 3 (composer integration).

Comparação de SHA: serialize ResolvedCapabilitySet com Jackson canonical writer (sorted keys), MessageDigest SHA-256, compare bytes.
