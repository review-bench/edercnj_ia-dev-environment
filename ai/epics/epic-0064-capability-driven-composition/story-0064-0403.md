## 1. Contexto

Refatora KP `database-patterns/jpa/` (e similares) extraindo fragmentos por engine de banco:

- `fragments/postgres.md` requires `data.database.postgres`.
- `fragments/mysql.md` requires `data.database.mysql`.
- `fragments/mariadb.md` requires `data.database.mariadb`.
- `fragments/h2.md` requires `data.database.h2`.

Parent `index.md` declara `fragment-slots: [{slot: db-engine}]` e referencia `{{ #each fragments.db-engine }}`.

Substitui o KP atual que tem conteúdo de todos os engines misturado, ativo independente do projeto usar Postgres ou MySQL.

## 2. Acceptance Criteria

```gherkin
Scenario: db-jpa parent declara fragment-slots
  Given knowledge/database-patterns/jpa/index.md
  When inspect frontmatter
  Then fragment-slots: [{slot: db-engine}]

Scenario: Fragments declaram requires-capabilities
  Given fragments/postgres.md
  When inspect frontmatter
  Then fragment-slot: {slot: db-engine, fragment-id: postgres, fragment-order: 10}
  And requires-capabilities: [data.database.postgres]

Scenario: Output projeto Postgres contém só postgres fragment
  Given profile com data.database.postgres ativo
  When generate
  Then knowledge/database-patterns/jpa/index.md gerado contém conteúdo postgres.md
  And NÃO contém conteúdo mysql.md ou mariadb.md

Scenario: Output projeto sem DB não contém db-jpa de jeito nenhum
  Given profile java-cli-picocli (sem DB)
  When generate
  Then knowledge/database-patterns/ não existe em output
```
