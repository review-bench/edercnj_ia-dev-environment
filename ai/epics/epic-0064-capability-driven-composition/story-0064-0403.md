## 1. Contexto

Refatora KP `database-patterns/jpa/` (e similares) extraindo fragmentos por engine de banco:

- `fragments/postgres.md` requires `data.database.postgres`.
- `fragments/mysql.md` requires `data.database.mysql`.
- `fragments/mariadb.md` requires `data.database.mariadb`.
- `fragments/h2.md` requires `data.database.h2`.

Parent `index.md` declara `fragment-slots: [{slot: db-engine}]` e referencia `{{ #each fragments.db-engine }}`.

Substitui o KP atual que tem conteúdo de todos os engines misturado, ativo independente do projeto usar Postgres ou MySQL.

## 6. Decision Rationale

**Decisão:** Esta story é a primeira aplicação concreta do padrão fragment-by-capability; serve de blueprint para 0404 (db-r2dbc), 0501 (x-review), Rule 09 fragments.
**Motivo:** Pioneirar o padrão num caso limpo (engines disjuntos por excludes simétricos) facilita generalização. Engineers que materializam stories subsequentes podem copiar a estrutura.
**Alternativa descartada:** Aplicar pattern em x-review (mais complexo, 8 fragments) primeiro. Rejeitada porque fragmentos de KP são mais simples (engines disjuntos) — bom test bed.
**Consequência:** PR de Phase 5 / Phase 4 podem reusar exato pattern (fragment-slot + fragment-id + fragment-order); economiza retrabalho.
