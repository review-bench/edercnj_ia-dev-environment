## 1. Contexto & Escopo

**Chave Jira:** —

EPIC-0064 reformula o gerador `ia-dev-env` de **copy-cego de tudo** para **composição dirigida por capabilities** declaradas no YAML do projeto-alvo. Hoje todo `.claude/` é copiado integralmente: um projeto Java CLI Picocli sem banco recebe `data-management/`, `database-patterns/`, `data-modeling/` knowledge packs, agente `database-engineer`, skill `x-review-db` e seções DB-inline em rules — tudo morto. Spring Boot e Quarkus compartilham o mesmo conteúdo `stack-patterns/spring-patterns/` + `stack-patterns/quarkus-patterns/`, com instruções contraditórias por projeto. `SkillRegistry.CORE_KNOWLEDGE_PACKS:43` lista `data-management` como hardcoded "core", contraditando o filtro condicional parcial em `KnowledgePackSelection.selectDataPacks()`.

Este épico estabelece um **modelo de capabilities** (`capabilities/<category>/<id>.yaml`) declarativo, um **resolver determinístico** com detecção de ciclos / mutex / prerequisites, um **frontmatter universal** (`requires-capabilities`, `excludes-capabilities`, `parameters-from`, `fragment-slots`) em todos os 182 artefatos, e um **CapabilityAwareComposer** que substitui ~20 dos 34 assemblers atuais. Artefatos polimórficos como `x-review` passam a ser **compostos em runtime de geração** a partir de fragmentos por especialista (`fragments/qa.md`, `fragments/db.md` requires `data.database.*`, etc.).

O escopo INCLUI: 79 stories distribuídas em 8 fases / 15 waves; novo pacote `dev.iadev.application.capability/` (Resolver, Registry, Graph, Validators); novo pacote `dev.iadev.application.composition/` (ArtifactScanner, CompositionEngine, CapabilityAwareAssembler); migração 1× dos 182 artefatos com frontmatter v3.0; split de `stack-patterns/` em `spring/`, `quarkus/`, `picocli/`, `helidon/`; refactor de `x-review` para 8 fragmentos especialistas; 6 audit scripts novos (`audit-capability-coverage`, `audit-capability-graph`, `audit-frontmatter-schema`, `audit-output-pruning`, `audit-fragment-coherence`, `audit-capability-determinism`); 10 smoke tests + property-based suite (jqwik, 10K casos); ADR-0016, SPEC-capability-composition-v1, Rule 28, 2 JSON schemas; CLAUDE.md + README de `.claude/` atualizados; CHANGELOG `[Breaking]` + bump major. EXCLUI: retrocompatibilidade com schema v2 (decisão explícita do dono — bump major); migração de projetos downstream consumidores (responsabilidade dos próprios consumidores, comunicada via release notes); novos frameworks além de Helidon/Micronaut (escopo das stories 0408/0409 como prova de onboarding linear, demais frameworks são follow-up).

## 4. Materialização SOLID

> Regras transversais que se aplicam a múltiplas histórias. Cada história referencia pelo ID.

| ID | Título | Descrição |
| :--- | :--- | :--- |
| **[RULE-001]** | Capability como contrato | Toda skill, rule, KP, agent, hook ou template DEVE declarar `requires-capabilities: [...]` em frontmatter (v3.0). Ausência = build error (`audit-capability-coverage.sh`). Universalidade é declarada explicitamente com `requires-capabilities: []`, nunca implícita por omissão. |
| **[RULE-002]** | Frontmatter v3.0 obrigatório | Schema validado por `governance/schemas/frontmatter-3.0.json`. Campos: `name`, `requires-capabilities`, `requires-any` (opcional), `excludes-capabilities` (opcional), `parameters-from` (opcional), `fragment-slot` (opcional, declara que ESTE arquivo é fragmento), `fragment-slots` (opcional, declara que recebe fragmentos). v2 quebra build. |
| **[RULE-003]** | Capability ID = identidade canônica | Toda capability tem ID `<category>.<subcategory>.<atomic>` único, declarado em arquivo dedicado em `capabilities/<category>/<id>.yaml`. Profile expande para set de atomics; `excludes` é simétrico (A.excludes B ⇒ B.excludes A); `requires` permite glob (`data.database.*`). |
| **[RULE-004]** | Determinismo bytewise | `compose(profile)` invocado 2× consecutivas DEVE produzir output idêntico SHA-por-arquivo. `LinkedHashMap`/`TreeSet` para ordenação estável; `audit-capability-determinism.sh` valida em 3 builds consecutivos. Quebra de determinismo é build error. |
| **[RULE-005]** | Three-level templating discriminado | Composer (`{{ slot: X }}`, `{{ #each fragments.X }}`) roda ANTES de Pebble (`{{ var }}`, `{% if %}`); ambos rodam em build-time. LLM placeholders (`{{UPPER_SNAKE}}`) ficam literais nos `_TEMPLATE-*.md` via `{% verbatim %}` automático. `PebbleSafeRenderer` faz pre-flight regex que falha se LLM placeholder foi processado por engano. |
| **[RULE-006]** | Sem retrocompatibilidade | Não há dual-mode `flowVersion`/`schema-version` para v2 vs v3. CHANGELOG marca `[Breaking]` + bump major; downstream comunicado via release notes. Goldens v2 deletados em Phase 7; goldens v3 são source-of-truth a partir do merge. |
| **[RULE-007]** | Fragment ≠ artifact | Fragmento sob `<artifact-parent>/fragments/` NUNCA gera arquivo de output próprio; é incorporado ao artifact-pai renderizado pelo `CompositionEngine`. Frontmatter `fragment-slot:` declara identidade + slot + ordem; sem ele, scanner trata como artifact standalone. |
| **[RULE-008]** | Migração 1× completa, sem migração incremental | Phase 2 migra os 182 arquivos em batch (12 PRs por categoria). Não há fase intermediária com mistura v2+v3. Após Phase 2, `audit-capability-coverage.sh` é hard-fail; antes, advisory. |
