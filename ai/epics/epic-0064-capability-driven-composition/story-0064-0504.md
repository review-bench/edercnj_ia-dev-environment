## 1. Contexto

`settings.json` (gerado) lista hooks ativos por evento (`SessionStart`, `PreToolUse`, etc.). Hoje, todos os hooks declarados em `targets/claude/hooks/` são incluídos. Esta story aplica capability filtering aos hooks também:

- `post-compile-check.sh` requires `lang.java` — apenas em projetos Java.
- `enforce-bypass-flags.sh` requires `[]` (universal).
- Hooks específicos de stack (futuros): requires `web.spring.boot`, `web.quarkus`, etc.

Composer (story-0064-0301) já scaneia hooks via header comment (story-0064-0213). Esta story garante que `settings.json` reflete o pruning — entries de hooks excluídos são removidas do JSON gerado.

## 6. Decision Rationale

**Decisão:** Capability filtering aplicado APENAS na seção `hooks` do settings.json; `permissions` e `env` continuam tal qual.
**Motivo:** Hooks são capability-driven (precisam dependency). Permissions são project-level (admin do projeto define). Env vars são configuration. Misturar filtering em todos confunde — operadores não esperam que setar `lang.java` desative permission `Bash(/usr/bin/git)`.
**Alternativa descartada:** Filtering em todas as 3 seções. Rejeitada por (a) confusão de scope, (b) project-level config não deveria depender de capabilities — pode levar a bugs surreais.
**Consequência:** `SettingsAssembler` ganha lógica isolada apenas para hooks; permissions/env passados via `Files.copy()` ou similar.

## 7. Implementation Notes

`SettingsAssembler.java` é hot file (Rule 04 — mas substituído pelo composer no Phase 3). Esta story consuma o composer para renderizar settings.json.

Atenção: settings.json também tem permissions, env vars — esses NÃO são capability-driven (são project-level). Apenas hooks são filtrados por capability.
