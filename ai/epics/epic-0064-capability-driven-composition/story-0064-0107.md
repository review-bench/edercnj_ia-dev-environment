## 1. Contexto

`CapabilityResolver` é a fachada pública do pacote `dev.iadev.application.capability`. Recebe `Profile` + catálogo, orquestra `MutexValidator` → `CycleDetector` → `PrerequisiteResolver` → `ProfileExpander`, e retorna `ResolvedCapabilitySet` ou `CapabilityError` tipado.

É o único entry point usado pelos assemblers/composer. Encapsula toda a complexidade de validação. Determinístico — duas invocações com mesmo input produzem mesmo output (Rule 04).

## 2. Acceptance Criteria

```gherkin
Scenario: Resolver feliz produz set válido (happy)
  Given valid catalog + valid profile
  When CapabilityResolver.resolve(profile)
  Then returns ResolvedCapabilitySet
  And contains all transitive capabilities
  And parameters are effective (profile overrides applied)

Scenario: Resolver detecta ciclo (error path)
  Given catalog with A→B→A
  When CapabilityResolver.resolve(profile activating A)
  Then throws CycleDetected

Scenario: Resolver detecta mutex (error path)
  Given profile activating [postgres, mongo] que se excluem
  When CapabilityResolver.resolve(profile)
  Then throws MutexConflict

Scenario: Resolver detecta prerequisite ausente (error path)
  Given profile activating "x" e x.requires=[y] mas y não está no catálogo
  When CapabilityResolver.resolve(profile)
  Then throws MissingPrerequisite

Scenario: Resolver é determinístico (RULE-004 enforcement)
  Given mesmo profile + catálogo
  When CapabilityResolver.resolve(profile) chamado 3 vezes consecutivas
  Then output1.equals(output2) == output2.equals(output3)
  And serializeToJson(output) bytewise idêntico nas 3 invocações

Scenario: Catálogo grande (boundary — 80+ capabilities)
  Given catalog com 80 capabilities + profile com 20 ativas
  When CapabilityResolver.resolve(profile)
  Then returns em < 50ms (target P95)
  And ResolvedCapabilitySet contém todas + transitive prereqs
```

## 5. DoD Local

- Fachada `CapabilityResolver.resolve(Profile)` implementada.

## 6. Decision Rationale

**Decisão:** Ordem de validação fixada: Mutex → Cycle → Prerequisite → Expand. Apenas `CapabilityResolver` é classe pública do pacote `application.capability`; demais validators são package-private.
**Motivo:** Mutex valida catálogo bem-formado (pre-condition); ciclos no grafo dependem do catálogo válido; prereqs assumem grafo acíclico; expansion é a fase produtiva final. Boundary explícito: consumer external (composer) só usa `resolve()`.
**Alternativa descartada:** Validators expostos publicamente para consumer flexibilidade. Rejeitada por aumentar surface area sem benefício; o resolver é a unidade transacional.
**Consequência:** Constructor injection dos 4 validators (cada um stateless); reuso do mesmo objeto entre invocações é seguro.

## 7. Implementation Notes

Constructor injection dos 4 validators. Cada validator é stateless. `CapabilityResolver` é a única classe pública do pacote — todos os outros são package-private (boundary explicit).

Ordem de validação importa: mutex primeiro (catálogo bem-formado é pre-condition), depois cycle (no grafo construído), depois prerequisite (assume grafo válido), por fim expansion (compõe resultado).
