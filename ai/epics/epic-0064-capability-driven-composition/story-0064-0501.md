## 1. Contexto

`/x-review` hoje é skill monolítica que invoca todos os specialists. Esta story refatora para composição: `x-review/SKILL.md` (parent) declara `fragment-slots: [{slot: review-specialist, ordering: fragment-order}]` e referencia `{{ #each fragments.review-specialist }}`. Cada specialist vira fragmento:

- `fragments/qa.md` requires `[]` (universal).
- `fragments/perf.md` requires `[]` (universal).
- `fragments/security.md` requires `[]` (universal).
- `fragments/devops.md` requires `infra.docker OR infra.cicd`.
- `fragments/db.md` requires `data.database.*`.
- `fragments/api.md` requires `web.*` (REST/gRPC/web framework).
- `fragments/event.md` requires `messaging.*`.
- `fragments/compliance.md` requires `compliance.*`.

Resultado: projeto Java CLI sem DB sem messaging não recebe `db.md`/`event.md`/`api.md`/`compliance.md` nos reviews — `x-review` SKILL.md gerado é menor e focado.

## 6. Decision Rationale

**Decisão:** x-review é o blueprint canônico de composite skill — pattern reusado em CLAUDE.md (0502), agents condicionais (0503), settings.json (0504).
**Motivo:** x-review tem complexidade real (8 fragments, mix de universal e capability-driven, requires com glob e OR) — exercita o pattern em case rico. Stories subsequentes do Phase 5 reusam a estrutura sem reinventar.
**Alternativa descartada:** Aplicar pattern em case simpler (e.g., x-doc-generate) primeiro. Rejeitada porque (a) x-review já tem maior demanda real, (b) blueprint precisa enfrentar casos complexos.
**Consequência:** Hot file `x-review/SKILL.md` — esta story é serial dentro de Wave M; stories 0502-0508 dependem (formal ou de pattern) desta concluída.
