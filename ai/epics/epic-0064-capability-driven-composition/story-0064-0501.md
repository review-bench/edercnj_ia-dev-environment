## 1. Contexto

`/x-review` hoje é skill monolítica que invoca todos os specialists. Esta story refatora para composição: `x-review/SKILL.md` (parent) declara `fragment-slots: [{slot: review-specialist, ordering: fragment-order}]` e referencia `{{ #each fragments.review-specialist }}`. Cada specialist vira fragmento:

- `fragments/qa.md` requires `[]` (universal).
- `fragments/perf.md` requires `[]` (universal).
- `fragments/security.md` requires `[]` (universal).
- `fragments/devops.md` requires `infra.docker OR infra.cicd`.
- `fragments/db.md` requires `data.database.*`.
- `fragments/api.md` requires `web.*` (REST/gRPC/web framework).
- `fragments/event.md` requires `messaging.*`.
- `fragments/compliance.md` requires `compliance.*`.

Resultado: projeto Java CLI sem DB sem messaging não recebe `db.md`/`event.md`/`api.md`/`compliance.md` nos reviews — `x-review` SKILL.md gerado é menor e focado.

## 2. Acceptance Criteria

```gherkin
Scenario: Parent x-review declara fragment-slots
  Given x-review/SKILL.md
  When inspect frontmatter

  And requires-capabilities: []

Scenario: 8 fragments criados
  Given x-review/fragments/
  When list files
  Then existem qa.md, perf.md, security.md, devops.md, db.md, api.md, event.md, compliance.md

Scenario: Output Spring REST + Postgres contém 6 fragmentos
  Given profile spring-rest-postgres (web + DB)
  When generate
  Then x-review SKILL.md gerado contém qa, perf, security, db, api fragments
  And NÃO contém event, compliance (não no profile)

Scenario: Output Java CLI sem DB contém 3 fragmentos universais
  Given profile java-picocli-cli
  When generate
  Then x-review SKILL.md gerado contém apenas qa, perf, security fragments
  And NÃO contém db, api, event, compliance, devops

Scenario: Determinismo: ordem de fragmentos por fragment-order
  Given fragments com orders [10 qa, 20 perf, 30 security, 40 db, 50 api]
  When generate
  Then output ordena exatamente nesta sequência
```
