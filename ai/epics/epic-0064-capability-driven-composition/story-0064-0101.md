## 1. Contexto

Materializa as classes de domínio puras que sustentam todo o EPIC-0064: `CapabilityId` (value object com glob support `data.database.*`), `CapabilityDefinition` (record imutável que reflete `capabilities/<cat>/<id>.yaml`), `Profile` (composição declarada de capabilities atômicas), `CapabilityGraph` (DAG topológico construído pelo resolver), `CapabilityKind` enum, `ParameterSpec`, `ResolutionWarning`. Tudo em `dev.iadev.domain.capability` — zero dependências de framework, conformidade com Rule 04 (domain layer puro).

A modelagem segue o schema 1.0 (`governance/schemas/capabilities-1.0.json` produzido pela story-0064-0004). Cada record tem construtor canônico validador (rejeita ID malformado, glob inválido, parameter sem tipo). `CapabilityGraph` expõe API somente-leitura: `nodes()`, `dependentsOf(id)`, `prerequisitesOf(id)`.

## 2. Acceptance Criteria

```gherkin
Scenario: CapabilityId rejeita formato inválido (degenerate)
  Given input "datadatabase" (sem dots)
  When CapabilityId.of(input)
  Then throws CapabilityError.UnknownCapability
  And message contains "must follow category.subcategory.atomic format"

Scenario: CapabilityId aceita formato canônico (happy)
  Given input "data.database.postgres"
  When CapabilityId.of(input)
  Then returns valid CapabilityId
  And category() == "data"
  And subcategory() == "database"
  And atomic() == "postgres"

Scenario: Glob suportado (boundary)
  Given input "data.database.*"
  When CapabilityId.of(input)
  Then isGlob() == true
  And matches("data.database.postgres") == true
  And matches("data.cache.redis") == false

Scenario: Profile expande para set de atomics (composition)
  Given Profile "spring-rest-api-postgres" listing 5 capabilities
  When profile.expand()
  Then returns Set<CapabilityId> with 5 elements
  And all elements are non-glob atomics

Scenario: CapabilityGraph com tie-break determinístico
  Given graph com múltiplos nós com indegree 0 simultaneamente
  When graph.topologicalSort()
  Then ordem segue alphabetical sort por id
  And 3 invocações consecutivas retornam mesmo array
```

## 6. Decision Rationale

**Decisão:** Records Java 21 imutáveis para todos os tipos de domínio.
**Motivo:** RULE-004 (determinismo bytewise) exige imutabilidade — defensive copies facilitadas, equals/hashCode automáticos, padrão idiomático Java 21.
**Alternativa descartada:** Classes regulares com builders mutáveis (Lombok ou hand-written). Rejeitada por aumentar surface area sem benefício no caso de uso (composer roda em build-time, não hot path).
**Consequência:** Toda manipulação produz novo record — overhead de alocação aceitável; leitura de código fica mais declarativa.

## 7. Implementation Notes

`CapabilityId` é value object — equals/hashCode em todos os campos. `CapabilityGraph` constrói uma vez e fica imutável (defensive copies internas). `ProfileExpander` (story-0064-0106) consome estes tipos.

Sem cycle detection ou mutex validation aqui — apenas tipos. Validações cruzadas vivem em `CapabilityResolver` (story-0064-0107).
