# História: Correção dos Phase Markers em `x-story-implement` e `x-task-implement`

**ID:** story-0066-0009
**Chave Jira:** —
**Status:** Pendente

---

## 1. Contexto & Escopo

Como **Telemetry consumer** (render skill de PR body e `/x-telemetry-analyze`), eu quero que `x-story-implement` e `x-task-implement` emitam pares balanceados `phase.start` / `phase.end` em cada fase numerada da execução, para que `plans/epic-XXXX/telemetry/events.ndjson` contenha dados de fase navegáveis e o template `_TEMPLATE-PR-IMPLEMENTATION.md` possa exibir tempos por fase.

**Problema verificado:** Auditoria dos EPICs 0057-0060 revelou **0 ocorrências** de eventos `phase.start` ou `phase.end` no NDJSON de produção, apesar do contrato Rule 13 §Telemetry Markers (story-0040-0006) exigir esses marcadores desde EPIC-0040. O `TelemetryMarkerLint` existente valida *balance* (DUPLICATE_START, DANGLING_END, UNCLOSED_START), mas não detecta *ausência total* de marcadores — portanto o lint passa mesmo sem nenhum marcador nas skills.

Esta story corrige o gap adicionando os marcadores `<!-- TELEMETRY: phase.start -->` + `Bash command: telemetry-phase.sh start ...` / `<!-- TELEMETRY: phase.end -->` + `Bash command: telemetry-phase.sh end ...` em **todas as fases numeradas** dos source-of-truth SKILL.md em:

- `java/src/main/resources/targets/claude/skills/core/dev/x-story-implement/SKILL.md`
- `java/src/main/resources/targets/claude/skills/core/dev/x-task-implement/SKILL.md`

E cria `PhaseMarkerEmissionTest.java` que valida, via fixture de stream de eventos simulado, que pares `phase.start`/`phase.end` estão presentes e balanceados para cada fase numerada de cada skill.

A story **não** modifica outros orchestrators (x-epic-implement, x-release etc.) — esses estão fora do escopo de EPIC-0066 (escopo D2 do plano: apenas 0066-0009 corrige markers das duas skills de implementação principal). Correção dos demais orquestradores fica para EPIC futuro.

### 1.1 Regras Transversais Aplicáveis

| ID | Título | Impacto |
| :--- | :--- | :--- |
| Rule 13 §Telemetry Markers | Contrato canônico dos phase markers (story-0040-0006) | Define a forma exata: HTML comment + Bash command com `telemetry-phase.sh start|end` |
| Rule 13 §CI Enforcement | `TelemetryMarkerLint` detecta DUPLICATE_START, DANGLING_END, UNCLOSED_START | Após adição dos markers, lint deve continuar GREEN |
| Rule 14 (Project Scope) | `PhaseMarkerEmissionTest.java` é um Java test — permitido (Rule 14 §Allowed Code, test layer) | Não é classe de runtime |
| Rule 22 (Skill Visibility) | Modificação em skills `core/dev/` — skills públicas | Frontmatter não muda; visibility/model preservados |
| Rule 13 §Forbidden | Não emitir `phase.start` de dentro de loop body; usar kebab-case em `$3` | Respeitar ao adicionar markers |

### 1.2 Entrega de Valor

- **Valor primário:** após esta story, toda execução de `x-story-implement` ou `x-task-implement` gera eventos `phase.start`/`phase.end` no NDJSON, tornando o aggregator `telemetry-consolidate.sh` capaz de calcular duração por fase.
- **Valor secundário:** `PhaseMarkerEmissionTest` previne regressão silenciosa — o lint existente detectaria apenas imbalance, não ausência. O novo test detecta ausência.
- **Métrica de Sucesso:**
  - `PhaseMarkerEmissionTest` GREEN com 4 cenários.
  - `jq 'select(.type=="phase.start" or .type=="phase.end") | .skill' < events.ndjson | sort | uniq -c` retorna valores > 0 após execução real de um story-implement.
  - `TelemetryMarkerLint` continua GREEN (sem DUPLICATE_START, DANGLING_END, UNCLOSED_START).
- **Impacto no Negócio:** desbloqueia a seção `## Telemetry` do template de PR com dados de fase; desbloqueia story-0066-0008 (smoke test E2E que verifica markers emitidos em execução real).

## 3. Contratos & Endpoints

### 3.1 Forma Canônica dos Markers (Rule 13 §Canonical Shape)

Cada fase numerada recebe **exatamente** um par de marcadores de entrada e um par de saída:

```markdown
## Phase N — <Nome da Fase>

<!-- TELEMETRY: phase.start -->
Bash command: `$CLAUDE_PROJECT_DIR/.claude/hooks/telemetry-phase.sh start x-story-implement Phase-N-<Nome>`

... corpo da fase ...

<!-- TELEMETRY: phase.end -->
Bash command: `$CLAUDE_PROJECT_DIR/.claude/hooks/telemetry-phase.sh end x-story-implement Phase-N-<Nome> ok`
```

**Regras de nomeação do identificador de fase (`$3` do helper):**
- Formato: `Phase-N-<Nome>` onde `<Nome>` é kebab-case truncado em 64 chars total.
- Exemplos válidos: `Phase-1-Planning`, `Phase-2-Implement`, `Phase-3-Verify`, `Phase-4-Report`.
- Proibido: dotted-case (`Phase.1.Plan`), espaços, uppercase no nome.

**Regras especiais para x-task-implement (sub-fases TDD):**
- Sub-fases Red/Green/Refactor são fases nomeadas (Rule 13 §When to Emit: "TDD sub-phase of `x-task-implement` (Red / Green / Refactor) → Yes — one pair per sub-phase").
- Forma: `Phase-N-Red`, `Phase-N-Green`, `Phase-N-Refactor` onde N é o número da fase numerada pai.
- Exemplo: se o ciclo TDD está na Phase 3, usar `Phase-3-Red`, `Phase-3-Green`, `Phase-3-Refactor`.

**Regra de erro (Rule 13 §When to Emit):**
- Se fase aborta: emitir `phase.end` com `status=failed`:
  ```bash
  $CLAUDE_PROJECT_DIR/.claude/hooks/telemetry-phase.sh end x-story-implement Phase-N-<Nome> failed
  ```

### 3.2 Contrato do `PhaseMarkerEmissionTest`

O test **não** executa as skills em produção. Em vez disso:

1. Lê o SKILL.md source-of-truth de cada skill alvo.
2. Extrai todas as fases numeradas via regex `^## Phase \d+`.
3. Verifica que cada fase numerada contém exatamente:
   - `<!-- TELEMETRY: phase.start -->` antes do corpo.
   - `Bash command:` com chamada ao `telemetry-phase.sh start` para o identificador esperado.
   - `<!-- TELEMETRY: phase.end -->` antes do próximo `## Phase` ou EOF.
   - `Bash command:` com chamada ao `telemetry-phase.sh end` para o mesmo identificador.
4. Verifica que nenhum `phase.start` fica sem `phase.end` (balance check — complementa TelemetryMarkerLint).

## 4. Materialização SOLID

### 4.1 Regras Aplicáveis

| ID | Impacto |
| :--- | :--- |
| Rule 13 §Telemetry Markers | Define a forma canônica; implementador deve seguir literalmente |
| Rule 13 §Forbidden | Proibido emitir marker de dentro de loop body; proibido hand-roll JSON |
| Rule 03 (Coding Standards) | `PhaseMarkerEmissionTest`: métodos ≤ 25 linhas; sem duplicação; sem lógica de produção no test |
| Rule 05 (Quality Gates) | Test não pode depender de ordem de execução; assertions específicas (não só `isNotNull`) |

### 4.2 Princípios SOLID no Test

- **SRP:** `PhaseMarkerEmissionTest` tem uma responsabilidade — verificar que markers existem e são balanceados por fase. Não verifica conteúdo de negócio das skills.
- **OCP:** Adicionar nova skill ao test requer apenas adicionar entry na lista de skills a escanear — sem modificar lógica de verificação.
- **DIP:** Test depende de path relativo resolvido ao root do projeto, não de path hardcoded de sistema.

### 4.3 Organização do Test

```java
class PhaseMarkerEmissionTest {

    // Cenário: degenerate — skill com 0 fases numeradas
    @Test
    void skillWithZeroNumberedPhases_emitsNoPhaseMarkers() { ... }

    // Cenário: happy x-story-implement
    @Test
    void xStoryImplement_hasBalancedMarkersPerPhase() { ... }

    // Cenário: happy x-task-implement
    @Test
    void xTaskImplement_hasBalancedMarkersPerPhase() { ... }

    // Cenário: boundary — fase com status=failed
    @Test
    void phaseWithError_emitsPhaseEndWithStatusFailed() { ... }
}
```

Método auxiliar `extractNumberedPhases(Path skillMd)` extrai fases; `assertMarkersBalanced(List<Phase> phases, String skillName)` valida cada uma. Ambos: ≤ 25 linhas.

## 8. Decision Rationale

### 8.1 Escopo limitado a 2 skills (não todos os 8 orquestradores)

**Decisão:** adicionar markers apenas em `x-story-implement` e `x-task-implement` neste epic.

**Motivo:** Decisão D2 do plano (`pr-body-templates-plan.md`) — o gap mais crítico para o template de PR body é nas skills de implementação (produzem o bulk dos eventos). Os demais orquestradores (`x-epic-implement`, `x-release`, etc.) têm volume menor de execução e seu gap pode ser corrigido em EPIC futuro sem bloquear EPIC-0066.

**Alternativa descartada:** corrigir todos os 8 orquestradores do Anexo B de Rule 25. Rejeitada porque:
- Modificar 8 SKILL.md em paralelo com outras stories do epic cria conflito de merge alto.
- ROI imediato vem das 2 skills mais executadas.
- `PhaseMarkerEmissionTest` é extensível: adicionar nova skill = adicionar entry na lista.

**Consequência:** 6 orquestradores restantes ficam sem markers. WARNING em `/x-telemetry-analyze` para skills sem markers é documentado na story de smoke test (0066-0008).

### 8.2 Test por inspeção estática de SKILL.md (não por execução da skill)

**Decisão:** `PhaseMarkerEmissionTest` lê o SKILL.md e verifica presença de markers via regex, sem executar a skill.

**Motivo:** executar `x-story-implement` em um test unitário é inviável (requer LLM + repositório ativo + telemetry hook). Inspeção estática é determinística, rápida (< 1 s), e suficiente para detectar ausência de markers que o `TelemetryMarkerLint` já não detecta.

**Alternativa descartada:** integration test que executa a skill e valida NDJSON resultante. Rejeitada porque:
- Requer ambiente LLM — não roda em CI standalone.
- Story-0066-0008 (smoke test E2E) cobre o cenário de execução real.

**Consequência:** o test não prova que o helper `telemetry-phase.sh` foi realmente chamado em runtime — apenas que o marcador está presente no texto do SKILL.md. O smoke test (story-0066-0008) fornece a prova de execução real.

### 8.3 Identificadores kebab-case vs. espaços

**Decisão:** identificadores de fase no formato `Phase-N-Nome-Kebab` (sem espaços).

**Motivo:** Rule 13 §Forbidden proíbe dotted-case; o helper valida `$3` como string opaca mas os consumers (telemetry-consolidate.sh e `/x-telemetry-analyze`) joinam em string exata — espaços criam problemas de parsing em pipelines shell.

**Consequência:** leve inconsistência com nomes de seção (`## Phase 1 — Planning` vs. `Phase-1-Planning`). Aceitável: o mapeamento é documentado nesta story e no SKILL.md.
