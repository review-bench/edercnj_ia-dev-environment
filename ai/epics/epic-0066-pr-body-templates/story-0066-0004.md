## 1. Contexto & Escopo

Como **Operador de PR de Scaffolding**, eu quero que a skill interna `x-internal-pr-body-render --kind=backlog` gere automaticamente o corpo do PR de épico/scaffolding a partir do epic markdown, do IMPLEMENTATION-MAP.md e do spec, para que PRs de criação de épicos (ex: `x-feature-create` pós-EPIC-0065) sigam o formato padronizado definido em `_TEMPLATE-PR-BACKLOG.md` — eliminando a divergência estrutural observada nos PRs #752, #753, #754.

Esta story **estende o mesmo arquivo SKILL.md** criado pela story 0066-0003, adicionando suporte a `--kind=backlog`. É uma modificação **no mesmo arquivo** — hotspot declarado — razão pela qual é sequencial em relação à story 0066-0003 (sem paralelismo possível por RULE-004 do EPIC-0041).

A extensão:
- Adiciona validação de `--epic-id` em **Phase 0 (ARGS)**.
- Adiciona uma nova sub-fase **Phase 1.5 BACKLOG-GATHER** para ler as fontes específicas do template de backlog (epic.md, IMPLEMENTATION-MAP.md, spec).
- Ramifica **Phase 3 (RENDER)** com base no `--kind` para selecionar `_TEMPLATE-PR-BACKLOG.md` ou `_TEMPLATE-PR-IMPLEMENTATION.md`.
- Mantém **fail-open**: campos ausentes resultam em placeholders humano-legíveis (`(map missing)`, `(no metrics declared)`) — nunca tokens de auditoria.

#### Phase 1.5 — BACKLOG-GATHER (nova sub-fase entre Phase 1 e Phase 2)

<!-- phase-no-gate: Phase 1.5 é sub-fase interna sem gate próprio — o gate POST pertence à Phase encapsulante -->

Esta sub-fase é executada apenas quando `--kind=backlog`. Lê as fontes específicas do template de backlog:

| # | Fonte | Localização (v4 layout — PathResolver) | Parse | Fallback (falha-aberto) |
| :--- | :--- | :--- | :--- | :--- |
| 1 | Epic markdown | `ai/epics/epic-XXXX-<slug>/epic-XXXX.md` | Regex para `## 1.1 Problema` (summary), `## 9.2 Stories` (lista), `## 9.4 Glossário` (outOfScope), `successMetrics` | placeholders por campo |
| 2 | IMPLEMENTATION-MAP.md | `ai/epics/epic-XXXX-<slug>/IMPLEMENTATION-MAP.md` | Regex para tabela de stories (Phase, Story ID, Layer, Bloqueada por), seção DAG (caminho crítico, paralelismo máximo, total phases) | `"(map missing)"` para o bloco inteiro |
| 3 | Spec markdown | `ai/epics/epic-XXXX-<slug>/specs/*.md` ou `docs/specs/*.md` | Leitura de path + SHA via `git rev-parse HEAD:<path>` | `specPath: "(spec not found)"`, `specSha: "(unknown)"` |

**Fallbacks de falha-aberto obrigatórios:**

- IMPLEMENTATION-MAP.md ausente → seção `## Estrutura do DAG` mostra `(map missing)` — NÃO aborta.
- epic.md sem bloco `successMetrics` → seção `## Métricas de Sucesso` mostra `(no metrics declared)`.
- Spec não localizado → `Spec SHA: (unknown)`, `Spec path: (spec not found)`.
- Lista de stories vazia (seção `## 9.2` ausente no epic.md) → `storyCount: 0`, `stories: []`.

**Coordenação com Epics em Andamento:** A skill lê `ai/epics/*/execution-state.json` para epics com `status: in_progress` e preenche a tabela `## Coordenação com Epics em Andamento`. Se nenhum epic in_progress, renderiza linha única com `(nenhum epic em andamento)`.

#### Phase 3 — RENDER (ramificada por --kind)

Substituir o bloco existente (que seleciona apenas `_TEMPLATE-PR-IMPLEMENTATION.md`) por dispatch baseado em `--kind`:

```
SE --kind == "implementation":
  template = "${TEMPLATES_DIR}/_TEMPLATE-PR-IMPLEMENTATION.md"
SENÃO SE --kind == "backlog":
  template = "${TEMPLATES_DIR}/_TEMPLATE-PR-BACKLOG.md"
```

Invocar `x-internal-report-write` via INLINE-SKILL com o template selecionado e o envelope JSON correspondente (implementation envelope ou backlog envelope — estruturas distintas).

### 3.5 Segurança (backlog-específico)

- **Injeção via `--epic-id`:** validar formato `^epic-[0-9]{4}$` antes de qualquer uso como path segment ou query de `git rev-parse`.
- **Expansão de glob para spec:** usar `find` com path restrito a `${REPO_ROOT}` para localizar spec — nunca expandir glob diretamente de input.
- **Secrets via epic.md:** a skill NUNCA propaga seções que possam conter credenciais (ex: `## Environment Variables`). Apenas seções estruturais listas mapeadas em §3.4.

## 8. Decision Rationale

**Decisão:** modificação do mesmo arquivo SKILL.md (story-0066-0003) em vez de arquivo separado.

**Motivo:** a skill `x-internal-pr-body-render` tem uma identidade única — ela renderiza PR bodies. Dividir em dois arquivos (`x-internal-pr-body-render-impl` + `x-internal-pr-body-render-backlog`) criaria duplicação de fases comuns (Phase 0 ARGS, Phase 4 WRITE), violando DRY (Rule 03 §Code Hygiene).

**Alternativa descartada:** skill separada `x-internal-pr-backlog-render`. Rejeitada porque:
- 60% das fases (Phase 0, Phase 2 TELEMETRY, Phase 4 WRITE) são idênticas — duplicação injustificada.
- Dois arquivos a regenerar nos golden files em vez de um.
- Aumenta surface de `audit-skill-visibility.sh` sem ganho de isolamento real (callers passam `--kind` explícito).

**Consequência:** story-0066-0004 é **sequencial obrigatório** em relação a story-0066-0003 (mesma razão que impede paralelismo em `PlanTemplatesAssembler.java`). Hotspot declarado em §9.3. Diff esperado: ~80-100 linhas adicionadas ao SKILL.md existente.
