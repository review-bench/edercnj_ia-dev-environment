**ID:** story-0066-0005
**Chave Jira:** —
**Status:** Pendente

## 1. Contexto & Escopo

Como **Operador de PR**, eu quero que o `x-pr-create` delegue a geração do corpo da PR para `x-internal-pr-body-render --kind=implementation` via Pattern 1 (INLINE-SKILL — Rule 13), de modo que toda PR de implementação criada após o EPIC-0066 tenha o marcador `<!-- template-version: 1.0 -->` exigido por `audit-pr-template.sh`.

Hoje a **Phase 3** de `x-pr-create/SKILL.md` gera o body da PR inline (prosa Markdown hardcoded em Bash) com 6 seções fixas (`## Summary`, `## Task Details`, `## Changes`, `## Review Checklist`) e a **Phase 3.5** injeta `## Orchestrator Evidence`. Ambas as fases funcionam, mas produzem um body sem o marcador de template-version, o que fará todo PR criado após EPIC-0066 ser rejeitado por `audit-pr-template.sh` (story-0066-0007).

Esta story refatora a Phase 3 para invocar a render skill (story-0066-0003) como **MANDATORY TOOL CALL** (Rule 24 §Camada-1), mantém a Phase 3.5 com lógica de deduplicação do `## Orchestrator Evidence` (a render skill já o gera via template), e preserva o comportamento inline legado como caminho de **fallback** no bloco `## Recovery` quando a render skill retorna exit ≠ 0 (fail-open, conforme RULE-004 do epic).

### 1.2 Entrega de Valor

- **Valor primário:** Toda nova PR de implementação terá body padronizado com `<!-- template-version: 1.0 -->`, passando no `audit-pr-template.sh`.
- **Métrica de Sucesso:** `audit-pr-template.sh --pr <N>` exit 0 para PRs criadas após este epic; `XPrCreateRenderIntegrationTest` GREEN.
- **Impacto no Negócio:** Elimina divergência de formato entre PRs de diferentes stories/epics — reviewers veem sempre as mesmas seções na mesma ordem.

## 3. Contratos & Endpoints

### 3.1 Contrato da Mudança em `x-pr-create/SKILL.md`

#### Phase 3 — Refatorada (novo fluxo)

```
MANDATORY TOOL CALL — Rule 24 §Camada-1 / Rule 13 Pattern 1 (INLINE-SKILL):

Invoke the `x-internal-pr-body-render` skill via the Skill tool:

    Skill(skill: "x-internal-pr-body-render", model: "haiku", args: "--kind=implementation --story-id=<STORY_ID> --out=<TMP_BODY_PATH>")

Se exit=0: BODY=$(cat <TMP_BODY_PATH>)   → prossiga para Phase 3.5
Se exit≠0: WARN "render skill failed (exit $?), using fallback body"
           → ativar caminho de fallback em ## Recovery
```

- `<STORY_ID>` é extraído do `TASK_ID` (`story-${TASK_EPIC_ID}-${TASK_STORY_NUM}`)
- `<TMP_BODY_PATH>` é um arquivo temporário com permissão 600 em `$TMPDIR` (Rule 06 §Temp files)
- O body gerado pela render skill JÁ CONTÉM `## Orchestrator Evidence` (via template `_TEMPLATE-PR-IMPLEMENTATION.md`)

#### Phase 3.5 — Deduplicação de `## Orchestrator Evidence`

Quando a render skill roda com sucesso, o template já inclui `## Orchestrator Evidence`. A Phase 3.5 deve:

1. Verificar se `$BODY` contém a string `## Orchestrator Evidence`
2. **Se presente:** pular a injeção (evitar duplicação); registrar `INFO: ## Orchestrator Evidence already present in rendered template — skipping injection`
3. **Se ausente** (body gerado pelo fallback legado): executar a lógica existente de injeção (idêntica ao código atual de Phase 3.5)

```bash
# Regra de deduplicação (Phase 3.5)
if echo "$BODY" | grep -q "## Orchestrator Evidence"; then
  # Template já incluiu a seção — dedup protege contra duplicação
  echo "INFO: ## Orchestrator Evidence already present — skipping injection"
else
  # Fallback path: body inline legado não tem a seção, injetar manualmente
  BODY="${BODY}${ORCHESTRATOR_EVIDENCE_SECTION}"
fi
```

**Invariante:** o PR body final SEMPRE conterá exatamente uma ocorrência de `## Orchestrator Evidence`, independente de qual caminho gerou o body.

#### `--no-story-evidence` — comportamento preservado

Quando `--no-story-evidence` está ativo, a Phase 3 ainda delega à render skill (a render skill inclui `## Orchestrator Evidence` com placeholder `(omitido por --no-story-evidence)`). A Phase 3.5 detecta a seção e pula a injeção manual. Sem mudança de comportamento observável para o caller.

### 3.2 Fallback Legado (caminho `## Recovery`)

Quando `x-internal-pr-body-render` retorna exit ≠ 0, o body inline legado é gerado:

```markdown
## Summary

{description derived from commits or --description flag}

## Task Details

| Field | Value |
|-------|-------|
| Task ID | TASK-XXXX-YYYY-NNN |
| Story | story-XXXX-YYYY |
| Epic | epic-XXXX |
| Task Plan | `plans/epic-XXXX/tasks/task-plan-XXXX-YYYY-NNN.md` |

## Changes

{list each commit in the branch}

## Review Checklist

- [ ] Tests pass locally
- [ ] Coverage thresholds met (>=95% line, >=90% branch)
- [ ] TDD commits present (RED -> GREEN -> REFACTOR)
- [ ] No TODO/FIXME/HACK comments
- [ ] Conventional Commits format followed
```

O fallback **não produz** o marcador `<!-- template-version: 1.0 -->`. Um WARN explícito é emitido para o operador:

```
WARN [render-fallback]: PR body gerado via fallback inline (sem template-version marker).
     audit-pr-template.sh reportará PR_TEMPLATE_VIOLATION para este PR.
     Investigar: x-internal-pr-body-render exit code = <N>.
```

**Decisão de design:** o fallback garante que o PR seja sempre criado (fail-open — RULE-004), mas sinaliza ao operador que o template não foi aplicado. O audit downstream (story-0066-0007) detectará e bloqueará o merge se o marcador estiver ausente.

### 3.3 Contrato de Invocação da Render Skill

```
Skill(skill: "x-internal-pr-body-render", model: "haiku", args: "--kind=implementation --story-id=story-XXXX-YYYY --out=/tmp/pr-body-XXXX-YYYY-NNN.md")
```

| Argumento | Valor | Fonte |
| :--- | :--- | :--- |
| `--kind` | `implementation` | fixo para x-pr-create |
| `--story-id` | `story-${TASK_EPIC_ID}-${TASK_STORY_NUM}` | extraído do TASK_ID na Phase 0 |
| `--out` | `$(mktemp -t pr-body-XXXXXX.md)` | arquivo temporário; chmod 600 antes de usar |
| `model` | `haiku` | Rule 23 §Utility — render skill é utilitário de template |

Exit codes que disparam fallback: qualquer exit ≠ 0 (`INVALID_KIND`, `OPERATIONAL_ERROR`, `INVALID_SCOPE`)

### 4.2 Princípios SOLID

- **SRP:** x-pr-create mantém responsabilidade de criar PRs; render skill tem responsabilidade de renderizar body. Separação clara.
- **OCP:** A lógica de body geração não é modificada — é substituída por delegação. O fallback é o comportamento legado preservado sem alteração.
- **DIP:** x-pr-create depende da interface da render skill (contrato de args/exit codes — §3.3 do epic-0066.md), não da implementação interna.

## 8. Decision Rationale

**Decisão:** invocar render skill via Pattern 1 (INLINE-SKILL síncrono) em vez de Pattern 2 (subagent).

**Motivo:** x-pr-create precisa do resultado (conteúdo do body) para prosseguir imediatamente para Phase 3.5 e Phase 4. Subagent introduziria overhead de spawn sem ganho (render é rápida — apenas leitura de template + substituição de tokens via jq). Pattern 1 mantém o fluxo linear já existente da skill.

**Alternativa descartada:** integrar a renderização diretamente no `x-pr-create` (copiar lógica da render skill). Rejeitada porque violaria SRP e impossibilitaria o reuso da render skill por `x-feature-create` (story-0066-0006) — defeating o purpose da extração como skill interna.

**Decisão sobre fallback:** o fallback preserva o comportamento pré-EPIC-0066 integralmente. O WARN sinaliza que o template não foi aplicado sem abortar a criação do PR. Esta escolha segue RULE-004 (fail-open) e garante que EPIC-0066 não quebre fluxos em andamento se a render skill tiver um bug.

**Decisão sobre deduplicação vs. supressão:** a Phase 3.5 não é removida — ela serve como safety net para o caminho de fallback. A deduplicação (verificar presença antes de injetar) é preferível a suprimir a Phase 3.5 porque manteia o invariante `## Orchestrator Evidence` presente em todos os casos, independente do caminho usado.
