## 1. Contexto & Escopo

Como **operador de skills e desenvolvedor do framework**, eu quero uma abstração central `PathResolver` que resolva paths para o layout v3 (legacy) ou v4 (novo) de forma automática via probe, garantindo que todos os artefatos de épicos, stories, plans, reviews e reports sejam localizados sem strings hardcoded nas skills.

Esta story estabelece a fundação arquitetural para toda a migração de layout. O `PathResolver` é o único ponto de resolução de paths operacionais do framework: qualquer skill, rule, hook ou assembler que hoje usa strings raw como `plans/epic-XXXX/` passará a chamar `PathResolver.epicDir("0060")` que retorna o path correto dependendo de qual layout está em uso. O probe automático detecta o layout pelo glob `ai/epics/epic-XXXX-*/` — se o diretório existe em v4, retorna o path v4; senão, fallback para v3 legacy.

A introdução do schema discriminador `flowVersion: 4` em `execution-state.json` marca epics criados no novo layout. Epics com `flowVersion ≤ 2` continuam em `plans/` (RULE-001). Esta story é pré-requisito para as Stories 0002, 0004 e 0005.

### 1.2 Entrega de Valor

- **Valor Principal:** Fonte única de resolução de paths elimina divergência entre skills quando o layout muda — 42 skills passam a chamar 1 helper ao invés de 42 strings hardcoded.
- **Métrica de Sucesso:** `PathResolverTest` verde; zero strings hardcoded `plans/epic-` ou `ai/epics/` em código que não seja o próprio `PathResolver`.
- **Impacto no Negócio:** Operadores humanos e skills automatizadas têm descoberta de artefatos confiável mesmo durante o período de co-existência dos layouts v3 e v4.

| `epicTelemetry(epicId)` | `String epicId` | `Path` | `epicDir(epicId)/telemetry/events.ndjson` |
| `epicState(epicId)` | `String epicId` | `Path` | `epicDir(epicId)/execution-state.json` |
| `releasesDir()` | — | `Path` | `ai/releases/` |
| `runsDir()` | — | `Path` | `ai/runs/` |

### 4.2 Princípios SOLID Aplicáveis

- **SRP:** `PathResolver` tem uma única razão para mudar: a definição de onde ficam os artefatos por epic. Nenhuma lógica de negócio de skills.
- **OCP:** Novos tipos de unidade (ex: `hotfix`) adicionam apenas um valor ao enum `UnitType` e uma entrada no `switch` — sem modificar os helpers existentes.
- **LSP:** N/A — sem hierarquia de interface nesta story.
- **ISP:** Expõe apenas os métodos que clientes precisam. Método de probe é package-private.
- **DIP:** Skills recebem `PathResolver` via injeção no construtor, não `new PathResolver()` inline.

### 4.3 Coding Constraints

- Métodos: ≤ 25 linhas (Rule 03)
- Classes: ≤ 250 linhas (Rule 03)
- `PathResolver.java` deve ser ≤ 150 linhas incluindo Javadoc mínimo
- Probe via `Files.newDirectoryStream(base, "epic-" + id + "-*")` — retornar primeiro match ou empty

## 8. Decision Rationale

**Decisão:** Implementar `PathResolver` como classe utilitária com métodos de instância (não estáticos), recebendo `basePath` no construtor.

**Motivo:** Permite injeção em testes sem modificar o filesystem real. Static methods exigiriam PowerMock ou setup de FileSystem virtual — complexidade desnecessária.

**Alternativa descartada:** Métodos static com `Path.of(System.getProperty("user.dir"))` hardcoded. Descartada por impossibilidade de testar com fixtures sem modificar o working directory do processo JVM.

**Consequência:** Skills que usam `PathResolver` recebem instância via construtor (DIP). Para skills no runtime Claude (Bash + Markdown), o PathResolver é instanciado com o `CLAUDE_PROJECT_DIR` como base path.
