## 1. Contexto & Escopo

Como **arquiteto do framework e responsável por release**, eu quero remover o compat layer do `PathResolver`, congelar `plans/` para novos writes via pre-commit hook, e documentar a mudança breaking no CHANGELOG com MAJOR bump de versão, garantindo que o layout v4 seja o único layout suportado para novos epics e que o `_CHANGELOG.md` reflita a mudança de forma clara e rastreável.

Esta story encerra o ciclo de migração. Após 2 sprints com ambos os layouts co-existindo, o probe v3 é removido do PathResolver: apenas a lógica v4 permanece (exceto leitura read-only de epics legados com `flowVersion ≤ 2` que permanecem em `plans/`). O hook pre-commit `forbid-writes-to-legacy-plans.sh` é registrado para bloquear criação de novos arquivos em `plans/`.

O shim `adr/README.md` criado na Story 3 é removido. O CHANGELOG recebe entrada de `BREAKING CHANGE` com link para `governance/baselines/migration-report-2026.md`. A versão do projeto recebe MAJOR bump conforme Rule 08.

### 1.1 Regras Transversais Aplicáveis

| ID | Título |
| :--- | :--- |

| RULE-011 | Compat Layer Removível |

### 1.2 Entrega de Valor

- **Valor Principal:** Finaliza a migração — elimina a dualidade de layouts e garante que novos epics sempre nasçam em `ai/epics/`. O CHANGELOG documenta o breaking change de forma clara com link para guia de migração.
- **Métrica de Sucesso:** Pre-commit hook recusa `git add plans/epic-XXXX/new-file.md`; `CHANGELOG.md` contém `## [X+1.0.0]` com nota de breaking change; `PathResolver.probeLayout()` retorna apenas v4 para epics novos.
- **Impacto no Negócio:** Zero ambiguidade sobre onde criar novos artefatos. O time não precisa lembrar "use ai/ não plans/". O hook faz enforcement automático.

## 3. Contratos & Endpoints

### 3.1 Comportamento do PathResolver após remoção do probe

| Método | Comportamento v4 apenas | Backward compat para legados |
| :--- | :--- | :--- |
| `epicDir("0060")` | Sempre retorna `ai/epics/epic-0060-*/` | N/A — novo epic, v4 por definição |
| `epicDir("0042")` | Retorna `plans/epic-0042/` apenas se `flowVersion ≤ 2` (read-only) | Leitura permitida, write bloqueado por hook |
| `probeLayout()` | Removido (não mais necessário) | N/A |

### 3.2 Pre-commit Hook Interface

```bash
# forbid-writes-to-legacy-plans.sh
# Disparado em PreToolUse(Write, Edit) quando path contém "plans/epic-"
# e o arquivo não existe ainda (é novo).
# Exit 2 = bloquear a operação
# Exit 0 = permitir (arquivo existente = hotfix documental permitido)
```

### 3.3 Entrada CHANGELOG

```markdown
## [X+1.0.0] - 2026-MM-DD

### BREAKING CHANGE

- **Layout v4 obrigatório para novos epics:** Todos os artefatos de épicos novos 
  (stories, plans, reviews, reports) são criados em `ai/epics/<epic>/work/<tipo>/<unit>/`
  ao invés de `plans/epic-<id>/`. Epics legados (flowVersion ≤ 2) permanecem em 
  `plans/` em modo read-only.
- **Guia de migração:** `governance/baselines/migration-report-2026.md`
- **Rollback:** Tag `pre-layout-v4` permite revert para o estado pré-migração via
  `git checkout pre-layout-v4`.
```

## 8. Decision Rationale

**Decisão:** Manter leitura read-only de epics legados (flowVersion ≤ 2) em PathResolver mesmo após remover o probe, ao invés de eliminar suporte v3 completamente.

**Motivo:** Os 60 epics legados têm artefatos permanentes (ADRs, reports) que o time consulta. Remover o suporte de leitura forçaria migração de todos eles ou quebra de skills de consulta histórica como `/x-telemetry-analyze --epic 0042`.

**Alternativa descartada:** Migrar forçadamente todos os 60 epics legados (incluindo flowVersion ≤ 2) para v4. Descartada porque epics com flowVersion ≤ 2 têm estruturas que o script de migração não suporta automaticamente (sem slug, sem sub-pastas por tipo de unidade) — requereria migração manual caso a caso com risco alto de perda de histórico.

**Consequência:** PathResolver mantém dois code paths: `flowVersion ≤ 2` → `plans/epic-{id}` (read-only), `flowVersion ≥ 4` → `ai/epics/epic-{id}-{slug}/`. O código é mais simples que o probe anterior mas ainda tem bifurcação. Story X futura pode migrar os legados manualmente se necessário.
