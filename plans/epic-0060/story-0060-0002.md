## 1. Contexto & Escopo

Como **operador de migração de layout**, eu quero um script `scripts/migrate-layout.sh` que migre epics do layout v3 (`plans/`) para o layout v4 (`ai/epics/`) de forma idempotente e reversível, garantindo que o histórico git seja preservado e que uma janela de freeze seja claramente documentada.

O script é o motor da migração. Ele percorre todos os epics em `plans/epic-XXXX/`, verifica o `flowVersion` de cada `execution-state.json`, e decide se migra ou ignora. Epics com `flowVersion ≤ 2` são preservados em `plans/` (RULE-001). Epics v3+ são movidos para `ai/epics/epic-XXXX-<slug>/` via `git mv` para preservar histórico.

A idempotência é garantida por verificação de existência: se `ai/epics/epic-XXXX-*/` já existe, o epic é pulado como no-op. O suporte a `--dry-run` permite simular a migração sem efeitos colaterais. A tag git `pre-layout-v4` é criada antes do apply como mecanismo de rollback (RULE-008). O relatório `governance/baselines/migration-report-2026.md` documenta tudo que foi migrado.

### 1.2 Entrega de Valor

- **Valor Principal:** Migração determinística e reversível de 60 epics do layout v3 para v4, sem perda de histórico git e com capacidade de rollback para qualquer ponto pré-migração.
- **Métrica de Sucesso:** `migrate-layout.sh --apply` em sandbox com 3 fixtures move os epics v3+ corretamente; re-execução é no-op (100% idempotente); `git log --follow` mostra histórico preservado.
- **Impacto no Negócio:** Elimina a necessidade de freeze prolongado — o script pode ser executado, verificado e revertido em < 30 min. Libera a equipe de migração manual de artefatos.

## 3. Contratos & Endpoints

### 3.1 CLI Interface do Script

| Flag | Tipo | Default | Descrição |
| :--- | :--- | :--- | :--- |
| `--dry-run` | boolean | true | Simula movimentos; não altera filesystem |
| `--apply` | boolean | false | Executa movimentos via `git mv`; cria tag `pre-layout-v4` antes |
| `--epic` | string | all | Migrar apenas o epic especificado (ex: `--epic 0060`) |
| `--self-check` | boolean | false | Verifica dependências (jq, git) e sai com exit 0 ou 2 |

### 3.2 Saída do Script

```
[DRY-RUN] would move: plans/epic-0060/epic-0060.md → ai/epics/epic-0060-folder-reorganization/epic.md
[DRY-RUN] skipped: plans/epic-0042/: flowVersion=2 (legacy, not migrating)
[APPLY] tag pre-layout-v4 created at <sha>
[APPLY] moved: plans/epic-0060/ → ai/epics/epic-0060-folder-reorganization/ (23 files via git mv)
[APPLY] report written: governance/baselines/migration-report-2026.md
```

### 3.3 Exit Codes

| Código | Condição | Significado |
| :--- | :--- | :--- |
| 0 | Sucesso | Migração (ou dry-run) concluída sem erros |
| 1 | Erro de migração | Falha ao mover arquivo; estado pode ser parcial |
| 2 | Dependência ausente | jq ou git não encontrado |
| 3 | Argumento inválido | Flags inválidas ou conflitantes |

## 8. Decision Rationale

**Decisão:** Usar `git mv` ao invés de `cp + git add + rm` para mover arquivos na migração.

**Motivo:** `git mv` preserva o histórico de mudanças do arquivo (rastreável via `git log --follow`). Sem isso, operadores que tentarem entender o histórico de um artefato migrado verão o histórico cortado na data da migração.

**Alternativa descartada:** `cp` + `git add` + `git rm`. Descartada porque `git log <arquivo>` após a operação não encontraria commits anteriores ao move sem o flag `--follow`, e mesmo com `--follow` o comportamento é inconsistente com renames não detectados pelo similarity threshold.

**Consequência:** A migração via `git mv` requer que os arquivos fonte não estejam dirty (unstaged changes). O script DEVE verificar `git status --porcelain plans/epic-XXXX/` e abortar com mensagem clara se houver mudanças não commitadas.
